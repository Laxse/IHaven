## 启动崩溃排查：macOS 26 + App Sandbox + 缺失 provisioning profile（commit 71c2a43）

现象：Xcode build 无报错，但 App 启动即崩溃，退出码 133（128+5 = SIGTRAP），无任何 stdout 输出。

崩溃栈（LLDB 复现，崩在 dyld 初始化阶段，main 从未执行）：
```
frame #0: libsystem_secinit.dylib _libsecinit_appsandbox.cold.9
frame #1: libsystem_secinit.dylib _libsecinit_appsandbox
frame #2: libsystem_trace.dylib _os_activity_initiate_impl
frame #4: libSystem.B.dylib libSystem_initializer
frame #5+: dyld prepare / findAndRunAllInitializers
exception: EXC_BREAKPOINT, signal SIGTRAP
```

根因：产物中**没有 embedded.provisionprofile**。`com.apple.security.app-sandbox` 是 entitlement，
必须由 provisioning profile 授权；profile 缺失时 macOS 26 的 libsecinit_appsandbox 直接 trap。
触发原因：project.pbxproj 里硬编码 `CODE_SIGN_IDENTITY = "Apple Development"` 绕过了 Xcode
的自动签名流程，profile 未生成。

修法演进（两步）：
1. commit 71c2a43：删除两处 `CODE_SIGN_IDENTITY = "Apple Development";`，
   只保留 `CODE_SIGN_STYLE = Automatic;` 让 Xcode 自动生成 profile。
   → **未生效**：profile 依然没生成（Apple 开发账号在 macOS 上不自动发 profile）。
2. commit 3ff48da（最终方案）：Debug 改用 ad-hoc 签名，绕开 profile 依赖。
   ```
   CODE_SIGN_IDENTITY = "-";
   CODE_SIGN_STYLE = Manual;
   ENABLE_HARDENED_RUNTIME = NO;
   ENABLE_APP_SANDBOX = YES;
   ```
   Release 保持 Automatic + ENABLE_APP_SANDBOX = YES（发布/公证时仍需 Developer ID）。

### 完整对照实验矩阵（同一二进制，只改签名/entitlement）
| 签名方式 | sandbox | profile | 结果 |
|---|---|---|---|
| ad-hoc (`--sign -`) | 有 | 无 | ✅ 正常运行 |
| Apple Development | 有 | 无 | ❌ SIGTRAP |
| Apple Development + 去除 get-task-allow | 有 | 无 | ❌ SIGTRAP |
| Apple Development | 无 | 无 | ✅ 正常运行 |

结论：只有「sandbox entitlement + 开发者证书 + 无 profile」这个组合会崩。
sandbox 本身没问题，get-task-allow 也不是原因，只是缺 profile。

排查方法论（可复用）：
- 崩溃报告在 ~/Library/Logs/DiagnosticReports/IHaven-*.ips，用 python 解析：split('\n',1)[1] 取 JSON
- exit code 133 = SIGTRAP，说明是 Swift 运行时主动 trap，不是普通崩溃
- 用 LLDB 定位：lldb -b -s cmds.txt -- <binary>，断点符号在 IHaven.debug.dylib 里
  （Xcode 16+ debug dylib 架构，主二进制是空壳，真实代码在 IHaven.debug.dylib）
- 对照实验法：同一二进制只改签名方式（ad-hoc / 开发者签名 / 有无 profile）逐一验证
- 注意：Xcode 16+ 主二进制通过 @rpath/IHaven.debug.dylib 加载代码，install_name_tool
  修改会因 headerpad 不足失败（需 relink）

## wallhaven API 错误行为实测矩阵（本机 2026-10-08 复现）

**根因：Accept 头内容协商**（架构师纠正了我的错误结论）
| 请求 | 不带 Accept | 带 Accept: application/json |
|---|---|---|
| atleast=abc | 500 + **HTML 页面** | 500 + {"message":"Server Error"} |
| page=0 / page=-1 | 500 + HTML | 500 + JSON |
| page=99999 | — | **400 + {"error":"Bad Request"}** |
| resolutions=9999x9999 | 200 JSON | 200 JSON |
| ratios=99x99 | 200 JSON | 200 JSON |
| q=### | 200 JSON（空结果） | 200 JSON |

客户端硬规则（ADR-006）：
1. **必须显式发Accept: application/json** —— 否则错误响应体是 HTML 而非 JSON
2. **先判 statusCode 再解码** —— 禁止先调 JSONDecoder（否则 HTML 喂给解码器产生误导性「解析失败」）
3. 本地校验 atleast 匹配 ^\d+x\d+$、page >= 1，**不依赖服务端 4xx 告知错误**
4. APIError 五类不可合并：invalidParameter / serverError / networkUnavailable / rateLimited / decodingFailed
   —— decodingFailed 与 serverError 合并会退回「一律显示加载失败」，是静默错误

数据实测（atleast 支持任意分辨率）：
3840x2160 → total 80905 / 3372 页；2560x1440 → 160732 / 6698 页；1920x1080 → 388406 / 16184 页；
5120x2880 → 22728 / 947 页

### API 参数真实语义（架构师更正，我的原始数据有误）
- `resolutions` / `ratios`：字符串**模糊匹配**（SQL LIKE）→ 任意格式合法值都返回大量结果
  实测 resolutions=9999x9999 → total=1；ratios=99x99 → total=5005（静默忽略不生效）
- `atleast`：**数值比较** → 超出实际尺寸上限时才有意义
  atleast=20000x20000 → 200 + data:[]（空态，非错误）
  atleast 上界实测：5120x2880→22728 / 7680x4320→5100 / 9999x9999→32 / 20000x20000→0
- 结论：**「格式非法」与「结果为空」在 API 层无法区分，必须客户端预校验**
- 只校验格式 ^\d+x\d+$，**不做数值上界校验**（否则把服务端该返的空态变成本地错误）

### PM 发现的 Key 验证端点缺陷（重要）
`/settings` **不能用于验证 API Key 有效性**：
| 端点 | 无效 Key | 无 Key |
|---|---|---|
| /search（X-API-Key 头） | **401** ✓ | 200 正常返回 |
| /settings?apikey= | **404** {"error":"Nothing here"} | 401 |

根因：/settings 是「读用户设置」，未授权访问设置的用户请求它得 404，
而 404 与「Key 无效」是完全不同的原因被映射到同一状态码。
**后果：按原规范实现会把完全有效的 Key 判为无效，用户根本配不进去。**
→ Key 验证必须用 /search，返回 401 才是无效。

### Key 验证端点实测矩阵（附录 A-8，team-lead 独立复现）
| Key 状态 | /search?apikey= | /settings?apikey= |
|---|---|---|
| 有效 Key | 200 | 200 |
| 无效 Key | **401** | **404** Nothing here |
| 空 Key / 纯空格 | **200（total 与匿名完全相同）** | 401 |
| 超长 Key(300字符) | 401 | — |
| 无 Key | 200 | 401 |

三条硬约束：
1. **禁止用 /settings 验证 Key** —— 404 与「Key 无效」被映射到同一状态码，
   会把完全有效的 Key 判为无效，用户根本配不进去。
2. **空 Key 必须本地拦截，绝不能靠服务端 200 判断有效性** —— 服务端把空 Key 当匿名请求，
   200 与「Key 有效」无法从响应区分。失败链：误判有效 → 保存空 Key → 浏览行为与未配置
   完全一致 → **用户不会发现任何异常**（静默错误，critical）。
3. 404 分支当前不可达（/search 七类边界实测无一返回 404），但禁令预写：
   404 绝不能说成「密钥无效」（前者引导去开启授权，后者引导重输 Key，混淆让用户白重输一次仍失败）。

补充实测（PM 发现，比我测得更细）：**任意非空字符串都返回 401，包括仅 1 个字符**。
故长度阈值只是额外防御，**不能替代非空判断**。

| purity=001 + 有权限的 Key | 200 | **>0**（筛选过窄） |

判定流程：主请求 200+total=0 且含 NSFW 条件 → 发探测`purity=001`（不带其他筛选）
→ total==0 确定权限不足 / total>0 确定筛选过窄 / 401 走鉴权失败。
成本：额外 1 次请求，占限流预算 2.2%。缓存：每 30s 至多 1 次。

**关键优势：用确定性替代推测**，用户不需要在两个可能原因间猜。
探测失败时降级为「不显示权限文案」（宁可少提示不可误报）。

### 权限不足归空态而非错误态（PM 洞察）
用户筛选操作本身没错，且无需重试即可通过开启权限解决 → 归空态但文案必须指向可执行动作。
这与「空态必须完全中性」不冲突：视觉中性，文字可执行。

## 验证纪律最终为三层机制（PM 补第三类）

| 层 | 内容 | 防住的错误 |
|---|---|---|
| 对照机制 | 样本是否覆盖能区分假设的对照组 | 数据全对、结论错 |
| 前提机制（4b）| 被测对象存在且语义明确（签名存在≠能力可用）| 测了从未运行过的代码 |
| **作用域机制（4c）** | **结论不可外推到超出实测范围** | 对照有效但作用域被放大 |

**4c 由 PM 提出，第一个实例就是我犯的**：
实测 /settings 对无效 Key 返404、无 Key 返401 → 推断「用它验证 Key 有效性」。
但该结论**作用域只是这个端点**，不能外推为「401 与 404 是两种 Key 状态」。
实际上 401 只有单一含义，NSFW 权限不足是「有效 Key + 200 + total=0」。

操作化判据：写下结论必须附「该结论的适用边界是 ____，超出此范围需重新实测」；
**填不出边界说明作用域还没想清楚**。

## 校验工具的两个坑（架构师发现，PM 认为值得警惕）
1. **未区分全角/ASCII 标点** → 2940 处假阳性（`0% -> 22%` 被当违规）。
   教训：**总在误报的检查等于没有检查** —— 假阳性的危害不是吵，而是让规则被放弃。
2. **Python正则不支持 `\h`**（PCRE 语法）→ 规则**静默失效**，不报错也不命中。
   教训：**静默失效的检查比没有检查更危险**，因为给人「已有防护」的错觉。
   已写「新增检查必须先做负向测试」进 GATE-USAGE.md。

## 元规则（本轮新增）
**判断门禁结果时，「我是否确认过该规则的判定逻辑」优先于「结果是否为 FAIL」。**
规则可能错，FAIL 不代表我错；只有先确认规则可信，才谈是否修复。
来源：设计师收到 81 处 WARN 后改了两次才回滚，因为她假设「FAIL 就是我错了」。

## 第三层机制抓出架构师自己的 bug（ADR-007 + verify-docs 第10 类检查）

架构师按三层框架回头审文档，在客户端校验表里找到一处作用域外推：
原文写「resolutions/ratios 宽松格式校验或直接放行 | 实测非法值返回 200，**不构成风险**」。
但 Trap 13 已正确记为「静默匹配」—— **同一实测，两处结论矛盾**。

根因：从「返回 200」外推「不构成风险」，而真实风险是**静默返回错误内容**
（ratios=99x99 返 200 + 24 条，但 ratio 全是 1，尺寸 2000×2000/6666×6666）。

**更严重的是表格里那版更显眼** —— 实施者照表格写代码，照 Trap 写文档。
已改为「封闭枚举，非法值构造请求前抛出」。

由此确立自查规则：**同一实测在文档不同位置出现时结论必须一致；矛盾的两版中更显眼的那版风险更高**（表格 > 正文）。

### 为什么第三层最危险（架构师判断，采纳）
前两层的症状是「我没测」，会暴露自己；**作用域错误的症状是「我测了，测得也对，结论也用了」**——只有回头检查适用边界才能发现。

已落地为 verify-docs 第 10 类检查 `check_conclusion_consistency`，
禁止出现与 Trap 13 矛盾的措辞。**有意不做全文语义比对**（需 LLM），
只对已实测的高风险参数做危险措辞抽查 —— 规则必须能被门禁检出，否则又退回「靠人判断」。

### 归因分歧暴露的风险
架构师与设计师都声称 DESIGN.md 的 emoji 是自己写的。根因是**多人在同一份文档上并行编辑**，
git blame 在批量写入下无法区分。已约定：改别人文档前先知会，且回执须声明改了什么。

## 前提失效的三种形态（附录 A-15，设计侧发现）

| 形态 | 描述 | 是否报错 |
|---|---|---|
| 4b-1 | 对象存在但从未被调用 | 不报（GIF→MP4 从未真正执行） |
| 4b-2 | 前提语法不被支持 | 退出码非0，但被 2>/dev/null 吞掉则无声 |
| **4b-3** | **失败被显式忽略** | **无** |

**设计侧实例**：pre-commit 用 `grep -qP`，**macOS BSD grep 不支持 -P**（实测退出码 2），
错误被 `2>/dev/null` 吞掉 → `if` 恒为 false → **一条规则都没跑过**。
她说「如果没人查出来，我会一直以为它在正常工作」。

4b-3 最危险：不是规则有 bug，而是**规则根本不存在**，但表象与「检查通过」完全一致。

### 强制要求：校验脚本必须自证可运行
启动时把规则中所有正则 compile() 一遍，抛异常则明确报「规则语法错误」并**拒绝执行**。
判据：**门禁输出「通过」时，必须能回答「刚才那条规则真的跑过吗？」**

本质是「静默失效比假阳性更危险」（A-14 纪律 A）的自动化版本。
人写错字会被看见，机器的语法错误常被 try/except 或 2>/dev/null 吞掉。

## 架构师 8 次错误自查（最有价值的复盘）

他统计本项目累计 8 次错误，**6 次是他自己的**：

| # | 性质 | 谁的 |
|---|---|---|
| 1-5 | 工具静默失效（`\s`/`\h`/`\|`/`-P`/正则错位） | 4 他 1 我 |
| 6 | **报告未验证就发**（「已恢复到 228 行」是修复中间态） | 他 |
| 7 | **报告范围未写清**（说「零 emoji」但只查了 md/scripts） | 他 |
| 8 | 紧急口吻 + 错误（设计侧 v3.4 误报） | 设计侧（已自纠） |

### 三条核心洞察

**1. 「在多文档并行 + 高频核验的场景下，『验证方法』比『验证结论』更容易出错」**
这是他统计 8 次后得出的，比任何单次技术发现有价值。

**2. 当错误的报告引发正确的修复时，修复会「消音」错误的报告**
症状消失既是错误报告的证据，也是修复成功的证据，**两者无法区分**。
我这轮又验证了一次：他报告「248 行」，实测285 行 —— **报告再次过期**。

**3. 编辑纪律的根因不是「归属」而是「脚本 vs Edit」**
他说「改别人文件要用 Edit」，设计侧纠正：她用脚本改**自己**的文件也出过三次（v2.4/v2.6/v2.9）。
风险来源是「正则匹配位置与人的意图不一致」，归属只是提高概率而非根因。
→表述改为：**修改代码一律逐处编辑，不区分文件归属。**

**4. 紧急程度与验证强度必须挂钩**
「紧急+正确」只是让接收方多花时间核实；
**「紧急+错误」会让接收方跳过核实，而核实恰恰是此时唯一的防线。**

## 报告纪律（我的理解，采纳）

缺任一项则接收方无法复核，只能选择「相信」或「不信」。

```
实测：当前仓库（无新代码）→ 正确 FAIL；隔离副本植入明文 Key → 正确检出。

### 教训：门禁必须能测「它能否检出违规」而非「当前是否干净」
后者只测通过，前者测有效性。
**门禁若无法被指向别处，就无法被回归测试 —— 这本身就是一个盲区。**

## 「不确定」状态的三行判据（设计师提出，采纳）
| 情况 | 默认动作 |
|---|---|
| 确定是错的 | 修复 |
| **不确定**（可能检索错/ 环境错 / 可能真错） | **冻结 + 查证** |
| 已确认但影响面未知 | 冻结 + 先写回归测试 |

中间那行是关键 —— 「不确定」是协作中最常见状态，而本项目几乎所有错误都发生在
「不确定但当成确定」的时候。

配套：**任何「某处有/没有 X」的判断，若是「没有」必须两种工具验证** ——
「没有」错了则静默（后续推理全建立在空中），而「有」错了通常一眼能看出。

## 跨工具正则方言（设计侧 v3.8 落地两个函数）
实测 `a\|b`（文本 `a|b`）：
- BSD grep basic `a\|b` → 视为 or，命中 1
- grep -E `a|b` → 视为 or，命中 1
- **Python re `\|` → 字面竖线**，findall 得 `['a|b']`（匹配到字面量而非 a 或 b）

**语法都能编译，但匹配的东西不同** —— 比「工具能力缺失」更隐蔽。
已落地 `check_regex_dialect()`（检测方言混用）+ `grep_pattern_safe()`（re.escape 转义后用 | 连接）。

### gate-selfcheck 的意义（设计师建议提为最高优先级，正确）
「能否检出植入违规」是所有门禁有效性的证据，而补 must_miss 只是完善。

```
且做了负向对照（干净 fixture → exit=0），确认能区分「干净」与「有违规」，不是无脑 PASS。

### 跨工具正则方言实为四种机制（架构师补充）
| 工具 | 写法 | 实测 | 机制 |
|---|---|---|---|
| BSD grep basic | `grep 'a\|b'` | exit=1 零命中无报错 | 语法无效 |
| Python re（raw） | `r'a\|b'` | `['a\|b']` | 字面竖线 |
| Python re（非 raw） | `'a\|b'` | 多一层 SyntaxWarning | 字面+警告 |
| grep -E | `grep -E 'a\|b'` | 匹配字面 | 字面匹配 |

四种都「不 or」，但机制不同。

## 「失败信号」判据会随工具能力进步，不应一刀切否决

## 否决「纯 \| 也报 WARN」提议（设计侧实测否决，采纳）
架构师提议纯 `\|` 也报警告，设计侧搜项目发现**自身就是正当用例**：
`docs/verify.py:197` → `re.match(r"^\| \d{4}-\d{2}-\d{2} \| (v[\d.]+)", l)`
用途：匹配 Markdown 表格行首竖线以提取变更记录版本号。
实测：表格行 → `['v3.8']`，非表格行 → `[]`。**对其报警会误报。**

否决依据：**误报比漏报更糟** —— 这是 2940 处假阳性教会的教训。
折中：`check_regex_dialect(pattern, warn_pure_escape=False)`，默认放行、需时可开。

## 「修改前先确认原状可被恢复」（设计侧提出，采纳）
架构师提「真实对象不该是唯一验证场所」，设计侧补了必然推论：
**一旦在真实对象上做了修改，「原状」就不可恢复 —— 而原状是判断「该不该改」的唯一依据。**

具体说：若架构师上轮直接重写self_test，
后来无论用什么工具都无法知道「原本有 self_test」，
gate-selfcheck 也无法证明门禁原本有效，**整个学习链会消失**。

→ **「先复制再改」比「先问再改」更根本：问只保护判断，复制才保护原状。**

## security-gate 在 Phase 1 保持 FAIL —— 设计侧裁定正确

**它选择了「诚实的红」而非「勉强的绿」** —— 与「症状消失掩盖原因错误」同源：
PASS 看起来是好消息，但如果它掩盖了「什么都没检查」，那它就是危险的。

|---|---|---|---|
| docs（Phase 1） | 0 | 合法，仓库本无源码 | SKIP |

## 评估新检查项的三问（架构师提出，采纳）
| 问题 | 决定什么 |
|---|---|
| 它的**失败信号**是什么？ | 要不要加 |
| 它在**本项目**会产生多少误报？ | 要不要加 |
| 结论不可撤销时，**原状可恢复吗**？ | 加的时候怎么做 |

第三问最易被忽略。前两问决定「要不要加」，第三问决定「加的时候怎么做」。

> **一条检查规则的价值 = 它能检出真问题 × 它不产生噪声。**
> 后者为 0 时前者再高也无用 —— 因为人会主动关掉它。

## 「盲区」的两个方向（设计侧提出）
盲区不只是「**不检查什么**」，也包括「**不该检查什么**」。
实例：`selftest_framework.py` 的docstring 里有 `\|`，那是解释文档的示例文本、不是可执行模式 ——
检查器不该检查解释它自己的文档，否则产生一类新误报。
与「检查器不检查 .py 的 emoji」同源。

## 盲区分类学（设计侧补全，三类）
| 类型 | 含义 | 本项目实例 |
|---|---|---|
| 能力盲区 | 我没有能力检查它 | emoji 检查器不扫 .py（无正则解析能力） |
| 范围盲区 | 有能力但设计上不覆盖 | check_punct_spacing 不管 emoji（分工） |
| **对象盲区** | **我检查的对象是错的** | 检查器把 docstring 当模式 |

第三类最危险，**因为它看起来有防护** —— 你以为在检查「方言混用」，
实际检查的是「所有含 \| 的字符串」。

成因很讽刺：**检查器为了讲清陷阱，不得不在 docstring 里写含 \| 的示例。
文档写得越详细，误报越多。**

→ 设计原则：**一个检查器如果它自己的文档会触发自己的规则，
它必须能区分「说明」与「使用」。**

已落地：`extract_code_patterns`（剥离 docstring 与注释）+ `is_descriptive_text`（排除描述性文本）。
双向实测：植入真违规到代码区被抓出，恢复后全绿 —— **证明不是永远 PASS 的假检查**。

## 净收益判据（设计侧提炼，采纳）
> **净收益 = 捕获的真问题 − 引入的假阳性。净收益不为正，无论那检查听起来多合理都不该加。**

架构师撤回提议时做了完整分析：纯 \| 检查 = verify.py 假阳性 1 处 + 自己代码 0 处 = **纯噪声零信号**。

**比「失败信号」判据更完整**：失败信号只问「能不能做」，净收益还问「值不值得」。

## 「验证本身可能破坏证据」（设计侧补架构师第二问）
两问：
1. 原状可恢复吗？ —— 改之前备份
2. **我的验证是在副本上做的吗？** —— 测之前备份

**第 2 问更根本**，它指出「验证」这个看似安全的动作本身就可能是破坏性的。
实例：架构师第一次测 security-gate 时若直接在真实仓库植入违规，仓库就永久脏了。
第 1 问覆盖「改」，第 2 问覆盖「测」，后者场景更隐蔽。
