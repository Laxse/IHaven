## 工具栏左侧空白/与侧栏对齐（用户纠正：不要调换控件顺序）

用户原话：「不是，怎么把两个控件顺序调整了，我想说的是左侧空白太多，和下方没对齐」。
上一提交 63447a4 误把「左侧对齐」当成控件顺序调整（把搜索框提到最前、侧栏开关挪到其后），本次回滚并做真正的对齐。

### 取证方法（可复用，重要）

- 屏幕坐标查询：写 Swift 脚本调 `CGWindowListCopyWindowInfo` 列出 owner=IHaven 的窗口 bounds / windowNumber。
  `System Events`（osascript）查窗口位置会被沙箱 SIGTERM，走不通。
- 无遮挡截图：`screencapture -x -o -l <windowNumber> out.png`（窗口级截图，不受其它窗口遮挡影响；本例 1280×800 → 2560×1600，2px/pt）。
- 像素级量测：Swift + CGImageSource 把 PNG 读进 RGBA 缓冲，逐行扫描「与参考底色差 > tol」的 x 区间 / 图形包围盒。
  比目测截图可靠得多，是验证「对齐」类需求的正解。

### 实测结论（旧构建）

- 交通灯：`x 9~68.5pt, y 10~22pt`，位于系统保留的 **标题栏安全区（内容从 y=32pt 开始）之内**。
  即：`hiddenTitleBar` 下交通灯在工具栏**行的上方**，水平方向不占工具栏空间 → 代码里的 64/72pt「交通灯让位」是多余的历史包袱。
- 工具栏内容：搜索框左缘 `x=63.5pt`；侧栏行高亮块 `x 8~200`，图标图形 `x 23~37`（中心 30），文字左缘 `x=50`。
- 线稿基准：工具栏开关 `x=8~36`、搜索框 `x=56~336`；侧栏行 `x=8~200`、标签 `x=46`。
- 因此「左侧空白太多、和下方没对齐」= 工具栏左空 64pt，且开关图标中心 26 与侧栏图标中心 30 差 4pt。

### 修复（本轮）

`Sources/IHavenApp/Features/Browse/BrowseView.swift`
1. 恢复原控件顺序：交通灯让位删除 → **侧栏开关在前、搜索框紧随**（不调换顺序，尊重用户原意）。
2. 工具栏左内边距 `Spacer(64)` → `.padding(.leading, 12)`：开关按钮 12~40，图标中心 26。
3. 搜索框 `.padding(.leading, 16)` → 左缘落在 56，与线稿一致。
4. `sidebarRow` 行内边距 `12` → `IHaven.Space.s4`（=8）：图标槽 16~36（中心 26，与工具栏开关图标同列）、标签左缘 46（线稿基准，原为 50）。

`Sources/IHavenApp/App/IHavenApp.swift` 注释同步（不再写「72px 让位」）。

### 验证

- `swift build --disable-sandbox` 零错误零警告；convention（300 行，压线 PASS）/ security / api 三门禁 PASS；重打包 dist/IHaven.app。
- 复测（新构建）：侧栏行 1 图标图形 `x 19~33 中心 26`，工具栏开关按钮 `x 12~40 中心 26` → **图标列精确对齐**；搜索框左缘 `55.5~56`；文字左缘 `46`；左侧空白 64 → 12pt。

## 筛选 popover 重做（用户反馈：不好看 / 和线稿差距大 / 没有确认按钮）

用户原话：「筛选的浮动框不好看，和线稿差距很大，布局不对，而且没有确认按钮？」

### 根因（实测，非猜测）

原生 `.pickerStyle(.segmented)` 的最小宽度由标签字宽决定，无法压缩：分辨率 6 档实测 ≈384pt
> 面板内容宽 288pt → 把 `VStack` 撑到 384 → popover 居中后左右各裁掉 32pt。
后果：**组标题（x=16）整条被裁没、每行左端少一项、行右侧留空** —— 与线稿的差距绝大部分来自这一条。

### 修复

- `Features/Filter/FilterSupport.swift`：新增自绘 `FilterSegmented<Value: Hashable>`（容器 h24/r6、`padding(1)`、
  子项是内缩 2pt 的 22pt 药丸、`surfaceSunken` 底、等宽项），分类/排序 4×72、分辨率 6×48。
- `ExactResolutionRow`：`Menu` 从 `.borderlessButton` + `fixedSize` 改为 `.menuStyle(.button)` +
  `.buttonStyle(.plain)` + `.frame(maxWidth:.infinity)` + `.menuIndicator(.hidden)`，否则收窄到 ~146pt。
- `FilterView.swift`：内容宽钉死 `.frame(width:320, alignment:.leading)`；新增 44pt 页脚
  （左「清除全部」fg2 + 右「完成」accent 实心 60×28）；`.defaultScrollAnchor(.top)` 防打开时停在底部。
- `Core/Models/Query.swift`：`BrowseQuery` 加 `Equatable` + `filterKey`（含除 page/seed 外的全部维度）。
- `BrowseViewModel.swift`：新增 `scheduleFilterReload()`（150ms 防抖 → page=1 → reload），
  由 `FilterView` 的 `.onChange(of: viewModel.query)` 驱动；`lastFilterKey` **在 init 里初始化为
  `query.filterKey`**，否则启动时的首次 onChange（多为 page/seed 改动）会误触发一次多余搜索请求。
- `BrowseView.swift`：popover 的关闭回调改为只 `showFilter = false`（筛选已即时生效，
  再 `reloadForNav()` 会与防抖任务重复发一次请求）。

### 取证补充（本轮新增）

- popover 是独立窗口，`CGWindowListCopyWindowInfo` 能拿到它的 bounds（本例 346×586 = 面板 320×560 + 箭头/阴影）。
- `screencapture -l <popoverWindowNumber>` 抓到的是主窗口尺寸（不准）→ 改用 `-R x,y,w,h` 按窗口 bounds 取屏幕区域。
- 面板几何反推：区域图里先找「箭头」（顶部中央的 bg 色三角），再找最长 `sunken` 横带定位分段容器。
- **`print()` 重定向到文件是块缓冲的，抓不到即时日志**；调试日志必须用 `NSLog`（走 stderr，无缓冲）。
- **合成点击（CGEvent tap）在本沙箱不生效**：点「完成」面板不关、点筛选档位 filterKey 不变，
  但 popover 会因 TEMP `showFilter = true` 自行弹出 → 只能靠截图取证，不能靠点击做端到端验证。

## 色调筛选不生效（用户反馈）→ 查询参数名写错

用户原话：「色调过滤条件目前不生效」。

### 根因：wallhaven 搜索参数名是复数 `colors`，代码下发的是单数 `color`

`Infrastructure/Network/WallhavenClient.swift` 的 `buildURL` 里写的是
`URLQueryItem(name: "color", ...)`。服务端对未知参数**不报错、直接忽略** → 返回未筛选结果。
UI / filterKey / 防抖重查链路全都是对的，只有这一处。

实测（同一 Key，`purity=110`，目标色 660000）：

| 参数 | meta.total | 24 条中命中 660000 |
|---|---|---|
| `colors=660000` | 60,509 | 24/24 |
| `color=660000` | 952,937（= 无筛选） | 4/24 |

无 Key 请求同样生效（total 45,336，24/24 命中），所以与 Key 无关。

顺带实测其余参数，全部生效：purity / categories / atleast / resolutions / ratios / topRange / seed。
（`sorting=favorites`、`order=asc` 的 total 与 baseline 相同是正常的——排序不改变结果集大小。）

### 修复

1. `WallhavenClient.buildURL`：`color` → `colors`（附实测数据注释）。
2. `FilterView.colorGroup`：再点已选中的色块即取消（与比例组一致）。
3. `scripts/convention-gate.sh`：新增「搜索参数名白名单」检查
   （q|purity|categories|sorting|order|topRange|atleast|resolutions|ratios|colors|page|seed）。
   这类 bug 服务端静默忽略、用户侧极难自查，必须靠门禁兜住。已做负向测试（改回 color → FAIL）。
4. 同脚本补「扫描不到 .swift 就 FAIL」：否则目录布局不对时 grep 全空匹配 → 假绿。

### 顺带修掉：启动即连发 page=1+page=2（「初始加载 48 张」的根因）

`BrowseView` 触底哨兵 `.onScrollGeometryChange`：首屏内容未布局时 `contentSize.height == containerSize.height`
→ `distance ≈ 0 < 240` → 被误判成已触底，立刻多拉一页。
改为「内容高度未超出视口时返回 `.infinity`」即不算触底。实测日志：首屏 distance 依次 `inf` → `655.0`（>240 不触发），
启动请求数 2 → 1。

### 取证补充

- 端到端验证改动生效的办法：临时在 `buildURL` 里 NSLog URL、在 `reload()` 里 NSLog 命中数，
  跑 debug 二进制看 stdout。实测 `...&colors=660000&page=1` → 返回 24/24 命中。
- **`print()` 重定向到文件是块缓冲的抓不到即时日志，必须用 `NSLog`。**
