## 关键经验（UI）
- **SwiftUI 陷阱**：`LazyVStack`/`LazyHStack` 必须放在对应方向的滚动容器内，否则塌缩为 0。
- `.glassEffect(_:in:)` 默认 Capsule 形状；用在宽扁/竖长的自定义容器上会得到意外胶囊，必须显式 `in:` 形状。

## 修布局：图片溢出列宽导致重叠（提交 468968a）
- 现象：图片能显示了，但布局是「巨图重叠、列间无沟槽、图片一直压到侧栏边缘」。
- **诊断方法（可复用）**：用 PIL 分析用户截图（1920×1276，2x）逐列「背景色占比」——
  内容区自始至终没有任何低方差『沟槽列』，且第一张图直接落在侧栏边缘（连 16pt 内边距都被覆盖）
  → 判定是**图片溢出**，而不是列数/宽度测量错误。
- 根因：缩略图用 `.aspectRatio(_, .fill)` + `.frame(maxWidth: .infinity)`，
  当高度提案不受约束时 `.fill` 会横向膨胀，而 `clipShape` 裁切的是膨胀后的自身尺寸，等于没裁。
- 修复：卡片根改 `GeometryReader` 撑满外层固定尺寸，图片用 `geo.size` 精确 `.frame` + `.clipped()`；
  `MasonryView` 在 `.frame(width:height:)` 后再 `.clipped()` 兜底；删除卡片内多余的 `aspect`。
- 经验：SwiftUI「图片填满固定盒子并裁切」必须用精确 frame + `.clipped()`，
  不要依赖 `.aspectRatio(.fill)` + `maxWidth` 的组合。

## 钥匙串每次启动都弹窗（用户提问：能不能不要）
- 现象：每次启动 IHavenApp 都弹「IHavenApp 想要使用你储存在钥匙串的 com.ihaven.apikey…请输入登录钥匙串密码」。
- 根因：`KeychainKeyProvider.init()` 启动即读钥匙串；而构建产物是 **ad-hoc 签名**
  （`codesign -dv` 显示 `Signature=adhoc`、无 team、`Info.plist=not bound`）。
  ad-hoc 签名的 designated requirement 基于 CDHash，**每次重建都变** → macOS 视为「新 App」，
  钥匙串 ACL 的「始终允许」无法命中 → 反复弹窗。属开发期现象，非应用 Bug。
- 实测：现代 data-protection keychain（`kSecUseDataProtectionKeychain: true`）对 ad-hoc 二进制返回
  **-34018（缺少必需 entitlement）**，所以这条路必须先有稳定签名身份（team/entitlement），当前不可用。
- 硬约束：`docs/decisions/OPEN-DECISIONS.md` 明确「Key 存储用 macOS Keychain，禁止 UserDefaults / plist / 硬编码」
  → **不能改成文件/plist 存储**。
- 可行方案：
  - A（推荐、一次性、不改代码）：钥匙串访问 → 搜 `com.ihaven.apikey` → 双击 → 「访问控制」→
    选「允许所有应用程序访问此项目」→ 存储。之后任何构建都不再弹。代价：同机任意 App 可静默读取。
  - B（保留仅本 App 可读）：给 App 稳定签名（自签名证书 + 打成 .app 签名），Xcode SwiftPM 的 ⌘R 恒为 ad-hoc，
    需改用签名脚本构建。
- **用户最终决策（2026-10-11）：选 C——改用 home 隐藏文件存储**，即推翻上面「不能改成文件存储」的结论。
  落地：`FileKeyProvider`（`Infrastructure/Security/FileKeyStore.swift`）存 `~/.ihaven/apikey`
  （目录 0700 / 文件 0600），`IHavenApp.swift:5` 切换过去，ADR-010 记录变更与回切条件。
  `KeychainStore.swift` 保留不删，加注释标注「ADR-010 旁路」。
