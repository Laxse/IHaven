# 门禁使用说明

> 本文件说明四个门禁的职责边界与**正确使用方式**。
> 用错门禁和没有门禁一样危险 —— 假阴性（漏报）与假阳性（误报）都会让团队失去对工具的信任。

---

## 四个门禁的分工

| 门禁 | 覆盖对象 | 检查方式 |
| --- | --- | --- |
| `api-gate.sh` | Apple API 签名 | `swiftc -typecheck` 对真实 SDK 编译 |
| `security-gate.sh` | 明文 Key / 私有 API / 反模式认证 | 正则扫描 |
| `convention-gate.sh` | 单文件行数 / 状态管理 / 分层依赖 / F9 依赖方向 | 正则扫描 |
| `verify-docs.py` | 文档 P0 / JSON / 章节编号 / **跨文档引用** / ASCII 框线 | 结构化解析 |

**无重叠、无遗漏**：前三个扫 Swift 源码，第四个扫文档。

---

## 三条使用纪律

### 1. 门禁报错时，必须核对当前文件实际状态，不可直接转述给作者

**这是本项目最重要的使用纪律**，来源是一次真实的误报：

- 门禁报出 `DESIGN.md` 有 emoji
- 我据此发紧急告警给设计师，称文件被破坏
- **核实后发现**：那些问题在作者的 git HEAD 里就已存在，是作者自己的脚本副作用；我的测试残留为 0
- 误报的后果：作者若按告警去恢复，会用旧版本覆盖掉她刚完成的修复

**正确做法**：

```bash
# 报错后，先确认问题是否真实存在且未被并发修复
python3 scripts/verify-docs.py 2>&1 | grep <规则名>
git diff <文件>              # 看是否有未提交的并发修改
git show HEAD:<文件> | grep <同样的规则>   # 对比 HEAD 版本
```

若 HEAD 版本同样有问题，则问题来自作者本人，**应报告而非代改**。

### 2. 负向测试必须在临时副本上做，禁止在真实文件上注入违规后恢复

```bash
# 正确：--root 指向副本，真实文件零触碰
cp -R docs /tmp/t/docs && cp -R scripts /tmp/t/scripts
python3 scripts/verify-docs.py --root /tmp/t

# 错误：备份 -> 改原文件 -> 恢复（会吞掉测试期间的并行修改）
cp docs/X.md /tmp/bak; python3 -c "改 docs/X.md"; cp /tmp/bak docs/X.md
```

**「备份 + 恢复」不是隔离** —— 它假设文件静止，而团队里多人同时在改文档。`--root` 参数已为此提供。

### 3. 不代改他人负责的文档

架构侧只改 `ARCHITECTURE.md` / `decisions/ADR-*.md` / `VERIFIED-API.swift` / `scripts/*`。

`PRD.md` 属产品侧、`DESIGN.md` 属设计侧。发现问题应**报告并附行号**，由作者决定修改时机。

例外：机械可检出的问题（如 emoji）可先报告，若作者长时间未处理再由主理人裁定。

## 文档维护规范：结论一致性

> **这一节是维护规范，不是验证纪律。** 它解决的是「结论在文档间不漂移」，
> 与 ADR-007 的三层机制（「如何正确得出结论」）不同层级。

### 为什么单独列

本项目的实测事实被重复写在多份文档中。以 `ratios=99x99` 为例：

| 文档 | 出现次数 |
| --- | --- |
| `decisions/ADR-007.md` | 4 |
| `ARCHITECTURE.md` | 6 |
| `PRD.md` | 8 |

**同一个实测样本共出现 18 次。** 任一处措辞与实测不符即产生结论漂移，
且**表格 / 摘要位置的那份风险最高** —— 实施者照表格写代码，照正文写文档。

实例：ARCHITECTURE 的客户端校验表曾写「非法值返回 200，不构成风险」，
而同一文档的 Trap 13 正确记录为「静默匹配，返回 1:1」。
**表格里那版更显眼、更容易被照抄。**

### 规则：表格与摘要只引用，不复写

```
表格里写「见 Trap 13」        <- 正确
表格里复制 Trap 13 的完整结论  <- 错误，会独立漂移
```

这样每条实测结论只有一处可漂移，改一处即全局生效。

### 自动化能力边界（重要，不要误读）

`verify-docs.py` 的 `check_conclusion_consistency` **仅检测互斥措辞**
（同一处说「静默/忽略」，另一处说「精确匹配/正常生效」）。

**它不做通用语义比对** —— 那需要 LLM，而门禁必须在 CI 里确定性运行。

**若把这条规范描述成「已被门禁全覆盖」，就是虚假安全感。** 这是
ADR-007 记录的那类错误的又一次翻版：*静默失效不会被人发现，
因为「检查通过」与「检查没跑」的表象完全相同。*

### 第四类：显式盲区声明

> 来源：设计侧 v3.5 实证。

她的三层防线全绿，但 `.py` 里仍有 3 处字面 emoji ——
因为 `check_punct_spacing.py` 不管 emoji，`verify.py` 只扫 `.md/.css/.json`。
**延迟两轮才发现。**

核心原则：**声明了才能被讨论，没声明就默认它被检查了。**
这是从「默认有防护」转向「显式声明防护边界」。

`verify-docs.py` 现输出自己的四条盲区：

```
[verify-docs] 已声明盲区: 不检查 scripts/*.py 自身的 emoji（字面样本须用 \u 转义）
[verify-docs] 已声明盲区: 不做通用语义比对 —— 结论一致性仅检测互斥措辞
[verify-docs] 已声明盲区: 不检查代码语义（仅文档一致性 + 源码规范）
[verify-docs] 已声明盲区: 不检查 Swift 编译期问题（那是 api-gate 的职责）
```

框架侧提供 `SelfTest.declare_blind_spot(description)`，见
`docs/selftest_framework.py`（设计侧交付，含 `POSITION_CASES` 位置用例维度）。

**新增检查器时必须声明盲区** —— 沿用 GATE-USAGE.md 第一条使用纪律的思路：
声明了才能被讨论，没声明就默认它被检查了，而这个默认往往是错的。

### 人肉部分（补机器检查的缺口）

写完一份文档后，反向搜一遍自己最核心的 3-5 条结论：

```bash
grep -n "<核心结论关键词>" docs/*.md docs/decisions/*.md
```

逐处核对措辞是否一致。成本很低，能防住一类很难自动发现的错误。

## WARN 与 FAIL 的区别

| 级别 | 含义 | 行为 |
| --- | --- | --- |
| **FAIL** | 确定性违规，阻断 | CI 红，必须修复 |
| **WARN** | 疑似问题，需人判断 | CI 绿，但列出待确认 |

`verify-docs.py` 当前把 **ASCII 框线不完整** 标为 WARN —— 因为修改 `DESIGN.md` 的时机属于设计侧，架构侧只报告不阻断。

## 校验器必须先证明自己能跑（启动自检）

> 来源：设计侧 v3.3 的真实教训。

她的 pre-commit 用 `grep -qP`，而 **macOS BSD grep 不支持 `-P`**：

```
$ echo test | grep -qP "test"
grep: invalid option -- P
exit code = 2
```

若 stderr 被 `2>/dev/null` 吞掉，`if [ ... ]` 恒为 false ——
**规则从未运行过，且没有任何声音**。如果不是 PM 查出来，会一直以为它在正常工作。

**这比「前提存在但没调用」更隐蔽**：后者至少能检查「它有没有被调用」，
而这里连检查的前提都不存在。

因此 `verify-docs.py` 启动时先跑 `self_test()`：

| 检查 | 内容 |
| --- | --- |
| 正则可编译性 | 所有规则正则 `compile()` 一遍，语法错误直接抛异常阻断 |
| 负向用例 | 每个关键规则给「必须命中」与「必须不命中」样本，两者都要验证 |

**自检失败时退出码为 2，阻断 CI** —— 不是警告。

**自己不能跑，就没资格检查别人。**

### 三类自检（缺一不可）

| 类别 | 能抓什么 | 抓不到什么 |
| --- | --- | --- |
| 1. 正则可编译性 | Python `re` 的语法错误 | 外部工具的选项是否存在 |
| 2. 负向用例 | 规则永不命中 / 过宽 | 外部工具的选项是否存在 |
| **3. 外部依赖能力** | **「以为有能力，实际没有」** | — |

**第3 类由设计侧提出**，她实测出前两类的结构盲区：
`self_test()` 报告通过，但外部 `grep -P` 的规则已死。

当前实现：验证 `scripts/*.sh` 中**是否真的用了 `grep -P`**。
- 用了-> **阻断**（退出码 2）
- 没用但平台不支持 -> 仅 WARN 提示「新增规则时务必用 -E」

不直接禁用该选项 —— 平台不支持不等于不能写文档说明问题。

已验证三类自检均能捕获对应失效：

| 注入的失效 | 自检结果 |
| --- | --- |
| 正则含 PCRE 专有语法 `\h` | CAUGHT（`bad escape \h`） |
| 规则永不命中（`ZZZ-NEVER`） | CAUGHT（无法命中必须命中的样本） |
| shell 门禁用了 `grep -P` | CAUGHT（退出码 2 阻断） |

## 新增检查项的要求

任何新增检查必须：

1. **先做负向测试**：在 `/tmp` 副本上注入违规 -> 确认拦截 -> 确认干净副本通过
2. **确认不是假阴性**：BSD grep 不支持 `\s` / `\d`，basic 模式不支持 `\|`。正则若未在 BSD 环境下验证，会静默失效（返回 PASS 但抓不到违规）—— 这是本项目踩过的坑
3. **确定 FAIL / WARN 归属**：能否用门禁自动检出的用 FAIL（先做），需靠人判断的用 WARN（后做）
