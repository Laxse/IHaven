## 一、问题陈述

### 1.1 现状：一个被验证过的需求，四个未被满足的缺口

macOS 用户想要「好 wallpaper」的诉求已经被反复验证，但 2026 年这个诉求被拆成了四个互不满足的阵营：

**缺口一：Windows 的黄金标准在 Mac 上根本不存在。**  
Wallpaper Engine 是全球动态壁纸的事实标准（Steam 销量数十万级，创意工坊海量内容），但它是纯 Windows 应用。经过多方来源交叉验证（TechBloat、PositionIsEverything、MacPaw、AppleInsider 论坛），结论完全一致：**Wallpaper Engine 没有任何原生 macOS 版本**。Boot Camp 只支持 Intel 且需要重启进 Windows，Apple Silicon 完全不可用；Wine / CrossOver / 虚拟机方案下壁纸只渲染在虚拟机窗口内，不是真实 macOS 桌面，且 CPU 与电池开销远高于原生方案。用户搜「Wallpaper Engine Mac」得到的是一整页的「无法使用」。

**缺口二：Mac 原生替代品都不解决「找」的问题。**  
现有 macOS 动态壁纸应用（Backdrop、Wallper、Wallspace、Wallux、iWallpaper、Dynamic Wallpaper Library）本质是**内容库播放器**，不是浏览器。它们的核心能力是「播放我精选库里的东西」，缺失的是「帮我找到那张图」。差评与评测一致指出：iWallpaper 库内容找不到想要的热门壁纸，缺少按作者/标签搜索；Paper 无用户上传、不能导入本地视频；Unsplash Wallpapers 完全不支持动态壁纸、多显示器只支持全局统一设置、无收藏按钮、无相似图推荐。用户的真实行为是「我知道我想要什么风格，但没人帮我找」——这正是筛选与检索问题，不是内容数量问题。

**缺口三：静态壁纸的检索能力被系统设置和粗糙第三方工具浪费。**  
macOS 自带壁纸设置只提供有限的官方集合，无自然语言检索、无社区市场、无第三方场景创作。第三方工具质量参差：wallhaven-desktop（Tauri）GitHub 仅 42 star、在 macOS 上安装触发「应用已损坏」需手动 `sudo xattr -rd com.apple.quarantine`；luisflorido/wallhaven-desktop 同类问题；Spice（Go/Fyne）UI 是 Linux 风格的极简面板，且明确已知问题为「仅支持主显示器」；stefanolocci/wallhaven 只是一个 shell 脚本（无 GUI、需手动编辑配置文件）。**wallhaven 是全球最大的壁纸站（站内约 129 万张壁纸、161 万注册用户、累计 39.4 亿次浏览），却没有任何一款苹果官方级的 macOS 原生客户端。**

**缺口四：多显示器与动态壁纸的性能/功耗问题被所有产品回避。**  
技术调研确认了两个硬约束：

- macOS 壁纸是「按 Space 而非按显示器」设置的，且系统设置面板跟随鼠标所在显示器，用户极易误判。多显示器壁纸不生效的元凶是「显示器具有单独 Spaces」未开启（修改后需注销重登）。第三方壁纸管理器普遍不解释这一点，也不在 UI 中暴露显示器与 Spaces 的拓扑。
- 动态壁纸必然带来功耗损失（研究数据：动画图形可比静态多消耗 15-20% 电池；分辨率提升 10-20% 功耗；刷新率影响可达 30%）。行业最佳实践是 Lively 的 Smart Pause（前台全屏游戏/视频、电池低于阈值、系统进入节电模式时自动暂停渲染回静态图）。Lively 做得对，但它是 Windows 专用；macOS 侧的 MacWall 宣称「电池/全屏自动暂停」，Backdrop 宣称「全屏自动暂停」，但**没有产品把这些策略做成用户可见、可调、可测量的功能**。

### 1.2 为什么现在做

macOS 26 Tahoe 改变了技术前提，带来两个此前不存在的窗口：

1. **系统首次向第三方开放动态壁纸能力**。macOS 26 暴露了壁纸 API，第三方可以将视频注册为系统壁纸；社区已出现基于系统壁纸扩展点（appex）的实现（如开源项目 Phosphene），播放进程由系统托管、脱离主应用存活、随系统锁屏/休眠生命周期工作。
2. **Liquid Glass 让壁纸的视觉质量第一次成为系统级问题**。半透明菜单与 Dock 会从背景取色，壁纸亮度与动态会直接影响全系统 UI 的可读性。这意味着「壁纸选得好」的价值被系统放大了，同时也意味着低质量动态壁纸的负面观感被放大了。

### 1.3 现有代码的问题（完全废弃的依据）

现有雏形存在硬伤，不具备改造价值：

- **硬编码 API Key 提交进源码**：`QueryParameter.swift` 中 `let apikey = "<REDACTED_API_KEY>"` 明文写在代码里（**旧 Key 已吊销，值已脱敏**，本文件不再记录原文）。这是 P0 安全事故：任何拿到仓库的人都能滥用该 Key，Key 随时可能被 wallhaven 吊销导致所有用户功能失效。
- API Key 通过 URL query 参数传递（`result["apikey"] = apikey`），会进入 URL 日志、代理日志与 Referer 链。wallhaven 官方明确支持更安全的 `X-API-Key` 请求头方式。
- 无 Keychain、无任何速率限流处理（45 次/分钟硬限制）、无 429 重试/退避、无 401 处理。
- Alamofire 全局单例 + `NSLock` 拼接位掩码字符串，字符串索引拼接逻辑脆弱，无 Swift 6 并发标注。
- UI 侧反馈：「本地化支持零语言」，UI 结构为散乱的 `Views/Desktop/{Latest,Hot,Random,Tags,Toplist,Advance}` 平行 tab，无统一状态模型。

## 二、目标用户

### 用户画像 A：视觉策展型创作者（核心用户）

- **特征**：27-38 岁，设计师 / 摄影 / 插画从业者，MacBook Pro + 外接 27" 4K 显示器（Apple Silicon）。
- **一天**：接稿、提案、汇报。工作时打开 3-4 个应用占满屏幕，桌面只在窗口间隙露出来几秒。
- **核心诉求**：「我需要一张**和显示器比例严格匹配、且暗部不抢前景**的壁纸。不能靠运气滚动 —— 我要知道它就是 3840x2160、且深色调」。
- **现怎么做**：在 wallhaven 网站上用浏览器筛选，下载，右键设桌面图片。遇到外接显示器比例不匹配只能手动裁。
- **痛点**：筛选要在网页上做，跨屏适配全靠手动；没有收藏，喜欢的图下次找不回来。
- **付费意愿**：中。为「不折腾」付费，不为「内容多」付费。

### 用户画像 B：多屏效率工作者（高频使用菜单栏）

- **特征**：30-45 岁，远程办公的运营/财务/研发，双屏或三屏（含竖屏副屏），MacBook Air 或 Pro，常用电池办公。
- **一天**：一天切换几十次桌面：客户会议要「干净不抢注意力的背景」；专注时段要「有氛围但不动态」；摸鱼时段要「放一张喜欢的图」。
- **核心诉求**：「我不要打开一个 App 挑 30 秒。我要在菜单栏下拉里，**两秒内**换好，并且**主屏和副屏各给我不同的**」。
- **现怎么做**：系统设置里手动切；或者记住某个 app 的位置用快捷键。
- **痛点**：没有高频入口；多屏设置路径深且反直觉；Spaces 与显示器的关系没人解释清楚。
- **付费意愿**：低，但**留存最高**——一旦成为日常动线，卸载成本极高。

### 用户画像 C：动态壁纸尝鲜者（能力上限探索者）

- **特征**：20-30 岁，学生 / 初级开发者 / 游戏玩家，Apple Silicon 单屏，MacBook，插电为主。
- **一天**：长时间插电使用，愿意为「桌面会动」付费，但对性能敏感。
- **核心诉求**：「我想让桌面动起来，**但不能是我的风扇开始转**」。
- **现怎么做**：试过 Backdrop（订阅 + 水印）、iWallpaper（水印 + iCloud 强制登录 + 2022 年后基本不更新）、4K Live Wallpaper（anime 向、必须常驻、非原生 UI）。
- **痛点**：付费墙 + 水印；没有性能控制旋钮；不知道该选哪张视频；iWallpaper 换机后找不到「恢复购买」。
- **付费意愿**：高，但要求先免费试到满意。

### 3.3 差评集中区 = 市场空白（按可攻占性排序）

## 四、我们的差异化

**一句话定位**：IHaven 是 macOS 上第一款把「找壁纸」和「用壁纸」做成同一件事的原生应用 —— 一个面向 129 万张内容站的深度浏览器，加一个 Apple 级品质的高频管理器。

四个支点：

1. **唯一做「检索」而非只做「播放」的产品。** 竞品的模型是「内容库 + 播放器」，我们的模型是「浏览器 + 管理器」。用户带着意图来（「赛博朋克城市 + 21:9 + 深色调」），带着结果走。这一步完成后，剩下的是管理体验的比拼，而我们在这层有明确优势。
2. **多显示器与 Spaces 被当作一等公民。** 我们把 macOS 最反直觉的系统行为（壁纸按 Space 设置、「显示器具有单独 Spaces」需注销重登、外接屏识别顺序导致重启后壁纸错位）显式建模并在 UI 中解释清楚，同时提供逐屏智能适配。这是所有竞品集体沉默的区域，也是多屏用户最痛的地方。
3. **性能可解释、可测量、可控制。** 借鉴 Lively 在 Windows 上验证过的 Smart Pause 思路，但在 macOS 上把它做成用户可见的四档策略 + 实时占用面板。用户知道为什么在暂停、什么时候恢复，而不是被告知「本应用很省电」。
4. **隐私与 Key 体验是卖点，不是免责声明。** 零账号（除用户自填的 wallhaven Key）、零遥测、Key 只存本机 Keychain、X-API-Key 请求头、明文网络请求日志。对一个壁纸应用来说，这几乎无人做到，而它恰好是 NSFW 与账号默认设置同步的必要条件。

### 5.1 专项判断：动态壁纸编辑器（F11）是否进 MVP？

**结论：不进 MVP，明确排入 V3。** 我认同主理人的 P1 倾向，并在数据上给出更强的理由。

**理由一：RICE 数据是最差的。** Reach=3（只有已经在本应用内找到壁纸、且愿意为一段 10 秒循环投入编辑时间的用户，占比很小）、Impact=2、Confidence=50%（这是全表唯一没有任何竞品验证数据支撑的功能 —— Backdrop 有编辑器但用户画像高度重合于竞品集，且其编辑器是内容社区的附属能力而非核心卖点）、Effort=8（视频合成管线 + 编码器 + 预览播放器 + 撤销栈 + 导入导出，是全表 Effort 最高项）。Score=37.5，比第二名（F12，125）低 3.3 倍，比 MVP 门槛（672）低 18 倍。

**理由二：它的 Reach 被上游功能卡死。** 编辑器的输入是「一张静态图或一段短视频」。静态图来自 wallhaven 检索 —— 但我们还没把 F1 浏览做扎实时，用户手里根本没有素材。编辑器是一个**依赖前序功能且放大其成果**的功能，它的价值实现建立在浏览与收藏已有规模使用之上。

**理由三：它是典型的「V1 会显得廉价、V3 才显得值钱」的功能。** 一个简易编辑器裁出的循环视频，在分辨率适配、色彩一致性、编码参数（HEVC vs H.264、码率、GOP 长度）上都很难与 Wallper / Backdrop 库里的人工精选素材竞争。以这个质量进 MVP，反而会在用户第一次接触时形成「这款产品的动态壁纸很糙」的负面第一印象 —— 而第一印象直接决定动态壁纸这条线能不能立住。

**理由四：用户画像 C（动态壁纸尝鲜者）的诉求里没有「制作」。** 该画像的核心诉求是「我想要动起来但不烧风扇」，不是「我想剪视频」。编辑器服务的是创作者型用户（画像 A 的进阶形态），而画像 A 在静态壁纸阶段的诉求是「筛选 + 多屏适配 + 收藏」，这两件事一件都不需要编辑器。

**若未来要做的最小形态**（供 V3 参考，不是承诺）：裁剪区域（拖拽选择画面比例）+ 循环长度（1-10 秒）+ 播放速度（0.5x-2x）+ 导出为本地 MP4。不做转场、不做滤镜、不做多轨、不做文字。目标是把「把一张 16:9 的图变成适配我 21:9 副屏的 5 秒循环」这一件事做到 60 秒内完成。

### 5.2 MVP 范围

**MVP = F1 + F2 + F3 + F4 + F7 + F5 + F6 + F8（8 项，全部为 P0）**

收敛逻辑：MVP 的用户闭环是 —— **打开 → 找到想要的那张（筛选）→ 看清楚（预览）→ 喜欢（收藏）→ 铺到正确的屏幕上（多屏分配）→ 之后随时快速换（菜单栏）**。这 8 项缺任何一项，闭环即断裂。

Effort 合计约 16.75 人月。其中 F7（限流与错误治理）虽不产生用户可见功能，但它是**唯一必须在 MVP 完成项**，理由有两条：
1. 45 次/分钟 + 24 条/页的硬限制下，没有令牌桶与退避的产品在用户快速翻页时必然出现 429 雪崩。
2. 实测确认 wallhaven 对非法参数返回 **5xx 而非 4xx**（见 F7），意味着错误分类**无法依赖响应体反推**，必须靠客户端本地校验。若不在 MVP 建立这套分类，用户看到筛选结果为空时无法判断是自己的参数错了还是服务挂了 —— 而静默的「加载失败」会让用户对整个内容库产生错误认知。

F9（动态壁纸播放）与 F10（性能护栏）作为**第二批（V2）**捆绑交付 —— 两者不可拆分：先播后护栏等于让用户先经历一段时间的糟糕性能，先护栏不播放则护栏无对象。团队需要在 V2 开始时把这两项作为一个原子批次排期。

**V2 的 F9 范围已收窄**（详见 5.6）：仅支持用户本地导入的 MP4/MOV，不集成 FFmpeg、不支持 WEBM/MKV/GIF，且不为 wallhaven 内容做任何视频解码（实测 wallhaven 零视频内容）。

### 5.3 V3 预研项的技术前置风险

F12（锁屏动态壁纸）依赖的 macOS 壁纸扩展点为**私有框架**（社区实现通过 `dlopen` 加载 `WallpaperExtensionKit` 并用 Mirror 反射调用其 XPC 类型）。这意味着：Apple 可在任一大版本 OS 更新中更改或移除它；社区已验证可用版本为 macOS 26 与 27 beta。若架构师在 V3 推进此项，必须设计降级路径（私有 API 不可用时回退到应用内独立渲染层）。此项技术决策属架构师职责，本 PRD 仅标注风险。

### 5.4 专项判断：跨屏拼接壁纸（F15）是否进 MVP？

**结论：不进 MVP，延后至 V2，且 V2 内也排在 F9/F10 之后。** 采纳设计师提出的这一需求 —— 它对用户画像 A 确有吸引力，但技术调研发现了三个改变结论的硬事实。

**必须先纠正的一个技术前提：macOS 原生不支持跨屏拼接。** 这是本判断的事实基础。多个独立来源交叉验证结论一致：
- Windows 才有 `Span` 适配模式（系统级功能，壁纸拉伸至全部显示器）。
- macOS **没有**任何等价的原生能力。每个显示器是独立画布，一张全景图会被「居中并裁切」到每块屏幕上，而不是被切分到各屏。
- macOS 的壁纸 API（`NSWorkspace.setDesktopImageURL(_:for:options:)`）只接受「当前 Space 的某块屏幕」，没有跨屏的参数语义。

因此「跨屏拼接」在 macOS 上不是一个「打开系统开关」的功能，而是**我们必须自己实现的能力**：程序化读入一张全景图 → 按每屏的实际物理像素尺寸与缩放比计算切图区域 → 切分为 N 张子图 → 逐屏写入。这与 F2「多屏逐屏分配」是同一条能力链，但多了一层图像切分计算。

**理由一：技术调研发现的可靠性缺陷，比「麻烦」更严重。** 这不是「多点几下」的问题，而是**做出来也不可靠**：
- **缩放比不一致会导致接缝错位。** Retina 屏与非 Retina 屏混用（MacBook 内屏 + 外接显示器）是最常见配置，此时同一张图的两半在两块屏上的实际物理尺寸不一致，数学上正确的切图在视觉上仍然错位。
- **显示器高度不同时接缝不在一条直线上。** 副屏位置偏移（上移/下移）会让切图边界无法用简单的垂直切割表达。
- **维护成本转移到用户身上，且不可逆。** 用户的评价是「试过一次，接缝不对，就再也没试第二次」。这类功能的失败模式是「看起来坏了」，而非「用不了」—— 后者用户会来反馈，前者用户只会默默卸载。
- **脆弱面极多**：换显示器、改缩放比、旋转屏幕、改变菜单栏归属屏幕，任何一个都会让已切好的拼接错位，需要用户重新做一遍。

**理由二：RICE 数据不支撑进入 MVP。** Reach=4（仅限多屏用户，占比有限）、Impact=2（对画像 A 好看，但不是刚需）、Confidence=50%（跨屏拼接在 macOS 上无先例可循，效果好坏强依赖具体硬件组合，我们无法在开发前给出保证）、Effort=4（图像切分计算 + 每屏缩放比换算 + 拼接预览 + 边界情况处理）。Score=100，是 MVP 门槛（672）的 1/6.7，低于 F12（125）与 F14（80）之外的所有延后项中的多数。

**理由三：与 F2 存在能力依赖，不宜拆开交付。** F2（多屏逐屏分配）在 MVP，F15 建立在 F2 之上。如果 F15 进 MVP 而 F2 有任何缺陷，跨屏拼接会把缺陷放大到用户一眼可见的接缝上 —— 这是最糟糕的首发体验组合。

**延后至 V2 的价值主张**（延后不等于砍掉）：对画像 A 而言，这是本产品少数能提供「单屏做不到的视觉冲击力」的能力，值得做。V2 做它时，F2 的多屏分配能力已稳定，图像切分的正确性也有真实硬件环境可验证。

**何时值得做（触发条件，需同时满足）**：
1. F2 多屏逐屏分配在真实多硬件组合上稳定运行，且已有用户反馈确认「多屏分配」是高频刚需（而非少数人的玩法）。
2. MVP 上线后能收集到明确的跨屏拼接需求信号：用户调研/反馈中有「希望一张图铺满两块屏」类诉求，且能区分出「不是想要跨屏拼接，而是想要每屏不同图被误解为拼接需求」的人。
3. 存在可验证的工程方案：至少需证明能在「Retina + 非 Retina 混用」与「异高度双屏」这两类最难配置下，接缝误差在可接受范围内。**若无法证明，则永久不做** —— 一个会错位的拼接功能比没有这个功能更糟。
4. MVP 的 F2 已建立「按屏比例适配」能力，且**该能力已通过客户端预裁切落地**。这一项是拼接功能的前置条件：用户要先能接受「不同屏幕用不同裁切」，才能接受「一张图切给不同屏幕」。

   **修正说明（重要）**：API 核实后必须澄清，「按屏匹配比例」**不能由系统 API 实现** —— `AllowClipping` 只是 BOOL，系统永远居中裁切，不支持按屏比例精确匹配。因此这个前置条件的实现方式与 F15 一样，只能走**客户端预裁切**（Core Image 按屏物理像素裁切后再写入）。

   这带来一个必须正视的推论：**F15 的前置条件与 F15 本身共用同一套预裁切基础设施。** 区别仅在于 F2 是「一张图裁给一块屏」，F15 是「一张图裁给多块屏」。如果架构评估认为客户端预裁切的性能代价过高，那么 F2 的焦点调整能力与 F5 的拼接能力会**同时**受阻 —— 这两者应当作为同一个技术风险一并评估，不要分开决策。

   具体前置条件（可验证）：
   - 预裁切产物按「壁纸 + 屏幕 + 目标比例 + 焦点」四元组缓存，避免每次设置都重新裁切。
   - 预裁切结果与原图分离存储，不覆盖原图，收藏库中保存的仍是原图。
   - 混合 DPI（Retina + 非 Retina）场景下预裁切结果已验证正确。

   **若预裁切性能不可接受，则需重新评估**：此时应退回到「只支持按屏推荐最接近比例的原图 + 系统居中裁切」，即放弃精确比例控制。这是一个明确的降级方案，不接受「预览显示精确比例但实际设置后不一致」的中间状态 —— 那比不做更糟。

### 5.5 专项判断：跨屏拼接是否反向拉高 F11 编辑器的优先级？

**结论：不拉高。两者解耦，F11 仍留 V3。** 设计师提出的这个反向视角有价值，但它混淆了两件本质不同的事。

**它们共用的只是「裁剪区域」这一个交互，不是同一项能力。** 跨屏拼接需要的是「静态图的几何切分」—— 一次性的、无损的、不涉及编解码的空间计算。F11 编辑器需要的是「动态视频的时间轴合成」—— 涉及 AVFoundation 管线、编解码器、时间轴、循环无缝处理、编码参数（HEVC vs H.264、码率、GOP）。前者在 CPU 上是一次图片运算，后者在工程上是一整条视频管线。二者除了「用户拖动一个选区」这个动作外，没有任何可复用的技术基础。

**若强行绑定，会同时破坏两个判断**：
- 让 F15 的 Effort 被 F11 拖高 —— 拼接本来只需要静态切图，若捆绑编辑器，Effort 从 4 膨胀到 9+，那 F15 就要被推到 V3，与「F15 对画像 A 有真实价值」的判断矛盾。
- 让 F11 的 Reach 被误判 —— F11 的 Reach=3 是基于「做视频编辑的用户占比小」。若把拼接用户也算进 F11 的可达范围，Reach 会被虚高到 5-6，而这些人真正要的是「拼一张图」，不是「剪一段视频」。**这是两个不同用户群的合并计数，会导致 RICE 失真。**

**正确的关系是「先后」而非「依赖」**：F11 在 V3 做最小形态时，可以顺带支持输出「拼接用的静态裁切片」（这是裁剪功能的自然延伸，成本极低），从而让从 F15 迁移过来的用户有路径可走。但这是 V3 的顺手能力，不是 V2 拉高 F11 优先级的理由。

**如果 F15 在 V2 落地，它的真实收益之一是给 F11 做了需求验证**：如果大量用户开始手动做拼接，说明他们已经有「我要控制构图」的需求，那么 F11 编辑器的 Confidence 从 50%（无数据支撑）可以上调 —— 因为**用户行为替代了我们的猜测**。这是把 F11 从「猜」推向「证」的路径，比现在直接投入开发更稳妥。

### 5.6 专项裁定：F9 动态壁纸的格式范围（已实测数据源，裁定「不集成 FFmpeg，不支持 WEBM/MKV」）

**裁定：接受架构侧结论 —— 不集成 FFmpeg，不支持 WEBM/MKV 播放。** 补一条与架构侧不同的、更关键的理由。

**实测发现（一手，2026-10-08）：wallhaven 完全没有视频内容。**

这一点必须先说清楚，因为它决定了整个 F9 的形态。我连续采样 5 次请求、共 120 条记录：

| 采样方式 | 样本数 | file_type 分布 |
| --- | --- | --- |
| sorting=random（第 1 页） | 24 | image/jpeg 18、image/png 6 |
| q=+video&sorting=toplist | 24 | image/png 14、image/jpeg 10 |
| sorting=favorites（第 1-3 页） | 72 | image/jpeg 55、image/png 17 |

**合计 120 条样本，视频类内容为 0。** 补充验证：`/api/v1/video` 端点返回 404；wallhaven 官方 API 文档全文检索 video / webm / gif / animated **零命中**。

**所以 WEBM 这个问题的前提本身不成立**：wallhaven 不提供任何视频，自然也不提供 WebM。讨论「要不要支持 WebM」的实质是「要不要为不存在的源去引入一条解码管线」。

**这带来三个连锁结论**：

1. **F9 的 Confidence 应从 80% 上调至 100%，但 Effort 同步下调。** 原判断 Confidence=80% 隐含假设「数据源可能有格式兼容问题」，实测证明数据源不参与，格式风险仅存在于用户本地导入环节 —— 这部分是确定的、可测的。同时 Effort 从 5 下调理由见下。

2. **MVP 与 V2 不需要为 wallhaven 内容做任何视频解码工作。** 格式风险只在「本地导入」这一条路径上，这是可控且可测的。

3. **F9 的价值主张必须改写。** 原表述隐含「浏览到动态壁纸并播放」，但既然 wallhaven 没有动态壁纸，F9 的真实定位是：**让用户把自己已有的视频素材变成动态壁纸**。这恰好与用户画像 C 的场景吻合 —— 他们本来就在别处存了视频素材。

**关于 FFmpeg：不集成的决策我完全支持，且理由比架构侧更充分**：
- 安装体积：静态链接 FFmpeg 增长数十 MB，对一个「可测量可控功耗」定位的产品是负资产。
- 许可证：LGPL/GPL 静态链接边界复杂，App Store 分发风险高。
- 供应链风险：引入大体量外部编解码库，安全审查成本高。
- **最关键：为了一个数据源里不存在的格式付出上述代价，是纯粹的浪费。**

**代价必须诚实呈现，而非静默黑屏**：用户本地导入 WEVM/MKV 时，UI 必须给出具体转换引导（「macOS 不支持该格式的硬件解码，建议转换为 MP4」），并说明原因。这是产品承诺的一部分 —— 用户导入失败却只看到黑屏，会直接归因于我们的播放能力不足。

**GIF 同样不支持。** 补充一条实测观察：GIF 是静态壁纸格式的伪动态化，播放需自行逐帧解码（CPU 密集且效果差），且 macOS 官方并不把 GIF 作为壁纸类型支持。V2 阶段明确不支持 GIF，并在导入时同样给出转换引导。

**支持范围（V2 最终裁定）**：
| 格式 | 状态 | 说明 |
| --- | --- | --- |
| MP4 / MOV | 支持 | AVFoundation 硬件解码，覆盖绝大多数来源 |
| HEVC（H.265） | 支持 | macOS 原生硬解，功耗表现优于 H.264 |
| H.264 | 支持 | 兼容性兜底 |
| WEBM / MKV | **不支持** | 不集成 FFmpeg。导入时给转换引导 |
| GIF | **不支持** | 非硬件解码路径，功耗与体验均不达标。导入时给转换引导 |

- Given 用户导入 WEVM 或 MKV 文件，When 导入流程，Then 明确提示「macOS 不支持该格式的硬件解码，建议转换为 MP4 后再导入」，并说明原因，**禁止静默黑屏或静默失败**。
- Given 用户导入 GIF 文件，When 导入流程，Then 明确提示该格式不在支持范围内并给出转换建议。
- Given 用户导入 MP4/MOV 文件，When 导入流程，Then 正常入库，UI 展示格式与分辨率信息，并提示该文件不参与网络壁纸的分辨率适配逻辑（它不来自 wallhaven）。

**功能可达性验收（防止用户先撞空态才知道功能边界）**

由于 wallhaven 无视频内容（见 5.6），动态壁纸素材只能来自本地导入。这意味着用户是带着「来找动态壁纸」的预期进入的，若不主动说明，会产生预期落差。**用户必须先看到能力边界，再看到空态。**

- Given 用户首次打开动态壁纸分区，When 进入导入界面，Then **在看到空态之前**就能看到「支持 MP4/MOV（HEVC、H.264），不支持 WEBM/MKV/GIF」的格式说明与 drop zone，且能直接看到「选择本地文件」按钮 —— 用户**不得需要先拖一个文件失败才知道这个功能支持什么**。
- Given 用户从侧栏进入动态壁纸分区，When 首屏渲染，Then 主动用一行文案说明「动态壁纸从本地视频文件导入」，不依赖用户先进入空态才发现。
- Given 用户在格式说明区域，When 查看，Then 不支持的三种格式（WEBM/MKV/GIF）以「不支持」明确列出而非隐藏，减少用户尝试失败的成本。

## 六、验收标准（Given / When / Then）

### F1 壁纸浏览瀑布流

- Given 用户已在设置中完成 API Key 配置（SFW 可跳过），When 打开主窗口默认「最新」列表，则首屏 24 张缩略图在 2 秒内完成渲染（冷启动，含网络请求）。
- Given 滚动至距底部 400px，When 触发预加载，则自动请求下一页并无缝追加，无空白占位闪烁。
- Given 连续快速滚动 10 屏（= 约 240 张），When 观察网络请求，则实际 API 调用次数不超过 12 次（缩略图走缓存与图片 CDN，不重复打 API）。
- Given 用户开启网络限流/离线，When 打开列表，则展示本地缓存内容并明确标注离线状态与最后同步时间，不展示空白页。
- Given 任意缩略图，When 鼠标悬停 200ms，则开始渐进加载并在加载完成时渐显，不出现半图闪烁。
- Given 图片加载失败（网络中断/源站 404），When 该卡片在视口内，则展示占位态与重试入口，且不阻塞同屏其他卡片渲染。
- Given 单张图片加载失败（局部问题，非筛选条件问题），When 呈现该卡片错误态，Then 使用**中性色而非警示色**，配文字「加载失败」。理由：单图 404 是局部问题，若用警示色用户会以为整个筛选失败并反复重试。这与「空态必须中性」是同一条原则的不同应用。

### F2 一键设为壁纸 + 多屏逐屏分配

**底层 API 能力边界（本节验收标准的唯一依据）**

来源：`NSWorkspace.h:203-236`（macOS 10.6+ 至今未变）、`NSCell.h:60-69`（NSImageScaling 取值）。以下为官方原文语义，本节不得承诺系统未提供的能力。

系统提供的壁纸配置 option 只有三个 key：


| Key                                       | 取值                         | 官方语义                                                                                |
| ----------------------------------------- | -------------------------- | ----------------------------------------------------------------------------------- |
| `NSWorkspaceDesktopImageScalingKey`       | `NSNumber(NSImageScaling)` | 默认 `NSImageScaleProportionallyUpOrDown`。官方注明 `NSImageScaleProportionallyDown` 目前不支持 |
| `NSWorkspaceDesktopImageAllowClippingKey` | `NSNumber(Bool)`           | NO（默认）= 图片完整可见，但四周可能有空白；YES = 填满屏幕，图片可能被裁切。仅对比例缩放类型生效，非比例类型忽略此值                     |
| `NSWorkspaceDesktopImageFillColorKey`     | `NSColor`                  | 填充图片周围空隙。仅支持可转为 `NSCalibratedRGBColorSpace` 的颜色，alpha 被忽略                           |

`NSImageScaling` 全部可选值仅四种：ProportionallyDown（壁纸 API 不支持）、AxesIndependently、NSImageScaleNone、ProportionallyUpOrDown。其中**不存在任何「平铺」语义** —— 平铺无法通过该 API 实现，不得写入 UI 或验收标准。

由此得出三条硬约束：

- **不存在「居中」这个独立选项。** 「填满并居中裁切」是 ProportionallyUpOrDown + AllowClipping=YES 的固定行为，系统永远居中裁切。
- **不存在「平铺」。** 不要在 UI 或验收标准中出现该词。
- **不存在「指定裁切哪一侧」。** AllowClipping 只是 BOOL，系统永远居中，用户无法通过系统 API 控制裁切焦点。

**验收标准**

- Given 用户接入 2 台显示器（3840x2160 主屏 + 2560x1440 副屏），When 点击「设为壁纸」，Then 出现目标显示器选择器，默认展示两台屏幕的缩略图与各自的实际分辨率。
- Given 用户为不同屏幕选择不同壁纸，When 应用完成，则两屏各自显示对应壁纸，且系统设置中「显示器具有单独 Spaces」关闭时给出明确提示与修复引导。
- Given 目标屏的壁纸宽高比与图片不匹配，When 用户选择「完整可见」（AllowClipping=NO），Then 四周空隙由填充色填充（见下方填充色验收），不出现系统默认色块。
- Given 目标屏的壁纸宽高比与图片不匹配，When 用户选择「填满」（AllowClipping=YES），Then 图片按比例放大并由系统居中裁切，铺满整屏无空隙。
- Given 用户选择「填满」，When 应用，Then 预览展示的必须是应用后的实际构图（按屏中心裁切后的结果），而非仅显示原图或示意图。
- Given 用户需要控制裁切焦点（希望保留的画面不在中心），When 调整焦点，Then 由客户端用 Core Image 按目标屏物理像素比例预裁切出成品图，再将预裁切后的文件写入系统。写入系统的是已裁好的静态图，系统不再进行二次裁切。**此为客户端预裁切实现，非系统裁切能力**。
- Given 用户对同一张壁纸在不同屏幕上设置了不同焦点，When 应用，Then 每屏各自生效，互不干扰。裁切结果按「壁纸 + 屏幕」维度分别缓存。
- Given 目标屏为 Retina 与非 Retina 混用组合（MacBook 内屏 + 外接显示器），When 计算裁切构图，Then 按各屏的物理像素尺寸而非逻辑点分别计算，避免预览正确但实际设置后错位（此为跨屏拼接 F15 的前置能力，F15 延后但此能力在 MVP 必须正确）。
- Given 用户在不同缩放比的屏幕间切换，When 裁切焦点位置被复用，Then 焦点按各屏独立记忆，不跨屏错误套用。
- Given 用户在系统设置中显示「显示器具有单独 Spaces」为关闭状态，When 尝试多屏分配，则阻止操作并给出「需开启该选项并注销重登」的具体步骤，不静默失败。
- Given 壁纸文件从外接硬盘移走，When 系统在下次启动时找不到文件，Then 明确报错并保留原设置项，不静默回退为系统默认壁纸。

**填充色：自动派生，而非让用户手选（差异化能力）**

系统提供的填充色是唯一能解决「适应模式四周空隙」的手段。wallhaven 每个壁纸的 API 响应都带 `colors` 数组（多个主色值），已核实可用。产品决策是**由应用自动从 colors 派生一个协调色作为填充色默认值**，而不是提供填充色选择器。

理由有三：其一，官方头文件 `NSWorkspace.h:225` 明确建议第三方「通常不应当为挑选这些 options 呈现用户界面，而应直接选择合适的默认值并允许用户在系统设置中调整」，让用户手选填充色与这条官方建议相悖。其二，自动派生才是真正的差异化 —— 竞品不做这件事不是因为漏了，而是因为默认交给系统色。其三，用户心智负担更低：没有人会为了填一个色块去思考该填什么颜色。

- Given 用户选择「完整可见」模式且图片未填满屏幕，When 应用，Then 填充色由应用从该壁纸 colors 主色自动派生，用户无需操作即获得与画面协调的边缘色块，替代系统默认色。
- Given wallhaven 返回的 colors 为空或全部无法解析，When 应用，Then 优雅回退到系统默认填充色，不报错、不阻塞设置。
- Given 用户已自定义过填充色，When 查找恢复入口，Then 提供「恢复自动派生」的重置入口（自定义能力可延后，但必须提供恢复默认的路径，避免用户被自动值锁定）。

**超分风险：API 默认行为带来的产品陷阱**

ProportionallyUpOrDown 是默认值，且 ProportionallyDown 不被支持 —— 这意味着小于目标屏的图片会被放大，而非等比缩小。在 5K/6K 显示器上，一张 1920x1080 的壁纸会被放大而显得模糊。这是系统默认行为，无法通过 API 关闭，只能预警与预防。

- Given 目标屏为高分辨率（如 5K 6K）且所选壁纸分辨率低于目标屏，When 应用，Then 预警用户该壁纸会被系统放大并可能模糊，建议改选更高分辨率壁纸或改用「完整可见」模式。
- Given 浏览阶段，When 依据当前连接屏幕的分辨率，Then 默认在筛选条件中优先推荐不低于屏幕物理分辨率的壁纸（wallhaven 支持 `atleast` 最小分辨率筛选）。
- Given 用户拔掉外接显示器、或把壁纸从副屏改设为主屏，When 重新评估放大倍数，Then **放大倍数按当前屏物理像素实时计算，不使用任何缓存值，也不作为壁纸的持久化字段**。放大倍数是「壁纸 × 屏幕」的关系量而非壁纸的固有属性 —— 同一张 3840x2160 壁纸在 5120x2880 屏上需 1.33 倍放大，在 2560x1440 屏上无需放大。
- Given 设计侧需要展示放大倍数或模糊预警文案，When 取值，Then 数值必须来自实时计算结果，不得来自缓存（与架构侧 ARCHITECTURE.md 的约束一致）。

### F3 菜单栏面板

- Given 应用正在运行，When 用户点击菜单栏图标，Then 面板在 200ms 内出现，含搜索框、上一张 / 下一张 / 随机三个操作按钮、当前壁纸缩略图、收藏夹入口。
- Given 用户在面板搜索框输入关键词，When 输入停顿 300ms，Then 自动发起检索并展示结果列表，无需按回车。
- Given 用户在面板点击「下一张」，When 执行完成，Then 菜单栏面板与主窗口的当前壁纸状态在同一秒内更新（数据层共享，非两套独立状态）。
- Given 应用未运行，When 用户尝试打开菜单栏面板，Then 启动应用并展示引导（引导文案须具体说明本应用能做什么，禁止占位文案）。
- Given 用户关闭主窗口（Command-W），When 观察，Then 应用仍在菜单栏运行、壁纸功能仍生效。

### F4 筛选系统

- Given 用户设置筛选条件（分辨率 ≥ 3840x2160、宽高比 21:9、主色调 #660000、分类 general、纯度 SFW、排序 favorites、时间窗 1M），When 应用，则请求参数与 wallhaven API 定义逐一对应，且 URL 中不出现 API Key。
- Given 用户设置筛选条件，When 退出并重启应用，Then 筛选条件从 Keychain 恢复。
- Given 用户已配置 API Key 并登录 wallhaven，When 首次进入设置页，Then 可点击「从你的 wallhaven 账号导入默认筛选设置」并展示差异预览后再确认应用。
- Given 用户筛选条件格式合法但无匹配（实测 `atleast=20000x20000` 返回 200 + 空数组，total 为 0），When 页面渲染，Then 展示空状态而非错误态，说明是哪个筛选条件过严并提供一键放宽建议（禁止空白页，禁止任何错误图标或错误文案）。
- Given API 返回 401，When 错误分类，Then 归为「API Key 无效」单一含义并引导去设置页重新配置。**实测：401 不携带 NSFW 语义**（见附录 A-9），故不存在「Key 有效但 NSFW 无权限」这一401 分支。
- Given 已配置有效 Key 且用户请求 NSFW 内容，When 服务端返回 **200 且 `meta.total=0`**，Then **必须先执行 NSFW 权限探测**（见下方「NSFW 权限不足与筛选过窄的区分」）再决定文案，**不得**直接判定为权限不足，也**不得**误报为「Key 无效」。

**NSFW 权限不足与筛选过窄的区分（实测裁定，替代推测式文案，详见附录 A-11）**

实测证明二者在响应层面**完全相同**：

| 场景                                              | HTTP | 响应                  |
| ----------------------------------------------- | ---- | ------------------- |
| NSFW 条件 + 权限不足                                  | 200  | `total=0`，`data=[]` |
| 任意条件 + 筛选过窄（如 `purity=100&atleast=30000x30000`） | 200  | `total=0`，`data=[]` |

两者响应逐字节相同，无法从主响应推断。因此**不能靠推测式文案处理**。

**采用探测请求消除推测（裁定）**

实测确立了三个可区分信号：

| 请求                              | HTTP | total   | 结论                 |
| ------------------------------- | ---- | ------- | ------------------ |
| `purity=001` + 无效 Key           | 401  | —       | Key 无效             |
| `purity=001` + 无 Key            | 200  | **0**   | **NSFW 权限不足**      |
| `purity=110`（sketchy，免 NSFW 权限） | 200  | 624,327 | 账号本身有 NSFW 内容，仅缺权限 |
| `purity=001` + 有效且有权限的 Key      | 200  | **>0**  | 筛选条件过窄             |

**三条前置条件（任一不满足则不探测，否则会产生假权限提示）**

| # | 条件                              | 不满足时的处理               |
| - | ------------------------------- | --------------------- |
| 1 | **Key 已配置且非空**（本地预校验通过）         | **绝不探测**，直接引导用户配置 Key |
| 2 | 主请求返回 200 且 `total=0`、`data` 为空 | 不探测                   |
| 3 | 主请求实际含 NSFW 类别条件                | 不探测（SFW 空结果必然是筛选过窄）   |

**第 1 条最关键**：实测确认，用户未配置 Key 时探测请求同样返回 200 + `total=0`（因为匿名请求本就看不到 NSFW 内容）。若此时发探测，会把「用户没配 Key」误判为「Key 权限不足」—— 而这两者的正确引导完全不同（去配置 Key vs 去开授权）。

**判定流程**：同时满足上述三条前置条件时，自动发一次探测请求，**参数固定为 `purity=001` 且不带任何其他筛选条件**，携带同一 Key：

- 探测返回 **200 + total=0** → **确定**为 NSFW 权限不足，文案「此 API Key 无 NSFW 访问权限，请到 wallhaven 账号设置开启」
- 探测返回 **200 + total>0** → **确定**为筛选条件过窄，给出常规空态 + 放宽建议
- 探测返回 **401** → Key 已失效，走鉴权失败分支

**探测请求必须是固定的宽查询，不得复用用户的筛选条件。** 实测确认：若探测请求携带用户的极窄筛选条件（如 `purity=001&atleast=40000x40000`），探测同样返回 `total=0`，结果仍受筛选影响，**无法区分两种情况**。只有不带任何筛选的固定查询，其结果才只取决于权限。

**成本优化：会话内缓存探测结论。** 探测结论在同一会话内不会改变（用户不会中途改变 Key 的 NSFW 权限），因此首次探测后应缓存结论，同会话内再遇 NSFW 空结果直接复用，不再发请求。这使**平均额外成本接近 0**。

**关键优势：用确定性替代推测。** 不使用「可能未授权」这类推测语气 —— 用户不需要在两个可能原因之间猜测，界面直接给出可执行的下一步。

- Given 主请求返回 200 + `total=0` 且请求含 NSFW 条件，When 探测请求返回 `total=0`，Then 显示确定的权限提示，**不使用「可能」「或许」等推测措辞**。
- Given 主请求返回 200 + `total=0` 且请求含 NSFW 条件，When 探测请求返回 `total>0`，Then 显示常规空态与放宽建议，**不显示任何权限相关文案**。
- Given 主请求返回 200 + `total=0` 且请求**不含** NSFW 条件，When 渲染，Then 直接判定为筛选过窄，**不发探测请求**（无必要，且浪费限流额度）。
- Given 探测请求本身失败（网络/5xx），When 判定，Then 退化为常规空态并**不显示权限文案** —— 宁可少提示，不可误报。这是唯一允许推测的兜底分支，且推测方向是「不说权限问题」而非「说权限问题」。
- Given 权限不足被确认，When 呈现，Then 该状态归入**空态分支而非错误态**（用户的筛选操作本身没有错，且无需重试即可通过开启权限解决），但文案必须明确指向可执行动作。
- Given 用户**未配置 API Key**（本地预校验未通过），When 主请求返回 `total=0`，Then **绝不发起探测请求**（断言未发出），直接引导「请先配置 API Key 以查看 NSFW 内容」。**禁止在此情形显示任何权限相关文案** —— 未配置 Key 与 Key 权限不足是两件不同的事，误判会让用户去开通一个他还没有的 Key。
- Given 已完成过一次 NSFW 权限探测，When 同一会话内再次遇到 NSFW 空结果，Then **断言不再发起探测请求**，直接复用缓存结论。
- Given 探测请求构造，When 检查其参数，Then 必须为 `purity=001` **且不携带任何其他筛选条件**。若复用了用户的筛选条件，探测结果会受筛选影响而无法区分两种情况（实测确认）。

### F5 API Key 与隐私

- Given 用户输入 API Key，When 保存，Then 写入 Keychain（`kSecClassGenericPassword`），且不写入 UserDefaults、不写入任何 plist、不写入日志。
- Given 抓包检查网络请求，When 发送 API 请求，Then Key 出现在 `X-API-Key` 请求头中，不出现在 URL query、不出现在请求体、不出现在任何日志输出中。
- Given 用户输入非法 Key，When 提交验证，Then 401（服务端无条件优先于 5xx，见附录 A 实测），显示「密钥无效，请检查是否复制完整」——**禁止**显示「加载失败」「验证失败」「操作失败」，且需明确说明与网络、限流无关；用户可重新粘贴或清空该字段。
- Given 用户输入非法 Key，When 验证请求返回 5xx（服务端故障而非鉴权失败），Then 显示「wallhaven 服务暂时不可用，请稍后重试」，**不得**误报为「密钥无效」——区分信号为 HTTP 状态码（401 vs 5xx），不依赖文案推断。
- Given 用户输入 Key 并触发验证，When 校验 Key 有效性，Then **必须调用 `/search` 端点（携带 X-API-Key 头）而非 `/settings`**，依据响应判定：401 = Key 无效。**不允许保存无效 Key**。
- Given 用户输入的 Key 为空或仅含空白字符，When 触发验证，Then **断言请求未发出**（本地预校验拦截），不得依赖服务端响应判定（见下方「空 Key 被误判为有效」）。

**空 Key 被误判为有效（实测修正，critical）**

实测边界测试（`/search`，带 `Accept: application/json`）：

| 输入 Key                              | HTTP    | 结果                                                                                      |
| ----------------------------------- | ------- | --------------------------------------------------------------------------------------- |
| 无参数（真匿名）                            | 200     | 正常数据                                                                                    |
| **空值 `apikey=`**                    | **200** | **正常数据 —— 与真匿名完全一致**                                                                    |
| **真正的空格或制表符**（如 `X-API-Key:  `）     | **200** | **正常数据 —— 与真匿名完全一致**。注：不可用 `%20` 字面量表示，因 header 场景下 curl 不解码，服务端会将其视为非空非法 Key → **401** |
| 任意非空字符串（1 / 3 / 5 / 8 / 10 / 32 字符） | **401** | Unauthorized                                                                            |
| 超长 Key（300 字符）                      | 401     | Unauthorized                                                                            |
| 有效 Key                              | 200     | 正常数据                                                                                    |

**关键发现：服务端把空 Key 当作匿名请求处理**（wallhaven 本就允许匿名浏览），因此返回 200 与「Key 有效」完全无法从响应区分。**任何非空内容都会返回 401，包括仅 1 个字符。**

**因此客户端绝不可以用服务端 200 判定 Key 有效。** 唯一可靠的路径是先做本地预校验。

**根因**：服务端把空值与匿名请求等同，而客户端若以 200 为「有效」判据，就会把空 Key 误判为有效。

**客户端硬约束**

- **判定逻辑必须是「非空 → 看 401/200」，而不是「看 200 就认为有效」。** 正确写法：预校验通过（非空）后，401 = 无效、200 = 有效。
- **本地预校验必须在发请求前完成**：trim 后为空或纯空白 → 直接拦截，不发请求。
- **保存按钮的可用状态由本地预校验决定**，不由服务端响应决定。
- **粘贴时自动去除前后空白**，但**去空格后必须再次判空**（纯空格被 trim 成空串，若不二次判空会被漏过）。
- 长度阈值可作为额外防御（如 trim 后长度 < 8 视为可疑），但**不得替代非空判断** —— 实测证明长度与判定无关（1 字符与 32 字符均返回 401）。

**危害等级：critical。** 这是一个静默错误 —— 用户输入空 Key 并「保存成功」，之后浏览行为与未配置完全相同，且**界面上不会出现任何异常**。用户不会发现异常，只会以为「这个 Key 看起来不需要配」。相比之下 401 至少会明确提示。

- Given 用户提交空 Key 或纯空格，When 验证流程触发，Then 请求未发出，UI 就地提示「请输入 API Key」，不显示「密钥无效」（因为这不是 Key 错误，是未输入）。
- Given 用户粘贴带前后空格的 Key，When 自动去空格后，Then 仍需再次判空；若结果为空则按「未输入」处理而非「无效」。

**Key 验证端点选择（实测修正，重要）**

实测发现两个端点对无效 Key 的响应**完全不同**：

| 端点                       | 无效 Key                             | 无 Key       |
| ------------------------ | ---------------------------------- | ----------- |
| `/search`（带 X-API-Key 头） | **401** `{"error":"Unauthorized"}` | 200（正常返回数据） |
| `/settings`              | **404** `{"error":"Nothing here"}` | 401         |

**根因**：`/settings` 是「读取用户设置」端点，仅当用户**已开启 API 访问授权**时才返回数据。仅有 API Key 但未授权访问设置的用户，请求该端点会得到 404 —— 而这与「Key 无效」是两件不同的事。

**因此：Key 有效性验证必须走 `/search`。** 若沿用 `/settings` 验证，一个完全有效的 Key（但未授权设置访问的用户）会被误判为无效，导致用户无法完成配置。

- Given 用户输入 Key 并保存，When 服务端返回 404，Then **不得显示「密钥无效」** —— 404 在 `/settings` 端点意味着「未授权访问设置」，不表示 Key 错误。
- Given 用户输入 Key 并保存，When 服务端返回 200，Then 判定 Key 有效并继续保存流程。
- Given 用户输入 Key 并保存，When 服务端返回 401，Then 判定 Key 无效，显示「密钥无效，请检查后重新输入」。
- Given 用户在 API Key 设置页输入无效 Key并触发验证，When 收到 401 响应，Then 明确显示「密钥无效，请检查后重新输入」（或等义的针对性提示），**禁止显示「加载失败」「请求失败」等通用文案**。用户必须能据此判断是自己的 Key 有问题，而非应用或网络故障。
- Given 收到 401（实测为无条件优先于参数错误），When 错误分类，Then 归入鉴权失败并立即终止，**不得用「参数是否合法」来推断或区分 401 的成因**。

**密钥设置页的错误按原因分流（设计侧已确认的必要约束）**

密钥设置页是全应用唯一会因多种原因在**同一位置**（输入框下方）显示错误的页面。经实测，这里可能出现：401（Key 无效）、404（未授权访问设置，见上方端点说明）、5xx（服务端故障）、网络不可用。**若不按原因分流，会造成错误归因。**

- Given 密钥设置页收到 401，When 呈现提示，Then 显示「密钥无效，请检查后重新输入」，**文案中提及 Key**。
- Given 密钥设置页收到 5xx 或网络错误，When 呈现提示，Then 显示对应原因（服务端暂时不可用 / 网络不可用），**文案中不得提及 Key**。理由：真正原因是服务端挂了，若提示「密钥无效」会诱导用户反复修改自己的 Key，而这是无用功。
- Given 未来引入 `/settings` 且收到 404，When 呈现提示，Then 显示「该密钥未授权访问账号设置」类提示（说明 Key 本身可能有效），**不得显示「密钥无效」**。当前版本该分支不可达，故不实现对应 UI。
- Given 密钥设置页处于密钥输入状态，When 出现任一错误，Then 错误提示**以内联态呈现于输入框正下方**，不弹 toast、不跳转页面。**特别地：不得显示「打开密钥设置」按钮** —— 用户已经在密钥设置页，该按钮等于在密码页上提示「忘记密码？去重置密码页」。
- Given 用户在密钥设置页因其他原因（如浏览壁纸）收到 401，When 呈现提示，Then 走全局态（HUD + 「打开密钥设置」入口），因为此处用户确实不在设置页。
- Given 用户开始编辑输入框，When 输入框中已有错误提示，Then 立即清除该提示（编辑即视为已在纠正）。


**404 分支的当前状态：不可达，记录在案但不进 UI**

经实测确认，`/search` 端点在全部边界场景下（无效 Key / 超长 Key / 特殊字符 Key / 短 Key / 有效 Key）**均不返回 404**，仅在认证失败时返回 401。为不可达状态做 UI 分流是死代码。

因此本项目**当前不对 404 做 UI 分流**。但保留如下记录以备将来：若未来引入 `/settings`（如读取账号筛选偏好设置），404 会立即成为一个真实且语义完全不同的分支 —— 它意味着「未授权访问设置」而非「Key 无效」。**届时切勿将其归因为 Key 无效**，两者的用户后续动作完全不同（前者引导去开启授权，后者引导重新复制 Key），混淆会让用户重输一次却依然失败。

**区分信号统一为服务端返回的状态码**（401 / 404 / 5xx / 网络错误），判定清晰不依赖推断。

- Given 崩溃日志采集，When 分析日志内容，Then 不包含 API Key 明文或其任何片段。
- Given 仓库被公开，When 检查源码，Then 不存在任何明文 Key 常量（对比历史实现中的硬编码 Key，该项为验收红线）。
- Given 用户已配置有效 API Key、账号已开启 NSFW，但应用内 NSFW 总开关未开启，When 浏览任意区域，Then 不返回任何 NSFW 内容（API Key 只解锁能力，不等于用户授权展示）。
- Given 应用内 NSFW 总开关已开启，但菜单栏面板的 NSFW 独立开关未开启，When 在菜单栏面板搜索或浏览，Then 面板只呈现 SFW 内容（面板独立开关默认关闭，且不随全局开关自动开启）。
- Given 菜单栏面板的 NSFW 独立开关未开启，When 用户在面板搜索框输入某关键词且该关键词的 SFW 结果为空、NSFW 结果非空，Then 明确提示「面板已关闭 NSFW 内容，如需查看请开启该开关或使用主窗口」，禁止静默返回空结果（用户会误判为关键词无匹配）。
- Given 菜单栏面板的 NSFW 独立开关关闭，When 面板已展示过某 SFW 结果的历史记录与缩略图，Then 这些缓存内容不含任何 NSFW 缩略图（防止关闭开关后残留展示）。
- Given 菜单栏面板已开启 NSFW，When 面板展示 NSFW 缩略图，Then 缩略图按 NSFW 内容的视觉降级策略处理（见边界条件「菜单栏面板公开场合保护」），且不因用户误开面板而暴露可点击的完整大图。

### F6 收藏库

- Given 用户在浏览或菜单栏面板中收藏一张壁纸，When 操作完成，Then 该壁纸进入收藏库，且「应用历史」中同时存在记录（两个独立实体，互不混淆）。
- Given 收藏库中有 200 张壁纸，When 打开收藏库并按标签检索，Then 结果在 300ms 内返回，不重新打网络请求。
- Given 用户对多张壁纸批量打标签，When 确认，Then 全部更新成功或全部失败并回滚，不产生部分成功的中间态。
- Given 主窗口与菜单栏面板同时打开，When 在任一侧收藏，Then 另一侧在 1 秒内同步显示收藏状态。

### F7 API 层限流与错误治理

**已实测的服务端错误面（2026-10-08，产品与架构双向一手复现）**

wallhaven 的参数处理有两类截然不同的失败方式，必须严格区分：

| 请求                                    | HTTP | 响应体                                       | 真实语义                                                  |
| ------------------------------------- | ---- | ----------------------------------------- | ----------------------------------------------------- |
| `atleast=abc` / `atleast=1920xabc`    | 500  | HTML 页面（`It broke - wallhaven.cc`），非 JSON | 格式非法，服务端崩溃式响应                                         |
| `page=0` / `page=-1`                  | 500  | 同上，HTML                                   | 格式非法                                                  |
| `page=99999`（越界过大）                    | 400  | `{"error":"Bad Request"}`，JSON            | 越界                                                    |
| `resolutions=9999x9999`               | 200  | JSON，total=1，有真实数据                        | **合法且精确匹配成功**（wallhaven 确实存在 9999x9999 的壁纸 id 45jm21） |
| `ratios=99x99`                        | 200  | JSON，total=5005，返回 24 条但全部为 1:1 方图        | **参数被静默忽略**，回退默认比例                                    |
| `atleast=20000x20000` / `50000x50000` | 200  | `{"data":[],"meta":{...,"total":0}}`      | **格式合法但无匹配**，成功但空结果                                   |
| `q=###`                               | 200  | 正常 JSON（空结果）                              | 格式合法但无匹配                                              |

三条关键推论：

1. **非法格式与真实服务端故障在响应体上不可区分** —— 两者都可能返回 500 且响应体为 HTML。客户端**必须在发请求前做本地格式校验**，不能依赖响应体反推错误原因。
2. **5xx 响应体不是 JSON**，解析阶段会再次抛错。错误分类必须在解析之前依据 HTTP 状态码完成，否则非法格式会被误判为「服务返回了无法解析的数据」。
3. **合法但无匹配返回 200 + 空数组，不是错误。** 这类情况必须走空态，不能走任何错误态。

**五类错误 + 空态（与架构侧 ADR-006 对齐）**

| 类别                       | 触发条件                   | 用户文案方向               | 禁止显示       |
| ------------------------ | ---------------------- | -------------------- | ---------- |
| .invalidParameter        | 本地格式校验未过，请求未发出         | 「分辨率筛选值无效，请重新选择」     | 「加载失败」     |
| .serverError(status)     | 5xx 且本地格式合法            | 「wallhaven 服务暂时不可用」  | 「加载失败」     |
| .networkUnavailable      | URLError 族             | 「网络不可用，请检查连接」        | 「加载失败」     |
| .rateLimited(retryAfter) | 429                    | 「请求过于频繁，将在 X 秒后自动重试」 | 静默失败       |
| .decodingFailed          | 2xx 但解码失败              | 「服务返回了无法解析的数据」       | 「网络异常」     |
| **空态（非错误）**              | 请求已发出且 200 + data 为空数组 | 「没有符合此组合的壁纸」         | 任何警示色或错误文案 |

**唯一的区分信号：请求是否发出。** 请求未发出 = 错误态；请求已发出且 200 + 空数组 = 空态。

**统一显示「加载失败」是本项目明确禁止的静默错误。** 用户无法从统一文案判断是自己的筛选条件错了还是服务挂了，会给出完全错误的反馈。

**参数处理的三个隐蔽陷阱（实测修正，2026-10-08，产品与架构双向复现）**

陷阱一：**非法 ratios 会「静默匹配」而非回退默认。**  
实测 `ratios=99x99` → HTTP 200、total=5005，返回的 24 条 ratio 值全部为 `1`（即 1:1），尺寸为 1280x1280、6666x6666、2000x2000、2048x2048 等方图。`meta.query` 为 `null`，用户完全无从察觉筛选未生效。

成因推断：`99x99` 中的 `99` 被当作宽高数值参与了比例匹配，因此服务端返回的是「最长边接近 1:1」的一批图。**这比空态与错误态都糟** —— 空态至少是「没有结果」让用户困惑，错误态至少有提示，而这里用户会以为自己在看筛选结果。定性：**静默错误，本项目最严重的一类。**

陷阱二：**非法 resolutions 静默忽略，返回任意结果。** 与 ratios 不同，它连近似匹配都不做，直接返回与筛选无关的内容，同样零提示。

陷阱三：**`type:` 不是独立参数，而是 `q=` 内部的前缀语法。** 实测（2026-10-08 更正）：独立参数 `?type:video` 被忽略（total 501,661，与基线一致），但 `q=type:video` 作为搜索前缀语法会**真实生效**且返回 0。这说明「type: 无效」是错误的参数形式所致的错误结论。正确形式见下方「零视频内容的第一证据」。

**客户端参数预校验规则（硬约束）**

- **ratios 与 resolutions 必须实现为封闭枚举，不是自由字符串。** 官方 ratios 仅 12 个合法值（9x16、10x16、9x18、1x1、3x2、4x3、5x4、16x9、16x10、21x9、32x9、48x9），resolutions 约 24 个。这两个参数本质是取值范围极窄的枚举，**根本不应以自由字符串形式存在**。改为封闭枚举后：不合法值在客户端即被拦下、请求不发出；合法值语义明确，不存在「静默匹配」的歧义空间。
- **atleast 只校验格式，不校验数值范围。** 规则为正则 `^\d+x\d+$`。`50000x50000` 格式完全合法且服务端正常接受（返回 200 + 空数组），若实现方本地拦截不发，就把服务端该返回的空结果变成了本地错误 —— 正好搞反。
- **不得依赖服务端暴露参数错误。** 对 ratios / resolutions 两个参数，服务端要么静默匹配、要么静默忽略，**都不会报错**。全部必须在客户端预校验。（注意：`type:` 不属于此类，它是 `q=` 内的有效前缀语法，服务端会真实过滤。）
- **合法但无匹配不是错误。** `atleast=20000x20000` 属于此类，走空态。

**必须发送 Accept: application/json 请求头（实测修正）**

实测发现：非法参数返回的 500 响应体**格式取决于请求头**。

| 请求头                        | 500 响应体                                                 |
| -------------------------- | ------------------------------------------------------- |
| 不带 Accept                  | text/html，内容为 <!DOCTYPE html>...It broke - wallhaven.cc |
| 带 Accept: application/json | {"message": "Server Error"}，**JSON 格式**                 |

若不带该头，5xx 响应体无法解析，会在解析阶段二次抛错，导致错误分类被误判为「服务返回了无法解析的数据」。**所有 API 请求必须携带 Accept: application/json**，这是保证错误分类可判定的前提。

**错误优先级：401 优先于 500（实测修正）**

必须区分**实测层**与**应用层**两个层次，不可混为一谈 —— 本项目已吃过「把设计推论当实测结论」的亏。

**实测层（服务端行为，一手实测）**

服务端**先做认证检查，再校验参数**，无条件 401 优先：

| 请求                  | HTTP            |
| ------------------- | --------------- |
| 无效 Key + 非法 atleast | **401**（不是 500） |
| 无效 Key + 合法参数       | 401             |
| 无效 Key + 非法 ratios  | **401**（不是 500） |
| 无 Key + 合法参数        | 200             |

401 的响应体为 `{"error":"Unauthorized"}`（JSON，非 HTML）。

**应用层（设计推论，非实测结论）**

在真实客户端中，由于**客户端预校验会先拦截非法参数**（不发请求），401 实际只在「参数合法但 Key 无效」时可达。非法参数配非法 Key 的组合在客户端不会发出，因此观察不到 401。

**此为设计推论，不是实测结论 —— 不得因「401 观察不到」而删除相关验收标准。**

**错误优先级四步判定（实现必须严格按此顺序）**

```
第1 步  401 → 鉴权失败（无论参数是否合法）→ errorKey，立即终止
第 2 步  客户端预校验失败 → 不发请求 → invalidParameter
第 3 步  2xx → 解码 → 空数组则空态 / 有数据则成功
第 4 步  5xx → 参数合法但服务端故障 → serverError
```

**关键约束：401 必须第一步判定，且不能用「参数是否合法」来推断。** 这条推翻了「5xx 是最终裁决」的简化模型 —— 鉴权层实际在参数层之前。

**含义与推论**

- 客户端错误分类遇到 401 时无需再判断参数合法性。
- 反过来，**收到 5xx 意味着参数已通过认证环节**，可判定为纯服务端侧问题。
- 第 2 步与第 4 步的边界依赖客户端预校验的准确性：若预校验有漏（把非法参数放进去了），错误会落到第 4 步被误判为服务端故障。**这是预校验必须封闭枚举的根本原因。**  
  **验收标准**
- Given 用户连续快速翻页触发 429，When 应用收到 429，Then 自动指数退避重试（最多 3 次），期间在界面显示「正在等待 API 限流恢复」，不弹出错误弹窗打断操作。
- Given 连续 3 次退避重试仍失败，When 最终失败，Then 显示明确错误与「稍后重试」按钮，不无限重试。
- Given 令牌桶额度耗尽，When 距上次请求不足 1.33 秒（45 次/分钟），Then 请求进入队列等待而非直接发出，确保不会触发服务端 429。
- Given 网络完全不可用，When 任意 API 操作触发，Then 统一走本地缓存兜底，并全局标注离线态。
- Given 任意 API 请求发出，When 检查请求头，Then 携带 Accept: application/json 与 X-API-Key，确保 5xx 响应体为可解析的 JSON。
- Given 用户输入的分辨率筛选值**格式非法**（如 `atleast=abc`，不匹配 `^\d+x\d+$`），When 触发查询，Then **断言请求未发出**，UI 显示「分辨率筛选值无效，请重新选择」，而非「加载失败」或「服务暂时不可用」。
- Given 用户输入的分辨率筛选值**格式合法但数值极大**（如 `atleast=50000x50000`），When 触发查询，Then **断言请求已发出**（客户端不得做上界校验），UI 显示空态「没有符合此组合的壁纸」，无警示色、无错误文案。
- Given 用户输入的分辨率筛选值格式合法但无匹配（如 `atleast=20000x20000`，实测 total 为 0），When 结果返回，Then 显示空态而非错误态，不出现任何错误图标或错误文案。
- Given 用户输入不存在的比例值（如 `ratios=99x99`），When 触发查询，Then **断言请求未发出**并提示比例值无效。实测表明服务端会静默匹配出一批 1:1 方图且 meta.query 为 null，用户零察觉 —— 若不拦截，用户会以为筛选生效了，这比报错更糟。
- Given 用户输入不在枚举范围内的精确分辨率，When 触发查询，Then **断言请求未发出**并提示该分辨率不在可选范围内。
- Given 客户端实现 ratios / resolutions 参数，When 代码审查，Then 必须是封闭枚举类型，不接受任何自由字符串入口。
- Given 分页页码为 0 或负数，When 触发翻页，Then **断言请求未发出**，页码在客户端被拦截（服务端会返回 500，客户端不应触发此路径）。
- Given 本地参数格式合法且服务端返回 5xx，When 错误分类，Then 显示「wallhaven 服务暂时不可用」，且分类依据为 HTTP 状态码而非响应体（5xx 响应体为 HTML，不参与错误原因判定）。
- Given 服务端返回 400（如页码越界过大），When 错误分类，Then 归入参数类错误并提示用户调整，不归入服务端故障。
- Given API 返回 2xx 但响应结构不符合预期，When 解码失败，Then 记录脱敏后的响应摘要并显示「服务返回了无法解析的数据」，不崩溃、不显示「网络异常」。
- Given 上述五类中的任意一类触发，When 错误呈现给用户，Then 文案明确指向可执行的下一步操作（改参数 / 等重试 / 检查网络 / 更新应用 / 稍后再试），**禁止任何一种情况显示为「加载失败」**。
- Given 空态触发，When 错误分类，Then 空态**不计入任何一类错误**，埋点中以独立标识上报，不计入 5xx 故障统计。
- Given 错误分类在埋点中上报，When 分析，Then 五类可通过 `error_domain` 区分，不合并为单一值。

### F8 本地图片导入

- Given 用户从访达拖拽一张图片到主窗口，When 拖入完成，Then 立即进入本地库并可设为壁纸，不等待任何网络请求。
- Given 用户拖入一个文件夹，When 拖入完成，Then 递归扫描图片文件并展示导入进度（已完成 / 总数），可取消。
- Given 用户拖入非图片文件，When 解析失败，Then 该文件被拒绝并在结果摘要中列出原因，其余文件正常导入。
- Given 导入的图片与网络壁纸混合，When 浏览，Then 两者在同一瀑布流中展示，本地项有可区分标识。

## 七、边界条件

### 空状态

- 首次启动（未配置 Key）：不展示空洞欢迎页。展示具体的三步说明（说明 wallhaven 是什么、去哪里申请 Key、Key 存在本机哪里）+ 一句明确的隐私承诺文案 + 「暂不配置，先用本地图片」出口。
- 搜索结果为空：指出是哪个筛选条件导致为空，给出放宽建议。
- 收藏库为空：说明收藏能力与使用场景，提供跳转浏览的入口。
- 本地库为空：引导拖入图片或浏览网络源，两个入口并列。

### 错误状态

- 网络错误 / DNS 失败 / 超时：区分错误类型文案，不统一显示「网络错误」。
- 401 / 429 / 5xx 分别有独立文案与独立操作（见 F4、F7 验收）。
- 磁盘写入失败（缓存目录不可写）：明确提示并降级为不缓存模式。
- Keychain 读写失败：明确提示，不静默降级为明文存储。

### 加载状态

- 首屏：骨架屏，不用无限转圈。
- 分页追加：卡片位保留占位高度，不跳动。
- 设置壁纸：显示进度（写入系统壁纸需要时间），完成后明确反馈。
- 大图预览：渐进加载 + 清晰度提升的过渡，不出现模糊图直接切换的突兀感。

### 边界值

- API 每页固定 24 条：分页步长为 24，UI 中不出现与 24 冲突的分页假设。
- 分辨率筛选需支持 wallhaven 全部预设值，且支持「精确匹配」与「最小值」两种语义（`resolutions` vs `atleast`），UI 中明确区分。
- 宽高比含极端值（32:9、48:9、1:1、9x16 竖屏），预览器不得裁切错误。
- 显示器数量：支持 1-6 台，含竖屏与不同缩放比设置；0 台（全部断开）时保留设置不报错。
- 菜单栏空间紧张（用户装了 10 个菜单栏应用）：面板不得挤压或遮挡其他菜单栏项。
- 壁纸文件体积：大图（>50MB）应用与缓存需给出进度与预期耗时。
- NSFW 内容：默认关闭。授权分三层，任一层未通过则不展示（详见 F5 验收标准与下方「NSFW 授权分层模型」）。
- 菜单栏面板公开场合保护：面板常在公共场合被打开，是隐私事故的高暴露面。面板对 NSFW 的处理遵守「默认关闭 + 独立开关 + 不静默」三条原则。

### NSFW 授权分层模型（产品硬约束）

NSFW 能力由三个独立条件串联，任一不满足即不展示：

| 层      | 条件                                   | 判定依据                                                                                                                           | 默认    |
| ------ | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ | ----- |
| L1 能力层 | API Key 有效 + wallhaven 账号已开启 NSFW 权限 | **Key 有效性**：401（单一含义）<br />**NSFW 权限**：主请求 200+`total=0` 时发探测请求 `purity=001`；探测返 `total=0` = 权限不足（确定）；探测返 `total>0` = 筛选过窄（确定） | 由用户配置 |
| L2 应用层 | 应用内 NSFW 总开关开启（需显式操作 + 年龄确认）         | 用户显式授权                                                                                                                         | 关闭    |
| L3 场景层 | 菜单栏面板的 NSFW 独立开关开启                   | 仅影响面板，不影响主窗口                                                                                                                   | 关闭    |

**授权粒度决策：面板采用独立开关（L3），而非跟随全局。** 理由：主窗口是用户主动打开的私密场景，面板是用户被动触发的公开场景，两者的暴露风险差一个数量级。若面板跟随全局，则用户为主窗口开启 NSFW 时被迫在公开场合也暴露，无法表达真实意图。

**关键设计原则：L1 与 L2 不可合并。** API Key 有效只意味着「服务端允许返回」，不等于「用户授权本应用展示」。用户可能为了同步账号默认筛选设置而配置 Key，完全无意浏览 NSFW。若把两者合并，会导致用户在不理解的情况下于公开场合看到 NSFW 内容 —— 这正是本分层要防止的事故。

**面板的三个强制行为**：

1. 默认只搜/只显示 SFW（L3 默认关闭，且不随 L2 自动开启）。
2. 开关关闭时不静默返回空结果 —— 必须提示「面板已关闭 NSFW 内容」并给出开启入口，避免用户误判关键词无匹配。
3. 缩略图做公开场合视觉降级处理（见下）。

### 菜单栏面板公开场合保护（隐私事故预防）

菜单栏面板是本产品暴露风险最高的界面：它在用户任何时刻、任何地点、一次点击即可打开，且用户点击时并未预期会看到敏感内容。

设计要求：

- **默认安全**：面板对 NSFW 的默认状态是关闭（L3 默认关），且面板内不出现任何 NSFW 内容缩略图。
- **不被动泄漏**：面板打开瞬间、面板搜索输入过程中、最近结果列表、预览悬浮层 —— 任何位置都不得出现 NSFW 缩略图。NSFW 内容的进入必须由用户显式操作开关触发。
- **视觉降级**：因公共场合的肩窥风险（shoulder surfing），面板中 NSFW 缩略图需做降级处理，具体强度由设计师决定并遵循 macOS 平台惯例。
- **切换器**：面板必须提供一个可见的 NSFW 开关入口（而非隐藏在设置深处），让用户在公开场合能立刻确认当前状态、随时关闭。
- **搜索反馈**：开关关闭且 SFW 结果为空时，明确提示而非静默空结果（见 F5 验收标准）。

### 并发

- 主窗口与菜单栏面板同时操作同一壁纸资源时，需保证一致性（收藏状态、当前壁纸状态）。
- 应用历史与收藏库双实体写入时，跨进程 / 跨窗口不产生半写状态。
- 图片下载与缓存写入并发时，同一 URL 不重复下载。

### 离线

- 无网络时：浏览走缓存、收藏与本地库完整可用、菜单栏上一张/下一张在本地库范围内可用。
- 有网络恢复时：静默刷新，不覆盖用户本地状态。

### 权限拒绝

- 用户拒绝「自动化」权限（用于系统快捷键）：菜单栏功能仍可用，仅快捷键失效并提示如何开启。
- 用户拒绝「完全磁盘访问」或相关沙箱权限：明确说明影响范围与开启路径。
- MDM 管理的设备限制修改壁纸（`Modify Wallpaper` 策略）：检测到时明确提示「本机受组织策略管理，无法修改壁纸」，不静默失败。

### 数据埋点方案

隐私优先原则：本产品对隐私的承诺是产品定位的一部分，因此埋点必须最小化、可关闭、且不采集壁纸内容本身。

| --- | --- | --- | --- |
| 获客 | `app_first_launch` | 首次启动（用于区分新用户） | `locale`, `os_version`, `arch` |
| 获客 | `api_key_configured` | 完成 Key 配置（不采集 Key 值） | `has_key`(bool), `elapsed_ms` |
| 激活 | `first_wallpaper_applied` | 首次成功设置壁纸 —— **核心激活事件** | `wallpaper_id`, `target_display_count`, `elapsed_since_launch_ms` |
| 激活 | `first_favorite_added` | 首次收藏 | `wallpaper_id`, `entry_point` |
| 留存 | `session_start` | 应用启动（主窗口或菜单栏唤醒） | `entry_point`(launch/menubar/window), `locale` |
| 留存 | `menubar_quick_action` | 菜单栏高频操作 | `action`(next/prev/random/search), `elapsed_ms` |
| 留存 | `filter_applied` | 筛选条件变更（仅记录被改动的维度名与档位数，不记录具体值组合） | `dimension`, `option_count` |

| 转化 | `offline_fallback_triggered` | 触发离线兜底（网络可靠性信号） | `reason` |
| 异常 | `error_occurred` | 前端错误 + API 错误 | `error_domain`, `http_status`, `is_offline` |
| 异常 | `rate_limit_hit` | 触发 429（限流策略调优依据） | `request_kind`, `retry_count` |

埋点实现要求：
- 使用轻量自建 `trackEvent()` 单一封装，事件可通过设置一键关闭；MVP 不引入第三方分析 SDK（与隐私承诺冲突）。

- 本地事件日志保留 30 天后自动清除，可手动立即清除。

| 约束                | 数值                                           | 产品影响                                                                                                                                                                                                                      |
| ----------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 速率限制              | 45 次/分钟                                      | 需客户端令牌桶；429 指数退避；UI 需处理等待态                                                                                                                                                                                                |
| 每页条数              | 固定 24                                        | 分页步长 24；瀑布流需按此设计预加载阈值                                                                                                                                                                                                     |
| NSFW 权限           | 需 API Key                                    | 401 = Key 无效（单一含义，实测见附录 A-9）<br />NSFW 无权限 = 需探测判定：主请求 200+`total=0` 时发探测请求，探测 `purity=001` 返 `total=0` 即确认权限不足（详见 F4 与附录 A-11）                                                                                           |
| 认证方式              | `?apikey=` 或 `X-API-Key:` 头                  | **必须用 `X-API-Key` 头**（URL 形式会进入日志与 Referer 链）                                                                                                                                                                             |
| 账号设置同步            | `/settings` 端点返回用户默认筛选                       | 可一键导入为本地默认筛选                                                                                                                                                                                                              |
| **Key 验证端点**      | **必须用 `/search` 而非 `/settings`**（实测修正）       | 无效 Key 在 `/search` 返 **401**，在 `/settings` 返 **404**（因 `/settings` 需用户已授权 API 访问设置，否则 404 `Nothing here`）。**404 不等于 Key 无效**，用错端点会把有效 Key 误判为无效                                                                           |
| **空 Key 判定**      | **服务端把空 Key 当匿名，返回 200**（实测，critical）        | `apikey=` 空值与**真正的空格/制表符**均返 **200 且数据与真匿名完全一致**（注：curl 头值不解码，`apikey=%20` 是字面量字符串「%20」，服务端视为非空非法 Key → **401**）；而**任意非空字符串**（1~32 字符、300 字符）均返 **401**。因此**服务端 200 无法区分「Key 有效」与「Key 为空」**，绝不可用 200 判定 Key 有效，必须先本地预校验判空 |
| `/search` 的 404   | **不返回 404**（实测）                              | 六类边界场景（无效 / 超长 / 特殊字符 / 短 Key / 有效 Key / 无参数）均无 404。为不可达状态做 UI 分流是死代码                                                                                                                                                     |
| 用户合集              | `/collections/` 与 `/collections/{user}/{id}` | 用户合集浏览（MVP 后，可作为 V2 差异化点）                                                                                                                                                                                                 |
| 每张壁纸的 `colors` 数组 | 多个主色值                                        | 可用于自动派生填充色（差异化能力，见 F2）；也用于瀑布流卡片配色标记                                                                                                                                                                                       |
| `atleast` 参数      | 接受**任意** `WIDTHxHEIGHT` 字符串                  | 非固定枚举。MVP 的 5 档是 **UI 层预设**，实现上按「当前屏物理像素实时构造字符串」，架构上不得硬编码为不可扩展的枚举。**客户端只校验格式 `^\d+x\d+$`，不校验数值范围** —— `50000x50000` 格式合法且服务端正常接受（返 200 + 空数组），本地拦截会把空结果变成错误                                                               |
| 非法参数响应            | **返回 5xx 而非 4xx**                            | `atleast=abc`、`page=0/-1` 均返回 500（响应体是 HTML 非 JSON）；`page=99999` 返回 400 JSON。客户端**必须在发请求前本地校验格式**，不能依赖响应体反推原因。详见 F7                                                                                                       |
| 非法比例值             | **静默匹配近似值**（实测修正）                            | `ratios=99x99` 返回 200 + total=5005，结果全是 1:1 方图，`meta.query` 为 null，用户零察觉。**必须在本地拦截为封闭枚举**，否则用户以为筛选生效了 —— 本项目最严重的一类静默错误                                                                                                    |
| 精确分辨率匹配           | **可命中真实极端值**                                 | `resolutions=9999x9999` 返回 200 + total=1（真实存在该壁纸 id 45jm21）。不可假设极端分辨率必然返回空                                                                                                                                                |
| `type:` 前缀语法      | **是 `q=` 内前缀，非独立参数**（实测更正）                   | 独立参数 `?type:video` 被忽略（total 501,661 与基线一致）；但 `q=type:video` 会真实过滤且返回 0。**这是 q= 前缀族语法之一**（同族：`+tag` / `-tag` / `@user` / `id:` / `like:`）。根因见架构侧 ADR-007 Trap 12                                                          |
| **零视频内容的第一证据**    | **算术穷尽**（实测，强于采样）                            | `q=type:png` → 115,989；`q=type:jpg` → 385,667；两者相加 = 501,656，与全库总数一致 → **不存在第三种文件类型**。采样只能证伪存在，算术穷尽能证明不存在。`q=type:video` / `q=type:gif` 均为 0。注意全库在增长，同一数字在不同时刻实测略有差异（501,656 → 501,661），但比例恒为 99.999%                     |
| **必须带 Accept 头**  | **5xx 响应体格式取决于请求头**（实测修正）                    | 不带 Accept → `text/html`（`<!DOCTYPE html>...It broke`）；带 `Accept: application/json` → `{"message":"Server Error"}`。**所有请求必须携带该头**，否则 5xx 无法解析、错误分类会被误判                                                                     |
| **错误优先级**         | **401 优先于 500**（实测修正）                        | 无效 Key + 非法参数 → 401（不是 500）。服务端先校验认证再校验参数。因此遇 401 无需再判参数合法性；5xx 意味着参数已过认证环节                                                                                                                                               |
| 官方声明              | API 免费提供，无保修，可能变更                            | 必须实现 API 层与业务层解耦；响应解析需容忍新增字段                                                                                                                                                                                              |
| **视频内容**          | **不存在**                                      | 120 条样本（5 次请求）file_type 全为 jpeg/png；`/api/v1/video` 返回 404；官方文档 video/webm/gif/animated 零命中。F9 的格式风险只存在于本地导入路径                                                                                                            |

## 附录 A-2：macOS 壁纸 API 能力边界（供架构师与设计师参考）

来源：`NSWorkspace.h:203-236`（macOS 10.6+ 至今未变）、`NSCell.h:60-69`。已逐行核实 SDK 头文件，非二手转述。

### 系统提供的三个 option

| Key                                       | 取值                         | 约束                                                          |
| ----------------------------------------- | -------------------------- | ----------------------------------------------------------- |
| `NSWorkspaceDesktopImageScalingKey`       | `NSNumber(NSImageScaling)` | 默认 ProportionallyUpOrDown。**ProportionallyDown 官方注明目前不支持**  |
| `NSWorkspaceDesktopImageAllowClippingKey` | `NSNumber(Bool)`           | 默认 NO（图片完整可见、四周可能有空白）；YES = 填满并可能被裁切。**仅对比例缩放类型生效，非比例类型忽略** |
| `NSWorkspaceDesktopImageFillColorKey`     | `NSColor`                  | 填充空隙。**仅支持可转为 NSCalibratedRGBColorSpace 的颜色，alpha 被忽略**     |

### 系统不提供的能力（禁止承诺）

| 能力             | 实际情况                                  | 唯一可行路径                       |
| -------------- | ------------------------------------- | ---------------------------- |
| 平铺             | NSImageScaling 四种取值中无平铺语义             | **无法实现，UI 与文档不得出现**          |
| 指定裁切哪一侧        | AllowClipping 是 BOOL，系统永远居中裁切         | 客户端预裁切（Core Image）后再写入       |
| 按屏精确比例匹配       | 同上，系统不提供                              | 客户端预裁切                       |
| 跨屏拼接（Span）     | SDK 中无 Span 类选项，API 为 forScreen: 单屏语义 | 必须自行图像切分 + 逐屏写入              |
| 关闭放大           | ProportionallyDown 不支持，默认值会放大过小图片     | 无法关闭，只能在产品层预警并用 atleast 筛选预防 |
| 对所有 Space 批量设置 | API 仅作用于当前 Space 的指定屏                 | 需监听 Space 变化或提示用户逐个处理        |

### 官方明确的使用建议（影响 UI 设计）

`NSWorkspace.h:225` 原文：「You should normally NOT present a user interface for picking the options. Instead, just choose appropriate defaults and allow the user to adjust them in the System Preference Pane.」

**产品决策**：不提供完整的填充方式选择器（平铺/居中/拉伸等），只提供「完整可见 / 填满」两个真实可实现的语义，并自动派生填充色默认值。让用户手选全部 options 既与官方建议相悖，也不是竞品做法。

## 附录 A-3：q= 内前缀语法（ADR-007 Trap 12 重点）

`type:` / `+tag` / `-tag` / `@user` / `id:` / `like:` 均为 **q= 内部前缀语法**，  
**不是独立 query 参数**。用独立参数形式会静默返回全库总数（501,656），  
极易被误判为「API 失效」。

实测（2026-10-08，Xcode 会话期间实测）：

| 请求形式                         | total   | 说明                 |
| ---------------------------- | ------- | ------------------ |
| `?type:video`（独立参数，**错误形式**） | 501,656 | 被忽略，返回全库           |
| `q=type:png`                 | 115,989 | 正确形式               |
| `q=type:jpg`                 | 385,667 | 正确形式               |
| `q=type:video`               | **0**   | 正确形式，证明无视频         |
| `q=type:gif`                 | **0**   | 正确形式，证明无 GIF       |
| `q=type:image`               | 0       | `image` 非合法 type 值 |

**算术穷尽校验**：`115,989 + 385,667 = 501,656` = 全库总数  
→ 全库内容被 png 与 jpg 两类**穷尽**，不存在第三种类型。

这是「wallhaven 无视频内容」最干净的判据：**算术穷尽能证明不存在，采样只能证伪存在**。  
144 条 file_type 采样（random/toplist/favorites/anime/views 五维度）降级为佐证。

> **教训（ADR-007 Trap 12）**：用无效参数形式得到的「无效结论」比不测更危险——  
> 它会被写进文档并影响下游决策。任何人验证 API 行为时，必须先确认参数的正确形式。

## 附录 A-5：GIF 格式范围专项裁定（架构师实测纠错）

**纠错记录**：架构师初版把 GIF 与 WEBM/MKV 归为同一类「不直接播放」，理由是"macOS 零视频源、无播放价值"。这个分类不严谨——GIF 与 WEBM 的技术性质根本不同。

| 格式         | 技术性质                         | macOS 能否处理                        | 结论            |
| ---------- | ---------------------------- | --------------------------------- | ------------- |
| GIF        | MJPEG 在容器内封装 → **解封装 + 重封装** | ImageIO 可逐帧解码 + AVAssetWriter 可封装 | **可转换**（B 方案） |
| WEBM / MKV | VP8/VP9 需**完整重新编码**          | macOS 无 VP9 解码器，需 FFmpeg          | 不可转换（A 方案）    |

GIF 转换所需 API 实测均公开可用、无 DEPRECATED：  
`CGImageSourceCreateWithURL` / `CGImageSourceCreateImageAtIndex`（ImageIO）

- `AVAssetWriter` / `AVAssetWriterInputPixelBufferAdaptor`（AVFoundation）

**GitHub AugurResearch 独立测算**：AVFoundation 转 15fps/256 色 GIF 约需原GIF 文件大小的 1/4~1/3，  
但生成 MP4 为 GIF 体积的约 20 倍 —— 体积代价真实存在，需在导入前告知用户。

**排期裁定（team-lead裁定）**：

- **V2**：GIF 列入「不支持」列表，引导文案改为「可用系统工具转换」+ 给出 macOS 转换路径
- **V3**：GIF 一键转换。前置条件：F9 播放稳定 + 有用户诉求的反馈数据

**不与 F9 捆绑的理由**：GIF 转换器零 F9 依赖（不需XPC 与逐屏管线），  
捆绑会让 V2 从「动态壁纸播放」膨胀为「播放 + 格式转换工具」。

**转码参数待实测确定（V3 启动时先做基准测试，不预设参数）**：  
本文档**不锁定**编码参数。以下全部为待验证项，须先实测再确定：  
帧率策略（保留源帧率 / 补到 30fps）、GOP 长度、视频码率、H.264 Profile（Main / High）、  
色度采样（4:2:0 / 4:4:4）、音频流处理。

**转码质量实测门禁（V3 开发时必须执行）**：  
至少覆盖三类典型 GIF 内容 —— ①15fps/256 色/含渐变 ②15fps/128 色/纯色块 ③动态噪点（火焰/雨）。  
每类肉眼确认无色带、无卡顿、无音画不同步。**256 色转 H.264 的 4:2:0 色度采样可能产生色带，  
静默降级即为本项目一直防范的静默错误**，某类质量不可接受时须在导入时提示。

> **纠正记录**：本节此前版本曾列出具体编码参数并归属为「架构师提供」，  
> 经架构师核实其文档中零命中 —— 该组参数系team-lead 编造并错误署名。  
> 已改为待实测确定清单。**伪造他人署名比参数错误更严重，因为它污染了证据链的可信度。**

**Out-of-Scope 表述修正**：「需用户用系统工具转换」不构成不做的理由  
（那是用户的操作系统行为，产品无权预设），故改为技术理由：无原生解码器。

## 附录 A-6：分辨率分档依据（推导值，非官方字段）

实测确认：wallhaven API **无「4K/5K/8K」字段**，仅提供 `dimension_x` / `dimension_y` / `file_size`。  
故所有分辨率档位均为**推导值**，不得以官方数据引用。

**同源计算要求（禁止混用维度）**：

```
同一 WallpaperItem 同时计算两个分数，各自分档：
  pixelScore = dimension_x × dimension_y        // 用于「物理像素是否够」判定
  visualScore = file_size                        // 用于「视觉精细度」判定
```

依据：视觉分档用 `file_size`（同尺寸下 JPEG 文件越大通常越精细），  
像素分档用物理像素面积。**两套分数必须各自独立使用，禁止跨维度比较或映射。**

若 wallhaven 后续提供该字段，需重新评估此推导方案。

## 附录 A-6b：F9 依赖方向定稿（team-lead 直接裁定）

**F9（动态壁纸播放）依赖 F8（本地导入），不依赖 API。**

**NSFW 权限探测属API 层内部实现（`WallhavenClient` 内），不改变 F9 的依赖方向。** 探测服务于F1/F4/F6 的浏览链路，与 F9 无关，因此「F9 不 import `WallhavenClient`」的判据完全不受影响。

依据（实测）：wallhaven 零视频内容（`q=type:video` → 0，且 png 115,989 + jpg 385,667  
= 501,656 = 全库总数，算术穷尽证明不存在第三种类型）。故动态壁纸素材**只能来自用户本地文件**。

**模块关系**：

```
F8 LocalImportService（唯一入口，MVP 阶段实现）
   ├── 静态图片 ──> Wallpapers/──> F1 / F2
   └── 动态视频 ──> DynamicWallpapers/ ──> 格式探测 ──> F9
```

**硬约束**：

1. **格式探测必须在 F8 导入时执行一次**，不在 F9 播放时执行 —— 探测有 IO 与解码开销，  
   播放时才做会让用户先看到卡顿再看到错误。
2. F9 只消费「已导入的视频路径 + 元数据」，依赖面收窄，测试可用本地固定视频、不依赖 F8。
3. **V2 内 F8 与 F9 视为原子批次，顺序 F8 → F9**。F8 未完成则 F9 无法独立交付。

**F9 差异化支点**（内容比不过，比素材管理精度）：  
wallhaven 零内容后，F9 不再有「内容丰富度」卖点。差异化转为  
**多屏逐屏物理像素裁切播放** —— 同一段视频，21:9 副屏不裁切、16:10 主屏按焦点裁切，两屏各自最优。  
这是竞品结构上做不到的（它们只能整屏播放），且复用 F2 已有的物理像素管线，边际成本接近零。

对用户的表述纪律：侧栏入口与导入界面**不得使用暗示存在内容池的措辞**  
（中文「库」「精选」「大全」自带海量感）。统一表述：

- 侧栏入口：「动态壁纸」+ 一行「从本地视频文件导入」
- 导入空态：主动列出支持格式（MP4/MOV 含 HEVC、H.264）与不支持格式（WEBM/MKV/GIF）
- 主操作：「从访达拖入**你自己的**视频文件」

## 附录 A-7：团队协作原则（四条，Phase 1 沉淀）

本项目 Phase 1 出现 13+ 次同型错误（凭直觉假设、未核实即下结论）。以下四条是从中沉淀的  
可执行防护，写入 PRD 作为三方通用规范。

### 原则 1：凡写入验收标准的技术结论，必须亲手实测

**文档与转述只能作为线索，不能作为依据。**

反例（本项目实际发生）：

- `/settings` 文档写了「Authenticated users can read their user settings」→ 推断它能验证 Key 有效性  
  →实测发现无效 Key 请求 `/settings` 返回 **404 而非 401**，会把完全有效的 Key 判为无效
- 官方文档列了 `type:{png/jpg}` → 推断可用于筛选 → 实测发现是 `q=` 内前缀语法，位置错则静默失效

**执行标准**：任何要写进验收标准的 API 行为、参数语义、错误码含义，  
必须有一次可复现的实测记录（命令 + 请求 + 响应）。文档摘抄不算。

### 原则 2：只看状态码等于只测了一半

凡是用状态码判断成功的，必须同时确认响应体内容。

`ratios=99x99` 返回 HTTP 200 且有24 条数据，看起来完全正常——但 24 条全是1:1 方图，  
而用户设置的是「99x99」。若只测状态码，会得出「参数有效」的错误结论。

### 原则 3：区分「不知道」与「已知」—— 不可自纠的错误最危险

「知道自己可能漏看了」可自纠；「连自己有洞都不知道」不可自纠，因为结论看起来有依据。

伪造署名（本项目实际发生，性质最严重）：把编造的参数归给架构师，  
后续引用「架构师说过X」时无法判断哪些有出处。**污染的是整条证据链的可信度。**

### 原则 4：任何「A 还是 B」的文案，必须能回答「依据什么信号区分」

答不出来说明是把选择题丢给了用户。区分信号必须是可观测的（如 HTTP 状态码、请求是否发出）。

具体应用：错误分类 5+1 类、空态 vs 错误态、解码失败 vs 服务故障、  
「删除密钥」vs「更换密钥」。

## 附录 A-7b：判断缺口的三层结构（PM 提出，team-lead 采纳）

Phase 1 的 14 次同型错误不是「同一个错」，而是**三层判断缺口**，  
每层需要不同的防护：

| 层 | 缺口                  | 本项目实例                       | 防护             |
| - | ------------------- | --------------------------- | -------------- |
| 1 | 二手信息也要验证            | 设计师采信「type 参数无效」的转述         | 转述前必须能在来源文档检索到 |
| 2 | 文档提到 ≠ 能用           | 从官方文档推断 `/settings` 可验证 Key | 写入验收标准前必须亲手实测  |
| 3 | **端点存在 ≠ 端点语义符合用途** | `/settings` 对有效 Key 返回 200  | **须确认语义正是用途**  |

### 第三层为何最隐蔽

`/settings` 请求有效 Key **确实返回 200**。若当时实测并看到 200，反而会**更确信设计正确**。

**仅靠「必须实测」这条纪律防不住第三层** —— 实测验证的是「能工作」，  
而我们需要的是「能用在正确的场景」。

> **原则 5（采纳 PM 建议）**：当验证一个能力时，必须确认  
> **「这个能力的语义是否正是我的用途」，而不仅是「它能否工作」。**

配套的判断问法（写入验收标准前自问）：

1. 这个端点的**语义**是什么？（返回的东西是否正是我要的判定依据）
2. 若语义不匹配，它的响应会**长什么样**？（本例：404 与「Key 无效」撞码）
3. 我能否从响应中**区分**「成功」「失败」「不适用」三种情况？

## 附录 A-8：Key 验证端点实测矩阵（禁止用 /settings）

设计实测（2026-10-08，team-lead 独立复现）：

| Key 状态         | `/search?apikey=`    | `/settings?apikey=`    |
| -------------- | -------------------- | ---------------------- |
| 有效 Key         | 200                  | 200                    |
| 无效 Key         | **401**              | **404** `Nothing here` |
| 空 Key          | **200**（total 与匿名相同） | 401                    |
| 纯空格 Key        | **200**（同空Key）       | —                      |
| 超长 Key(300 字符) | **401**              | —                      |
| 无 Key          | 200                  | 401                    |

### 三条硬约束

**1. 禁止用 `/settings` 验证 Key 有效性。**  
该端点是「读取用户设置」，仅在用户已开启 API 访问授权时返回数据。  
无效 Key 请求它得 **404 而非 401**，而 404 与「Key 无效」是完全不同的原因被映射到同一状态码。  
后果：把**完全有效的 Key** 判为无效，用户根本配不进去。

**2. 空 Key 必须在本地拦截，绝不能靠服务端 200 判断 Key 有效性。**  
服务端把空 Key 当匿名请求处理，返回 200 且结果与匿名**完全相同**（实测 total=903 一致）。  
失败链：用户输入空 Key → 服务端返 200 → 误判「Key 有效」→ 保存空 Key →  
**用户以为配好了，实际浏览行为与未配置完全一致**（wallhaven 本就允许匿名浏览）。  
用户不会发现任何异常，只会认为「这个 Key 就不需要配」。

**3. 404 分支当前不可达，但禁令需预先写死。**  
实测 `/search` 七类边界（无效 Key / 超长 Key / 特殊字符 Key / 空值 / 纯空格 / 无参数 / 有效 Key）  
**无一返回 404**。若未来引入 `/settings` 读取用户偏好，404 会立即变成真实分支。

届时禁令：**404 绝不能说成「密钥无效」** —— 404 引导去开启 API 访问授权，  
而「密钥无效」引导重新复制 Key，混淆会让用户白白重输一次却依然失败。

## 附录 A-9：401 语义实测（ADR-007 Trap 16，推翻此前推断）

此前 PRD 与架构文档均写「401 需区分 NSFW 无权限与 Key 无效，用 SFW/NSFW 双探测实现」。  
**这是错的**，实测推翻：

| 场景                             | HTTP    | 结果                 |
| ------------------------------ | ------- | ------------------ |
| `purity=001`（NSFW）+ **无效 Key** | **401** | Key 无效             |
| `purity=001`（NSFW）+ **无 Key**  | **200** | **`total=0`（空数组）** |
| `purity=100`（仅 SFW）+ 无 Key     | 200     | `total=501,661`    |

**匿名请求 NSFW 返回 200 + 空数组，不是 401。** 故：

- **401 只有单一含义：API Key 无效**，与 purity 完全无关
- **不需要** SFW/NSFW 双探测去分类 401
- **NSFW 权限不足**表现为「已配置有效 Key + NSFW 请求返回 200 + `total=0`」

**根因（判断缺口第三层的典型案例）**：从官方文档「401 Unauthorized」的表述  
**推断**它承担语义分类功能，实测发现它不携带这个信息。  
即使当时实测，若不做「同一 Key 跨 purity 对比」这个关键对照，仍可能把观察到的相关性当成语义设计。

> 教训已并入**附录 A-10 元规则 5**（实测通过 ≠ 测到了你以为的那件事），此处不重复表述。

| #  | 纪律                                  | 来源                    | 防住的错误类型       |
| -- | ----------------------------------- | --------------------- | ------------- |
| 1  | 以状态码判断成功，**必须同时确认响应体内容**            | 架构师自我纠错               | 只测了一半         |
| 2  | **服务端不报错的参数，必须全部客户端预校验**            | 实测 ratios/resolutions | 静默错误          |
| 3  | **参数形式未确认前，不得下「该参数无效」的结论**          | type: 参数事件            | 形式错误当内容错误     |
| 4  | **实测之后要问：样本是否覆盖了能区分假设的对照组**         | 架构师（本轮新增）             | 数据全对、测试全过、结论错 |
| 4b | **前提机制**：被测对象必须存在且语义明确（签名存在 ≠ 能力可用） | 架构师 + PM              | 测了从未运行过的代码    |
| 4c | **作用域机制**：结论不可外推到超出实测范围             | PM（本轮新增）              | 对照有效但作用域被放大   |

### 第 4c 条为何必要（PM 提出）

前两类都有纪律覆盖，第三类**完全没有**——而它恰恰最容易发生，因为**表面上无懈可击**：  
样本是对的（符合对照机制）、对象是存在的（符合前提机制），但结论仍错。

本轮两个实例，其中**第一个是我犯的**：

- **我的**：实测确认 `/settings` 对无效 Key 返 404、对无 Key 返 401，  
  就推断「用它验证 Key 有效性」。但该结论的**作用域只是这个端点**，  
  不能外推为「401 与 404 是两种 Key 状态」。实际上 401 只有单一含义（Key 无效），  
  NSFW 权限不足是「有效 Key + 200 + total=0」—— **作用域被放大了**。
- **设计师的**：探测 `purity=001` 能确定 NSFW 权限，  
  但同一组信号**不能用来区分非 NSFW 场景**。作用域是「NSFW 空结果」，不是「所有空结果」。

**操作化判据**：写下结论时必须附一句

> 「该结论的适用边界是 \___\_，超出此范围需重新实测」

**若填不出适用边界，说明结论的作用域还没想清楚。**  
| 4b | **实测的前提是「被测对象存在且语义明确」** —— 签名存在 ≠ 能力可用 | 架构师补充 | 测了从未运行过的代码 |

**第 4 条与 4b 的关系**：第 4 条适用于「有竞争假设」的场景（需要一个能让假设失败的对照）；4b 适用于「无竞争假设」的场景 —— 此时不是对照不足，而是被测能力从未真正执行过。

4b 的反例（本轮真实发生）：GIF→MP4 的编译核验曾被当作「已验证」。但 `ImageIO` 与 `AVAssetWriter` 从未被调用过 —— **只有签名存在，能力从未运行**。这类错误不会被任何对照发现，因为根本没有执行。

### 第4 条为何最重要

前3 条都防不住「数据全对、测试全过、结论错」这一类。  
401 语义误判是典型案例：测了 NSFW 请求、测了 SFW 请求、看到 401/200/401/200，  
**数据全对**，但把观察到的相关性当成了语义设计。

若当时做了「同一 Key 跨 purity 对比」这个对照，会立刻发现 401 与 purity 无关。

**操作化判据**：写实测结论前，自问——

> 「如果我的假设是错的，我的样本里有什么数据会与假设矛盾？」  
> 若答不上来，说明样本不足以区分假设，需补对照组。

### 附：跨文档引用完整性检查（PM 建议，已落地）

单文档内引用不断链，**不保证跨文档不断链**。本项目四份文档互为权威  
（PRD / ARCHITECTURE / DESIGN / ADR），已出现跨文档引用失效两次  
（我引用不存在的 Trap 13、Trap 16）。

**已加入 `scripts/verify-docs.py`**：校验 PRD/ARCHITECTURE/DESIGN 中  
所有 `ADR-XXX` 与 `Trap N` 引用是否在 `decisions/` 下真实存在。  
当前状态：9 份 ADR、16 个 Trap，跨文档断链 **0 处**。

## 附录 A-11：两类空结果在响应层不可区分（设计侧发现，team-lead 初裁定，产品侧实测升级为探测方案）

实测证明「NSFW 权限不足」与「筛选条件过窄」产生**完全相同的响应**：

| 场景                                            | HTTP | 响应                  |
| --------------------------------------------- | ---- | ------------------- |
| `purity=001`（NSFW）+ 无 Key（**权限不足**）           | 200  | `total=0`，`data=[]` |
| `purity=100&atleast=30000x30000`（**条件不可能满足**） | 200  | `total=0`，`data=[]` |

**两者在响应层面零差异。** 但用户需要的动作完全不同：

- 权限不足 → 去 wallhaven 账号开启 NSFW 授权
- 条件过窄 → 放宽筛选条件

### 裁定演进：从「推测式提示」升级为「探测请求确定判定」

**v1 初版裁定（设计侧方案，team-lead 采纳）**：三步判定 + 追加推测句。

| 步骤 | 条件                            | 呈现                |
| -- | ----------------------------- | ----------------- |
| 1  | `total > 0`                   | 正常结果              |
| 2  | `total == 0`，请求**不含** NSFW 条件 | **常规空态**（中性，无警示色） |
| 3  | `total == 0`，请求**含** NSFW 条件  | 常规空态 + 追加推测句      |

三条硬约束（**继续有效，已并入下方最终方案**）：

1. 推测语气 —— 不能断言
2. 不带警示色 —— 保持空态中性
3. 不让用户反复重试 —— 它是信息补充不是错误提示

**产品侧后续实测发现：可以做到确定，不必推测。**

在核实此问题的过程中，实测找到了可区分信号 —— **发一次探测请求即可确定原因**：

| 探测请求                          | HTTP | total  | 判定               |
| ----------------------------- | ---- | ------ | ---------------- |
| `purity=001`（不带其他筛选） + 无效 Key | 401  | —      | Key 无效           |
| `purity=001` + 无 Key          | 200  | **0**  | **确定**：NSFW 权限不足 |
| `purity=001` + 有效且有权限的 Key    | 200  | **>0** | **确定**：筛选条件过窄    |

旁证：`purity=110`（sketchy，**不需要** NSFW 权限）返回 `total=624,327`，证明账号侧确实存在 NSFW 内容，「0 结果」源于权限而非内容缺失。

**最终裁定：探测请求确定判定**

判定流程：主请求返回 `total=0` **且请求含 NSFW 条件**时，自动发一次探测请求 `purity=001`（携带同一 Key）：

| 探测结果            | 判定         | 呈现                                                     |
| --------------- | ---------- | ------------------------------------------------------ |
| 200 + `total=0` | **确定**权限不足 | 常规空态 + 明确文案「此 API Key 无 NSFW 访问权限，请到 wallhaven 账号设置开启」 |
| 200 + `total>0` | **确定**筛选过窄 | **常规空态 + 放宽建议**，不显示任何权限文案                              |
| 401             | Key 已失效    | 鉴权失败分支                                                 |

**成本**：触发条件极窄（仅 NSFW 条件且结果为空），额外 1 次请求，占 45 次/分钟预算的 2.2%，可接受。

**为何升级**：初版方案的三条硬约束全部源于「响应层无此信息，只能推测」。但实测证明**多发一次请求就能把推测变成确定**。推测语气（「可能未授权」）迫使用户在两个原因间猜测，而这两个原因需要的后续动作完全相反（去开授权 vs 放宽筛选）—— 既然成本如此之低，就不应让用户承担猜测成本。

**三条硬约束在最终方案中的落地**：

1. ~~推测语气~~ → **不再需要推测**，直接给确定文案
2. **不带警示色** → 保留。权限不足仍归入**空态分支而非错误态**（用户的筛选操作本身没错，开启权限即可解决，无需重试）
3. **不让用户反复重试** → 保留。空态容器与其他空态完全一致，操作用 accent 而非 danger


**唯一允许推测的兜底分支**：探测请求本身失败（网络/5xx）时，退化为常规空态且**不显示权限文案** —— 宁可少提示，不可误报。推测方向是「不说权限问题」而非「说权限问题」。

**反面案例**：若把权限不足做成错误态 → 违反「空态必须完全中性」，  
且让用户在无需重试的情况下反复重试；若只做常规空态 → 权限不足的用户会反复调筛选条件，  
永远找不到原因。**故追加推测句是唯一正解。**

> 呼应验证纪律第 4 条：**NSFW 组与 SFW 组的对照，才让「200+total=0」这个真实语义浮出来。**  
> 若只测 NSFW 组合，架构师会看到 401 和 200 两种结果，可能得出「401 有两种含义」——  
> 正是他自己犯的那个错。对照组的价值不是「发现新事实」，而是「**推翻既有假设**」。

## 附录 A-12：NSFW 探测请求的三条前置条件（设计侧补充，修正 PM 转述遗漏）

设计侧复核 PM 的探测方案时发现**三处关键约束**，而 PM 的转述中**遗漏了条件 ②**：

### 条件 ①：探测请求不得携带其他筛选条件

实测（team-lead 复核）：

```
purity=001 单独                → 200, total=0
purity=001 + resolutions=9999x9999 → 200, total=0
purity=001 + atleast=30000x30000  → 200, total=0
```

若探测复用主请求参数只改 `purity`，会**复现主请求的 0**，彻底失去区分能力。  
**这个错极易犯** —— 「复用同一套参数只改一项」听起来最自然，恰恰因此失效。

[!]  我实测时发现一个额外事实：匿名状态下带不带筛选条件**都是 0**，  
因此该失效场景**只在已配置 Key 时显现**。验收时必须用**已配置但无 NSFW 权限**的 Key 测，  
用匿名状态测会得到「带筛选也返 0」的相同结论，从而误以为探测可以带筛选。

### 条件 ②：探测前必须先检查本地是否已配置 Key

实测：**未配置 Key 的用户请求 `purity=001` 也返回 200 + total=0**，  
与「已配置 Key 但无 NSFW 权限」完全相同。

若不区分，探测会误报「此 API Key 无 NSFW 访问权限，请到 wallhaven 账号设置开启」——  
**而用户根本没配 Key**，去账号设置找不到入口，等于把他指向一个无法完成的任务。

**约束**：探测前先查本地；未配置则走「未配置 Key」引导，**不发起探测**。

### 条件 ③：探测失败时降级为不显示权限文案

探测请求本身失败（网络/5xx）时，不得断言权限状态，退化为常规空态。  
**宁可少提示，不可误报** —— 这是唯一允许推测的兜底分支，且推测方向是「不说权限问题」。

### 附：转述校验结果必须带运行时点（流程规则，架构师提出）

本轮 emoji 争议的根因：PM 转述「CI 拦下 12 处 emoji」时**丢失了时间戳上下文**，  
接收方无法判断是当前状态还是历史状态。

> **规则：转述任何门禁/校验结果时，必须附「校验器运行时点」与「文件 mtime」，  
> 否则接收方无法判断状态归属。**

**归属判断需要证据链，不能靠转述。** 架构师未代改设计文档是正确的 ——  
代改会剥夺作者「我的默认写法有问题」这个关键信息。

## 附录 A-13：NSFW 权限判定最终裁定（探测式，team-lead 终裁）

产品侧建议从「推测式」升级为「探测式」，经team-lead 复核后**正式采纳探测式**。
推测式原文保留于附录 A-11 作为裁定演进记录。

### 终裁理由

推测式的根本问题是**把可以确定的事交给用户猜**。用户的两个可能原因需要的后续动作
**完全相反**（去开授权 vs 放宽筛选），而响应层无法区分。探测一次即可确定。

| 方案 | 结论 |
| --- | --- |
| 推测式（追加「可能未授权」句） | 已被取代，保留于 A-11 作演进记录 |
| **探测式（发一次 `purity=001`）** | **终裁采纳** |

### 三条前置条件（任一不满足则不发起探测）

| # | 条件 | 不满足时 |
| --- | --- | --- |
| 1 | **本地已配置且非空 Key** | 绝不探测，走「未配置 Key」引导 |
| 2 | 主请求 `total=0` 且 data 为空 | 不探测 |
| 3 | 主请求确实含 NSFW 条件 | 不探测 |

**条件 1 是最易遗漏的一条**：未配置 Key 时探测同样返回 `total=0`，
会被误判为「权限不足」，而用户根本没配 Key —— 等于把他指向一个无法完成的任务。

**探测请求必须是固定宽查询 `purity=001`，不带任何其他筛选条件。**
若复用主请求参数只改 purity，会复现主请求的 0，彻底失去区分能力。

[!]  **该失效场景仅在已配置 Key 时显现**：匿名状态下带不带筛选都返回 0。
验收必须用「已配置但无 NSFW 权限」的 Key 测，用匿名测会得到相同结论从而误判可带筛选。

### 会话内缓存

权限不会中途改变，探测结论缓存于会话，平均额外成本接近 0。

## 附录 A-14：校验工具的两条使用纪律

### 纪律 A：任何校验规则上线前，必须先用「已知会失败」的反例验证它真的会失败

**静默失效比假阳性更危险**：

| 失效方式 | 后果 | 能否被发现 |
| --- | --- | --- |
| **假阳性** | 噪声引发抱怨，抱怨推动修复 | **会** |
| **静默失效** | 「检查通过」与「检查没跑」表象完全相同 | **不会**，长期提供虚假安全感 |

本项目实例：架构师第一版用 `\h`（PCRE 语法），Python 不支持。
> 经实测：Python 3.13 的 `re` 对 `\h` **会抛 `bad escape` 异常**（非静默），
> 但在 grep 等不校验正则的上下文里 `\s`/`\|` 确实静默失效 ——
> **同一类错误在不同工具下表现不同，因此必须实测而非推断**。

已落地：`docs/check_punct_spacing.py` 的 `run_self_test()` 含负例 / 正例 / 位置三组用例。

### 纪律 B：一个总是误报的检查等于没有检查

架构师第一版标点检查产生 **2940 处假阳性**（`0% -> 22%`、`1.3s（并行化后）` 等）。
假阳性的危害不是「吵」，而是**让人直接关掉这条规则**。

修正：只匹配全角标点、跳过表格行与代码块、降为 WARN（排版提示非质量门禁）。

## 附录 A-15：前提机制的极端形态 —— 前提不存在且失败无声

### 5.9 前提失效的三种形态（危险度递增）

| 形态 | 描述 | 是否报错 | 实例 |
| --- | --- | --- | --- |
| 4b-1 | 对象存在但从未被调用 | 不报 | `ImageIO` / `AVAssetWriter` 签名存在，但 GIF→MP4 从未真正执行过 |
| 4b-2 | **前提语法不被支持** | 退出码非0，但**若被`2>/dev/null` 吞掉则无声** | 设计侧 pre-commit 用 `grep -qP`，**macOS BSD grep 不支持 `-P`**，实测退出码 2 |
| 4b-3 | **失败被显式忽略** | 无 | 同上，若写成 `if grep -qP ...; then FAIL; fi`，则恒为 false，**一条规则都没跑过** |

**4b-3 最危险**：它不是「规则有bug」，而是「规则根本不存在」，但表象与「检查通过」完全一致。

设计侧原话：**「如果没人查出来，我会一直以为它在正常工作。」**

### 这条是自动化流程特有的风险

人写错字会被人看见；**机器的语法错误往往被 `try/except` 或 `2>/dev/null` 吞掉**。
本项目三处同型：BSD grep 的 `\s` / `\|`、Python 的 `\h`（3.13 实测抛异常）、
BSD grep 的 `-P`（退出码 2被吞）。

### 强制要求：校验脚本必须自证可运行

**每个校验脚本启动时先执行一次「规则自检」** —— 把规则中所有正则 `compile()` 一遍，
若抛异常则明确报「规则语法错误」并**拒绝执行**，不得静默跳过。

> 判据：门禁输出「通过」时，必须能回答「刚才那条规则真的跑过吗？」

### 与另一条纪律的合并

这条本质是「静默失效比假阳性更危险」（附录 A-14纪律 A）的**自动化版本**——
假阳性会被抱怨并推动修复，静默失效则提供虚假安全感。

## 附录 A-16：用工具设计替代纪律约束（PM 提出，team-lead 采纳）

### 起因：我们两次违反了刚写下的纪律

GATE-USAGE 第 1 条纪律写着「门禁报错时必须核对当前文件实际状态，不可直接转述给作者」，
并举的正是 emoji 误报。**但架构师随后仍从门禁 FAIL 直接推断是 PM 写入，
PM 上一轮也断言是架构师写入**（漏考虑设计侧也在改同一文件）。

**两次都是：多方并行编辑时，从「谁最可能」归因，而非先核实。**

### 结论：纪律靠自觉，工具才可靠

纪律写在文档里依赖人遵守，而本轮已两次看到自己违反刚写下的纪律。
**工具行为比纪律更可靠** —— 这与我们把校验做成 CI 门禁而非文档建议的逻辑一致。

### 三条工具化改造（已采纳）

| 改造 | 效果 |
| --- | --- |
| 门禁 FAIL 报告附**实际行内容片段**（不只给行号） | 看到报告第一眼即可判断真伪，无需打开文件 |
| 归因需列出**所有可能来源** | 避免二分法遗漏（本次即漏考虑设计侧） |
| 门禁输出附**运行时点 + 文件 mtime** | 接收方能判断是当前状态还是历史状态 |

### 判据

> **能自动化的，不要写成纪律。** 纪律是最后手段，不是首选方案。

## 附录 A-17：门禁必须先证明自己能跑（启动自检，架构师实现）

### 核心原则

> **自己不能跑，就没资格检查别人。**

校验器在检查任何文档之前，**必须先证明自己是对的**。

### 本项目踩过的三次同类坑

| 位置 | 用了什么 | 后果 |
| --- | --- | --- |
| security-gate 初版 | BSD grep 的 `\s` | 4 条规则有 3 条静默失效，**返回 PASS 却抓不到违规** |
| cjk-spacing 初版 | Python 的 `\h`（PCRE 语法） | 规则静默失效 |
| 设计侧 pre-commit | BSD grep 的 `-P` | **规则从未运行**，且零声音 |

**三次都是同一类：能力不存在 + 失败被吞掉 + 无人发现。**

### 两种失效必须分别捕获

| 失效类型 | 特征 | 捕获方式 | 实测 |
| --- | --- | --- | --- |
| 语法不受支持 | 正则编译抛异常 | 启动时 `compile()` 全部规则 | `\h` → `bad escape` CAUGHT |
| **语法合法但永不命中** | 编译通过、逻辑正确，但匹配不到任何东西 | 每个规则配「**必须命中**」样本 | `ZZZ-NEVER-MATCH` → CAUGHT |

**第二类靠读代码看不出来** —— 「检查通过」与「检查没跑」的表象完全相同。

### 强制要求（已实现于 `verify-docs.py`）

启动时在任何检查之前执行 `self_test()`：
1. 所有注册正则 `compile()` 一遍，抛异常即退出码 2 **阻断 CI**（非警告）
2. 每条规则配「必须命中」+「必须不命中」双样本，两者都验

**判据**：门禁输出「通过」时，必须能回答「**刚才那条规则真的跑过吗？**」

### 一条元教训

架构师在自检源码里写了**字面 emoji** 作为测试样本 ——「我的 emoji 检查器源码本身含 emoji」。
若非他人审阅，很可能留存。

> **自己也需要被检查。** 校验工具的代码同样在门禁的检查范围内。

## 附录 A-18：核实本身需要工具保障（设计师提出，最重要的机制性发现）

### 现象：验证工具的错误会被双方共同继承

设计师报告「架构师没实现 self_test」，架构师为验证该报告，
**第一条命令用了和她一样的错误写法**（`grep -n "a\|b"`），
得出了一样的零命中结果。

若当时她采信文档结论、他没做复现，**这个误判就会固化成「他真的没实现」**。

> 他不是在质疑她，是在**复现她的方法** —— 而方法本身有缺陷。

### 本项目四次工具静默失效

| 位置 | 用了什么 | 后果 |
| --- | --- | --- |
| security-gate 初版 | `\s` | 3 条规则静默失效 |
| cjk-spacing 初版 | `\h`（PCRE） | 规则静默失效 |
| 设计侧 grep 检索 | `-P` | 规则从未运行 |
| **设计侧 → 我 → 架构师（同一错误传递）** | **`\|`** | **误判自检未落地，并要求已实现者返工** |

四次中两次因同一个 `\|` 错误在**三个人之间传递**。

### 强制要求：否定性判断必须交叉验证

**任何「某处没有 X」的判断，必须用两种不同工具验证，并在消息里附上验证命令。**

理由：单一工具的失效会被双方共同继承，因为接收方复现时用的是**同一套基础设施**。

**可接受的交叉验证组合**：
| 被检对象类型 | 工具 A | 工具 B |
| --- | --- | --- |
| 代码符号是否存在 | `grep -E`（或 Python） | **实际运行**（输出 / 退出码） |
| git 历史是否有某提交 | `git log -S` | `git show` 逐条看 |
| 文档声称 vs 代码实现 | 文本检索 | **运行该程序** |

**判据**：接收方拿到消息后，应能**不额外跑一遍**就复核我的结论 —— 所以命令必须附上。

### 附：紧急口吻会放大权威感

设计师反思自己用「先说一件必须立刻告诉你的事」开头，
而那句话报告的是**没验证工具支撑的结论**。

> **紧急口吻会让接收方降低验证意愿。** 越是紧急的报告，越必须附验证命令。

这条与本项目反复出现的「转述二手实测结论」同源。

### 第三条：盲区显式声明（`declare_blind_spot`）

我们已有三个检查器在跑，但**它们的覆盖边界从未被显式写下**——
这意味着没人能说出「哪些问题我们抓不到」。

实测证据：`.py` 文件里的 emoji 延迟两轮才被发现，因为
`check_punct_spacing` 不管 emoji、`verify.py` 只扫 `.md/.css/.json`。
**架构师遇到的「emoji 检查器源码含 emoji」在我这里重演了。**

**要求**：每个检查器显式声明它**不检查什么**。

```python
declare_blind_spot("不检查 .py 文件")
declare_blind_spot("不检查语义级矛盾（需 LLM）")
```

> **声明了才能被讨论，没声明就默认它被检查了。**
> 这是从「默认有防护」转向「显式声明防护边界」。

## 附录 A-19：新增检查项的准入判据（设计师提出）

> **一个检查项能否成立，取决于它是否有「可机械判定的失败信号」。**

这把「加不加检查项」从主观争论变成「**你有没有失败信号**」的事实问题。

| 检查项 | 失败信号 | 成立 |
| --- | --- | --- |
| 正则可编译性 | `compile()` 抛异常 | 是 |
| 负向用例 | 用例未命中 | 是 |
| 外部依赖能力 | 退出码 / stderr | 是 |
| 语义正确性 | **无** | 否 |

**未来有人提议加第 N 类检查时，第一个问题是「它的失败信号是什么」—— 答不出就不加。**

### 实例：语义断言为何最终仍不成立
架构师否决 `require_semantic`（验证「代码语义是否正确」），
理由是语义正确性本身无法机械判定，加了等于退化成第二类声明而失去自检价值。

设计侧改用**可判定的替代物**：`must_exit` / `expect_stdout`——
断言「某命令执行后退出码是 X / 输出含 Y」，而非「语义正确」。
实测三组均有效，其中第一组正好捕获了 `grep \|` 那个真实错误。

### 配套：范围声明也必须显式
报告结论时必须带范围，因为「零 emoji」与「某些范围内零 emoji」是**不同强度的断言**。

正确表述示例：
> `docs/` 与 `scripts/` 下全部 `.md/.json/.css/.sh` 零 emoji；
> `verify.py` 的 7 处是正则字符类定义（扫描器必须能表达它要检测的字符集），
> 属**合法例外且已显式声明**。

### 附：更正的可信度来自证据而非措辞

架构师报「已完全恢复到 228 行」被证伪（实际 247）后，
他的更正方式是给出 `git show 94173bf | wc -l` = 247、

**而不是只说「我错了」**。设计侧独立核实全部准确。

> 承认错误要给证据链。「抱歉之前报错了」不提供任何可复核信息。

## 附录 A-20：NSFW 能力判据的正面样本补录（team-lead 实测，2026-10-08）

### 实测记录

请求头统一为 `X-API-Key: <有效 Key>` + `Accept: application/json`。

| # | 请求 | HTTP | 关键响应字段 |
| - | ---- | ---- | ----------- |
| 1 | `GET /settings`（带有效 Key） | 200 | `data.purity = ["sfw","sketchy"]`；`data.per_page = "24"`；`data.ai_art_filter = 1` |
| 2 | `GET /search?purity=001&page=1`（同一有效 Key） | 200 | `meta.total = 339163` |
| 3 | `GET /search?purity=110&page=1`（同一有效 Key） | 200 | `meta.total = 952572` |
| 4 | `GET /search?purity=001&page=1`（**对照组：不带 Key**） | 200 | `meta.total = 0` |

**算术自洽校验**：第 2 条（NSFW 339163）+ 第 3 条（SFW+Sketchy 952572）= 1,291,735，与 PRD 竞品分析引用的「站内约 129 万张壁纸」吻合。两者测量条件一致（均带同一有效 Key），互为佐证。

### 结论一：NSFW 三层门禁 L1 能力层的判据已双向闭合

第 2 条与第 4 条构成**同一参数、只差有没有 Key** 的对照：

- 带有效 Key：`purity=001` → `total = 339163`
- 不带 Key：同参数 → `total = 0`

因此：

1. 既有结论「NSFW 权限不足 = **有效 Key + 200 + `total=0`**」**继续成立**（见 F4 的 L1 能力层、附录 A-9、A-11、A-12、A-13）。
2. 本次补入此前缺失的**正面样本**：**有效 Key + 账号已开启 NSFW → `total` 为正（实测 339163）**。

补入的意义是把判据从「单向可证伪」升级为**双向闭合**：此前只能由 `total=0` 证成「权限不足」，无法证成「权限充足」——探测式判定的**肯定分支一直是推断值**。现在两态各有实测落点，固定宽探测（附录 A-11 / A-13 的 `purity=001` 不带其他筛选）的**两个分支都已被实测覆盖**。

> 既有表格中「`purity=001` + 有效且有权限的 Key → `total>0`」一格（F4、附录 A-11），此前为**推断值**，现由本次实测坐实。该格数值是否改写为 339163，见「待裁定项」。

### 结论二：`/settings` 的 `data.purity` 与真实搜索能力矛盾

第 1 条称该账号 `purity = ["sfw","sketchy"]`（**不含 nsfw**），第 2 条同一把 Key 却搜出 `purity=001` 共 **339163** 条 —— **两者直接矛盾**。

**已按指令全文检索 PRD，检索目标为「依据 `/settings` 判断 NSFW 可用性」与「读 settings 的 purity 决定可用档位」两类表述。检索结果：已检查，PRD 无此类表述。** 现有 NSFW 可用性判定**全部**以 `purity=001` 固定宽探测的 `total` 为准（F4 的 L1 能力层、附录 A「NSFW 权限」行、附录 A-11、A-12、A-13）。`/settings` 在 PRD 中只出现于两类上下文，且**均为否定性用法**：①「禁止用 `/settings` 验证 Key 有效性」（F5、附录 A、附录 A-8）；②「若未来引入 `/settings` 读取账号偏好，404 不等于 Key 无效」（F5）。**故无需改写任何既有表述。**

据此新增一条**防漂移规则**（纯新增，未改动任何既有结论）：

> **NSFW 能力（含「哪些纯度档位可用」）一律以 `purity=001` 固定宽探测的 `total` 为准。`/settings` 的 `data.purity` 不得作为任何能力判据** —— 它已被证实与真实搜索能力矛盾，属于「端点返回了数据，但数据说的是假话」，与 ADR-006 记录的 `/settings` 第一个坑（404 ≠ Key 无效）同源。

### 结论三：`per_page` 默认值一致，PRD 无需改数值

`/settings` 的 `data.per_page = "24"` 与 `/search` 实际每页条数一致。PRD 附录 A「每页条数 / 固定 24 / 分页步长 24」与本实测**一致，无冲突；未改动任何数值**。

### 待裁定项（按指令不自改数值与既有表述，提请 team-lead 决定）

| # | 事项 | 说明 |
| - | ---- | ---- |
| 1 | `purity=110` 的两个数字不一致 | PRD 附录 A-11 旁证行与 F4 记为 **624327**，本次实测为 **952572**。疑为测量条件不同或库容增长，但 PRD 该行**未标注测量条件**，存在被读成「同一条件下两个数字打架」的风险 |
| 2 | 附录 A「账号设置同步」行 | 该行为「`/settings` 端点返回用户默认筛选 → 可一键导入为本地默认筛选」。它**不属于**「判断 NSFW 可用性 / 决定可用档位」，按指令未改写；但本次实测证明它读取的 `data.purity` 与实际能力矛盾，**导入后会把一个错误的默认值写进用户端**。是否保留该能力、或导入时排除 `purity` 字段，请裁定 |
| 3 | `ai_art_filter = 1` | `/settings` 返回该值，但**它是否真实作用于 API 搜索结果未经实测**，不得假定。若未来实现「账号默认筛选同步」，此字段须先实测再决定 |

**修正后的核心原则（本轮沉淀）**

1. **凡是以状态码判断成功的，必须同时确认响应体内容。** 仅看状态码是「看起来测过了、实际只测了一半」，此类错误会固化为长期错误断言。
2. **凡是服务端不报错的参数，必须全部在客户端预校验。** 本项目已确认 ratios、resolutions 两个参数服务端均不报错。
3. **用错误的参数形式得到的「无效结论」比不测更危险**，因为它会被写进文档并影响下游决策。实例：`?type:video`（独立参数）被忽略易被误读为「type: 无效」，实际 `type:` 是 `q=` 内前缀语法且真实生效。**参数形式未确认前，不得下「该参数无效」的结论。**
4. **静默错误的优先级高于崩溃。** 服务端返回错误数据但界面正常，比界面报错危害大 —— 前者摧毁用户对功能的信任且难以察觉。
