## 0. 旧版 UI 问题诊断（重写依据）

设计方向不是凭空定的。先对 2020 雏形做代码级审计，问题清单即优先级：

| # | 问题 | 代码证据 | 严重度 |
|---|------|---------|--------|

## 1. Visual Theme & Atmosphere

### 视觉主题关键词
**克制 · 中性 · 沉浸 · 精准 · 呼吸感**

### 氛围描述
UI 退到画面最边缘，把整个屏幕让给壁纸。用户看到的第一眼应该是照片本身，而不是导航条、分隔线和筛选控件。控件只在需要时浮现（hover / 聚焦 / 滚动），操作完成后退回无形。这种"**chrome 隐形、内容主导**"的气质，是 Apple Photos「图库」视图与 Raycast「暗色舞台」共同的气质。

### 对标品牌（3 家，各取所长）

| 品牌 | 借鉴什么 | 明确不借鉴什么 |
|------|---------|--------------|
| **Apple Photos**（图库视图） | 内容优先的层级、hover 才出现的元信息、多选/拖拽的直觉、图片作为唯一主角 | — |
| **Raycast** | 非纯黑带蓝冷调底色（避免死黑）、克制的强调色、键盘优先、多层阴影带内高光的"物理感"、正字距正文 | 它的珊瑚红品牌色（红误读为错误态），密集列表布局（我们要留白） |
| **Craft** | 三栏工作区布局（导航/内容/属性）的比例分配、大量留白、文档级排版秩序 | 它的圆角与柔和度过高（我们要更"工具化"） |

### Liquid Glass 策略 —— 你的倾向我完全同意，且有 HIG 原文背书

**结论：玻璃只用在 chrome 层面，内容层保持纯净 —— 且这不是"审美偏好"，是 Apple 的明文规定。**

Apple HIG 原文：

> "**Do not use Liquid Glass in the content layer.** Liquid Glass works best where it can clearly separate interactive elements from content; incorporating it into the content layer introduces unnecessary complexity and confusing visual hierarchy."

Apple 定义的严格分层：
- **内容层**（文档、列表、照片、媒体）-> 用**标准材质**或不透明表面
- **功能层**（控件、导航、标签栏、侧边栏、瞬态浮层）-> 用 **Liquid Glass**

**为什么壁纸 App 用大量毛玻璃会自伤**（我加的三条产品特异性论证）：

1. **动态壁纸 = 采样源在动**。壁纸 App 的底层背景不是静态图，而是**持续播放的视频/动态壁纸**。玻璃的实时折射（lensing）会随每一帧重新采样，chrome 的边缘高光、透光色相会随视频内容持续漂移。结果是：UI 看起来"脏"、不稳定，且用户无法建立"这个蓝色按钮一直是蓝的"认知。

2. **玻璃材质降低图片判读精度**。用户挑壁纸的核心动作是**判断构图与画质**。玻璃卡片边缘的折射形变会在图片周围产生类似色散的光晕，直接干扰"这张图边缘细节是否干净"的判断。壁纸详情大图上叠加玻璃更是灾难。

3. **玻璃会偷走图片的主色**。琥珀色强调色叠在暖色壁纸上会被"同化"，用户看到的按钮颜色 = 壁纸颜色 + 琥珀色，变量失控。UI 强调色必须**跨壁纸保持恒定可辨识**。

**IHaven 的落地映射（玻璃白名单 / 黑名单）**：

| [OK] 允许（chrome 层） | 具体位置 | SwiftUI 实现 |
|---------------------|---------|--------------|
| G1 主窗口工具栏 | 搜索框、视图切换、筛选按钮 | `NavigationSplitView` + `.toolbar`（自动获得） |
| G2 侧边栏 | 发现/收藏/已设置壁纸/设置 | `NavigationSplitView` sidebar |
| G3 菜单栏面板 | 整个 400×500 面板（它浮在壁纸**之上**，本身是 chrome） | `glassEffect(.regular)` |
| G4 操作确认 HUD | "已设为壁纸" toast | `glassEffect(.regular.tint(accent))` |
| G5 Sheet / Popover / Menu | 筛选面板、密钥设置、多屏分配 | `.presentationBackground` / `glassEffect` |

| [NG] 禁止（内容层） | 原因 |
|-----------------|------|
| F1 瀑布流图片卡片 | 内容层；玻璃折射干扰判读 |
| F2 壁纸详情大图 | 内容层；图片是主角 |
| F3 筛选面板内输入框与表单控件 | 玻璃不可用于表单，对比度不可控 |
| F4 动态壁纸编辑器画布 | 裁剪需要精确边缘判断，玻璃引入畸变 |
| F5 窗口背景 / 瀑布流沟槽底 | 系统明令禁止 |
| F6 玻璃之上再叠玻璃 | `GlassEffectContainer` 共享采样，嵌套导致渲染错误 |

**技术约束（写给架构师）**：
- 多个玻璃元素必须在**同一个** `GlassEffectContainer` 内，`spacing` 与实际视觉间距一致
- 禁止手写 `CGAffineTransform` / layer 特效模拟玻璃
- **禁止自行指定 blur radius / saturation** —— Apple 未公布可移植数值，必须用系统实时渲染
- 优先 `.regular`；`.clear` 仅可用于覆盖媒体内容的小浮动控件，且必须配 dim 层
- `reduceTransparency` 开启时降级为不透明 `--surface-raised`，**不要与之对抗**（系统已自动降级 vibrancy）
- 性能预算：每 pane 最多 6 个 live-blurred surface

## 2. Color Palette & Roles

### 2.1 深色为主 —— 你的倾向我同意，但结论更强：**深色为默认，浅色作为"跟随系统"的完整支持，而非可选项**

**理由**：

1. **物理事实**：macOS 的壁纸设置界面本身就是深色优先 —— 壁纸预览需要环境压暗才能准确呈现图片。用户在系统壁纸 UI 里已经习惯了这个环境。
2. **对比度**：深色底 + 中性灰 chrome = 任何壁纸（无论多亮）都能保证 chrome 文字 ≥ 4.5:1。浅色底遇到白色/雪景壁纸会直接崩掉对比度。
3. **内容主导**：深色环境的视觉噪声最低，让高饱和壁纸成为画面唯一的亮点。浅色底会跟浅色壁纸"撞车"。

**但浅色必须做对**（不是敷衍的反色）：

| 处理 | 做法 |
|------|------|
| 语义色整体重算 | 琥珀在浅色下用 `#B06A10`（对比度 5.2:1），深色用 `#E8A33D` |
| 阴影需要更实 | 浅色下阴影 opacity 从 0.36 提到 0.16 才可见 |
| 玻璃在浅色下更弱 | 浅色 + 玻璃 = 边界不清 -> 浅色主题下 chrome 用不透明 `--surface-sunken`，玻璃仅保留在菜单栏面板 |
| 发丝线 | 0.5px 线在浅色下几乎不可见 -> 提高到 1px |

**实现方式**：`NSColor(name:dynamicProvider:)` 或 Asset Catalog 的 Any/Dark 变体。**禁止**在代码里写 `if colorScheme == .dark` 分支。

### 2.2 中性灰阶 —— 带蓝冷调偏移，不是死灰

关键决策：中性色不是 `#808080` 式纯灰，而是**带冷蓝偏移**的灰阶（Raycast 的做法，也是"暗色不发脏"的关键）。

```
--p-void:     #0B0D10   <- 最深
--p-surface-sunken: #101317
--p-surface-base:   #16191E   <- 内容区基准
--p-surface-raised: #1D2128
--p-surface-overlay:#252A32
```

四层背景靠**亮度递进**（ΔL 递增）表达层级，**不靠阴影** —— 这是 macOS 暗色的核心手法。

前景同样四层，且**每层都实测过对比度**：

| Token | 值 | 对 surfaceBase 对比度 | 用途 |
|-------|-----|---------------------|------|
| `--p-fg-primary` | `#F2F5F8` | 14.2:1 | 标题 |
| `--p-fg-secondary` | `#B6BEC9` | 8.6:1 | 正文默认 |
| `--p-fg-tertiary` | `#7E8794` | **4.7:1** [OK] | 辅助说明、时间戳 |
| `--p-fg-quaternary` | `#5A626D` | ~2.8:1 | [!] **仅装饰**，不承载任何语义 |

### 2.3 强调色：Amber `#E8A33D`

选型论证（四个候选的淘汰过程）：

| 候选 | 淘汰/采纳 | 理由 |
|------|----------|------|
| **系统蓝 `#0A84FF`** | [NG] | macOS 已占用为全局 accent，用户看到蓝色会归因为"系统控件"而非本应用。缺乏品牌辨识度 |
| **红 `#FF453A`** | [NG] | 语义冲突 —— 用户看到红色第一反应是"错误/删除"，而"设为壁纸"是正面操作 |
| **绿 `#30D158`** | [NG] | 语义冲突 —— 绿色读作"成功/在线"，且在绿色壁纸上完全不可辨 |
| **琥珀 `#E8A33D`** | [OK] | 见下 |

**琥珀的四条采纳理由**：
1. **语义空白** —— 不与任何状态色冲突，可以安全承担"选中/激活"语义
2. **冷暖互补** —— 壁纸内容以冷色（蓝/青/灰）为主，暖琥珀在冷调壁纸上自然凸显；这在冷色系 UI 里是经典的"点缀暖色"策略
3. **不落禁区** —— 琥珀是暖色系，与紫粉渐变（`#7C3AED`->`#EC4899`）无任何交集，且**纯色使用**
4. **跨壁纸恒定** —— 在雪景（日光 100%）、夜景（日光 5%）、全彩风景三种极端壁纸上，琥珀的可辨识度都稳定

**硬性约束**：
- **每屏可见使用 ≤ 2 处**（选中态 + 主 CTA 图标，仅此）
- **纯色使用，禁止参与任何渐变**
- 唯一允许的"渐变"是 `--accent-scrim`：同色相 amber 从 0% -> 22% 透明度，用于主按钮 hover 态。这不是视觉渐变，是状态反馈，且上限 0.22 远低于 P0 禁区阈值

### 2.4 语义色（低饱和，向灰阶靠拢）

```
--success: #4FA85C    --warn: #D9A441    --danger: #D8574B    --info: #7FB8E8
```

语义色**只用于状态表达**，绝不做装饰。每屏语义色面积 ≤ 5%。

### 2.5 每屏强调色配额表（可验收）

| 界面 | 强调色用途 | 数量 |
|------|----------|------|
| 瀑布流 | 选中卡片的 2px 描边 | ≤ 1（通常 0 或 1） |
| 壁纸详情 | 主 CTA「设为壁纸」的图标 | 1 |
| 筛选面板 | 已应用筛选的 chip 底色 | ≤ 2（正常 0-1） |
| 菜单栏面板 | 搜索框聚焦环 | 1 |

## 3. Icon System

### 3.1 结论：SF Symbols 足够，无需第二套图标库

**覆盖率评估**（对照本项目全部 23 个功能点）：

| 功能 | SF Symbols | 状态 |

| 上一张/下一张 | `chevron.left` / `chevron.right` | [OK] |
| 设为壁纸 | `checkmark.circle` / `desktopcomputer` | [OK] |
| 收藏 | `star` / `star.fill` | [OK] |
| 搜索 | `magnifyingglass` | [OK] |
| 筛选 | `line.3.horizontal.decrease` | [OK] |
| 分类发现 | `square.grid.2x2` / `rectangle.stack` | [OK] |
| 动态壁纸 | `play.circle` / `play.fill` / `pause.fill` | [OK] |
| 播放速度 | `speedometer` | [OK] |
| 编辑器 / 裁剪 | `crop` / `slider.horizontal.3` | [OK] |
| 多显示器 | `display` / `display.2` | [OK] |
| 下载 | `arrow.down.circle` | [OK] |
| 详情信息 | `info.circle` | [OK] |
| 设置 / 密钥 | `gearshape` / `key` | [OK] |
| 清除/关闭 | `xmark` / `xmark.circle.fill` | [OK] |
| 纯度标记 | `checkmark.shield` | [OK] |
| 标签 | `tag` | [OK] |
| 收藏夹 | `folder` | [OK] |
| 警告/错误 | `exclamationmark.triangle` | [OK] |
| 时间/自动切换 | `clock` / `timer` | [OK] |

**缺口：2 处**，处理原则 —— **宁可不画，也不引入第二套图标库**：

| 缺口 | 处理 |
|------|------|
| IHaven App 图标（既有 `AppImage` 位图） | 保留为品牌资产，非功能图标，不算图标系统缺口 |
| 屏幕排布的"全部屏拼接"示意 | 用 `display.2` 表达多屏语义 + 文字标签「所有显示器」，不自定义图形 |

**为什么坚决不补第三套图标库**：混用图标库是 P0 红线（flat/skeuomorphic 混用），两套风格打架比一个缺口更伤。SF Symbols 已覆盖 21/23，缺口用文字标签补是 macOS 标准做法。

**技术约束**：
- 禁止把 SF Symbols 导出为 PNG 塞进 Asset Catalog（旧版的 `StarBtn`/`TagBtn` 就是这样，必须清退）
- 禁止覆写 `symbolWeight` 做自定义描边
- 随系统外观自动适配，不需要也不允许手动设 `foregroundColor` 到固定色（除非在图片上需要白/黑自适应遮罩）

### 3.2 尺寸规范（全项目统一，不可协商）

| 尺寸 | 用途 | 场景 |
|------|------|------|
| **16px** | 行内 | 菜单项、chip、列表元信息、快捷键芯片 |
| **20px** | 按钮内 | 工具栏按钮、次级按钮 |
| **24px** | 独立图标 | 空态、详情页大图标、侧边栏 section 图标 |

配套 SwiftUI 实现：
```swift
// 16px -> .caption / Image(systemName:).controlSize(.small)
// 20px -> .body
// 24px -> .title3
Image(systemName: "line.3.horizontal.decrease")
    .imageScale(.medium)   // 20px
    .symbolRenderingMode(.hierarchical)  // 跟随系统前景色
```

**禁止** `Image(nsImage:)` 加载位图作为功能图标（旧版 `MainHeader.swift:41,60` 的问题）。

### 3.3 Emoji 禁令（P0）

**任何位置**禁止 emoji 作为功能图标 —— 包括菜单栏图标、空态插图、按钮文案、筛选 chip。旧版 UI 已存在这个问题（截图中侧边栏的 tab 图标是位图）。

替换方案：
- 空态图标 -> SF Symbols 24px（`photo.on.rectangle.angled`）
- 菜单栏应用图标 -> 品牌资产或 SF Symbol（`mountain.2.fill` 语义贴切：山 = 风景）
- 成功提示 -> `checkmark.circle.fill` + 文字，不写 "[OK]"

## 4. 关键交互设计（本节是成败关键）

### 4.1 瀑布流布局 —— 修掉旧版的"伪瀑布流"

**旧版问题**：`ImageLine.swift` 只有 `left`/`right` 两字段 = 固定 2 列。

**新版方案：真自适应瀑布流**

| 参数 | 值 | 依据 |
|------|-----|------|
| 列宽目标区间 | 240 – 340px | 低于 240px 壁纸细节看不清；高于 340px 一屏只能看 3 列，失去"发现感" |
| 列数计算 | `floor((容器宽 + gap) / (colMax + gap))`，然后按实际列数均分 | 保证列宽始终落在区间内 |
| 沟槽 | 8px（`--masonry-gap`） | 小沟槽让图片成为画面主角 |
| 圆角 | 10px（`--radius-lg`） | 上限 12px，禁止 ≥24px |
| **宽高比** | **严格按图片真实 `dimensionX/dimensionY`** | [!] 修掉旧版的强制 3:2 —— 壁纸被裁是致命伤 |

**列数参考**：

| 窗口宽度 | 列数 |
|---------|------|
| 900px | 3 |
| 1200px | 4 |
| 1600px | 5 |
| 2000px | 6 |

**懒加载与占位**：

| 状态 | 表现 | 实现 |
|------|------|------|
| 未进入视口 | 不发起请求 | 视口外 600px 预取缓冲 |
| 加载中 | **骨架块**，高度 = 真实宽高比 × 列宽，底色 `--card-skeleton` | 先占位再加载，**CLS = 0** |
| 骨架微光 | 一道 12% 透明度白光横扫，1.6s 循环 | [!] `prefers-reduced-motion` 下改为静态 |
| 加载完成 | 淡入 150ms | `--motion-fast` |
| 加载失败 | 卡片内居中 `photo.badge.exclamationmark` 24px `--muted` + 文字「加载失败」 | 点按可重试，**失败率 > 40% 时自动重试一次**。[!] 单张图片加载失败是**局部**问题（可能是这张图 404），[!] **不要用警示色** —— 一张图挂掉不代表筛选有问题，用警示色会让用户以为整个操作失败了 |
| 已缓存 | 瞬时显示 | 内存 LRU 缓存 300 张 |

**关键工程约束**：占位高度必须用 `aspectRatio = dimensionY / dimensionX` 预先算出，**禁止**先给固定高度再加载完成时跳变。

### 4.2 Hover 信息浮层（旧版最难用的部分）

macOS 用 hover 而非 tap —— 这一点旧版做对了方向，但做得粗糙（黑渐变 + `FFFBF0` 米白文字压在图上）。

**新版设计：底部渐起 + 安全区隔离**

```
┌─────────────────────────┐
│                         │  <- 图片本体，零遮挡
│                         │
│ 32×32 收藏星标（右上）    │  <- 常驻可见
├─────────────────────────┤  <- 从 40% 高度开始渐变
│ 3840 × 2160      16 PNG │  <- 12px mono，左下
│ Nature · 4.2k 收藏       │  <- 12px，次要文字
└─────────────────────────┘
```

| 元素 | 规格 | 说明 |
|------|------|------|
| 遮罩 | `--scrim-image`：40% 处透明 -> 78% 处 55% 黑 -> 100% 处 78% 黑 | 从底部渐起，**不遮图片主体** |
| 分辨率 | `--font-mono` 12px，`--text-xs` | 分辨率是数值，用等宽对齐更专业 |
| 收藏数 | `--text-xs` + `star.fill` 16px 琥珀 | [!] **仅在已收藏时用琥珀**，未收藏用 `--muted`，避免"每张图都有琥珀 = 强调色失效" |
| 格式徽标 | PNG/8K 等，`--radius-xs` 徽标，`--text-2xs` | 用 `--bg` 半透明底，不用彩色底（旧版的橙底 `DB7C0F` 太跳） |
| 收藏按钮 | 右上 32×32（≥ `--hit-target-min`），`star` / `star.fill` | hover 态才浮现 |
| 出现延迟 | **90ms** | [!] 关键防抖 —— 鼠标扫过瀑布流时逐张闪现是灾难 |
| 消失延迟 | 40ms | 快于出现，扫过时不粘滞 |
| 动画 | `--motion-fast` 150ms ease-out | [!] 旧版用 `easeIn` 是错的 |

**多选与批量操作**（旧版完全没有）：
- `Shift` + 点击 = 区间多选
- `⌘` + 点击 = 加选/减选
- 选中态：2px 琥珀内描边 + 4px 内缩（`--card-ring-selected`）
- 选中 ≥ 1 后，工具栏浮出操作条：「设为壁纸（N）」「分配到显示器…」「下载（N）」
- `Esc` 清除选择

### 4.3 筛选面板 —— 全面废弃 Slider

**旧版反模式的根因**：`Slider` 表达**连续量**，而分辨率（24 个枚举值）、比例（12 个枚举值）是**离散集合**。用 Slider 选择离散枚举，用户既看不到有哪些选项，也不知道自己在第几个 —— 这是把选择成本转移给了用户。

**新版核心原则：所有筛选维度是「可视的、可枚举的、可一次看全的」。**

#### 筛选面板形态

**工具栏下 popover（320px 宽）**，而非侧栏常驻。理由：筛选是临时任务，展开时需要看到瀑布流结果以验证效果。

```
┌────────────────────────────────┐
│ [随机] 分类                          │  <- 分段控件（Segmented）
│ [全部] [风景] [人物] [动漫]      │
├────────────────────────────────┤
│ 比例 Aspect Ratio               │
│ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ┌──┐     │  <- 可视比例图形，非文字列表
│ │▢ │ │▢ │ │ □│ │▢ │ │▢▢│     │     竖/方/横/16:10/21:9
│ │9:│ │4:│ │1:│ │16│ │21│     │
│ │16│ │3 │ │1 │ │:9│ │:9│     │
│ └──┘ └──┘ └──┘ └──┘ └──┘     │
├────────────────────────────────┤
│ 分辨率 Resolution               │
│ [不限] [≥1080p] [≥1440p]       │  <- 只保留有意义的档位
│ [≥4K]     [超宽 ≥21:9]          │     不要 24 个精确值
├────────────────────────────────┤
│ 色调 Dominant Color             │  <- Wallhaven API 有限枚举
│ ●●●●●●●●●●  (30 色有限枚举)      │     色板 + 无障碍标签
├────────────────────────────────┤
│ 排序 Sort                       │
│ [最新] [热门] [收藏] [随机]      │
└────────────────────────────────┘
```

#### 各维度具体方案

**① 分类 Category** -> **分段控件**（3 个 + 全部）
- Wallhaven 枚举：`general` / `anime` / `people`
- 用 `.pickerStyle(.segmented)`，映射为中文「风景 / 动漫 / 人物」
- 单选（因为语义上三类互斥），而非旧版的复选按钮组
- 唯一例外：「全部」= 三类全开

**② 比例 Ratio** -> **可视比例图形网格**（本方案最大改进点）
- Wallhaven 枚举：`9x16` `10x16` `9x18` `1x1` `3x2` `4x3` `5x4` `16x9` `16x10` `21x9` `32x9` `48x9`
- **12 个枚举 -> 按方向归并为 5 组**，每组用一个真实宽高比的矩形表示：

| 组 | 含枚举值 | 视觉 |
|----|---------|------|
| 竖构图 | 9x16, 10x16, 9x18 | 竖长方形 |
| 方图 | 1x1 | 正方形 |
| 横构图 | 3x2, 4x3, 5x4, 16x9 | 4:3 矩形 |
| 宽幅 | 16x10, 21x9 | 16:9 宽矩形 |
| 超宽 | 32x9, 48x9 | 极宽矩形（一眼可辨） |

- 每个矩形用 `RoundedRectangle` 按真实比例绘制，`aspectRatio` 来自枚举值
- 点击即选中，选中态 = 琥珀 2px 描边 + `--accent-wash` 底
- [!] 每个图形必须有 `accessibilityLabel("竖构图，9:16 等 3 种比例")` —— **信息不仅靠视觉传达**

**③ 分辨率 Resolution** -> **分段控件只保留 5 个有意义的档位**
- Wallhaven 有 24 个精确值（`1280x720` 到 `3840x3072`）—— **全部展示是暴力，直接用 `atleast` 参数**
- 方案：`不限` / `≥1080p` / `≥1440p` / `≥4K` / `超宽`
- 映射：直接传 `atleast=1920x1080` / `2560x1440` / `3840x2160`；超宽传 `ratios=21x9,32x9,48x9`
- [!] **不要给用户 24 个精确分辨率选项** —— 壁纸的实际约束是"能否填满我的屏"，用户关心的是档位不是精确像素

**[!] 这 5 档是 UI 预设，不是 API 枚举（架构师已核实）**

`atleast` 接受**任意** `WIDTHxHEIGHT` 字符串，不是枚举值。这对设计的含义是：**新增档位只加一条 UI 预设，不改数据结构**。加 8K 档就是加一条 `{id: "8k", atleast: "7680x4320"}`。

**[!] 档位旁的结果数必须用中文紧凑格式**

架构师实测的各档数据量差异极大：

| 档位 | atleast | total |
|------|---------|-------|
| ≥1080p | 1920x1080 | 388,406 |
| ≥1440p | 2560x1440 | 160,732 |
| ≥4K | 3840x2160 | 80,905 |
| ≥5K | 5120x2880 | 22,728 |

**5K 档只有 2.2 万张，1080p 档有 38.8 万张 —— 差 17 倍。**

| 规则 | 说明 |
|------|------|
| 格式 | 中文紧凑格式：`2.2万` / `38.8万`（999 以下原样显示） |
| [!] 禁止 | 显示原始千分位整数（`388,406`）—— 用户会以为高分辨率档「筛选坏了」或「内容库太小」 |
| 呈现样例 | `≥5K（2.2万）` / `≥1080p（38.8万）` |
| 空间不足时 | **优先不显示总数**。档位标签本身已足够表达条件，总数是锦上添花不是必需 |
| [!] 不要按比例映射结果数 | 各档数量非线性（5K→1080p 是 17倍，不是 5 倍），**绝不能**按分辨率比例估算或线性映射 |

**④ 色调 Dominant Color** -> **有限色板网格 + 名称标签**
- Wallhaven 颜色是**有限枚举**（30 个 hex），这点和设计团队指出的约束一致
- 方案：5×6 色板网格，每格 24×24，`--radius-xs`，间距 8px（≥ `--hit-target-min`）
- 每格：
  - 无色名时（如 `660000` 深红）显示 hex 值 mono 8px 在格内右下（用 `--text-2xs`）
  - 首个元素是 **「不限」** —— 用 `--surface-sunken` 底 + `xmark` 图标
  - 末位是 **「黑白灰」**（对应 `000000`/`999999`/`CCCCCC`/`FFFFFF` 的合并语义）
- 选中态：琥珀 2px 描边 + 角标 `checkmarkmark`
- [!] 每个色块必须有 `accessibilityLabel`（如「深红，660000」）—— 颜色是 API 枚举的映射，不是可自由组合的色盘

**⑤ 纯度 Purity** -> **移除**
- 旧版只暴露 SFW（其他两项被注释掉），单一选项的筛选器没有存在价值
- Wallhaven 账户本就只有 SFW 层级
- 改为：内容安全靠**结果层**保证（空态/错误态明确提示），不做成一个永远选中的筛选维度

**⑥ 排序 Sorting** -> **分段控件**（4 个高频）
- Wallhaven 8 个枚举 -> 暴露 4 个：`最新`（date_added）/ `热门`（toplist）/ `收藏最多`（favorites）/ `随机`（random）
- 隐藏 `relevance`（仅搜索时有效，放搜索结果排序里）、`views`（与 toplist 高度重合）、`toplist_random`（组合项，UI 上等价于"随机热门"）
- 「随机」选中时：图标换为 `shuffle` 并禁用分页（无限加载无意义）

#### 筛选摘要与清除（关键交互）

工具栏上的筛选按钮旁显示**摘要 chip 组**：

```
[比例: 横构图 ×] [≥4K ×] [色彩: 深蓝 ×]        清除全部
```

- 每个 chip 可单独 `×` 移除（点 chip 主体 -> 直接选中该维度的其他值）
- 「清除全部」仅在有筛选时出现，用 `--fg-2` 而非 `--danger`（清除不是破坏性操作）
- 筛选变更后 150ms debounce 再请求，避免连续拖动打爆 API

### 4.4 壁纸详情的信息层级

**形态**：大图自适应 + 右侧 300px inspector（不是居中弹窗 —— 居中弹窗会遮住来源，用户想「对照着看」）。

```
┌──────────────────────────────────────┬─────────────────┐
│                                      │ 3840 × 2160     │  <- 等宽字体，最大值
│                                      │ 16 PNG · 2.4 MB │     信息最先读到
│                                      │ ─────────────── │
│         大图（按真实比例）             │ 风景 · 4K       │  <- 分类 chips
│                                      │ 2026-03-14 上传 │  <- 时间用 --muted
│                                      │ ─────────────── │
│                                      │ by 空山新雨      │  <- 上传者，可点
│                                      │ ─────────────── │
│                                      │ [收藏] [分享]    │  <- 次级操作，ghost
│                                      │ ─────────────── │
│                                      │ 设为壁纸         │  <- 主 CTA，琥珀图标
│                                      │ 分配到显示器…    │  <- 次 CTA
│                                      │ 编辑为动态…      │  <- 次 CTA
│                                      │ ─────────────── │
│                                      │ 标签             │
│                                      │ [山] [雾] [晨]    │
└──────────────────────────────────────┴─────────────────┘
```

**层级排序的依据**（用户找壁纸的真实决策顺序）：

1. **画质信息**（分辨率 + 格式 + 大小）—— 能不能用，第一决策
2. **图本体** —— 大图无遮挡，占据最大面积
3. **风格归类**（分类 + 标签）—— 适不适合当下心情
4. **来源信息**（上传者 + 时间）—— 可信度与新鲜度
5. **操作区** —— 主 CTA 明确，其余收进次级

**具体规格**：
- 元数据表行高 `--row-height` 32px，标签用 `--text-xs`，数值用 `--font-mono`（右对齐，用等宽让小数点对齐 —— 这是专业感细节）
- 收藏数单独一行，因为它是**社交证明**：格式 `heart.fill  12,847`，用 `--fg-2` 而非强调色
- 标签用 flow layout chips，`--radius-md`，hover 时底色加深
- 上传者可点 -> 打开该上传者的壁纸列表（这是老派图库的高价值功能，Wallhaven 支持）
- **底部：相关壁纸**（同标签/同上传者，横向滚动条，`--space-4` 间距），让浏览不中断
- 大图 hover 时显示 `1:1` 检视按钮（`⤢` 语义 -> `arrow.up.left.and.arrow.down.right`），进入全屏无 chrome 检视，`Esc` 退出

### 4.5 多屏分配 —— 核心难点

**设计目标**：让"这张图给哪块屏"一眼可辨，且**不需要用户理解缩放/裁剪算法**。

**形态**：sheet（`.presentationBackground(.glass)`），主区为**按真实分辨率比绘制的屏幕缩略图矩阵**。

```
┌──────────────────────────────────────────────────────────┐
│  分配到显示器                                    [完成]   │
│                                                          │
│  ┌─────────────┐  ┌─────────────┐                        │
│  │ ▢▢▢▢▢▢▢▢▢▢ │  │     ▢▢▢▢▢  │                        │
│  │ ▢▢▢▢▢▢▢▢▢▢ │  │     ▢▢▢▢▢  │   <- 缩略图按物理像素比例
│  │ ▢▢▢▢▢▢▢▢▢▢ │  │     ▢▢▢▢▢  │      显示当前壁纸预览
│  │ ▢▢▢▢▢▢▢▢▢▢ │  │             │                        │
│  └─────────────┘  └─────────────┘                        │
│  显示器 1            显示器 2                             │
│  3840 × 2160       2560 × 1440                          │
│  主显示器 2x        外接 1x             [当前壁纸]         │
│  物理像素 3840×2160   物理像素 2560×1440                  │
│                                                          │
│  填充方式  [完整可见] [填满]                         │
│  填充色    自动派生 · [恢复自动派生]                   │
│  裁切焦点  [左上][上][右上] / [左][中][右] /           │
│            [左下][下][右下]                            │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**关键设计决策**：

| 决策 | 方案 | 理由 |
|------|------|------|
| 屏幕缩略图形状 | **严格按各屏物理像素的宽高比绘制**（`frame.width × backingScaleFactor`） | [!] Retina 与非 Retina 混用时，逻辑点比例相同但物理像素不同。只看 `NSScreen.frame` 会算错，见下方专门说明 |
| 屏幕身份识别 | 缩略图 + 「显示器 N」+ 分辨率 + 缩放倍率 + `主显示器` 标记 | 不能只靠缩略图，用户不知道哪块是主屏、哪块是 Retina |
| **缩放倍率显式展示** | 每块屏下方标注 `2x` / `1x` | [!] 这是 MVP 必须做的。让用户看到「同样是 16:10，主屏 2x、外接 1x」，才能理解为什么同一张图在两屏上清晰度不同。旧版完全没有这个概念 |
| 「主显示器」标记 | `star.fill` 16px + 文字（不只靠图标） | 可访问性 |
| 分配动作 | 点缩略图即分配（单击即完成，**不需确认按钮**） | 高频操作，多余的确认是摩擦 |
| 分配反馈 | 缩略图立即换为新壁纸 + 琥珀 2px 描边 + HUD toast | 三重反馈，明确成功 |
| 已分配状态 | 缩略图右下角小徽标 `checkmark.circle.fill` | 不打断浏览 |
| **填充方式** | **只有两档分段控件**：`完整可见` / `填满` | [!] 这是 macOS 壁纸 API 的**全部**真实语义（`AllowClipping` BOOL）。详见下方「填充方式的语义边界」—— 我原先设计的五项里有两个根本不存在 |
| **填充色** | **自动派生，用户不选**。只提供「恢复自动派生」重置入口 | [!] Apple 官方建议不为此呈现 UI。自动派生也是差异化（竞品交给系统默认色，通常与壁纸不协调） |
| **裁切焦点** | 9 点网格选择器，**按屏独立记忆**。[!] 客户端预裁切实现（见下） | 焦点是客户端行为而非系统能力，因此**预览必须与实际结果完全一致** |
| 拖拽分配 | 从详情页把缩略图拖到目标屏幕卡片 | 高手路径，但**非唯一路径**（点击同样可用） |

**[!] 填充方式的语义边界（我此前的设计错误，已修正）**

我原先在 DESIGN.md v2.0/v2.1 设计了「填充 / 适应 / 拉伸 / 平铺 / 居中」五项。经PM 核实本机 SDK 一手来源（`NSWorkspace.h:204-237` + `NSCell.h:60-69`），**其中两项根本不存在**：

| 我原设计的项 | 实际情况 | 处理 |
|------------|---------|------|
| 填满 | [!] 可实现：`AllowClipping = YES` + `scaleProportionallyUpOrDown`。[!] 但**永远居中裁切**，用户无法指定裁切哪一侧 | 保留，改为「填满」 |
| 完整可见（我写作「适应」） | [!] 可实现：`AllowClipping = NO`。图片完整显示，四周空隙由填充色填充 | 保留，改为「完整可见」 |
| 拉伸 | [!] **不可作为独立选项**。`scaleAxesIndependently` 会忽略裁切设置，导致变形 | **删除** |
| 平铺 | [!] **完全无法实现**。`NSImageScaling` 四个取值中没有任何平铺语义 | **删除，且 UI 与文案中不得出现「平铺」二字** |
| 居中 | [!] **不是独立选项**，它是「填满」的固定行为（系统永远居中裁切） | **删除** |

**最终 UI 只有两档分段控件**：`完整可见` / `填满`。

这个修正反而是好事：Apple 在 `NSWorkspace.h:225` 的官方建议是「通常不应当为挑选这些 options 呈现用户界面，而应直接选择合适的默认值并允许用户在系统设置中调整」。我们给出两档真实语义 + 自动派生填充色，既不违背官方建议，也比竞品（交给系统默认色，通常与壁纸不协调）更有差异化。

**[!] 填充色：自动派生，不给用户手选**

系统提供的填充色是解决「完整可见模式四周空隙」的唯一手段（`NSWorkspaceDesktopImageFillColorKey`）。但 Apple 明确建议不为此呈现 UI。

**设计决策**：从壁纸 API 响应的 `colors` 数组自动派生协调色作为填充色，用户零操作。界面上只提供一个「恢复自动派生」入口 —— 自定义能力可以延后，但**必须提供恢复默认的路径**，否则用户被自动值锁定且无法退出。

| 规格 | 值 |
|------|-----|
| 呈现 | 只读色块 + 文字「自动派生」+ `↺` 图标按钮（`arrow.counterclockwise` 16px） |
| 色块 | 24×24，`--radius-xs`，`--surface-sunken` 底 + 1px `--border-soft` |
| 派生失败 | 优雅回退系统默认填充色，**不报错、不阻塞设置**（colors 为空或无法解析时） |
| 与壁纸卡片的关系 | 详情页可显示「填充色将取自此壁纸的主色」，让自动行为可预期 |

**[!] 色彩空间转换链（team-lead 已核验签名，实现必须按下述兜底）**

`NSWorkspaceDesktopImageFillColorKey` 只接受可转为 `NSCalibratedRGBColorSpace` 的颜色，且**alpha 被忽略**。因此派生值必须经过一次转换，转换失败则静默放弃传该 key。

```
wallhaven 返回 hex（如 "#abbcda"）
  └─> NSColor(hex:)                // 默认 sRGB
      └─> usingColorSpace(.calibratedRGB)   // 返回 Bool，不抛异常
├─ true  -> 作为 NSWorkspaceDesktopImageFillColorKey 写入
           └─ false -> 静默回退：完全不传该 key，让系统用默认色
```

| 关键事实 | 说明 |
|---------|------|
| `usingColorSpace(_:)` **返回 `Bool`** | 失败时返回 `false`，**不会抛异常**。所以回退路径是「不传 key」而非「try/catch」 |
| 不做任何颜色补偿 | 若转换失败就回退系统默认色，**不要**临时换个近似色 —— 近似色可能与壁纸不协调，反而更差 |
| alpha 一律忽略 | 不要试图传入带 alpha 的颜色，alpha 会被系统丢弃 |
| 多色时的选取 | `colors` 数组有多值时取第一个可成功转换的；全部失败则整体回退 |
| [!] 绝不阻塞设置 | 无论成功与否，**填充壁纸的主流程必须继续走完**。填充色是修饰项，不是前置条件 |

```swift
// [OK] 正确：Bool 返回 + 静默回退
let fillColor: NSColor? = wallpaper.colors
    .compactMap { NSColor(hexString: $0) }          // hex -> sRGB
    .first { $0.usingColorSpace(.calibratedRGB) }     // 返回 Bool，不抛
// fillColor 为 nil 时不传该 key，系统使用默认色

// [NG] 错误：try/catch 假设它会抛异常
// [NG] 错误：转换失败后换个近似色 —— 可能与壁纸更不协调
```

**[!] 裁切焦点是客户端预裁切，不是系统能力**

系统 API 无法指定裁切哪一侧（`AllowClipping` 只是 BOOL，永远居中）。所以焦点的实现方式是：**我们用 Core Image 按目标屏物理像素预先裁好，再把裁好的成品图写入系统**。写入的是已裁好的静态图，系统不再做二次裁切。

**产品硬红线（PM 明确）**：如果技术上做不到「预览即所得」，**砍掉焦点调整功能**，而不是做打折版本。

| 要求 | 说明 |
|------|------|
| 预览 = 实际结果 | 预览渲染的必须是我们将要写入的那张成品图，不是「系统会怎么裁」的模拟 |
| 允许的误差 | 仅允许抗锯齿级别的像素差。**不接受**「预览 A、设置后得到 B」 |
| 若无法保证 | 功能不上线。理由：一次不一致就会让用户对我们所有预览失去信任，后续所有预览都会被怀疑 |

**[!] 实现约束：预裁切输出必须是可被 UI 直接消费的产物对象（team-lead 采纳）**

因为写入系统的是我们已裁好的成品图，「预览即所得」天然成立 —— **前提是预览与写入共用同一份裁切产物**。真正的风险是实现时另写一套「模拟系统裁切」的渲染逻辑。

| 约束 | 说明 |
|------|------|
| 单一产物对象 | 预裁切模块输出一个**产物对象**（含裁切后图像 + 尺寸 + 缓存 key），**预览与写入共用同一对象** |
| [!] 禁止 | [!] **不允许各自实现一套** —— 预览不得另写渲染逻辑，写入不得绕过产物直接裁图 |
| 缓存 key | `hash(壁纸ID, 屏displayID, 填充模式, 焦点, 缩放倍率)`。同 key 复用缓存，避免用户反复切换时重复编码 |
| 预裁切时机 | **只在「设为壁纸」时执行**，浏览瀑布流/详情页时不预裁切（否则拖慢滚动） |
| 加载态 | 预裁切 + 编码是同步耗时操作，卡片需 spinner 态（见 §6.5 状态矩阵） |

---

**[!] 物理像素计算（P0 级正确性要求，PM 已列为 F2 验收标准）**

这是多屏分配最容易出错的地方，且**错误是静默的**——预览正确但实际设置后错位，用户会认为是"壁纸质量差"而不是"App 有 bug"。

| 概念 | 获取方式 | 用途 |
|------|---------|------|
| 逻辑点尺寸 | `NSScreen.frame.size` | [!] **不可用于**壁纸裁切计算 |
| 缩放倍率 | `NSScreen.backingScaleFactor` | 2x / 1x |
| **物理像素尺寸** | `frame.size × backingScaleFactor` | [OK] **所有壁纸缩放/裁切/填充计算必须基于此** |

```swift
// [OK] 正确：物理像素
let scale = screen.backingScaleFactor      // 2.0 for Retina, 1.0 external
let physicalSize = CGSize(
    width:  screen.frame.width  * scale,
    height: screen.frame.height * scale
)
let targetAspect = physicalSize.width / physicalSize.height

// [NG] 错误：逻辑点。Retina 屏与外接屏会算出相同比例但实际裁切区域不同
let wrongAspect = screen.frame.width / screen.frame.height

// [OK] 低分辨率预警的倍数计算（给用户具体数字，不给「可能模糊」）
let imagePixels  = image.dimensionX * image.dimensionY
let screenPixels = Int(physicalSize.width) * Int(physicalSize.height)
let scaleUpFactor = Double(screenPixels) / Double(imagePixels)
// 展示时保留一位小数：「放大约 2.7 倍」
```

| 场景 | 为什么必须用物理像素 |
|------|-------------------|
| MacBook 内屏 2x + 外接 4K 1x | 两者逻辑点可能都是 16:10，但 4K 屏的实际像素是内屏的 2.25 倍。用逻辑点算会让 4K 屏的壁纸被放大到模糊 |
| 缩放设为「更大文字」 | `backingScaleFactor` 不变但逻辑点尺寸变化，只看逻辑点会在用户切换缩放时静默算错 |
| 判断图片是否够清晰 | 「这张图 3840×2160，屏幕物理像素也是 3840×2160 -> 刚好 1:1 清晰」。这个判断只有物理像素能给出 |

**[!] 放大倍数禁止跨屏缓存（架构师实测追加，与物理像素要求同源）**

放大倍数 = 屏物理像素 / 壁纸物理像素，这是 **(壁纸, 屏幕) 这一对的关系量**，不是壁纸的固有属性。

| 同一张 3840×2160 壁纸 | 放大倍数 |
|----------------------|--------|
| 在 5120×2880 屏上 | 1.33 倍（需预警） |
| 在 2560×1440 屏上 | 0（完全无需放大，不显示预警） |
| 用户拔掉外接屏 | 倍数立即改变 |
| 壁纸从副屏拖到主屏 | 倍数立即改变 |

| 规则 | 说明 |
|------|------|
| [!] 禁止 | 把倍数作为**壁纸的持久化字段** |
| [!] 禁止 | 缓存跨屏的倍数结果 |
| [!] 禁止 | 在壁纸详情页显示与屏无关的「放大倍数」 |
| 缓存键必须含 | 目标屏标识（`displayID` + `backingScaleFactor`） |
| 文案影响 | 若 UI 标签来自缓存值，**多屏场景下用户会看到张冠李戴的数字** |

这与「预览正确但实际错位」是**同一类静默错误，只是发生在文案上** —— 用户看到 2.7 倍但当前屏只需 1.3 倍，会认为系统算错。

**裁切焦点按屏记忆**：

```swift
// 每块屏独立存储焦点，不跨屏套用
struct FocusMemory {
    // key 必须用 NSScreen 的稳定标识，不能用 index（屏序会变）
    private var store: [String: FocusPoint] = [:]

    func focus(for screen: NSScreen) -> FocusPoint {
        store[screen.displayID] ?? .center   // 默认居中
    }

    mutating func set(_ point: FocusPoint, for screen: NSScreen) {
        store[screen.displayID] = point
    }
}
```

[!] **禁止用 `NSScreen` 数组下标作为 key** —— 用户拔插外接显示器后屏序会变，用下标会导致焦点套用到错误的屏幕上。

**跨屏拼接 = V2，MVP 不做**

PM 已裁决延后（技术上 macOS 无原生支持，需自行切图，且 Retina 混用会导致接缝错位）。MVP 阶段的处理：

| 处理 | 说明 |
|------|------|
| **UI 不出现** | 分配器里**不渲染**「跨所有显示器」选项，不做置灰占位，不做「即将推出」标签 —— 一个用不了的按钮只会消耗信任 |
| 物理像素能力**必须做对** | 这是 F15 的前置条件。在 MVP 做对，V2 就是增量而非重做 |
| 埋点预留 | 若日后要做「用户手动控制构图」的行为数据采集，MVP 的填充方式 + 焦点选择已足够作为信号 |

#### 4.5.1 分辨率不足预警（新增）

**触发条件**：目标屏物理像素 > 壁纸物理像素，且用户选择「填满」（放大必然发生）。

系统会**放大**过小的图片，且 `NSImageScaleProportionallyDown`（只缩小不放大）在壁纸 API 中**不被支持** —— 也就是说这个放大行为**无法通过参数关闭**，只能靠下载足够分辨率的原图避免。

```
┌──────────────────────────────────────┐
│ [!] 该壁纸分辨率低于屏幕               │
│                                        │
│ 壁纸 1920 × 1080                      │
│ 屏幕 5120 × 2880（外接，1x）           │
│ 填满模式下会放大约 2.7 倍，画面可能模糊  │
│                                        │
│ [仍要使用]  [在主窗口查看]              │
└──────────────────────────────────────┘
```

| 规格 | 值 |
|------|-----|
| 出现位置 | 分配器内选中该屏时**内联**显示，不弹模态 —— 这是常规信息，不是错误 |
| 出现时机 | 选中屏幕 + 壁纸低于屏幕物理像素时。**切换到「完整可见」时自动消失**（不放大，不模糊） |
| 图标 | `exclamationmark.triangle` 24px，`--warn` |
| 标题 | `--text-md` `--fg`：「该壁纸分辨率低于屏幕」 |
| 数据对比 | 用 `--font-mono` 等宽展示「壁纸 W×H」与「屏幕 W×H（倍率，1x/2x）」 |
| 放大倍数 | **必须算出来给具体数字**（「放大约 2.7 倍」）。模糊倍数可感知，说「可能模糊」太模糊 |
| 主操作 | 「**在主窗口查看**」→ 跳主窗口详情页（那里有筛选入口） |
| 次操作 | 「仍要使用」→ 照常应用，不阻止用户 |
| 不阻断 | [!] **绝不阻止用户设置**。用户有权选择，接受后果是我们的责任不是替他决定 |

**[!] 跨屏重算要求（静默错误来源，team-lead 指出）**

同一张壁纸在不同分辨率的屏幕上，预警结论可能完全不同 —— 4K 屏够用、5K 屏不足。

| 规则 | 说明 |
|------|------|
| 计算范围 | **按当前选中屏幕独立计算**，文案与倍数不跨屏共用 |
| 必须重算的时机 | 切换选中屏幕 / 切换填充模式 / 显示器热插拔 / 缩放倍率变化 |
| [!] 禁止 | 沿用上一次的 `{factor}` `{screenW}` `{screenH}` `{scaleFactor}` |
| 静默错误风险 | 倍数是上次的但当前屏不同 —— 用户会认为系统算错了。这是**跨屏场景最容易被忽略的错误** |
| 测试要求 | 必须覆盖「同一张壁纸 + 三块不同分辨率屏」的用例 |

```swift
// [!] 预警计算必须绑定当前选中屏，不能是全局缓存
func warning(for wallpaper: WallpaperImage, screen: NSScreen) -> Warning? {
    // 每次都基于传入的 screen 重算，不读任何跨屏缓存
    let scale = screen.backingScaleFactor
    let screenPixels = Int(screen.frame.width * scale) * Int(screen.frame.height * scale)
    let imagePixels  = wallpaper.dimensionX * wallpaper.dimensionY
    guard imagePixels < screenPixels else { return nil }
    return Warning(factor: Double(screenPixels) / Double(imagePixels),
                   screenSize: ..., scaleFactor: scale)
}
```

**[!] 与 hover 浮层的一致性要求**：分配器里的预警数据（壁纸尺寸、屏幕尺寸、倍率）与 hover 浮层显示的分辨率必须是**同一份计算结果**。不能出现浮层说 1920×1080、预警说 1920×1080 但缩略图是另一个尺寸的情况。

**[!] 文案禁令**：「可能模糊」要具体化。同理**不要**写「该壁纸质量较低」—— 用户要的是数字，不是形容词。

#### 4.5.1.1 动态分辨率档位 → MVP 不做（决策记录）

**决策**：MVP 保持固定 5 档（不限 / ≥1080p / ≥1440p / ≥4K / 超宽），**不做按当前屏动态生成的档位**。低分辨率预警的主操作降级为「在主窗口查看」。

**理由（基于实测数据，非工程量考虑）**：

```
$ curl "wallhaven.cc/api/v1/search?atleast=5120x2880&sorting=date_added"
→ total: 22728 张, last_page: 947 页
```

`atleast` 参数**支持任意分辨率**，且 5K 档位有 2.2 万张图可用 —— 数据基础极其充足。

但正因充足，**才更不该做成动态档位**：用户屏幕尺寸是连续值（5120×2880 / 6016×2160 / 5120×3200…），动态生成会产生无限组合。固定 5 档已是合理抽象，再动态化属过度设计。

**V2 触发条件**：若数据显示大量用户是 5K/6K 屏，再做「以当前屏为基准的智能筛选」。

---

**反模式警告**：
- [NG] 不要做成 Wallpaper Engine 那种「预览区 + 显示器下拉列表」—— 下拉列表无法让用户建立空间感
- [NG] 不要让用户在详情页猜"会是几屏"—— 缩略图直接显示结果
- [NG] 缩略图**不要**用统一 16:9 画布 —— 形状必须反映真实比例
- [NG] **不要用逻辑点做裁切计算** —— 这是静默错误，用户不会报 bug，只会觉得 App 做得差
- [NG] 不要在缩略图标签里塞满分辨率数字 —— 逻辑分辨率一行 + 缩放倍率标记，物理像素只在辅助文案或 tooltip 里出现（信息分层，别让标签变成技术面板）
- [NG] **不要设计系统做不到的控件** —— 我曾设计五项填充方式，其中「平铺」「居中」系统根本无法实现。设计任何控件前必须先确认 API 能力边界（见上方语义边界表）
- [NG] **不要做「预览与实际不一致」的折扣版功能** —— 做不到预览即所得就砍功能。一次不一致会让用户对所有预览失去信任
- [NG] **不要把放大倍数缓存成壁纸的固有属性** —— 它是 (壁纸, 屏幕) 的关系量，缓存后多屏场景会张冠李戴
- [NG] **不要把不同原因的错误合并成一句话** —— 「检查网络或服务异常」等于让用户自己猜该查哪边

|------|------|
| [!] **不需要「格式」筛选维度** | 只有两种格式，浏览器场景下几乎无差别，不值得占用筛选空间 |
| [!] 现有格式徽标价值极低 | hover 浮层与详情页的「PNG / JPEG」标记可考虑移除 —— 74% 是 JPEG，且 JPEG 内部还有质量档差异，该标记传递的信息量极低 |
| 可作空态兜底话术 | 若需向用户解释「为什么没有动图」，可用「wallhaven 为静态图片库」 |

**[!] 若后续仍要引用 `type:` 做验证，必须使用 `q=type%3A` 形式** —— 独立参数形式会给出「返回全库」这个看似合理实则完全误导的结果。

补充验证（仍成立）：`/api/v1/video` 端点返回 404；官方 API 文档全文检索 `video` / `webm` / `gif` / `animated` **零命中**。

**F9 的真实定位因此改变**：不是「浏览到动态壁纸 → 播放」，而是「**让用户把自己已有的视频素材变成动态壁纸**」。这意味着动态壁纸是**本地库的下游**，不是瀑布流卡片的下游。

| 结论 | 设计含义 |
|------|---------|
| [!] 入口挂在导入流程之后 | 动态壁纸的入口在**本地库 / 导入**，不在浏览结果上 |
| [!] 瀑布流卡片不设计任何「动态」标识 | 网络内容里不存在这种卡片。**不加播放标记、不加动效徽标、不加时长标签** |
| [!] 导入到设置需路径连贯 | 访达拖入 mp4 → 导入 → 可设为动态壁纸，这条路径在 UI 上必须连贯无断点 |

| 规格 | 值 |
|------|-----|
| 空态 | 虚线框drop zone + 两行说明（拖入 / 点击选择）+ 支持格式 + **明确列出不支持的格式** |
| [!] 不支持格式的明示 | 空态里**主动写出来**（「不支持 WEBM、MKV、GIF」），而不是等用户导入失败才知道。这比失败后提示便宜得多 |
| 导入后卡片 | 首帧缩略图 + 时长（`--font-mono`，如 `12s`）+ 文件名截断 |
| 卡片动作 | 单击 = 打开编辑器；右键 = 设为壁纸 / 从列表移除 |
| 空列表文案 | 「还没有动态壁纸」+「从访达拖入视频文件，或点击选择」+「选择文件…」按钮 |
| [!] 删除需确认 | 「从列表移除」是破坏性操作（若已设为壁纸需说明影响），用确认弹窗 |
| 排序 | 默认为最近导入 |

#### [!] 不支持格式的转换引导（P0 级）

**已裁定的格式支持**：支持 MP4/MOV（含 HEVC、H.264）；**不支持 WEBM/MKV 与 GIF**。

GIF 明确不支持的理由：需逐帧解码，功耗与体验都不达标，且 macOS 官方不把 GIF 作为壁纸类型支持。

**探测时机（架构侧约束）**：格式探测在**导入时做一次**，不在播放时做。因此所有错误提示都出现在「拖入文件」这一刻，不是「点播放」时。**不静默转换、不静默跳过** —— 失败必须显式告知。

**[!] 四态视觉必须可区分**

| 态 | 条件 | 提示文案 | 用户能做什么 | 主要操作 | 色彩 |
|----|------|---------|------------|---------|------|
| **成功** | MP4 / MOV（H.264 / HEVC） | —— | 直接使用 | —— | 正常 |
| **引导转换** | **GIF** | 「macOS 不支持 GIF 作为动态壁纸，请转换为 MP4」<br>「GIF 需要逐帧解码，功耗较高」 | [!] **能转换** | 「转换为 MP4 后重试」 | `--warn` |
| **不支持** | WEBM / MKV / 其他 | 「此格式无硬件解码，无法作为动态壁纸」<br>「该容器不受支持」 | [!] **只能换素材** | 「重新选择」 | `--warn` |
| **损坏** | 损坏 / 无法解析 | 「无法读取这个文件，文件可能已损坏」 | 换一个文件 | 「重新选择」+「查看详情」 | `--danger` |

**[!] 引导转换态与不支持态的区别是本节重点**

两者都是「导入失败」，但**用户可采取的行动完全不同**：

| 态 | 用户行动 | 为什么不同 |
|----|---------|-----------|
| GIF 需转换 | 转码后再试 | 转码可行且用户能自己完成 |
| WEBM/MKV 不支持 | **只能换素材** | 转 MP4 通常需重编码（耗时且质量损失），说「换个素材」更诚实 |

**[!] 不要给 WEBM/MKV 提供「转换为 MP4」作为主要操作** —— 那会暗示一条其实很重的路。GIF 态可以提供（GIF→MP4 是轻量转码），WEBM/MKV 态不应该。

[!] **禁止把两者合并成一个「格式不支持」** —— 那会让 GIF 用户以为自己只能换素材（其实能转），也让 WEBM/MKV 用户以为自己能转（其实不该转）。

```
┌──────────────────────────────────────┐
│ [!] macOS 不支持 GIF 作为动态壁纸      │  <- GIF 态（可转换）
│                                        │
│  rain.gif                              │
│                                        │
│ GIF 需要逐帧解码，功耗较高，│
│ 不适合作为动态壁纸。│
│                                        │
│ 建议转换为 MP4 后再导入。│
│                                        │
│ [转换为 MP4 后重试]  [重新选择]         │
└──────────────────────────────────────┘

┌──────────────────────────────────────┐
│ [!] 此格式无硬件解码                    │  <- WEBM/MKV 态（换素材）
│                                        │
│  clip.webm                             │
│                                        │
│ 该容器不受支持，无法解码。│
│ 转换为 MP4 需重新编码，│
│ 可能损失画质，建议选择其他素材。│
│                                        │
│ [重新选择]                             │
└──────────────────────────────────────┘
```

| 规格 | 值 |
|------|-----|
| [!] 必须包含 | **文件名**（等宽字体）+ **为什么不支持**（该格式的具体理由，不是「格式错误」）+ **可执行的出路** |
| 主体 | 分两句：一句说不支持的原因（针对该格式的具体理由），一句给出路 |
| 转换方法 | 仅 GIF 态提供「查看转换方法」，给一段可复制的命令或打开对应工具 |
| 禁止 | 只说「不支持该格式」—— 用户会归因为「这 App 播放能力不行」而不是「格式选错了」 |
| 禁止 | 静默失败或黑屏 —— 那会让用户对我们的整个导入能力产生怀疑 |
| 图标 | `exclamationmark.triangle` 24px；损坏态用 `--danger`，其余用 `--warn` |
| VoiceOver | label 必须含**文件名 + 格式 + 可采取的行动**，如「无法导入 rain.gif，GIF 不支持作为动态壁纸，建议转换为 MP4」 |

**[!] 这个提示是P0 级的原因**：用户导入失败却只看到黑屏或笼统报错，会直接归因为「这个应用播放能力不行」—— 这是对产品能力的错误判断，而且用户不会来反馈，只会更谨慎地不再尝试。**文案必须指向可执行的下一步，不是告知一个失败结果。**

**[!] 多屏裁切差异必须可视化（架构侧新增差异化能力）**

同一段视频会**按每块屏的物理像素分别裁切播放** —— 21:9 副屏不裁切、16:10 主屏按焦点裁切。这意味着动态壁纸的多屏分配界面**不能只做「选一张视频」，必须展示各屏的裁切差异**。

| 规格 | 值 |
|------|-----|
| 分配界面 | 复用 §4.5 的屏幕缩略图矩阵，但每块屏内显示**该屏实际裁切后的画面**（非原始首帧） |
| 裁切差异提示 | 若各屏裁切区域不同，在缩略图下方标注「已按此屏比例裁切」 |
| 焦点独立 | 每块屏的裁切焦点**独立记忆**，复用 §4.5 的 `cropFocus.memoryScope: perDisplay` |
| [!] 一致性约束 | **预览渲染的必须就是各屏将写入的裁切产物** —— 复用 §4.5 的预裁切产物契约，禁止为不同屏写不同裁切逻辑 |

**为什么这条值得单独强调**：这是静态壁纸做不到的能力。静态壁纸一套图铺所有屏，动态壁纸可以**每屏一套裁切**。如果分配界面只显示「这张视频已分配到 3 块屏」，用户无法理解为什么每屏看到的内容不同 —— 会以为播放异常。**必须让用户看到「这是按你的屏幕比例裁过的」**。

**形态**：独立窗口（非 sheet —— 编辑需要空间和专注）。三栏：源素材 + 预览 + 参数。

**[!] 源素材是本地导入的视频文件，不是网络图片**（见 §4.6.0）。下方布局图中「源图」应理解为**视频的首帧或选区内的视频画面**。

```
┌────────────────────────────────────────────────────────────┐
│  <-  动态壁纸编辑器                          [预览效果]      │  <- 工具栏
├─────────────────────────────┬──────────────────────────────┤

│  │    ╔═══════════╗      │  │  │ │ ░░░░ 裁剪区域 ░░░ │ │   │
```

#### 裁剪区域交互

| 手柄 | 行为 |
|------|------|
| 8 个手柄 | 四角 + 四边中点，`--crop-handle-size` 10px，填充白色，hover 时放大到 12px |
| 手柄命中区 | 视觉 10px，**命中区 24px**（保证指针精度） |
| 边拖动 | 单轴缩放，另一轴固定（锁定比例可在选项中开启） |
| 角拖动 | 等比缩放（默认锁定比例，避免用户得到畸形裁剪区） |
| 区域内部拖动 | 整体平移 |
| 双击内部 | 快速填满源图 |
| 三分构图线 | 拖动时显示 2 条 `--crop-rule-line` 水平 + 2 条垂直线，松开即隐 |
| 键盘调整 | 方向键移动选区 1px，`⇧` + 方向键移动 10px，`⇧⌥` 缩放 |
| 约束 | 最小选区 64×64px，最大 = 源图全尺寸 |
| **持久比例** | 选区下方显示 `16:9 · 3840×2160`，随拖动实时更新 | 

**预览区设计**（这是"所见即所得"的关键）：
- 预览显示的是**模拟目标屏幕**，含**安全区标记**：
  - 顶部 28px 虚线 = 菜单栏遮挡区
  - 底部 60px 虚线 = Dock 遮挡区（`--crop-safe-area`）
- 超出裁剪区的源图部分用 `--crop-safe-area` 遮罩压暗，**明确告知"这部分用户看不到"**
- 预览实时播放（循环），用户改速度立刻看到效果
- 播放中显示红色 live 圆点 `--live-indicator`，1.2s 呼吸（reduced-motion 下常亮不呼吸）

**[!] 循环接缝提示**：动态壁纸是**循环**播放，源视频首尾帧不连续时会有可见的跳变。这是素材本身的属性，UI 应在**导入后即告知**，而非等用户看到跳变才发现问题。

| 规格 | 值 |
|------|-----|
| 检查时机 | 导入时检测首尾帧差异（架构侧实现），**导入后就提示** |
| 提示形态 | 导入成功后的一次性非阻断提示：「此视频首尾帧不连续，循环时可能有明显跳变」+「仍然使用」 |
| 不阻断 | [!] 静默循环播放，播放中不重复提示 —— 只在导入时说一次 |
| 若首尾帧接近 | **不提示**。不要对所有视频都显示这个提示，那会变成噪声 |

#### 速度滑块

**这里用 Slider 是正确的** —— 播放速度是**连续量**，与 §4.2 的分辨率枚举有本质区别。

| 规格 | 值 |
|------|-----|
| 范围 | 0.25× – 3.0×（0.25 步进） |
| 默认 | 1.0× |
| 轨道 | `--playback-scrub-bg`（16% 白），已播放部分琥珀 |
| 数值显示 | 等宽字体跟随滑块右侧 |
| 快捷预设 | `0.5×` `1.0×` `1.5×` `2.0×` 点击跳转 |
| 键盘 | 方向键 0.05 步进，`⇧` 0.25 步进 |
| VoiceOver | `accessibilityLabel("播放速度")` + `accessibilityValue("1.5 倍")` + `.accessibilityAdjustableAction` |

**关键**：滑块旁必须显示**性能预估**（CPU / GPU / 内存）。用户调高速度的代价是耗电，这个权衡必须可见 —— 这是 Wallpaper Engine 用户最常抱怨的点（"动态壁纸吃 CPU"）。

### 4.7 菜单栏面板（400 × 500）

**设计目标**：这是**高频快捷面板**，不是迷你版主窗口。用户从菜单栏点开，1 秒内完成"换一张"。所以排序原则是**高频动作在上、低频信息在下**。

```
┌──────────────────────────────────────┐
│ [搜索] 搜索壁纸、标签、上传者    [筛选] │  <- 32px（筛选按钮收进面板，同行右）

│ ┌──────────────────────────────────┐ │

├──────────────────────────────────────┤
│   [上一张]   [随机]   [下一张]  │ [收藏] │  <- 48px 主操作行，按钮 40×40
├──────────────────────────────────────┤
│ NSFW 内容                             │  <- 仅 L1 通过时出现（见 4.8）
│ 应用内 NSFW                   [ON ]   │     全局开关

├──────────────────────────────────────┤

│ ┌────┐ ┌────┐ ┌────┐                  │     48×48 缩略

│ [动态] 播放 ○   [30min]   [设置]        │  <- 28px 页脚
└──────────────────────────────────────┘
```

**具体规格与理由**：

| 区域 | 高度 | 关键决策 |
|------|------|---------|
| **搜索框** | 32px | ⌘F 打开面板时**自动聚焦**。placeholder「搜索壁纸、标签、上传者」—— 点明三类可搜对象 |
| **筛选按钮** | 32px（同行右） | [!] 400px 宽放不下搜索+筛选两个全宽控件。筛选收进面板为图标按钮，与主窗口共用同一份筛选状态 |
| **搜索结果** | 替换预览区 | [!] 输入时预览区变为**垂直结果列表**（最多 6 行，每行 44px），不用瀑布流 —— 空间太小，瀑布流无法阅读 |
| **当前预览** | 200px | 显示当前壁纸，让用户有"我现在在用什么"的锚点。左上角「当前壁纸」标签用 `--badge-bg` |
| **信息行** | 20px | 标题 · 分辨率。标题超长截断 + `.help()` tooltip。[!] NSFW 项此行隐藏（见 §4.8.3） |
| **主操作行** | 48px | `[上一张] [随机] [下一张]` 三个等权按钮（**不是**"下一张"主导 —— 上一张/下一张使用频率相当），加 `[收藏]` 收藏 + `[更多]` 更多 |
| **NSFW 区** | 52px（条件出现） | [!] 仅 L1 通过时出现。空间不足时优先牺牲「最近条」，NSFW 开关**永不可折叠**（见下方空间预算） |
| **最近条** | 72px | 显示最近 8 张设置的壁纸，横向滚动。这解决了"设错了想找回"的痛点 |
| **页脚** | 28px | 动态播放开关 + 自动切换间隔 + 设置入口。`--text-xs` 低权重 |
| **安全区** | 底部 `env(safe-area-inset-bottom)` | 刘海屏区域不被遮挡 |

**空间预算（500px 固定高度下的取舍顺序）**：

```
基础占用 = 32 + 200 + 20 + 48 + 72 + 28 = 400px（+ 分割线与安全区约 460px）
剩余 ≈ 40px -> 恰好容纳 NSFW 区（52px，含分割线）
若不足，牺牲顺序：最近条（可折叠为单行标题） -> 当前预览缩至 160px -> 主操作行压至 44px
[NG] 永不牺牲：NSFW 开关可见性、主操作行、搜索框
```

**玻璃使用**：整个面板 `glassEffect(.regular)` —— 它是**浮在壁纸之上的 chrome**，符合白名单 G3。

### 4.8 NSFW 三层门禁与视觉降级（PM 裁决落地）

PM 已裁决为三层串联，任一层不通过即不展示。设计落地如下。

#### 4.8.1 状态机

| 层 | 条件 | 默认 | 表达位置 |
|----|------|------|---------|
| **L1 能力层** | API Key 有效 **且** wallhaven 账号已开启 NSFW | 由用户配置 | [!] **L1 不通过时，面板内不渲染任何 NSFW UI** —— 不做置灰开关，置灰会让用户反复点击找原因 |
| **L2 应用层** | 应用内 NSFW 总开关（显式操作 + 年龄确认） | **关闭** | 主窗口设置 + 面板 NSFW 区第一行 |
| **L3 场景层** | 菜单栏面板 NSFW 独立开关 | **关闭** | [!] **仅面板内**。主窗口是主动打开的私密场景，再加一层是过度设计 |

**状态机流转**：

```
L1 不通过 ─────────────────────────────► 面板无 NSFW UI
   │
   └─► L1 通过
         │
         ├─► L2 关闭 ─────────────────► 面板无 NSFW UI
         │                                （主窗口可见 NSFW 筛选能力）
         │
         └─► L2 开启（需年龄确认）
               │
               ├─► L3 关闭 ────────────► 面板结果不含 NSFW（SFW 照常）
               │                           [!] 搜索无结果时必须显式提示，见 4.8.4
               │
               └─► L3 开启 ────────────► 面板可见 NSFW，缩略图降级，见 4.8.3
```

#### 4.8.2 两个开关的视觉层级（表达「全局 vs 仅此面板」）

PM 要求：用户在公开场合要能**一眼看出当前状态**。两层开关同处一区块，但视觉权重必须区分。

```
┌──────────────────────────────────────┐
│ NSFW 内容                              │  <- --text-2xs ALL CAPS +0.06em --muted
│                                        │
│ 应用内 NSFW                      [ ●] │  <- --text-sm --fg，明确写「应用内」
│ 影响全部界面，需年龄确认                │  <- --text-2xs --meta，作用域说明
│ ────────────────────────────────────  │
│ 本面板显示 NSFW                 [ ○] │  <- --text-sm --fg-2，写「本面板」
│ 仅菜单栏弹出时生效，不影响主窗口          │  <- --text-2xs --meta，作用域说明
└──────────────────────────────────────┘
```

| 设计手段 | 作用 |
|---------|------|
| **文案必须带作用域词** | 「应用内 NSFW」vs「本面板显示 NSFW」—— 不用「全局/局部」这类术语，用自然语言说清范围 |
| **每行带辅助说明** | `--text-2xs` `--meta`，一句话说明影响范围。这是唯一可靠方式，图标无法表达作用域 |
| **分隔线分组** | 两开关间用 `--divider-hairline` 分隔，明确是不同层级 |
| **主开关字重更高** | L2 是全局设置，用 `--fg`；L3 是场景开关，用 `--fg-2` |
| **L3 开启时不加警示色** | [!] 不用 `--danger` 或警告图标。L3 开启是用户自主决定，不是错误态；加警示色会让用户不敢用，且暗示我们不支持 |

#### 4.8.3 NSFW 缩略图降级强度 —— 我的裁决

PM 授权我决定强度。以下是我的选择与理由。

**裁决：面板内的 NSFW 项使用「完全不透明占位块」+ 全部元数据抑制**，不做模糊。

```
┌──────────────────┐    ┌──────────────────┐
│                  │    │                  │
│      [盾]           │    │      [盾]           │
│    NSFW 内容      │    │    NSFW 内容      │
│                  │    │                  │
│  ┆ 在主窗口查看 ┆ │    │  ┆ 在主窗口查看 ┆ │
└──────────────────┘    └──────────────────┘
   默认态：完全不透明      悬停/聚焦后：仅出现跳转按钮
```

**为什么不做模糊（这是最重要的判断）**：

1. **模糊在壁纸场景下等于没做**。壁纸的识别特征是**构图** —— 一片山脊、一条海岸线、一个人物剪影。这些轮廓在 20px 模糊半径下依然清晰可辨。而模糊会让用户以为"已经保护了"，从而放松警惕。**给出虚假的安全感比不给保护更危险。**

2. **Apple 自己的选择是「隐藏」而非「模糊」**。macOS 的「隐藏通知预览 / Sensitive Content」开启后是**完全不显示内容**，不是模糊。Apple 在明确的敏感内容场景下选择了更强的手段，我们应遵循平台惯例而非发明更弱的方案。

3. **元数据比像素更容易泄露**。分辨率、标签、收藏数、上传者名字 —— 这些**文字**往往直接点明内容性质。旧版 hover 浮层把它们全压在缩略图上，是最大的泄露口。**抑制元数据的保护收益高于模糊像素。**

**降级规格**：

| 元素 | NSFW 项的处理 | 理由 |
|------|--------------|------|
| 缩略图 | **不透明** `--surface-raised` 占位块 + `checkmark.shield` 24px `--meta` + 「NSFW 内容」`--text-xs` | 遵循 macOS Sensitive Content 惯例 |
| 分辨率 | **隐藏** | 数值易被反推内容规格 |
| 收藏数 / 标签 / 上传者 | **隐藏** | 元数据泄露风险高于像素 |
| 纯度徽标 | **隐藏**（已由「NSFW 内容」文案表达） | 冗余 |
| hover 浮层 | **不显示任何信息浮层** | 唯一交互是「在主窗口查看」 |
| 唯一可用动作 | `arrow.up.forward.app` 16px +「在主窗口查看」-> 跳转主窗口对应壁纸 | [!] 把敏感内容的完整查看**迁移到私密场景**，而非在公开场景半允许 |
| VoiceOver | `accessibilityLabel("NSFW 内容，已在公开场景隐藏预览")` + `hint("在主窗口中查看完整内容")` | 状态必须可读，不能只靠视觉 |

**「在主窗口查看」是核心设计决策**：它不是妥协，而是正确的场景迁移。用户在公开场合点一下，App 打开主窗口（一个明确的私密动作，用户能看到自己在做什么），在那里完整浏览。既保护了公开场景，又没剥夺用户能力。

**降级仅限菜单栏面板**。主窗口是主动打开的私密场景，L2 开启后正常展示完整内容 —— 分层要表达的就是这个真实状态差异。

#### 4.8.4 搜索无结果时的显式提示（PM 补充的关键交互）

**PM 的判断我完全采纳**：静默返回空结果会让用户误判内容库规模。

当 **L3 关闭** 且 搜索/筛选结果为空 且 若开启 L3 则**有结果**时：

```
┌──────────────────────────────┐
│ [盾]                             │
│ 面板已隐藏 NSFW 内容          │  <- --text-md --fg
│                              │
│ 当前搜索「雾中森林」有 12 张  │  <- --text-xs --muted，必须含具体数字
│ NSFW 结果，未在此显示。│
│                              │
│ [开启本面板 NSFW]  [在主窗口打开]│  <- 两个明确出口
└──────────────────────────────┘
```

| 规格 | 值 |
|------|-----|
| 高度 | 与结果列表同高（复用列表容器，不跳动布局） |
| 图标 | `checkmark.shield` 24px `--meta`（**不用** `--warn` 色 —— 警告色会让人以为出错了） |
| 标题 | `--text-md` `--fg` |
| 说明 | `--text-xs` `--muted`，**必须含具体数字**（「12 张」）—— 具体数字比「有结果」更可信，也暗示内容库规模正常 |
| 主操作 | 「开启本面板 NSFW」—— 直接打开 L3 并重跑查询（一次点击完成，不需两步） |
| 次操作 | 「在主窗口打开」—— 跳转主窗口 |
| 键盘 | `⏎` = 开启本面板 NSFW；`⇧⏎` = 在主窗口打开 |

**判定逻辑**：仅当「结果为空」且「移除 NSFW 门禁后有结果」时才提示。若移除门禁后同样为空，那是真实的无结果，走标准空态文案（§6.5）。

[!] **不允许的实现**：把 NSFW 结果静默过滤后显示标准空态「没有匹配的壁纸」。这会让用户以为 wallhaven 上没有这张图。

### 4.9 错误状态六分类（架构师实测 + PM 裁定，不可合并）

**实测结论**：wallhaven 对非法参数返回 **5xx 而非 4xx**，且 5xx 响应体是 **HTML 页面而非 JSON**（PM 复现确认）—— **无法靠响应体区分「参数非法」与「真实故障」**。

后果：统一显示「加载失败」会让用户无法判断是自己的筛选条件错了还是 wallhaven 挂了，等于把排查成本转嫁给用户。

**五类互斥，UI 必须分开呈现**：

| # | 触发条件 | 文案（须指向可执行的下一步） | 禁止显示 | 图标 |
|---|---------|------|---------|------|
| 1 | **本地校验未过，请求未发出** | 「筛选条件无效」<br>「分辨率筛选值无效，请重新选择。」→ 下一步：**改参数** | 「加载失败」 | `exclamationmark.triangle` |
| 2 | **5xx 且本地参数合法** | 「wallhaven 服务暂时不可用」<br>「请稍后重试。**你的筛选条件没有问题。**」→ 下一步：**等重试** | 「加载失败」 | `exclamationmark.triangle` |
| 3 | **`URLError` 族** | 「网络不可用」<br>「请检查网络连接。」→ 下一步：**检查网络** | 「加载失败」 | — |
| 4 | **429** | 「请求过于频繁」<br>「将在 **{seconds}** 秒后自动重试。」→ 下一步：**等待倒计时** | 静默失败 | — |
| 5 | **2xx 但解码失败** | 「服务返回了无法解析的数据」<br>「请稍后重试。」→ 下一步：**重试** | 「网络异常」 | `exclamationmark.questionmark` |
| 6 | **401（密钥无效）** | **内联态**：「密钥无效 / 请检查后重新输入」<br>**全局态**：「API 密钥无效 / 请在设置中检查」→ 下一步：**检查 Key** | 「加载失败」「请求失败」 | `exclamationmark.triangle` 16px |

**[!] 第 5 类实际很少见，文案应简洁**

架构侧已确认携带 `Accept: application/json` 时 **5xx 响应体也是可解析的 JSON**（`{"message": "Server Error"}`），该头为硬约束。因此解码失败实际很少见。

| [!] 禁止 | 原因 |
|--------|------|
| 在第 5 类写推测性归因（「可能是参数不被接受，或服务临时异常」） | 既然罕见且原因不确定，坦率告知无法解析 + 建议重试即可。**推测会让用户去猜一个可能不存在的问题** |

错误态设计可假定「拿到的状态码与消息可靠」，不必为「解析失败导致信息丢失」设计宽泛兜底。

**[!] 规则出处：区分性文案铁律（team-lead 提议升级为三方通用自查规则）**

> **任何写了「A 还是 B」的文案/分类，必须能回答「依据什么可观测信号区分 A 和 B」。答不出来，说明是把选择题丢给了用户。**

这条规则的价值在于**它能自我执行** —— 不需要查文档、不需要查 SDK，靠自查就能做。适用范围不止错误文案：PM 写验收标准、架构师定错误映射、我写文案，三方都适用。

**它在本项目已捕获的实例**（证明这条规则不是空谈）：

| 原本的写法 | 问题 | 按规则修正 |
|-----------|------|-----------|
| 「检查网络连接后重试。**若持续失败，可能是 wallhaven 服务暂时不可用**」 | 无法区分信号 —— 用户不知道该查网络还是该等待 | 拆为第 2 类（5xx 且参数合法）与第 3 类（`URLError` 族），区分信号 = 本地参数是否合法 |
| 「服务异常」把「2xx 但解码失败」并入其中 | 无法区分 —— HTML 错误页与真实服务故障响应体相同 | 独立为第 5 类，区分信号 = HTTP 状态码是否 2xx |

**判定方法**：写完文案后自问一句 ——「如果这条是A、那条是B，UI 侧靠什么可观测信号判断当前是A 还是 B？」答不出来就说明合并过度了，必须拆。

**[!] 「加载失败」这四个字在本项目是明确禁止的**

用户无法从统一文案判断是自己的筛选条件错了还是服务挂了。这四个字的本质是**把排查成本转嫁给用户**。

| 类 | 为什么必须独立 |
|----|--------------|
| [!] 第 5 类 | 实际很少见（见下方说明），但万一发生真实原因与网络无关，归入网络错误会让用户查错方向 |
| 第 4 类 | 必须显示**具体秒数**（架构师实测可从响应头拿到重试时间）。不给数字的「稍后」等于没给信息 |

**[!] 第 5 类可以简化（PM 更正后的结论）**

架构侧已确认：携带 `Accept: application/json` 请求头时，**5xx 响应体也是可解析的 JSON**（`{"message": "Server Error"}`），且该头为硬约束。

| 项 | 结论 |
|----|------|
| 解码失败的实际发生率 | **很低**。既然响应头已保证 JSON，5xx 也能解析 |
| 文案应如何设计 | **简洁**。不再需要承载过多推断 |
| [!] 禁止 | 写「可能是请求参数不被接受，或服务临时异常」这类**推测性归因** |
| 原因 | 既然罕见且原因不确定，坦率告知「无法解析」+「重试」即可。**推测会让用户去猜一个可能不存在的问题** |

错误态设计可以假定「拿到的状态码与消息是可靠的」，不必为「解析失败导致信息丢失」设计宽泛兜底。

### 4.9.1 API Key 无效的内联态（PM 裁定）

401 有一个特殊之处：**它几乎总是发生在「密钥设置页」这个上下文里**，因为只有粘贴 Key 这个动作会直接产生 401。

[!] **同一个 401 在两个上下文里需要两套设计**：

```
密钥设置页（内联态）              其他界面（全局态）
┌──────────────────────┐
│ API 密钥 *│
│ ┌──────────────────┐ │
│ │ ••••••••••••••│ │
│ └──────────────────┘ │
│ [!] 密钥无效            │  <- 内联，输入框正下方 8px
│     请检查后重新输入。│     不要跳转，用户已在该页
│     确认复制时没有      │
│     包含前后空格。│
└──────────────────────┘
```

| 上下文 | 标题 | 正文 | 操作 | 关键规则 |
|--------|------|------|------|---------|
| **内联（设置页）** | 「密钥无效」 | 「请检查后重新输入。确认复制时没有包含前后空格。」 | 用户**直接修改输入框**，无额外按钮 | [!] **绝对不要写「打开密钥设置」** —— 用户已经在这个页面，跳转是荒谬的 |
| **全局（其他界面）** | 「API 密钥无效」 | 「wallhaven 返回 401。请在「设置 › 密钥」中检查密钥是否复制完整。」 | 「打开密钥设置」按钮 | 此时用户在其他界面，需要引导 |

| 内联态规格 | 值 |
|-----------|-----|
| 位置 | 输入框**正下方** 8px，不弹 toast |
| 图标 | `exclamationmark.triangle` 16px |
| 色彩 | `--danger`（这是输入校验失败，不是提示） |
| 输入框状态 | 边框转 `--danger`；focus 时**保留 danger** 而非切回 info 蓝 |
| [!] 清除时机 | 用户**开始编辑时立即清除**（`clearOnEdit`），不等重新提交 |

**[!] 为什么要单独做这个态**

用户输入 Key 是在做一个明确的操作（粘贴一个字符串）。失败时他需要知道是「**这个字符串不对**」而不是「应用或网络有问题」。这两种归因导致完全不同的后续动作 —— 前者去检查 Key，后者去检查网络。**给错归因会让用户做无用功。**

这也印证了 §4.9 的区分性文案铁律：401 与网络错误的区分信号是**服务端返回的状态码**，清晰可判。

**[!] 401 与参数非法互斥（架构师实测）**

服务端**先校验认证、再校验参数**，无条件 401 优先。但参数非法的请求**根本不会发出**（被本地预校验拦截），因此：

> 401 只会在「参数合法但 Key 无效」时出现 —— 两者不会同时显示。

这简化了 UI：**不需要设计「密钥错误 + 参数也错误」的组合态**。

**[!] NSFW 权限不足的表现形式（PM 修正，设计师已grep 确认无旧表述）**

**401 只有单一含义：Key 无效。与 purity 无关。** PM 原PRD 曾写「401 需区分 NSFW 无权限与 Key 无效，用 SFW/NSFW 双探测实现」—— **该规范是错的**，架构师实测已推翻（ADR-007 Trap 16）。

实测结论：

| 请求 | 返回 |
|------|------|
| `purity=001`（NSFW）+ 无效 Key | **401** |
| `purity=001`（NSFW）+ 无 Key | 200，**total=0** |
| `purity=100`（SFW）+ 无 Key | 200，total=501661 |

**NSFW 权限不足表现为「有效 Key + 200 + total=0」，不是 401。** 这个模型更简洁 —— **不需要任何探测逻辑**，只有一个判据。

**[!] 对设计的直接影响：NSFW 三层门禁的错误呈现要改**

原设计假设「NSFW 内容因无权限而不可见」会走错误态。**实际不���** —— 它返回 200 空结果，与「筛选项太窄导致无结果」在响应层面**完全一样**。

| 场景 | 实际返回 | UI 应呈现 |
|------|---------|----------|
| Key 无效 | 401 | [!] **错误态**（密钥无效） |
| NSFW 权限不足 | 200 + `total=0` | [!] **空态**，不是错误态 |
| 筛选条件太窄 | 200 + `total=0` | [!] **空态** |

**这带来一个必须解决的设计问题**：后两种在响应层面无法区分，而**它们的正确处理完全不同**。

| 情况 | 用户需要的动作 | 若用错空态会怎样 |
|------|--------------|-----------------|
| NSFW 权限不足 | 去开启 API 访问授权，或用主窗口 | 用户以为是自己筛选条件的问题，反复调筛选 |
| 筛选条件太窄 | 放宽筛选 | 用户反复调整却始终出不来 |

**解决方案（三层门禁已给��上下文信息）**：

| 判定顺序 | 逻辑 |
|---------|------|
| 1 | 响应 `total=0` → 显示**常规空态** |
| 2 | [!] 若当前请求包含 NSFW 筛选条件（`purity` 含 sketchy/nsfw）**且** 结果为空 → 追加一句「当前密钥可能未获授权浏览 NSFW 内容，可在「设置 › 密钥」确认，或在主窗口查看」 |
| 3 | 该追加句**不改变空态的中性视觉**（不用警示色），仅作为 `--text-xs` `--muted` 的补充说明 |

[!] **关键约束**：这句提示**不得带任何警示色或错误图标** —— 否则就违反了 §4.9.2「空态必须完全中性」，且会让用户在无需重试的情况下反复重试。

[!] **这与 §4.8.4 的 NSFW 门禁提示是同一类问题的两种形态**：
- §4.8.4：L3 关闭时结果为空 → 提示「有 N 张 NSFW 结果未显示」（因为**我们知道有结果**）
- 本节：请求含 NSFW 条件但 `total=0` → 提示「可能未授权」（因为**我们不知道服务端有什么**）

区别在于确定性：前者我们知道确切数量，后者只能推测。所以措辞必须不同 —— 前者「有 12 张未显示」是确定的，后者「可能未授权」必须表达不确定性。

#### [!] 验证端点决定错误分流的档数（PM 实测 + 设计师复现）

**PM 实测发现原规范缺陷**：原 F5 指定用 `/settings` 端点验证，但该端点对无效 Key 返回 **404 而非 401**（因为 `/settings` 是「读取用户设置」，仅在用户已开启 API 访问授权时才返回数据）。后果：一个**完全有效**的 Key（未授权设置访问那类用户）会被判为无效，用户根本配不进去。

**PM 已修正为走 `/search` 验证。设计师独立 curl 复现，四项全部一致**：

| 端点 | 无效 Key | 无 Key |
|------|---------|--------|
| `/search`（带 `apikey`） | **401** `{"error":"Unauthorized"}` | 200（匿名可正常浏览） |
| `/settings` | **404** `{"error":"Nothing here"}` | 401 |

**因为改走 `/search`，设置页的四类结果**：

| 服务端返回 | 含义 | 文案该提 Key 吗 | 视觉 |
|-----------|------|----------------|------|
| **200** | Key 有效（或未提供 Key） | —— | 成功态 |
| **401** | Key 无效 | **是** | 内联 `--danger` |
| **404** | [!] **在本页不可达** —— `/search` 不返回 404（见下方边界测试） | —— | —— |
| **5xx / 网络** | 服务端故障 | **否** | 内联但不提 Key |

**[!] 404 档在本页不可达 —— 不做进 UI**

设计师实测 `/search` 的五类边界，**无一返回 404**：

| 请求 | 返回 |
|------|------|
| 无效 Key | 401 |
| 超长 Key（300 字符） | 401 |
| 特殊字符 Key | 401 |
| 空 `apikey=` | **200** |
| 纯空格 `apikey=%20` | **200** |
| Tab `apikey=%09` | **200** |
| 换行 `apikey=%0A` | **200** |
| 混合空白 `apikey=%20%09%20` | **200** |
| 完全无 `apikey` 参数 | **200** |
| 单个点号 `.` | 401 |
| **有效 Key** | 200 |

`/search` 是核心查询端点，只在认证失败时给 401，**不存在 404 分支**。为一个不可达状态做 UI 分流是死代码。

**[!] 但 404 必须作为已知事实记录在案**

若未来引入 `/settings`（例如读取用户偏好设置），**404 会立即变成一个真实且语义完全不同的分支**：

| 状态 | 含义 | 文案 |
|------|------|------|
| 404 | 该密钥**未授权访问账号设置**（Key 本身可能完全有效） | 「该密钥未授权访问账号设置，Key 本身可能有效」 |

[!] **绝不能把 404 说成「密钥无效」** —— 两者归因完全不同：前者要引导用户去开启授权，后者要引导用户重新复制 Key。混淆会让用户白白重输一次却依然失败。

**[!] 边界测试还发现一个更隐蔽的失败模式：空 Key 会被误判为有效**

| 请求 | 返回 | 问题 |
|------|------|------|
| `apikey=`（空值） | **200** | [!] 服务端把空 Key 当匿名请求 |
| `apikey=%20`（空格） | **200** | 同上 |
| `apikey=%09`（Tab） | **200** | 同上 |
| `apikey=%20%09%20`（混合空白） | **200** | 同上 |
| `apikey=.`（单个点号） | **401** | 正常判定为无效 |
| 任意非空字符串 | **401** | 正常判定为无效 |

**这意味着：若用户输入空 Key 或纯空白，服务端会返回 200，我们会误判「Key 有效」并保存一个空 Key** —— 用户以为配好了，实际浏览时行为与未配置完全一致（因为 wallhaven 本来就允许匿名浏览）。

**[!] 关键实测结论：判定与长度无关（PM 修正初版方案，设计师复现确认）**

设计师逐长度实测：

| 长度 | 1 | 2 | 3 | 5 | 8 | 10 | 32 | 64 |
|------|---|---|---|---|---|---|----|----|
| 返回 | 401 | 401 | 401 | 401 | 401 | 401 | 401 | 401 |

**唯一分界线是「非空 vs 空」，长度完全无关。**

[!] 初版方案写的「trim 后长度 ≥ 8 才放行」是**错的** —— 用户输入 `"a"` 会因长度不足被拦截，但服务端其实会返回 401 明确告知无效。**预校验反而掩盖了服务端能提供的准确信息。**

**[!] 正确的判定逻辑（PM 提出，设计师认可）**

> **必须是「非空 → 看 401/200」，而不是「看 200 就认为有效」。**

| [!] 禁止 | 原因 |
|--------|------|
| 把 200 当成「Key 有效」的**充分条件** | 这是错误根源。200 只能作为「非空前提下的结论」 |
| 用长度阈值替代非空判断 | 实测证明长度与判定无关。`"a"` 长度不足但服务端能准确告知无效 |
| 只判 `isEmpty` 而不 trim | 纯空格/Tab/混合空白 trim 后才是空 |

| 防护层 | 要求 |
|--------|------|
| [!] **第一层：非空判断（唯一实质判断）** | trim 后判空。为空 → 判为「请输入 API Key」，**不发请求** |
| 第二层：长度（**可选**防御） | 可保留额外下限，但**不得替代非空判断**。若采用，不得因长度不足而拒绝一个服务端本可准确判定的输入 |
| 保存按钮状态 | 输入框为空或仅空白时，「保存」保持 disabled |
| [!] **trim 范围** | 必须覆盖**所有 Unicode 空白**：空格、Tab、换行及混合 |

**[!] trim 范围的实测依据**

设计师测试了常见空白变体，**全部返回 200**（即全部会被误判为有效）：

| 输入 | 返回 |
|------|------|
| 单空格 `%20` | 200 |
| 多个空格 `%20%20%20` | 200 |
| Tab `%09` | 200 |
| 换行 `%0A` | 200 |
| 空格+Tab 混合 `%20%09%20` | 200 |

**结论**：`whitespacesAndNewlines` 的 trim 是必要的，但**不能只 trim 空格** —— 用户从各种来源粘贴（网页复制、终端、编辑器）时带入的 Tab 与换行同样会导致误判。

### 4.9.2 空态与错误态的视觉语言必须分离

[!] **空态与错误态的唯一区分信号是「请求是否发出」**：

| 类型 | 请求状态 | 视觉语言 |
|------|---------|---------|
| **错误态** | 请求发出但失败 | [!] 带警示色（`--warn` / `--danger`）+ 警示图标 + 明确行动指引 |
| **空态** | 请求已发出且 `200` + 空数组 | **完全中性** —— 无任何警示色、无错误图标、无警告语气 |

**空态的禁止项**（PM 明确要求）：

| 禁止 | 后果 |
|------|------|
| [!] 任何警示色 | 用户以为操作失败 |
| [!] 任何错误图标 | 同上 |
| [!] 错误类文案（「没有找到」像在报错） | 同上 |

**如果空态带警示色，用户会反复重试** —— 因为他们会认为「刚才失败了，再试一次可能就成功了」。这是空态与错误态混在一起最实际的后果。

| 规格 | 值 |
|------|-----|
| 空态图标 | 可用中性图标或不用图标。[!] **不要**用 `exclamationmark.triangle` / `xmark.circle` / `folder.badge.questionmark` |
| 空态容器 | `1px solid var(--border-soft)` + `--surface`（与其他空态完全一致） |
| 空态标题 | `--text-lg` `--fg` |
| 空态正文 | `--text-md` `--muted` |
| 空态操作 | `--accent` 文字按钮（不是 `--danger`、不是警示色） |

### 4.9.3 密钥设置页

侧栏「设置 › 密钥」的完整设计。这个页面很小但承载了最敏感的输入。

```
┌──────────────────────────────────────┐
│  API 密钥│
│  ┌────────────────────────────────┐  │
│  │••••••••••••••••••        [眼]│  │  <- SecureField + 显示/隐藏
│  └────────────────────────────────┘  │
│  在 wallhaven.cc 申请 API Key（[前往申请]）│  <- help text
│                                        │
│  [!] 密钥无效                            │  <- 内联错误（触发条件见 §4.9.1）
│      请检查后重新输入。│
│      确认复制时没有包含前后空格。│
│                                        │
│  ┌────────────────────────────────┐  │
│  │验证中…                        │  │  <- 校验中状态
│  └────────────────────────────────┘  │
│                     [取消]  [保存]        │
└──────────────────────────────────────┘
```

| 区域 | 规格 |
|------|------|
| 输入框 | `SecureField`，宽度按内容（不撑满），`--input-height` 32px |
| [!] 显示/隐藏切换 | `eye` / `eye.slash` 16px 图标按钮，在输入框右侧内联 |
| help text | `--text-xs` `--muted`：「在 wallhaven.cc 申请 API Key」+ 「前往申请」文字按钮（`--accent`） |
| [!] 粘贴处理 | 从剪贴板粘贴时**自动去除前后空格与换行** —— 这是最高频的失败原因，且用户不会自己想到 |
| [!] trim 覆盖所有空白 |  **必须覆盖 Tab 与换行**，不只空格。实测空格/Tab/换行/混合空白全部返回 200（用户从网页、终端、编辑器粘贴会带入这些） |
| [!] 去空格后判空 | trim 之后必须再判空。纯空白输入会被 trim 成空串，若直接发送，服务端返回 200，会被误判「Key 有效」 |
| [!] 本地预校验 | trim 后判空 → 直接判「请输入 API Key」，**不发请求**。绝不能靠服务端 200 判断有效性 |
| [!] 不设长度下限 | [!] 实测长度与判定无关（1 字符与 32 字符都返回 401）。若设长度下限，不得因长度不足而拒绝一个服务端本可准确判定的输入 |
| 校验端点 | **`/search`**（不是 `/settings`，见 §4.9.1） |
| 校验时机 | 点「保存」时校验，不在输入时校验（避免每次打字都发请求） |
| 校验中 | 「保存」按钮转 spinner，**同时禁用重复提交** |
| 校验失败 | 内联错误（§4.9.1），不弹 toast |
| 校验成功 | 密钥存 Keychain，关闭 sheet，HUD「密钥已保存」 |
| [!] 回显 | 已保存状态**永不回显明文**，只显示 `••••••••` + 「已保存」标记 |

**9 态覆盖**：

| 状态 | 表现 |
|------|------|
| 默认 | 空输入框，「保存」disabled（`opacity 38%`） |
| 输入中 | 「保存」enabled |
| 校验中 | 「保存」转 spinner 且 disabled |
| [!] 无效（401） | 内联错误（§4.9.1），输入框边框 danger |
| 有效 | 关闭 + HUD |
| 错误（5xx/网络） | 内联错误，但文案是服务/网络原因（**不是**「密钥无效」）——[!] 这点很重要：不能把服务端故障说成密钥问题，否则用户会去反复改 Key |
| 空提交 | 「保存」保持 disabled，**不触发校验也不发请求** |
| [!] 纯空白提交 | trim 后为空 → 同上。[!] 服务端对 `apikey=`、空格、Tab、换行均返回 **200**，若不做本地预校验会误判「Key 有效」 |
| 已保存 | 输入框 disabled + 「已保存」标记 + 「更换密钥」文字按钮 |
| Edge | 超长粘贴（>512 字符）→ 输入框横向滚动，不换行；>512 时仍可保存（服务端返回 401） |

**[!] 已保存态不提供「删除密钥」按钮** —— 若需要，改为「更换密钥」入口，二次确认时提供移除选项。理由：删除会让用户突然失去浏览能力，且这个动作不可逆。

**[!] 我此前的设计错误：把两个原因合并成一句话**

v2.3 的 `errorNetwork` 写的是：「图片加载失败，检查网络连接后重试。**若持续失败，可能是 wallhaven 服务暂时不可用**。」

一句话同时说了两个原因，用户无法判断该检查网络还是该等待—— **合并两个不同原因的错误文案等于没说**。已拆分为第 2 类与第 3 类。

**保留的第六态**：`errorKey`（401 API 密钥无效）可独立判定，不与上述五类重叠。

**[!] 空态与错误态必须视觉可区分**

架构师实测：`resolutions=9999x9999`、`ratios=99x99` 这类**格式合法但语义无效**的参数，wallhaven 返回 **200 + 正常 JSON**，不是错误。

所以存在「结果为空但无任何错误提示」的状态，空态设计需区分两种：

| 类型 | 含义 | 文案 | 视觉 |
|------|------|------|------|
| **格式非法** | 参数超出支持范围，请求未发出 | 错误态（第 1 类） | [!] 用 `--warn`，带 `exclamationmark.triangle` |
| **格式合法但无匹配** | 条件有效，wallhaven 上真没这组合 | 空态：「没有符合此组合的壁纸」<br>「筛选条件本身有效，但 wallhaven 上没有同时满足这些条件的图片。」 | 空态视觉，**无警示色** |

[!] **绝不能让这两种共用一个「没有找到壁纸」** —— 否则用户会以为是自己操作错了，实际是内容库真的没有这组合。语义上前者是「条件无效」，后者是「条件有效但无匹配」。

## 5. Motion Specification

### 5.1 时长阶梯

| 场景 | 时长 | 缓动 |
|------|------|------|
| 按下/开关切换 | 80ms `--motion-instant` | ease-out |
| hover / 状态确认 | 150ms `--motion-fast` | ease-out |
| 面板展开 / 浮层出现 | 220ms `--motion-base` | spring(0.30, 1.00) |
| 跨屏过渡 / sheet | 320ms `--motion-slow` | spring(0.36, 1.00) |
| 瀑布流分批入场 | 420ms 上限 `--motion-cascade` | spring(0.42, 1.00) |

**所有 spring 的 `dampingFraction` = 1.0**（临界阻尼 = 零过冲）。这直接对应 P0 红线第 6 条 —— 桌面端弹跳显廉价，macOS 的沉稳感来自无过冲的收敛。

### 5.2 SwiftUI 实现

```swift
// [OK] 正确：临界阻尼，零过冲
.animation(.spring(response: 0.30, dampingFraction: 1.00), value: state)

// [OK] 快速切换（按钮、chip）
.animation(.spring(response: 0.22, dampingFraction: 1.00), value: isSelected)

// [OK] 简单淡入淡出用离散曲线
.animation(.easeOut(duration: 0.15), value: isHovered)

// [NG] 禁止：弹跳
.animation(.bouncy, value: state)          // P0 红线
.animation(.spring(response: 0.3, dampingFraction: 0.55), value: x)  // damping < 0.7 = 弹跳

// [NG] 禁止：CSS 式弹跳曲线
cubic-bezier(0.68, -0.55, 0.265, 1.55)
```

### 5.3 macOS 特有的 spring 响应式体验

**"跟手"的三条原则**：

1. **直接操控的视图必须零延迟跟手**
   裁剪手柄、速度滑块、屏幕分配拖拽 —— 这些是 pointer-down 期间持续跟手的元素，**不加动画**或用 80ms 以下。任何延迟在直接操控中都会读作"卡"。

2. **结果反馈用 spring 表达物理因果**
   弹簧的收敛曲线暗示"这个东西被放下了"，比 `easeOut` 更有物理感。但只有 1.0 阻尼版本。

3. **不要给图片加载完成加弹跳**
   图片淡入用 `--motion-fast` 150ms 线性淡入即可。图片是内容不是控件，加动效会显得"轻浮"。

### 5.4 符号动效（SF Symbols）

macOS 26 的 `symbolEffect` 可用，但必须克制：

| 允许 | 禁止 |
|------|------|
| 收藏成功 -> `.symbolEffect(.bounce, value: isFavorited)` | 每次 hover 都动 |
| 壁纸切换 -> `.symbolEffect(.replace, value: iconName)` | 循环播放的动效 |
| 下载完成 -> `.symbolEffect(.checkmark, value: didDownload)` | `.pulse` 常驻 |

[!] 全部 symbolEffect 在 `reduceMotion` 下需显式禁用：
```swift
.symbolEffect(.bounce, value: isFavorited) { isActive, effect in
    isActive && !reduceMotion ? effect : nil
}
```

### 5.5 减少动态效果

```swift
@Environment(\.accessibilityReduceMotion) var reduceMotion

// 全局收敛
var anim: Animation { reduceMotion ? .linear(duration: 0.001) : .spring(response: 0.30, dampingFraction: 1.00) }
```

必须同步关闭的：骨架屏微光、瀑布流入场 stagger、live 圆点呼吸、`symbolEffect`。

### 6.3 动态壁纸的可访问性

这是**最有责任的设计问题** —— 动态壁纸持续消耗 CPU/GPU，耗电，且对认知障碍与注意力障碍用户可能造成干扰。

| 设计 | 说明 |
|------|------|
| **默认关闭** | 动态壁纸必须用户主动开启，绝不默认自动播放 |
| **一键全停** | `⌘⇧K` 立即暂停所有动态壁纸。菜单栏面板提供显眼开关 |
| **自动降级** | 检测到电池供电 -> 自动降到省电模式（15fps + 降分辨率），并在 HUD 告知「已切换省电模式」 |
| **自动暂停** | 全屏应用 / 视频播放 / 会议中（macOS `NSWorkspace` 可检测）-> 自动暂停。这是 Wallpaper Engine 的用户最认可的功能 |
| **可见状态** | 菜单栏图标在动态壁纸播放时显示小圆点（`--live-indicator`），随时知道"正在耗电" |
| **性能预算** | 编辑器内显示实时 CPU/GPU/内存，超预算时主动警告并建议降低速度 |
| **认知负担** | 动态壁纸不参与窗口缩略图与 Mission Control（避免视觉混乱） |
| **系统开关尊重** | 尊重 `NSWorkspace` 的 Reduce Motion 与系统级降低透明度 |

### 6.4 对比度与视觉可达性

| 项 | 要求 | 实测 |
|----|------|------|
| 正文 | ≥ 4.5:1 | `--fg-2` 8.6:1 [OK] |
| 辅助文字 | ≥ 4.5:1 | `--muted` 4.7:1 [OK] |
| 图片上文字 | ≥ 4.5:1 | `--scrim-image` 底 78% 黑 + `#F2F5F8` ≈ 13:1 [OK] |
| UI 组件边框 | ≥ 3:1 | `--border` 白色 12% 对 `--surface-base` ≈ 2.1:1 [!] 见下 |

**[!] 已知项处理**：`--border`（白 12%）对深色底只有 ~2.1:1，不达 3:1。这是 macOS 全平台的普遍做法（macOS 自身分隔线也如此），因为边框不承担**唯一**信息载体（元素有底色差 + 位置双重区分）。但**输入框、开关、选中态**这三类必须用 ≥3:1 的边框 —— 已用 `--input-border-focus` / `--card-ring-selected` / `--border-accent` 满足。

**高对比度模式**：系统开启时，`--border` -> `--p-fg-tertiary`（4.7:1），`--muted` -> `--p-fg-secondary`。

## 8. Typography

**字体决策：不打包任何字体文件。**

理由：① Apple HIG 要求 macOS 应用使用系统字体，打包会带来版本不一致与中文字形渲染劣化；② SF Pro 是全球排版质量最高的界面字体之一，"用系统字体"在 macOS 上不是"偷懒"，是**正确答案**；③ 反射拒绝列表明确排除"用 Inter 装 macOS"这类做法。

| 角色 | 栈 | 用途 |
|------|-----|------|
| Display | `-apple-system, "SF Pro Display", "PingFang SC"` | 仅 22px+ 标题 |
| Body | `-apple-system, "SF Pro Text", "PingFang SC"` | 全部正文（SF Pro 的 Optical Size 会自动切换） |
| Mono | `ui-monospace, "SF Mono", "JetBrains Mono"` | **仅**：分辨率数值、快捷键、API Key 遮罩 |

**基准字号 13px**（不是 Web 的 16px）—— macOS 界面惯例是 13px。

**字距规则**：
- 正文 0
- 12px 以下 `+0.02em`（小字在深色底上需要额外字距才不糊）
- 标题 ≥22px `-0.015em`
- ALL CAPS 侧栏分组标题 `+0.06em` 且大写

**字重三级**：`400`（正文）/ `510`（按钮、小标题）/ `590`（主标题、数值强调）

[!] **不要用 `.ultraLight`**（旧版 `MainHeader.swift:18`、`FilterPartLabel.swift:207`、`ImagePanel.swift:93` 全在用）—— 极细字重在深色底上几乎不可读，是 2020 年代 UI 的标志，也是"廉价感"来源之一。

## 9. Do's & Don'ts

### [OK] Do

1. **让 UI 消失，让壁纸说话** —— 控件默认半透明/低对比，只在 hover 或聚焦时显形
2. **所有筛选维度可视且可枚举** —— 分段控件、可视比例图形、色板；不用 Slider 表达离散枚举
3. **数值用等宽字体** —— 分辨率、文件大小、快捷键，让小数点对齐，这是专业感的细节
4. **尊重图片真实宽高比** —— 永不强制裁切，壁纸被裁是产品致命伤
5. **hover 延迟 90ms** —— 防止鼠标扫过瀑布流时逐张闪现
6. **强调色每屏 ≤2 处** —— 琥珀是标点符号，不是正文
7. **玻璃只给 chrome** —— 工具栏/侧栏/菜单栏面板/Sheet，内容层绝不玻璃
8. **零过冲动画** —— `dampingFraction: 1.00`，桌面端弹跳显廉价
9. **主色提取做环境衬底** —— 详情页可从壁纸提取主色作极低透明度（≤0.10）窗口底衬，让 UI 与内容呼应；[!] 绝不用在强调色或任何文字上
10. **错误说清原因与出路** —— 「API 密钥无效，在「设置 › 密钥」中重新填入」而非「操作失败」
11. **敏感内容的保护要「真保护」** —— 面板 NSFW 项完全不透明 + 元数据全抑制，不做模糊（模糊在壁纸场景等于没做，且给出虚假安全感）
12. **静默过滤是错的** —— 内容被门禁隐藏时必须显式告知数量（「有 12 张未显示」），不能让用户误判内容库规模
13. **壁纸裁切计算一律用物理像素** —— `frame.size × backingScaleFactor`，逻辑点会导致 Retina 混用时静默算错
14. **设计任何控件前先确认 API 能力边界** —— 我曾设计五项填充方式，其中「平铺」「居中」系统根本无法实现。控件存在的意义是承载真实能力。本项目已在同类错误上踩坑三次（PM 以为有平铺 / 我设计两个不存在的选项 / 架构师把居中与平铺写成同档），**附录 A 是三方唯一事实来源，未覆盖的必须实测 SDK 头文件并记录**
15. **模糊就给出具体倍数** —— 「放大约 2.7 倍」而非「可能模糊」。用户要数字不要形容词
16. **常规风险提示内联、不阻断** —— 低分辨率预警是信息不是错误，绝不阻止用户设置
17. **按屏计算的状态绝不跨屏沿用** —— 切换屏幕必须重算所有依赖屏参数的文案与数值（倍数、尺寸、倍率）
18. **不同原因的错误绝不合并成一句话** —— 「检查网络或服务异常」等于让用户自己猜该查哪边。五类错误各有独立文案、图标与操作
19. **数字用用户能理解的量级** —— 388,406 显示为 38.8万。原始整数会让用户误判规模
20. **每条错误文案都要能回答「用户现在该做什么」** —— 改参数 / 等重试 / 检查网络 / 等倒计时 / 重试。答不出来就是把选择题丢给用户。**规则出处见 §4.9「区分性文案铁律」**（三方通用自查规则）
21. **不支持的格式在导入前就说清** —— 空态里主动写出「不支持 WEBM、MKV、GIF」，比用户导入失败后才知道便宜得多

### [NG] Don't

1. [NG] **emoji 作为功能图标**（P0）—— 全部 SF Symbols
2. [NG] **紫->粉渐变主视觉**（P0）—— 琥珀纯色，且每屏 ≤2 处
3. [NG] **Slider 选离散枚举**（P0）—— 这是旧版最严重的语义错误
4. [NG] **裸 hex 硬编码**（P0）—— 一律 `var(--token)` / SwiftUI 语义色资产
5. [NG] **空洞占位文案**（P0）—— 「Welcome to」「Get started」全部禁止；按钮写「设为壁纸」不写「确定」
6. [NG] **千篇一律 Hero**（P0）—— 本产品**没有 Hero**，首屏就是内容本身（瀑布流）。这是刻意的：壁纸 App 的 Hero 就是壁纸
7. [NG] **弹跳缓动**（P0）—— `cubic-bezier(0.68,-0.55,0.265,1.55)` / `.bouncy` / `dampingFraction < 0.7`
8. [NG] **彩色左边框卡片**（`border-left: 3px solid accent`）—— AI 味特征。区分状态用**边框整体颜色**或底色，不用侧边强调条
9. [NG] **图片当功能图标** —— 旧版 `StarBtn`/`TagBtn` 等位图必须全部清退为 SF Symbols
10. [NG] **`.ultraLight` 极细字重** —— 深色底不可读，2020 年代廉价感来源
11. [NG] **彩虹导航** —— 侧栏每个 tab 一个饱和色（紫/绿/橙/红/粉/蓝）互相打架。全部统一 `--fg-2`，仅选中项用琥珀
12. [NG] **内容属性编码进装饰** —— 旧版用 purity 决定图片边框色（黄/红）。应该用 `checkmark.shield` 徽标表达安全等级
13. [NG] **强制裁切图片比例** —— 旧版 `imageWidth * 2.0/3.0` + `.fill`
14. [NG] **每个 section 都用相同淡入动画** —— 揭示动画应匹配揭示的内容（图片入场用淡入，详情展开用位移+淡入）
15. [NG] **居中大标题 + 副标题 + CTA** —— 本产品无此模式
16. [NG] **用模糊当作敏感内容保护** —— 壁纸的识别特征是构图，模糊轮廓仍可辨。macOS Sensitive Content 的做法是隐藏，不是模糊
17. [NG] **静默过滤内容后显示标准空态** —— 会让用户误判内容库规模。必须显式说明「有 N 张被隐藏」
18. [NG] **用逻辑点做壁纸裁切计算** —— `NSScreen.frame` 是逻辑点，Retina 屏需乘 `backingScaleFactor`。这是静默错误，用户不会报 bug，只会觉得 App 做得差
19. [NG] **用屏序下标做 per-screen 状态 key** —— 拔插外接显示器后屏序会变，必须用 `NSScreen.displayID` 等稳定标识
20. [NG] **把用不了的 V2 功能做成置灰按钮** —— 跨屏拼接 MVP 不做就是不做。置灰项消耗用户信任，且会被反复点击问为什么
21. [NG] **在 UI 或文案里出现「平铺」「居中」「拉伸」** —— 这三个在 macOS 壁纸 API 中不存在（详见 §4.5 语义边界表）
22. [NG] **给填充色做手选色板** —— Apple 官方明确建议不为此呈现 UI。改为自动派生 + 重置入口
23. [NG] **接受「预览与实际不一致」的折扣版功能** —— 做不到预览即所得就砍。一次不一致会让用户对所有预览失去信任
24. [NG] **在瀑布流卡片上加动态壁纸标识** —— wallhaven 无任何视频内容（120 条样本实测），加了就是永不出现的假功能（§4.6.0）
25. [NG] **写「加载失败」**（P0 禁止）—— 本项目五类错误各有独立文案，这四个字本质是把排查成本转嫁给用户
26. [NG] **导入不支持的格式时静默失败或笼统报错** —— 必须给文件名 + 不支持原因 + 可执行出路（P0，§4.6.0）

### 10.3 已知的坑（务必规避）

| 坑 | 后果 | 规避 |
|----|------|------|
| `Slider` 用于枚举 | 旧版已犯，筛选体验崩坏 | 用 `IHSegmented` / `IHRatioGrid` |
| `Array(repeating:)` 生成瀑布流列 | 全等高，退化成网格 | 按最短列 append（真 masonry） |
| 图片先给固定高度再加载 | CLS 抖动 | 预计算 `aspectRatio` |
| `.aspectRatio(contentMode: .fill)` | 壁纸被裁 | `.fit` + `maxHeight` 约束 |
| `EaseIn` 用于出现动画 | 起步慢收尾急，读作"卡" | 出现用 `easeOut`，消失用 `easeIn` |
| hover 无延迟 | 扫过瀑布流时整屏闪烁 | 90ms 出现延迟 + 40ms 消失延迟 |
| `dampingFraction: 0.6` | 弹跳，廉价感 | 一律 1.00 |
| 玻璃嵌套 | 渲染异常/性能崩 | 同一 `GlassEffectContainer` |
| 自定义 blur radius | 与系统材质不匹配 | 用系统 glassEffect，不写数值 |
| `NSWorkspace.setDesktopImageURL` 不加选项 | 多屏 + 缩放模式全错 | 传 `.fillClipToBoundaries` / `.fillScreen` 等 |
| 用 `NSScreen.frame`（逻辑点）算壁纸裁切 | Retina 混用时静默错位，用户以为壁纸质量差 | `frame.size × backingScaleFactor` 算物理像素（PM F2 验收项） |
| 用 `NSScreen` 数组下标做 per-screen key | 拔插显示器后状态串屏 | 用稳定标识（`displayID` / `CGDirectDisplayID`） |
| NSFW 项做模糊处理 | 构图轮廓仍可辨，且给出虚假安全感 | 完全不透明占位 + 元数据全抑制 |
| NSFW 被门禁后显示标准空态 | 用户误判内容库规模 | 显式提示「有 N 张 NSFW 结果未显示」 |
| 把跨屏拼接做成置灰按钮 | 用户反复点击找原因，消耗信任 | MVP 不渲染该选项 |
| API Key 明文入 UserDefaults | 安全问题 | Keychain + 遮罩回显 |
| 裁切焦点全局共用一份 | 16:10 与 21:9 裁掉的区域不同，构图被毁 | 按屏独立记忆，key 用稳定标识 |
| **UI 暴露系统做不到的控件** | 我曾设计五项填充方式，其中「平铺」「居中」系统根本无法实现 | 设计任何控件前先确认 API 能力边界（PRD 附录 A-2） |
| **填充色让用户手选** | Apple 官方建议不为此呈现 UI；且手选是负担 | 从 `colors` 自动派生 +「恢复自动派生」重置入口 |
| **做「预览与实际不一致」的折扣版焦点调整** | 一次不一致会让用户对所有预览失去信任 | 预览渲染的就是写入系统的成品图；做不到就砍功能 |
| **低分辨率预警只写「可能模糊」** | 用户无法判断严重程度 | 算出具体放大倍数（「放大约 2.7 倍」）+ 物理像素对比 |
| **预警倍数跨屏沿用** | 倍数是上次的但当前屏不同，用户认为系统算错 | 按选中屏独立重算；重算时机=切屏/切模式/热插拔/缩放变化；测试覆盖「同一壁纸+三块不同分辨率屏」 |
| **`usingColorSpace` 当作会抛异常** | 误用 try/catch 或漏掉 false 分支 | 它返回 `Bool`；失败时**不传该 key** 走系统默认色 |
| **转换失败后换个近似色** | 近似色可能与壁纸更不协调 | 整体回退系统默认色，宁可普通不可违和 |
| **用 `type:` 参数验证「无视频内容」** | 该参数被服务端忽略（`type:video` 与 `type:image` 返回相同 total），基于它得不出任何结论 | 只用三条有效证据：多维度采样 file_type 分布 / `/api/v1/video` 404 / 文档检索零命中 |
| **预览与写入各自实现裁切** | 预览与实际不一致，用户对所有预览失去信任 | 共用同一预裁切产物对象；禁止两套实现 |
| **写入与预览用不同滤镜/色调处理** | 预览与实际不一致 | 单一渲染管线，两处共用 |
| **错误文案写「检查网络，或可能是服务异常」** | 无法区分信号，把选择题丢给用户 | 按 §4.9 区分性文案铁律拆分为独立状态 |
| **用脚本批量改设计文件后靠脚本自检** | v2.4漏扫 emoji、v2.6 JSON 语法错误、v2.9 脚本引入 emoji —— 三次都是自动化流程中人工嵌入的内容未被同一流程校验 | **写入与校验必须分离**：改完立刻跑一次独立校验脚本（emoji 扫描 + JSON 合法性 + 章节结构），不使用写入脚本自检。架构师的 `scripts/verify-docs.py` 是更好的范式：**刻意不参与任何写入**，判断逻辑与生成逻辑完全解耦 |
| **清理 emoji 后留下多余空格** | 删emoji 留下「。 」这类痕迹，文档质量下降 | 清理后检查中文标点后的多余空格；两个校验器都不查这个，需人工或脚本补 |

### 10.4 设计冲突的默认归属与例外（team-lead 裁定）

**默认规则**：Phase 3 实现中出现设计与实现冲突时，**默认是实现走偏，而非设计没考虑到**。

**例外条件（必须触发设计侧修正）**：若实测证明某个 API 能力与设计假设不符（如 v2.2 那次五档填充方式收敛为两档），则：

| 要求 | 说明 |
|------|------|
| [!] 必须同步修正设计侧 | 设计文档与 token 都要改，不能只改实现 |
| [!] 必须走「记录判断错误原因」流程 | **不得静默改动** |
| 记录内容 | 原设计是什么 → 错在哪→ 正确结论是什么 → 为什么错 |
| 目的 | 保持「谁错了、为什么错」的可追溯性，避免三年后重犯同一个直觉错误 |

**本项目已有的两例**（均已按此流程留痕）：

| 版本 | 原设计 | 错误原因 | 正确结论 |
|------|--------|---------|---------|
| v2.2 | 五档填充方式（填充/适应/拉伸/平铺/居中） | 凭直觉假设 API 能力，未核实 SDK 头文件 | 仅「完整可见 / 填满」两档；平铺无法实现、居中非独立项 |
| v2.4 | 「图片加载失败，检查网络或服务异常」 | 合并两个不同原因的错误 | 五类不可合并，各有独立文案与信号 |

**为什么这条例外重要**：本项目已发生**五次同型错误**（PM 以为有平铺 / 我设计两个不存在的选项 / 架构师把居中与平铺写成同档 / 我合并两个错误原因 / PM 引用了被忽略的 type 参数）。五次都是「凭直觉假设而未核实一手来源」，且都是不同人在不同环节犯的同一种错。留痕的价值在于让这个模式本身变得可见。
