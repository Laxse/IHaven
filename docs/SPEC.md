## 0. 全局约束（动手前必读）

以下约束**违反时无编译错误、测试全绿**，但会产生静默错误 —— 即失败只发生在运行时，且用户界面不会给出任何异常提示。

### 0.1 四条 API 调用禁令

| # | 禁止 | 后果 | 详见 |
| --- | --- | --- | --- |
| 1 | 不要用 `/settings` 验证 API Key | 它对无效 Key 返回 404 而非 401，会把**完全有效的 Key 判为无效**，用户根本配不进去 | §9.0 |
| 2 | 不要用 `200` 判定 Key 有效 | 空 Key 与「未配置」在服务端**不可区分**（均返回 200），用户会「保存成功」而实际未配置 | §9.0 |
| 3 | NSFW 探测请求**不要带用户筛选条件** | 会复现主请求的 `total=0`，完全失去区分能力 | §9.2 |
| 4 | 不要用 `/settings` 的 `data.purity` 判定 NSFW 能力 | 实测：有效 Key 下它返回 `["sfw","sketchy"]`（**不含 nsfw**），同一把 Key 搜 `purity=001` 却返回 `total=339163`。照它判定会把「可用」静默错判为「不可用」 | §9.2 |

### 0.2 设计侧禁止项

设计侧禁止项集中在 §7.4，包括：

| 禁止 | 详见 |
|---|---|
| MVP **不做**跨屏拼接（不渲染该选项，也不做置灰按钮） | §7.4.3 |
| WEBM/MKV **不得**提供「转换为 MP4」 | §7.4.6 |
| 动态壁纸卡片**不得**加播放标记 / 动效徽标 | §7.4.6 |
| 填充方式**不得**出现「平铺/居中/拉伸」 | §7.4.7 |
| 填充色**不做**手选色板（只给「恢复自动派生」） | §7.4.7 |
| NSFW 空态**不得**用警示色 | §7.4.4 |
| NSFW 缩略图**不做**模糊处理 | §7.4.7 |

### 0.3 为什么这四条需要前置

这四条禁令是**调用约定**，不是代码结构 —— `convention-gate` 检查 import 结构，无法机器检查它们。**只有文档留存。**

而它们恰好属于「违反无编译错误、测试全绿、只有静默错误」这一类 —— 最需要前置曝光，故放在开头而非仅留在 §9。




> **门禁能证明「规则被检出」，但无法证明「规则被读到」。**
> 下面四条**没有任何自动检查能覆盖** —— 它们是调用约定而非代码结构，
> 违反时**不产生编译错误、测试全绿、只有静默错误**。
> 详见 §9.0，同步固化于 `ARCHITECTURE.md` §6.4「三条全局禁令」。

## 6. 协作约定（文档编辑）

> Spec 是执行契约，**格式不一致会让读者怀疑内容是否经过核对**。
> 因此本项目的编辑权限按「内容/ 格式」分界：

| 维度 | 规则 | 理由 |
|---|---|---|
| **内容** | **严格不代改** —— 设计内容归设计侧，API 契约归架构侧 | 越界会掩盖责任归属 |
| **格式与错字** | **任何一方可直接修**，但须告知 | 见下|

**为什么格式错误的危害不对称**：

- **措辞分歧** → 实现方困惑，**会来问**（成本：一次澄清）
- **错字 / 格式不一致** → 读者怀疑整份文档是否经过核对，**不会说**（成本：文档可信度受损，且隐蔽）

**因此**：
1. 发现对方文件里的错字/ 格式问题，**直接修并告知**，不必等确认
2. 修内容则不行 —— 即使是明显的错误，也应报告而非动手
3. 判断依据：**这个改动会不会改变读者对「谁做的判断」的归属感** —— 会则不代改，不会则可代改

### 6.1 判据的适用条件（架构师修正，team-lead 采纳）

判据**不全都依赖失败样本积累**。核实后区分两类：

| 用法 | 依据 | 是否需要历史失败样本 |
|---|---|---|
| 算「捕获 0 个真问题」 | 需实测数据 | **是** |
| 算「一次性 vs 永久」 | **只需判断生命周期** | **否** |

**第三例的验证**（否决 Spec 章节引用门禁时）：
只需问「这个问题在 Spec 合并后会不会消失？」—— 会，则捕获的是一次性问题，
引入的是永久检查，净收益显然为负。**无需任何历史失败样本。**

**Phase 3 实践含义**：
- 第一类用法：评估新检查项时「真问题数」需实测（Phase 3 会有代码 bug 级样本）
- 第二类用法：**Phase 3 立即可用，不需等新失败样本**

**若只给判据不给适用条件**，Phase 3 可能误以为「所有判断都需先攒够失败样本」——
那会让它在第一个检查项前就卡住。

### 6.2 大文件（≥500 行）禁止整体重写（2026-10-08 事故后定）

**已发生的事故**：`docs/PRD.md`（1723 行）在 23:03 之后的工作区版本中丢失约 490 行 —— 「五、核心功能（RICE 排序）」168 行、「八、非功能需求 + 数据埋点」39 行、「附录 A-13 ~ A-19」284 行。由产品侧比对 HEAD 后发现，并以**纯插入**还原（三个块逐块取自 HEAD，未改动工作区任何既有内容）。

**根因已排除脚本**：`scripts/*.py`、`scripts/*.sh`、`docs/*.py` 全部只读，无任何写模式的文件打开操作。事故来自对大文件的整体重写 —— 重写者手中的内容不完整时，覆盖后的文件不报错、不警告，且看起来像一次正常编辑。

| 文件规模 | 允许的编辑方式 |
|---|---|
| 新文件 / < 500 行 | 可整体写 |
| **≥ 500 行** | **只允许增量编辑，禁止整体重写** |

**为什么必须写进 Spec 而不是口头约定**：覆盖式丢失**不产生任何错误信号** —— 门禁全绿（它检查内容合规性，不检查完整性）、diff 看起来正常、编译无关。发现它的唯一方式是有人拿它和 HEAD 逐项比对，而没有人会例行做这件事。

**检出手段**：改动任何 ≥500 行的文档后，用 `git diff --stat` 确认删除行数在预期内。删除行数异常大即为事故信号（本例据产品侧报告为 864 删）。

**保护窗口的边界（不要把「有检查」当成「有保护」）**：自动检查 `heading-regression` 比对的是**工作区 vs HEAD**，因此它**只覆盖未提交状态**。一旦回归被 commit，HEAD 本身就变成坏基线，此后该检查**永远绿**——本轮那 490 行如果当初被 commit 进去，这个检查会从事故发生的那一刻起一直显示通过。

**实际保护窗口是：编辑后、commit 前。** 要覆盖已提交的回归，只能在 commit 后额外比对 `HEAD~1`；该项作为只读报告（不阻断）列入解冻后待办，见 `GATE-USAGE.md`。

这条边界本身就是我们反复在防的那类问题：**能力看起来存在、实际不存在**。门禁存在 ≠ 它拦得住这个场景。

**还原方式**：发现后**不要整体回滚**（会抹掉工作区里同样未提交的有效编辑），应逐块从 HEAD 取回并插回原位。

#### 7.4.4 NSFW 四态探测判定

**[!] 401 只有单一含义（Key 无效），与 purity 无关。** NSFW 权限不足表现为「有效 Key + 200 + `total=0`」。

**探测请求**：`GET /search?purity=001`

| 探测结果 | 判定 | UI |
|---|---|---|
| `401` | Key 已失效 | 走鉴权失败态 |
| `total=0` | **确定**：权限不足 | 空态 +「此 API Key 无 NSFW 访问权限，请到 wallhaven 账号设置开启」 |
| `total>0` | **确定**：筛选过窄 | 常规空态 + 放宽建议，**不显示任何权限文案** |
| 探测自身失败 | 网络 / 5xx | 退化为常规空态，**不显示权限文案**（宁可少提示，不可误报） |

**三个前置条件，缺一不可**：

| # | 前置条件 | 缺失后果 |
|---|---------|---------|
| 1 | 本地已配置 API Key | 未配 Key 时探测结果与「权限不足」相同 → 误报到用户无法完成的任务 |
| 2 | 探测为固定宽查询，**不带任何用户筛选条件** | 携带用户筛选会复现主请求的 0 → 完全失去区分能力 |
| 3 | 探测结果会话内缓存 | 重复请求浪费预算（性能问题，不影响正确性） |

[!] **换 Key 必须失效缓存** —— 否则新 Key 的权限状态会被旧缓存覆盖。

**[!] 作用域声明**：本判定**仅适用于「请求含 NSFW 筛选条件且结果为空」**。非 NSFW 场景的空结果走常规空态，**不使用探测**。

**[!] 空态必须完全中性** —— 无任何警示色、无错误图标。理由：空态带警示色会让用户在**无需重试**的情况下反复重试。

#### 7.4.5 错误六分类（不可合并）

`apiErrorClass` 枚举值（`design-tokens.json` → `content.microCopy.errorStatesMustNotMerge.classes`）：

| class | 触发 | 文案方向 | 禁止显示 | 图标 |
|---|---|---|---|---|
| `errorInvalidParams` | 本地预校验未过，请求未发出 | 「分辨率筛选值无效，请重新选择」 | 加载失败 | `exclamationmark.triangle` |
| `errorServiceUnavailable` | 5xx 且本地参数合法 | 「wallhaven 服务暂时不可用」 | 加载失败 | `exclamationmark.triangle` |
| `errorNetwork` | `URLError` 族 | 「网络不可用，请检查连接」 | 加载失败 | — |
| `errorRateLimit` | 429 | 「请求过于频繁，将在 X 秒后自动重试」 | 静默失败 | — |
| `errorMalformedResponse` | 2xx 但解码失败 | 「服务返回了无法解析的数据」 | 网络异常 | `exclamationmark.questionmark` |
| `errorKey` | 401 | 「密钥无效，请检查后重新输入」 | 加载失败 / 请求失败 | `exclamationmark.triangle` 16px |

**[!] 六类互斥，不得合并为统一提示。**

**401 的双上下文**：

| 上下文 | 标题 | 正文 | 操作 |
|---|---|---|---|
| **密钥设置页（内联）** | 「密钥无效」 | 「请检查后重新输入。确认复制时没有包含前后空格。」 | [!] **不得显示「打开密钥设置」** —— 用户已在此页 |
| **全局（其他界面）** | 「API 密钥无效」 | 「wallhaven 返回 401。请在「设置 › 密钥」中检查。」 | 「打开密钥设置」 |

[!] **内联态位置**：输入框正下方 8px，不弹 toast；输入框边框转 `--danger` 且 focus 时**保留 danger**；**用户开始编辑即清除错误**。

[!] **5xx / 网络错误时，密钥页文案不得提及 Key** —— 否则用户会反复修改 Key，而真正原因是服务端故障。

**Key 验证端点**：`GET /search`（**禁止用 `/settings`** —— 它对无效 Key 返回 404 而非 401，会把完全有效的 Key 判为无效）。

[!] **空 Key / 纯空白必须本地拦截** —— 服务端对空 `apikey=` 与空白均返回 **200**，误判会导致保存空 Key 而用户以为配好了。trim 须覆盖空格 / Tab / 换行 / 混合。**不得设长度下限**（实测长度与判定无关）。

#### 7.4.6 动态壁纸导入四态

**素材来源：本地导入**（wallhaven 无任何视频内容，已实测 120 条样本 + 端点 404 + 文档检索确认）。

| 格式 | 处理 | 用户行动 |
|---|---|---|
| MP4 / MOV（H.264 / HEVC） | 导入成功 | 直接使用 |
| **GIF** | 引导转换态 | **能转换** —— 「转换为 MP4 后重试」 |
| **WEBM / MKV / 其他** | 不支持态 | **只能换素材** —— [!] **不得提供「转换为 MP4」**（需重编码，耗时且损画质） |
| 损坏 / 无法解析 | 损坏态 | 换一个文件（`--danger`） |

[!] 四态**视觉必须可区分** —— GIF 与 WEBM/MKV 虽都是导入失败，但用户行动完全相反。

[!] **探测在导入时做一次**，不在播放时做；**不静默转换、不静默跳过**。

[!] **不得在瀑布流卡片上设计任何「动态壁纸」标识**（播放标记 / 时长标签 / 动效徽标）—— 网络内容里不存在这种卡片。

[!] **循环接缝提示**：导入时检测首尾帧差异 → 不连续则导入后**一次性非阻断**提示（「此视频首尾帧不连续，循环时可能有明显跳变」+「仍然使用」）；播放中不重复；**首尾帧接近则不提示**。

#### 7.4.7 其他行为契约

### 8.6 收藏页 NSFW 呈现（team-lead 裁定，2026-10-08）

**结论：不显示 + 明确告知。**

设计侧提出的矛盾成立：L3 面板开关关闭时，若收藏列表仍显示 NSFW 项，
用户可通过收藏绕过 L3 门禁，与 §4.8.4 的门禁一致性要求冲突。

**裁定理由**：

| 方案 | 问题 |
|---|---|
| 显示 NSFW | L3 形同虚设 —— 用户可从收藏绕过，这是隐私门禁的漏斗 |
| 静默不显示 | 用户会问「我收藏的图怎么少了」，且数量对不上，更困惑 |
| **不显示 + 明确告知** | **采纳** —— 与菜单栏面板的 NSFW 门禁提示同构 |

**具体规则**：
1. 收藏列表复用瀑布流组件时，**L3 关闭状态下不渲染 NSFW 项的缩略图**
2. 列表顶部显示中性提示：「已隐藏 N 张 NSFW 收藏，开启 NSFW 显示」
3. 该提示用`--muted`，**禁用警示色** —— 用户没做错任何事，不该被警告
4. 计数必须显示**总数与隐藏数**（如「12 张收藏 · 已隐藏 3 张」），否则用户以为收藏丢了

**与既有门禁的一致性**：
- L2（应用总开关）关闭 → 全部 NSFW 不显示
- L3（面板开关）关闭 → **主窗口收藏页也不显示**（关键差异点）
- L2 + L3 均开启 → 正常显示

**这意味着 L3 的作用域不止面板**，而是「公开场合可见性」。
建议在 §4.8.4 的 L3 定义上补一句作用域说明（Phase 2 处理，不在本次改 DESIGN.md）。

## 9. API 契约（架构侧，2026-10-08）

本节定义 `WallhavenClient` 的接口行为。所有结论来自实测，**每条禁令都有对应的静默错误**——签名能表达「怎么调」，不能表达「不要这样调」，而后者才是出问题的地方。

### 9.0 四条全局禁令（违反即产生静默错误，无编译错误）

| 禁止 | 后果 |
| --- | --- |
| **不要用 `/settings` 验证 Key** | 它对无效 Key 返回 404 而非 401，会把完全有效的 Key 判为无效 |
| **不要用 `200` 判定 Key 有效** | 空 Key 与「未配置」在服务端不可区分（均 200），用户会「保存成功」而实际未配置 |
| **探测请求不要带用户筛选条件** | 携带筛选会复现主请求的 `total=0`，完全失去区分能力 |
| **不要用 `/settings` 的 `data.purity` 判定 NSFW 能力** | 实测：有效 Key 下该字段为 `["sfw","sketchy"]`（不含 nsfw），同一 Key 搜 `purity=001` 却返回 `total=339163`。会把「可用」静默错判为「不可用」，无编译错误、无运行时报错 |

**第四条的通则形式**：`/settings` **整体不得作为任何能力或状态判据** —— 不只 `data.purity`。它描述的是账号**偏好设置**，服务端从未承诺它等于**搜索权限**。`200` 只说明「该端点这次可读」，不说明「它回答的是你问的问题」。

尤其注意这条推论是错的：「`/settings` 对无效 Key 返回 404，那么它返回 200 + 完整数据时内容就可信」。200 与内容可信之间没有推导关系。

### 9.1 Key 验证

```swift
/// 验证 API Key。仅支持 /search —— /settings 语义不同不可用。
func verifyKey(_ key: String) async throws -> KeyVerdict
```

**判定逻辑（方向不可写反）**：

```
1. 本地预校验：key.trim() 为空或纯空白 -> 抛 .emptyKey，**不发请求**
2. GET /search?page=1，header X-API-Key: <key>
3. 401  -> .invalidAPIKey
   200  -> .valid          // 这是「非空前提下的结论」，不是「有效」的充分条件
```

实测依据：

| `X-API-Key` | HTTP | 语义 |
| --- | --- | --- |
| 头缺失 | 200 | 匿名 |
| 空串 / 纯空格 / 制表符 | **200** | **等同匿名，服务端无法区分** |
| 任意非空非法值 | 401 | Key 无效 |
| `/settings` + 无效 Key | **404** | 语义不同，禁止用于验证 |

**长度阈值不得替代非空判断**：实测长度与判定无关（1 字符与 300 字符均 401）。长度阈值会先拦截并给出更含糊的提示，掩盖服务端本可提供的准确 401。

**Key 不得出现在**：UserDefaults / SQLite / 日志 / 崩溃报告。只经Keychain，且只放 `X-API-Key` 头。

### 9.2 NSFW 权限探测

**请求必须是固定宽查询**：`GET /search?purity=001`，**不带任何其他筛选条件**。

判定：

| 探测结果 | 结论 |
| --- | --- |
| `total=0` | 权限不足（确定） |
| `total>0` | 权限正常，用户那次 0 是「筛选过窄」 |
| 401 | Key 失效 |

**为何不能带筛选**：固定宽查询的结果只取决于权限，与用户筛选无关。携带筛选时，探测与主请求都会返回 0，判定失效。

**实测依据（有效 Key，2026-10-08，curl + `X-API-Key` + `Accept: application/json`）**：

| 请求 | HTTP | 结果 |
| --- | --- | --- |
| `/search?purity=001`（带 Key） | 200 | `total = 339163`，返回 24 条 |
| `/search?purity=110`（带 Key） | 200 | `total = 952572` |
| `/search?purity=001`（匿名） | 200 | `total = 0` |
| `/settings`（带 Key） | 200 | `data.purity = ["sfw","sketchy"]`，`per_page = "24"`，`ai_art_filter = 1` |

最后一行是**关键反例**：`/settings` 声称账号不含 nsfw，同一把 Key 却能检索 339,163 条 NSFW。两个接口对同一能力给出矛盾答案，因此：

- 「读 `/settings` 的 `purity` 决定 NSFW 档位 / 是否渲染 NSFW 开关」是**禁止实现**；
- NSFW 能力的**唯一**判定依据是 `purity=001` 探测的 `total`，正负各一个样本均已实测闭合（`total>0` = 有能力，`total=0` = 无能力）。

（本表记录实测**全量**字段；ARCHITECTURE §6.4.0 与 ADR-007 Trap 17 只摘与判据相关的字段。粒度差异是有意的，不是遗漏 —— 判据文档不需要携带 `ai_art_filter` 这类与能力判定无关的值。）

**三条前置条件**（缺任一即误报）：

1. **本地已配置 API Key** —— 未配 Key 时探测同为 `total=0`，会引导用户「去开通一个他还没有的 Key 的权限」
2. **主请求 `total=0` 且 `data` 为空**
3. **主请求含 NSFW 类别** —— 非 NSFW 的空结果是筛选过窄

**作用域声明**（与 Spec §7.4.4 一致）：本判定**仅适用于「请求含 NSFW 筛选条件且结果为空」**。非 NSFW 场景走常规空态，**不使用探测**。

**探测结果会话内缓存**：权限不会中途改变，缓存避免重复消耗限流预算。换 Key 必须失效缓存。

### 9.3 401 的单一含义

| 场景 | HTTP | 结果 |
| --- | --- | --- |
| NSFW + 无效 Key | 401 | Key 无效 |
| **NSFW + 无 Key** | **200** | **`total=0`** |
| SFW + 无 Key | 200 | 正常数据 |

**401 只表示 Key 无效，与 purity 无关。** 匿名请求 NSFW 返回 200 + 空数组。

因此：**不要做 SFW/NSFW 双探测来分类 401** —— 401 只有一个含义。NSFW 权限不足表现为「已配置有效 Key + NSFW 请求 200 + `total=0`」。

### 9.4 参数校验（客户端负责，服务端不可信）

| 参数 | 本地校验 | 不通过时 |
| --- | --- | --- |
| `atleast` | `^\d+x\d+$` | **不发该参数** |
| `page` | `>= 1` | 停止翻页，不发请求 |
| `ratios` / `resolutions` | **封闭枚举** | 构造请求前抛出 |
| `q` | 直接放行 | —— |

**`ratios` 非法值是最隐蔽的一个**：`ratios=99x99` 返回 HTTP 200 + `total=5005` + 24 条数据，但那些数据 `ratio` 全为 `1`（1:1 方图）。**服务端静默匹配「比例≈1」，无任何错误信号**，用户只会认为「这个比例的壁纸本来就少」。

**`atleast` 不做上界校验**：`atleast=50000x50000` 格式合法、服务端正常接受，返回 200 + 空数组。这是「格式合法但无匹配」，走空态不走错误态。

### 9.5 响应处理顺序（顺序错误即产生误导性错误）

```
1. 拿到 (data, response)
2. 先判 response.statusCode      <- 必须第一步
3. 非 2xx -> 直接走错误分支，**完全不碰 data**
4. 2xx   -> 才尝试 JSONDecoder 解码
```

**禁止先解码再判状态码。** 服务端错误响应体可能是 HTML（取决于 `Accept` 头），先解码会产生误导性的「数据解析失败」，把「筛选条件写错了」误报成「网络异常」。

**必须显式发送 `Accept: application/json`** —— 不带该头时错误响应体是 HTML 页面，把HTML 喂给解码器必然失败。

### 9.6 `APIError` 六分类（不可合并）

| 类别 | 触发 | 文案方向 |
| --- | --- | --- |
| `.emptyKey` | 本地预校验拦下，**请求未发出** | 请输入 Key |
| `.invalidParameter` | 本地格式校验未过 | 筛选值无效 |
| `.invalidAPIKey` | 401 | Key 无效 |
| `.serverError` | 5xx 且本地参数合法 | 服务异常 |
| `.networkUnavailable` | `URLError` 族 | 网络不可用 |
| `.rateLimited` | 429（带 `retryAfter`） | 请求频繁，X 秒后重试 |
| `.decodingFailed` | 2xx 但解码失败 | 服务返回无法解析的数据 |
| `.nsfwPermissionDenied` | 有效 Key + NSFW 请求 200 + `total=0` | 此 Key 无 NSFW 权限 |

**空态不是错误**：`200 + data: []` 是成功响应，UI 显示「没有符合此组合的壁纸」，不显示任何错误提示。

区分信号只有一条：**请求是否发出**。未发出= 错误态；已发出且 200 + 空数组 = 空态。

### 9.7 限流

45 次/分钟。令牌桶容量 45，匀速 0.75次/秒。429 时按 `Retry-After` 退避，不静默失败。

**探测请求的预算影响**：每会话最多 1 次（`total=0` 后 `last_page` 也是 0/1，用户不会继续翻页），加会话内缓存后平均接近 0。

### 9.8 未配置 Key 的结果集静默缩水（2026-10-08 实测）

| `purity` | 含义 | 匿名（无 Key） | 带有效 Key | 匿名可见比例 |
| --- | --- | --- | --- | --- |
| `100` | 仅 sfw | 501,662 | **626,387** | **80.1%** |
| `010` | 仅 sketchy | 122,667 | **326,186** | 37.6% |
| `001` | 仅 nsfw | 0 | **339,163** | 0% |
| `110` | sfw+sketchy | 624,329 | 952,572 | — |
| `111` | 全部 | 624,329 | **1,291,737** | — |

自洽验算：626,387 + 326,186 + 339,163 = 1,291,736 ≈ 实测 `111` = 1,291,737（差 1，库实时增长）；匿名侧 501,662 + 122,667 = 624,329（吻合）

**Key 门控覆盖全部三个档位，不只 NSFW。** 未配置 Key 时，SFW 也少 124,725 张。

**客户端无法检测这种缩水。** 它不是错误响应，是「正确的响应里少了数据」：HTTP 200、`total` 看起来合理、`data` 满 24 条、分页正常、`meta.query` 为 null。响应字段层面没有任何线索。

因此：**唯一对策是产品层提示，不是技术层校验**。实现者不得试图寻找一个「检测缩水」的字段 —— 它不存在。

产品规则：未配置 Key 时，应用必须**全局**提示「结果不完整」，且不限于某一 purity 档位。尤其注意 SFW 是默认档位，用户连「我勾了特殊档位」这个自我提醒都没有。

**不得用「返回了数据」推断「筛选完整生效」。**
