# ADR-015: 本地导入（F8）与动态壁纸播放（F9）落地 —— 统一导入项模型 + 单进程桌面层播放，XPC 隔离延后

## Status: Accepted (2026-10-15)

## Background

F8（本地图片导入）与 F9（动态壁纸播放）在 PRD 里被裁定为**同原子批次、顺序 F8 → F9**（PRD §5.2、附录 A-6b）：wallhaven 实测零视频内容（120 条样本 `file_type` 全为 `image/jpeg` / `image/png`），动态壁纸素材只能来自用户本地文件，因此 F9 无法独立交付，F8 的导入管线是 F9 的唯一入口。

架构侧已有两件关键裁定：

- **ADR-003**（Accepted 2026-10-08）：动态壁纸采用「桌面层窗口 + AVPlayerLayer，逐屏 XPC Service 隔离」，双层结构 = 静态层 `NSWorkspace.setDesktopImageURL` 设静帧兜底 + 动态层每屏一个 borderless `NSWindow` + `AVPlayerLayer`，`AVQueuePlayer` + `AVPlayerLooper` 无缝循环。
- **ADR-008**：不集成 FFmpeg、不依赖任何私有 API、**格式探测必须在导入时执行一次**，错误信息必须具体，禁止静默失败。

代码现状：侧栏 `NavItem` 已有 `.import`（`square.and.arrow.down`）与 `.live`（`play.circle`）两个占位 case，都走 `browsePlaceholder`；全仓无 `NSOpenPanel`、无拖放、无 AVFoundation 播放代码；GRDB 已到 `v2`（`favorite` / `applied` 两表）；原图与数据库路径在两处各自硬编码，无 `AppContainer` helper。

本轮必须回答、而文档没有答案的问题有四个：本地导入项的数据模型归属、导入产物的落盘位置、F9 播放在本轮的进程形态、以及 F8 验收标准里「本地项与网络壁纸混在同一瀑布流」如何落地。

## Decision

### 一、数据模型：单一 `ImportedWallpaper` + `ImportedKind`，一张表

```swift
public struct ImportedWallpaper: Codable, Identifiable, Sendable, Hashable {
    public let id: String            // 导入时生成的 UUID
    public let fileName: String      // 原始文件名（展示用）
    public let filePath: String      // 导入后本机容器内的原文件绝对路径
    public let thumbnailPath: String // ≤640px 缩略图（图片）或首帧 poster（视频）
    public let kind: ImportedKind    // .image / .video
    public let width: Int
    public let height: Int
    public let duration: Double?     // 仅视频（秒）
    public let fileSize: Int         // 字节
    public let seamless: Bool?       // 仅视频：首尾帧是否连续（SPEC §7.4.6）
    public let addedAt: Date
}
```

表 `imported`（GRDB 迁移 `v3`），列风格照 `applied`：URL/路径存 `.text`、日期存 `.double`（`timeIntervalSince1970`）、尺寸存 `.integer`、可空列不设 `.notNull`。

**不拆两张表**（本地图片一张、本地视频一张）：导入管线对两类文件共用同一条链路（探测 → 复制 → 生成缩略图/首帧 → 落库 → 进度/取消/摘要），拆表意味着这条管线要写两遍，而两者的差异只在「探测用哪个框架」和「多一个 duration / seamless 字段」。F9 只消费 `kind == .video` 的子集，由视图层过滤，不需要在存储层分开。

### 二、落盘位置：收敛到单一 `AppPaths`

`Application Support/IHaven/` 下两个子目录，与 ARCH §4.1 已规划的 `Wallpapers/` 与 `DynamicWallpapers/` 同名：

| 内容 | 路径 | 命名 |
| --- | --- | --- |
| 静态图原文件 | `…/IHaven/Wallpapers/<uuid>.<ext>` | 原样保留扩展名 |
| 静态图缩略图 | `…/IHaven/Wallpapers/<uuid>-thumb.jpg` | ≤640px 长边 |
| 视频原文件 | `…/IHaven/DynamicWallpapers/<uuid>.<ext>` | 原样保留扩展名 |
| 视频首帧 poster | `…/IHaven/DynamicWallpapers/<uuid>-poster.jpg` | ≤640px 长边，兼作卡片缩略图与静帧兜底 |

二进制一律不入 SQLite（ARCH §3.2 既定：BLOB 会使 DB 膨胀）。现状数据库路径（`Database.swift`）与原图临时目录（`ImageFileDownloader.swift`）两处各自拼路径，在出现第三处之前先收敛成一个 `AppPaths` 枚举 —— 三处漂移是「改了目录名漏改一处」这类静默 bug 的标准入口。

### 三、导入管线（F8 全量）

`Core/Protocols/LocalImporting.swift` 一个协议，实现在 `Infrastructure/LocalLibrary/LocalImportService.swift`：

```
importFiles(_ urls: [URL], onEvent: @escaping @MainActor (ImportEvent) -> Void) async -> ImportSummary
```

- 文件夹**递归扫描**，文件按名字排序保证进度可预期；`Task.isCancelled` 在每个文件之间检查 → **可取消**（PRD:695）。
- 每个文件：探测（图走 `CGImageSource`，视频走 `AVURLAsset`）→ 不支持则 **reject 并带具体原因**（不进入后续流程，ADR-008:70）→ 复制进容器 → 生成缩略图/首帧 → 落库 → `yield(.imported)`。
- 进度事件 `started / progress(done:total:current) / imported / rejected / finished(summary)`；摘要在 toast 与结果区各出一份。
- 入口两条：`NSOpenPanel` 多选（`Platform/System/SystemFileImportPanel.swift`，经 `FileImportPresenting` 协议注入，参照 `FileSavePresenting`）+ 主窗口拖放（`.dropDestination`）。
- **沙盒**：本项目无 entitlements（`Packaging/` 下无 `.entitlements`），非沙盒态，`NSOpenPanel` 选中的 URL 直接可读；不做 security-scoped bookmark（ARCH §4.1 把它列为 F8 管线组成部分，但那是在沙盒假设下的方案，本项目未开沙盒，引入它只会增加不会释放的资源）。

### 四、本地项并入瀑布流（PRD:697）

不把 `Wallpaper`（网络模型）改成能装本地项 —— 它的 20 个字段全是 wallhaven 响应形状，塞本地项进去会出现一半字段恒为假值。改为新增统一网格项：

```swift
public enum GridItem: Identifiable, Sendable, Hashable {
    case network(Wallpaper)
    case local(ImportedWallpaper)
}
```

`MasonryView<Item: Identifiable>` 的泛型约束不变，`BrowseViewModel` 暴露 `gridItems` = 网络项 + 本地项（本地项附在网络项之后）。本地项**不参与筛选与翻页**（筛选参数是 wallhaven 搜索参数，对本地文件无意义），卡片带「本地」标识（PRD:697 的可区分标识）。

> **[!] 本节已于 2026-10-18 被用户否决并撤销**（见 `OPEN-DECISIONS.md` 的「决策变更登记（2026-10-18）」）。
> `WallpaperGridItem` 枚举已删除，瀑布流直接用 `[Wallpaper]`，本地导入项不再混入任何检索页签，
> 只在「导入…」页签管理。本节保留作为历史记录，不要照它重新实现。

### 五、F9 播放：单进程桌面层窗口，XPC 隔离延后

本轮实现 ADR-003 双层结构中的**动态层**，进程形态取 ADR-003 里被降级为备选的「同进程」方案：

- `Platform/Wallpaper/DynamicWallpaperEngine.swift`（协议 `Core/Protocols/DynamicWallpaperPlaying.swift`）：每屏一个 borderless `NSWindow`，`level = CGWindowLevelForKey(.desktopWindow)`，`collectionBehavior = [.canJoinAllSpaces, .stationary, .ignoresCycle, .fullScreenNone]`，`sharingType = .none`，`ignoresMouseEvents = true`，`isOpaque = false` / 背景透明；每屏独立 `AVQueuePlayer` + `AVPlayerLooper`（**looper 必须持有为属性，否则循环静默停止**），`isMuted = true`，`videoGravity = .resizeAspectFill`（各屏按自身比例独立裁切，即 PRD 附录 A-6b 的差异化支点）。
- **静帧兜底**：播放前先用 poster 调 `NSWorkspace.setDesktopImageURL` 写静态层；停止时恢复进入前的壁纸 URL（`currentWallpaperURL(for:)` 先存后写）。锁屏/休眠（`screensDidSleep` / `sessionDidResignActive`）暂停播放，窗口不销毁。
- **内存压力**：`DispatchSource.makeMemoryPressureSource`，`.critical` 时全停并回落到静帧 + toast 提示；`.warning` 只暂停播放不销毁窗口。
- **一键全停** `⌘⇧K`（DESIGN §6.3 可访问性硬要求）：菜单命令 + 侧栏入口，销毁全部窗口并恢复静帧。

**XPC 逐屏隔离不在本轮。** 三条理由：①它需要在 `Package.swift` 新增 target、在打包脚本里嵌入 helper bundle 并处理其代码签名，属于独立的打包工程；②ADR-003:148-154 明确「沙盒/真机行为必须实测，不得假设可用或不可用」，而本轮不具备实测条件（无法在自动化环境里锁屏、切 Space、制造内存压力、观察多显示器拓扑）；③单进程版先把「交互、循环、静帧兜底、降级链」跑通，再拆进程，比同时改两套东西更容易定位问题。**这不是否决 ADR-003，是把它的一个已记录备选方案提前落地，并把隔离列为下一步。**

### 六、循环接缝检测（SPEC §7.4.6）

导入视频时采样首帧与尾帧，各自降到 8×8 求平均色，欧氏距离超过阈值即判定「首尾帧不连续」→ `seamless = false`。导入完成后出**一次性非阻断提示**（「此视频首尾帧不连续，循环时可能有明显跳变」+「仍然使用」），播放中不重复提示；首尾帧接近则不出。阈值与降采样尺寸写为常量并注释依据，不暴露给用户调。

### 七、文案纪律（PRD 附录 A-6b）

侧栏入口「动态壁纸」下固定一行「从本地视频文件导入」；导入空态**主动列出**支持格式（MP4/MOV，含 HEVC、H.264）与不支持格式（WEBM/MKV/GIF）及原因；主操作文案「从访达拖入你自己的视频文件」。全功能不得出现「库 / 精选 / 大全」这类暗示存在内容池的措辞。

### 八、单击卡片 = 播放 / 停止切换（补齐文档缺口）

DESIGN §4.6 原规定动态壁纸卡片「单击 = 打开编辑器」，但编辑器是 V3 功能（PRD §5.1，RICE 37.5 全表最低）。V2 交付播放时该动作**在文档里没有定义**（调研缺口第 9 条）。本轮补齐为：**单击 = 播放，再次单击同一张 = 停止**。这是唯一不依赖尚未存在的界面、且与「把这段视频设为壁纸」的用户预期一致的动作；不引入右键菜单 —— 悬浮浮层的两个按钮已覆盖播放与删除。

### 九、实测踩坑记录（2026-10-15，离线复刻脚本跑真文件验证）

以下两条都不是「读文档可知」的，是跑出来才发现的，且**都不会报错、只会让功能静默失效**：

1. **`AVURLAsset.loadTracks(withMediaType: .video)` 遇到静态图会抛错**（`AVFoundationErrorDomain -11828 "Cannot Open"`），不是返回空数组。若按「先视频后图片」的顺序探测，**所有静态图都会因这个错误被拒掉**。因此 `AVMediaProbe.probe` 必须先用 ImageIO 试图（零解码、只读属性），再走 `AVURLAsset`。
2. **`AVAssetImageGenerator` 的默认时间容差会吸附到关键帧**，首尾两次取样会拿到同一帧，循环接缝判定恒为「连续」。必须显式 `requestedTimeToleranceBefore/After = .zero`；且末帧时间取 `duration - 1ms`，正好取在 `duration` 上对部分文件越界失败。

验证方式（可复现）：用 `AVAssetWriter` 合成一段首尾颜色不同的 MP4 与一段同色 MP4，跑同一套判定逻辑，断言前者 delta 超阈值、后者 ≈ 0。实测 delta 分别 0.336 与 0.0。

## Rationale

### 一、导入项单独建模，而不是复用 `Wallpaper`

`Wallpaper` 的 20 个字段全部由 wallhaven 响应形状决定（`purity` / `category` / `views` / `favorites` / `colors` / `short_url` …）。本地文件没有这些概念，硬塞进去的每一个字段都会是恒定的假值，而假值比缺失更危险 —— 它会让后续所有「按 purity 过滤」「按上传者分组」的逻辑在本地项上静默出错。新增模型 + 统一网格项的成本是几十行，收益是两种来源的语义边界清晰。

### 二、探测前置而不是播放时探测

ADR-008:70 已裁定，理由是用户可感知的顺序：导入时探测 → 失败立刻告诉用户「这个文件不支持，原因是 macOS 没有 WebM 原生解码器，建议转 MP4」；播放时探测 → 用户先点「设为动态壁纸」，看到卡顿或黑屏，才知道文件不行。前者把错误成本放在用户还没有投入期待的时刻。

### 三、缩略图/首帧在导入时生成，而不是渲染时缩放

本地库的卡片是 `MasonryView`，一屏可能同时存在几十张卡。若直接喂原图 file URL，Nuke 会对每张卡解码整张 4K 图（单张约 30MB 位图）。导入时用 `CGImageSourceCreateThumbnailAtIndex`（`kCGImageSourceThumbnailMaxPixelSize = 640`，不整图解码，ARCH §6.2.2 既定做法）产出 ≤640px 缩略图，卡片成本降到几十 KB。视频首帧则一物二用：卡片缩略图 + 静帧兜底层，不必在播放时再抽帧。

### 四、单进程播放先落地，XPC 后置

ADR-003 选择 XPC 的核心收益是崩溃隔离（单屏解码崩溃不波及其他屏）与按屏回收。这是一个**可靠性增强**，不是**功能前提** —— 没有它，播放功能依然完整可用。把没有实测条件的隔离架构提前落地，风险是「两层同时有问题时分不清是哪层」；先落地单进程版，可用真机验证交互与稳定性，再拆进程，届时拆出来的问题是纯工程问题。

## Consequences

### 正面

- F8 四条验收标准全部有着落：拖入即入库不等待网络、文件夹递归 + 进度 + 取消、非图片文件拒绝并在摘要中列原因、本地项带标识并入瀑布流。
- F9 的「用户必须先看到能力边界，再看到空态」（PRD:311-313）由导入空态主动列支持/不支持格式满足，不需要用户先失败一次。
- 动态壁纸的差异化支点（多屏逐屏物理像素裁切播放）由 `resizeAspectFill` + 每屏独立窗口天然获得，复用 ADR-007 已验证的窗口配置与 looper 写法。
- 导入产物（缩略图/首帧）在导入时一次生成，列表滚动成本与网络壁纸持平。

### 负面

- 单进程播放：任一屏解码崩溃会带走整个 App。这是 ADR-003 已记录的已知代价，本轮显式接受。
- 导入会复制原文件进容器，磁盘占用 ≈ 原文件总和；不提供「引用原路径不复制」选项（那会让本地库依赖访达里的文件不被移动）。
- 循环接缝用 8×8 平均色判定，是**启发式**：缓慢的整体位移（如镜头缓慢横移）会被判为连续，而大色块切换会被判为不连续。宁可多提示一次，不可漏提示。
- `⌘⇧K` 是全局菜单命令，与「停止动态壁纸」语义绑定；若将来 F9 增加多套配置，该快捷键需要重新定义语义。
- 瀑布流里的本地项不参与筛选与翻页，用户可能对「为什么筛选对本地项无效」感到困惑 —— 由卡片上的「本地」标识与提示语承接。

### 未做（明确不在本轮）

- XPC 逐屏 helper（ADR-003 主体，延后）
- 动态壁纸编辑器 F11（V3）、GIF→MP4 一键转换（PRD §983-986 明确不与 F9 捆绑）
- WEBM/MKV 播放（不集成 FFmpeg）
- 跨屏拼接 F15（V2 末位）
- 导入进度条的分段取消（只能整批取消）

## Alternatives Considered

**本地项直接复用 `Wallpaper`，空字段填假值。** 会让 purity/category 等过滤逻辑在本地项上静默出错，且 `aspectThumb` 等派生属性对本地项无意义。否决。

**本地图片与本地视频分两张表、两条导入管线。** 两条管线 90% 代码相同，差异只有探测框架与两个字段；拆开必然漂移（PRD 附录 A-6b 已警告「不得为 F9 另建一套导入逻辑」）。否决。

**导入不复制原文件，只存访达里的路径。** 用户在访达里移动/删除原文件后本地库出现死链，且重设壁纸会静默失败。复制进容器让本地库自包含。否决。

**先用 XPC 版再优化。** 在无法实测 GUI 行为的环境里同时引入新 target、新打包流程与新进程边界，任何问题都无法归因。否决（延后而非否决）。

**视频缩略图用 `AVAssetImageGenerator` 实时生成而非导入时抽帧。** 每张卡每次出现都要异步抽帧，滚动时 CPU 持续占用；导入时一次抽帧、落盘复用，成本差一个量级。否决。
