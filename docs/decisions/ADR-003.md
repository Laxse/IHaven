# ADR-003: 动态壁纸采用桌面层窗口 + AVPlayerLayer，逐屏 XPC Service 隔离

## Status: Accepted (2026-10-08)

## Background

IHaven 需支持动态壁纸播放（PRD F9，RICE Score 288，PM 排入 V2）。要求：GIF/WEBM/MP4 硬件解码、逐屏独立循环、CPU 可控。

这是全项目技术风险最高的部分。team-lead 明确要求：架构必须进程隔离，并给出 CPU/内存/GPU 占用、内存泄漏风险、多屏可行性的深度方案，以及无显示器接入时的降级策略与内存压力下的自我回收。

PRD 另有一条硬性非功能需求：「主窗口崩溃后菜单栏功能仍存活」，以及核心主张「可测量可控的功耗」。

## Decision

采用**双层结构 + 每屏一个 XPC Service 进程**：

- **静态层**：`NSWorkspace.setDesktopImageURL` 设置静帧，负责所有兜底场景
- **动态层**：每屏一个 borderless `NSWindow` + `AVPlayerLayer`，窗口置于 `CGWindowLevelForKey(.desktopWindow)`，由独立 XPC Service 承载播放

## Feasibility Analysis: 先排除不可行项

以下路径经核验不可行，团队不得尝试：

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 系统级「视频壁纸」API | **不存在** | macOS 无公开 API 将视频设为桌面背景。`setDesktopImageURL` 只接受静态图片。Windows 动态壁纸是 Windows 特有能力，不可移植 |
| `AVPlayer` 直接渲染为壁纸 | 不可行 | `AVPlayerLayer` 必须有宿主视图，即必须有窗口 |
| `ScreenSaverEngine` 复用 | 不可行 | 需 `.saver` 扩展点（独立 target + 特定 Info.plist），且与系统屏保抢占同一进程槽位。属屏保整合，PRD 已列 Out-of-Scope |
| SpriteKit 序列帧 | 可行但否决 | 需预渲染全部帧为位图，4K 60fps 10 秒内存占用巨大，且无法按显示器分辨率动态适配 |
| WebView 播 WEBM | 可行但否决 | WKWebView 确能播 WebM，但每壁纸需一 WebContent 进程（约 300MB 级），与「可测量可控的功耗」直接冲突。PRD 已否决 HTML/CSS/JS 壁纸 |
| `WallpaperExtensionKit` 私有框架 | 不可依赖 | 需 `dlopen` + Mirror 反射调用私有 XPC 类型。Apple 可在任一系统版本移除。社区仅验证 macOS 26 与 27 beta |

## Rationale: 为何是双层结构

`WindowServer` 合成时按层级从低到高绘制。静态壁纸在系统层，动态窗口贴在壁纸之上、桌面图标之下。

**静态层不可省略**，因为以下场景动态窗口不存在或不显示：

- 锁屏（系统接管显示）
- 用户切到全屏 Space 且窗口未跟随
- helper 进程崩溃或被系统回收
- 屏幕休眠

没有静态层，用户在这些时刻看到的是黑屏而非壁纸。

## Rationale: 为何是 XPC Service 而非其他隔离方式

| 方案 | 隔离性 | 崩溃影响 | 评估 |
| --- | --- | --- | --- |
| AppKit 应用内嵌（同进程） | 无 | 主窗口崩溃 = 壁纸全挂；渲染负载污染主进程稳定性 | **否决**。违反 PRD「主窗口崩溃后菜单栏功能仍存活」 |
| 独立 helper（NSApplication 无 UI） | 进程级 | 仅动态壁纸失效 | 备选，但所有屏共用一个 main run loop，单屏解码异常影响全部 |
| **XPC Service，每屏一实例** | 进程级 | 仅该屏失效 | **选定** |
| LaunchAgent（登录项） | 进程级 | 同上 | 否决。需用户授权安装登录项，违反零打扰定位；难以精确跟随主应用生命周期 |

**每屏一实例的理由**：

1. `AVPlayer` 解码管线与 GPU 资源是 per-player 的，单进程多屏多 player 会在一处异常时互相影响
2. 内存压力下系统可选择性回收单屏实例（配合静帧兜底，用户无感）
3. XPC 天然提供跨进程状态同步

## Window Configuration（已编译核验）

```swift
w.level = NSWindow.Level(rawValue: Int(CGWindowLevelForKey(.desktopWindow)))
w.collectionBehavior = [.canJoinAllSpaces, .stationary,
                        .ignoresCycle, .fullScreenNone]
w.sharingType = .none
w.isOpaque = false
w.backgroundColor = .clear
w.ignoresMouseEvents = true
w.hasShadow = false
```

- `level = .desktopWindow`：关键。用 `.normal`（0）会被普通窗口遮住；用 `.desktopIconWindow` 会盖住桌面图标
- `canJoinAllSpaces`：所有 Space 都显示，否则切 Space 后壁纸消失
- `stationary`：切 Space 时不参与窗口移动动画
- `ignoresCycle`：Cmd+` 不选中它
- `ignoresMouseEvents = true`：点击穿透，用户正常操作桌面图标
- `sharingType = .none`：不参与屏幕共享/录制。避免动态壁纸出现在用户的屏幕共享里——这是隐私预期，不是疏漏

## Looping Playback（已编译核验）

```swift
let player = AVQueuePlayer()
player.isMuted = true
player.actionAtItemEnd = .none
let looper = AVPlayerLooper(player: player, templateItem: AVPlayerItem(url: url))
let layer = AVPlayerLayer(player: player)
layer.videoGravity = .resizeAspectFill
```

- `AVQueuePlayer` + `AVPlayerLooper`：系统级无缝循环，比自行监听播放结束 seek 可靠（无空帧、无累积漂移）
- `isMuted = true`：壁纸无声。这同时是**隐私选择**——播有声壁纸等于持续出声
- `actionAtItemEnd = .none`：必须设，否则与 looper 默认行为冲突
- `videoGravity = .resizeAspectFill`：铺满屏幕，与静态层裁剪一致；不同分辨率显示器各自独立裁剪
- `AVPlayerLooper` 必须被持有为属性。若被释放循环会停——这是典型的静默 bug

**已知系统行为**（macOS 26 SDK Release Notes）：`AVPlayerLayer` 替换 item 期间 `isReadyForDisplay` 可能短暂为 false。切换壁纸时应先暂停旧 player、设新 item、等一帧再显示，避免黑帧闪烁。

## Degradation Chain

```
1. 动态壁纸正常播放
2. 显示器休眠 / 锁屏 -> 暂停播放，静帧层仍在（省电，用户无感）
3. helper 崩溃 / 被回收 -> 静帧层接管，UI 提示「动态壁纸已停止」
4. 解码失败（格式不支持 / 文件损坏）-> 静帧 + 明确错误原因
5. 无可用显示器（全拔） -> 销毁窗口，暂停播放，保留配置
```

## Memory Pressure Self-Recovery

| 压力等级 | 动作 |
| --- | --- |
| warning | 暂停非主显示器的动态壁纸（主屏优先保留） |
| critical | 暂停全部动态壁纸，静帧层接管 |
| 缓解 | 恢复播放（需校验文件仍存在） |

**屏幕拓扑变化**：监听 `NSApplication.didChangeScreenParametersNotification`，比对 `NSScreen.screens` 差异，为新增屏建窗口、移除屏销毁窗口。**只有拓扑真正变化时才重建窗口**（分辨率/位置变化也要处理，窗口需 resize 并重算裁剪）。

**看门狗**：检测主线程无响应与播放停滞。超时即退出 helper，让静帧兜底，而不是留一个卡死的窗口。

## Format Support

| 格式 | 支持 | 说明 |
| --- | --- | --- |
| MP4 / MOV（H.264 / HEVC） | 是 | AVFoundation 原生硬解 |
| GIF | 是 | CPU 较高，长时间播放需降级策略 |
| WEBM / MKV | **否** | macOS 无原生解码。明确不支持并给出原因，**不静默黑屏** |

## Consequences

### 正面

- 崩溃隔离到单屏，符合 PRD 可用性要求
- 功耗可控：可按显示器优先级分级降级
- 静帧兜底覆盖所有失败场景，用户永不看到黑屏
- XPC 通信受系统管控，无需自建 IPC

### 负面

- 增加一个 XPC Service target，签名与 entitlements 配置复杂度上升
- 静帧与动态层可能不一致（切换瞬间、helper 崩溃时），需在 UI 上说明
- 每屏一个进程，2 屏即 3 个进程（含主应用），内存基线升高
- App Sandbox 下行为未验证（见下）

### 关键约束

**App Sandbox 风险（必须实测，不得假设）**：

- 沙盒应用创建 `canJoinAllSpaces` 窗口是否被系统接受
- 沙盒下 `NSWorkspace.setDesktopImageURL` 是否需额外 entitlement
- 沙盒应用能否在无焦点状态下维持播放

MVP 阶段若实测受阻，Debug 临时关闭沙盒（`com.apple.security.app-sandbox = false`）。**这一项必须在 V2 前用最小实验验证，不要留到集成阶段才发现。**

## Alternatives Considered

**同进程 AppKit 窗口**：最简单，但违反 PRD 可用性要求，且渲染负载污染主进程。否决。

**单 helper 多屏多 player**：进程数少，但一处解码异常影响全部屏幕，且难以单屏回收。否决。

**LaunchAgent**：需用户授权登录项，违反零打扰定位。否决。

**降级预案**：若 XPC Service 在沙盒下不可行，降级为沙盒外独立 helper（NSApplication 无 UI 单例）。若窗口层级方案完全不可行，降级为仅静帧 + 明确告知动态壁纸不可用。**不采用私有 API 作为降级路径。**
