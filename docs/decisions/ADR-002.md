# ADR-002: 本地存储选用 GRDB.swift 7.11.1（DatabasePool）

## Status: Accepted (2026-10-08)

## Background

IHaven 需要本地持久化的数据：收藏集与分组（PRD F6）、应用历史（与收藏库物理隔离）、多屏逐屏配置、下载/导入记录、本地埋点日志。

候选方案：GRDB.swift、SwiftData、Core Data。

项目硬约束为 macOS 26+ / Swift 6 严格并发 / Xcode 27.0 / Swift 6.4。三者在并发模型上的差异直接决定能否通过编译器的数据竞争检查。

## Decision

选用 **GRDB.swift 7.11.1**，配置 `DatabasePool`（WAL 模式）。

版本经 GitHub API 核验：v7.11.1 发布于 2026-06-18，为当前最新。

## Rationale

### 决定性因素：Swift 6 下的 Sendable 可验证性

| 方案 | Swift 6 状态 |
| --- | --- |
| GRDB 7 | 7.0 起全 API 严格并发检查，公开类型全量 Sendable 审计 |
| SwiftData | `@ModelActor` 的 Sendable 约束在 Xcode 16.x 仍有公开未决讨论 |
| Core Data | macOS 26 SDK 刚调整了 `NSManagedObject` / `NSManagedObjectContext` 的 Sendable 注解以迁就 MainActor 默认隔离——这块仍在变动中 |

GRDB 把并发正确性交给类型系统：记录是值类型（`FetchableRecord` / `PersistableRecord` 均为 struct），跨 actor 传递天然安全，无需锁。这是选 GRDB 而非其他两者的核心理由。

### DatabasePool 而非 DatabaseQueue

瀑布流浏览是典型读多写少场景。`DatabasePool` 开启 WAL 模式，维护一组读者连接 + 独立写者，并发读不排在写者后面；`DatabaseQueue` 把所有读写串行化到单连接。收藏集检索、浏览历史追加、显示配置读取并发发生时，Pool 才有吞吐优势。

### 响应式直接对接 UI 层

`ValueObservation.tracking { }` 返回 async sequence，可直接喂给 `@Observable` 模型：

```swift
let observation = ValueObservation.tracking { db in
    try WallpaperRecord.fetchAll(db)
}
for try await rows in observation.values(in: dbPool) {
    await model.update(rows)
}
```

不需要 `NSFetchedResultsController`，不需要 Combine 桥接。

## Data Placement

| 数据 | 存储 | 理由 |
| --- | --- | --- |
| 收藏集、分组、标签 | GRDB `favorites` / `collections` | 需检索、分组、批量操作、跨屏同步，关系型最自然 |
| 应用历史 | GRDB `wallpaper_history` | PRD F6 明确要求「与应用历史分离」——物理隔离到独立表 |
| 多屏逐屏配置 | GRDB `display_assignments` | 需按显示器标识索引与结构化查询，UserDefaults 不适合 |
| 用户设置（非敏感） | `@AppStorage` / UserDefaults | 键值对、高频读写、无需查询 |
| **API Key** | **Keychain**（`kSecClassGenericPassword`） | **绝不入 UserDefaults / SQLite / 日志** |
| 图片二进制 | 磁盘 `Application Support/Wallpapers/` | SQLite 存 BLOB 会让 DB 膨胀、查询变慢、备份成本高；DB 只存路径 |

## display_assignments 表设计（team-lead 批准）

多屏逐屏配置有一个**静默错误陷阱**：显示器标识若选错，用户重启后裁切焦点会串到错误的屏幕——不崩溃，用户只会认为「设置错了」。

### 两级显示器标识

`CGDirectDisplayID` **不保证跨重启稳定**（Apple 文档用 *typically* 而非 *always*，且多 GPU 机型切换 GPU 时会变）。因此采用两级：

| 层级 | 键 | 用途 |
| --- | --- | --- |
| 会话级 | `CGDirectDisplayID` | 运行期索引、窗口与播放器绑定 |
| 持久级 | `v\{vendor}-m\{model}-s\{serial}` | 落库存储键 |

依赖的 `CGDisplayVendorNumber` / `ModelNumber` / `SerialNumber` / `UnitNumber` 经核验无弃用标记（`CGDisplayConfiguration.h:352/357/362/367`）。详见 ADR-007 Trap 9。

### 表结构

```sql
CREATE TABLE display_assignments (
    id                    INTEGER PRIMARY KEY AUTOINCREMENT,
    session_key           INTEGER NOT NULL,      -- CGDirectDisplayID，仅运行期
    hardware_key          TEXT,                   -- 'v{vendor}-m{model}-s{serial}'
    hardware_key_ambiguous INTEGER NOT NULL DEFAULT 0,  -- 0/1 同型号多屏
    physical_w            INTEGER NOT NULL,      -- 物理像素宽（裁切计算用）
    physical_h            INTEGER NOT NULL,      -- 物理像素高
    backing_scale         REAL    NOT NULL,      -- 便于回溯与诊断
    wallpaper_id          TEXT    NOT NULL,
    fill_mode             TEXT    NOT NULL,
    -- CHECK 约束见下方独立 DDL：拒绝 fit/fill 之外的一切值
    CONSTRAINT ck_display_fill_mode CHECK (fill_mode IN ('fit','fill')),
    focus_x               REAL,                   -- 裁切焦点，归一化 0...1
    focus_y               REAL,
    created_at            DATETIME NOT NULL,
    updated_at            DATETIME NOT NULL,
    FOREIGN KEY (wallpaper_id) REFERENCES favorites(id) ON DELETE CASCADE
);

CREATE INDEX idx_display_assignments_hardware ON display_assignments(hardware_key);
CREATE UNIQUE INDEX idx_display_assignments_session ON display_assignments(session_key);
```

**`fill_mode` 的 CHECK 约束单独列出**（便于检索与评审）：

```sql
CONSTRAINT ck_display_fill_mode CHECK (fill_mode IN ('fit','fill'))
```

语义：**数据库层拒绝 `fit` / `fill` 之外的一切值。** 合法值只有这两个。

### 实现约定：枚举类型命名前缀

筛选参数的 Swift 枚举**必须带 `Wallhaven` 前缀**，避免与 AppKit / 领域概念混淆。

```swift
enum WallhavenRatio: String, CaseIterable, Sendable {
    case unset  = ""
    case r9x16  = "9x16"
    // ...（12 个值见 ARCHITECTURE.md §6.2.4）
}

enum WallhavenExactResolution: String, CaseIterable, Sendable {
    case unset = ""
    // ...（24 个值见 ARCHITECTURE.md §6.2.4）
}
```

**为什么需要前缀**：`Ratio` 在 AppKit / SwiftUI 语境里易与几何比例、视图宽高比混淆；`Resolution` 同样。带上前缀后，阅读代码时能立刻分辨「这是 wallhaven API 的筛选枚举」还是「这是 UI 层概念」。

**为什么放在这里而非单独立项**：这是纯命名约定，**无法用门禁自动校验**（`WallhavenRatio` 与 `Ratio` 都是合法 Swift 标识符，编译期不会报错）。按团队约定「能被门禁自动检出的先做，需靠人判断的后做」，它的优先级低于会导致编译失败的语法错误类修复，故作为 schema 章节的实现约定记录，不单独立项。

完整枚举值列表见 ARCHITECTURE.md §6.2.4（单一事实来源，避免两处枚举定义漂移）。

### 两处关键设计决策

**1. `fill_mode` 用 CHECK 约束而非自由 TEXT**

PRD F2 已明确只有「完整可见/填满」两档。既然是枚举，就让数据库层拒绝非法值，而不是靠应用层判断——静默的非法 fill_mode 会导致设置壁纸时行为与 UI 预期不符。

```swift
enum FillMode: String, Codable, CaseIterable {
    case fit    // 完整可见，四周留边
    case fill   // 铺满，系统居中裁切
}
```

**约束：不得出现 `tile` / `center` / `stretch`。** `NSImageScaling` 枚举只有四个值，其中不存在任何平铺语义；「居中」是 `ProportionallyUpOrDown` + `AllowClipping=YES` 的固定行为而非独立选项；`stretch` 在 UI 收敛为两档预设（见 ARCHITECTURE.md §6.2）。

**2. `hardware_key_ambiguous` 处理同型号双屏**

用户接两台同型号显示器时，vendor/model/serial 完全相同，物理上是两块屏。`hardwareKey` 相同会导致裁切焦点互相串——**静默错误**，用户只会觉得「设置错了」。

启动时检测同组 `hardware_key` 的屏幕数量，若 >1 则置 `hardware_key_ambiguous = 1`，UI 对该组屏幕禁用「跨重启记忆裁切焦点」（退化为每次启动询问），并提示「检测到多台相同型号显示器，无法区分」。

宁可诚实告知，不静默错误。

### 冗余存物理尺寸的理由

`physical_w` / `physical_h` / `backing_scale` 冗余存储，不只存显示器引用。若每次裁切都重新解析显示器拓扑，拓扑变化时无法给出正确的历史配置；缓存后即使拓扑变化也能还原当时的计算依据。

**所有缩放/裁切/填充判断必须基于物理像素，不得用逻辑点**（`NSScreen.frame` 是逻辑点）。完整推导见 ARCHITECTURE.md §6.4。

### 诚实行为清单

| 情况 | 行为 |
| --- | --- |
| `CGDisplaySerialNumber` 返回 0 | `hardware_key` 为 NULL，该屏配置不跨重启保留 |
| 同型号双屏 | `hardware_key_ambiguous = 1`，UI 禁用跨重启记忆 + 明确提示 |
| 显示器被拔出 | 该行保留在库中，不静默删除 |
| 壁纸文件被移走 | 保留配置项并报错，不静默回退为系统默认 |

## Consequences

### 正面

- 并发正确性由编译器保证
- 原始 SQL 一等公民，复杂查询无需绕 ORM
- 显式版本化迁移，schema 变更可控可审计
- `DatabaseQueue`/`DatabasePool` 均为 Sendable，读写 async/await 一等支持
- 内建 FTS5 支持，未来需要全文检索无需换方案

### 负面

- 迁移需手写（相比 SwiftData 的托管迁移有摩擦）
- 需要按「表」而非「对象图」思考，团队需适应
- SwiftData 的 `@Query` 声明式语法不可用，列表刷新需自行接 `ValueObservation`

### 关键约束

**全文检索不进 MVP。** 收藏集检索先用 `LIKE` + 索引；数据量逼近 1万条再评估 FTS5。不要提前优化。

## Alternatives Considered

**SwiftData**：语法最简洁，但 `@ModelActor` 的 Sendable 问题有公开未决讨论，Swift 6 严格并发下有编译风险。否决。

**Core Data**：Apple 官方且成熟，但 Swift 6 Sendable 注解在 macOS 26 SDK 刚变动，且需管理 `NSManagedObjectContext` 与对象图，对纯 Swift 值类型架构不友好。否决。

**降级预案**：若 GRDB 7.11.1 在 Xcode 27.0 出现兼容问题，回退至 GRDB 7.10.0 或 6.29.0（后者为 CocoaPods 最后可发布版本）。不使用 SwiftData 作为降级方案（并发保证不同，降级等于放弃核心选型理由）。
