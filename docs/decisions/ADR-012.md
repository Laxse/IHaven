# ADR-012: NSFW 档位改为「本机意愿开关」门禁（设置 · 内容）

## Status: Accepted (2026-10-14)

## Background

ADR-011 取消了 NSFW 档位的**权限**门禁：三档（全年龄 / 轻微暗示 / NSFW）交互对等，不再灰置，也不再做任何账号侧探测。ADR-011 当时否决线稿方案的两条理由之一是「承载界面不存在」——线稿要求灰置并在 hover 里给出三层原因（缺 Key / 账号未开 / 本次可见未开），而解锁其中两层所需的设置页与菜单栏面板在 MVP 阶段都没有，结果会是「看得见、点不了、且无处解锁」的坏掉状态。

产品侧随后提出了相反方向的需求：**NSFW 这个过滤按钮默认应该是禁用的；设置界面里放一个启用按钮，开启表示允许包含裸露、暴力或色情等不适合在工作场合浏览的内容**。

这与 ADR-011 并不冲突，因为两者门的性质不同：

| | ADR-011 取消的 | ADR-012 引入的 |
| --- | --- | --- |
| 门禁性质 | 权限门禁（你配不配看） | 意愿门禁（你想不想看） |
| 判定依据 | 服务端信号（账号开关 / Key） | 本机 UserDefaults 开关 |
| 是否需要网络 | 需要一次探测请求（吃配额） | 不需要，零请求 |
| 解锁路径 | 站点设置 / 菜单栏面板（均不存在） | 设置面板 · 内容页签（已存在） |
| 失败态能否误报 | 能（网络错误被说成「无权限」） | 不能（没有失败态） |

也就是说，ADR-011 否决的前提在本次已经不成立：承载界面（设置面板）自多语言改造后已经落地，且新方案**不做任何探测**，ADR-011 Rationale 二节指出的「配额开销 + 失败态误报」问题根本不会出现。按 ADR-011 末尾的交代——重新引入门禁应以它为起点逐条核对前置条件——逐条核对的结果是：两条前置条件本次均已满足。

## Decision

一、**NSFW 档默认锁定**。新增本机开关 `UserPreferenceKey.nsfwAllowed`（UserDefaults key `ihaven.nsfwAllowed`），默认 `false`。默认态下筛选面板的 NSFW 档不可勾选：视觉上 `opacity(0.45)`，点击不切换勾选状态，而是走 `onOpenContentSettings` 打开设置面板并直接落在「内容」页签。锁定态必须有可达出口——「灰置且无处解锁」正是 ADR-011 否决线稿方案的理由，本次不得重蹈。

二、**设置面板新增「内容」页签**承载开关。文案为「允许成人内容（NSFW）」，下方说明「默认关闭。开启后，筛选面板的 NSFW 档位才允许勾选，结果中可能包含裸露、暴力或色情等不适合在工作场合浏览的内容。」——按产品原话明确点出裸露、暴力、色情与「不适合在工作场合浏览」。页签顺序为 密钥 / 外观 / 内容 / 关于。

三、**开关只表达本机意愿，不做任何账号侧探测**。`WallhavenAPIProtocol` 不新增任何方法，`PurityFilter` 的取值与下发逻辑一字不改：`purity` 串照旧由 sfw/sketchy/nsfw 三位拼出，NSFW 是否能被勾上完全是 UI 层的事。服务端若因账号未开 NSFW 而过滤结果，那是服务端既有的行为（Trap 17 已禁止用 `data.purity` 反推权限），本 ADR 不新增任何推断。

四、**关掉开关要收回已勾选的 NSFW 档并重查**。设置里把开关从「开」拨到「关」时，`BrowseViewModel.disableNSFWIfNeeded()` 把 `query.purity.nsfw` 置回 `false`、回到第 1 页重查。只在此方向做收敛：开关打开**不**自动勾上 NSFW（开启只是「允许」，不是「替你选好」）。

五、**筛选面板与设置面板读同一个 key**。两处都通过 `UserPreferenceKey.nsfwAllowed` 常量取 key，不允许各自写字面量——拼错一个字符就会变成「设置里开了、面板里还是灰的」这种静默 bug，`UserPreferenceKey` 的文档注释已就此写明原因。

## Rationale

### 一、意愿门禁不需要任何服务端信号，因此 ADR-011 的成本论证对它不成立

ADR-011 反对门禁的两条技术理由都绑定在「探测」上：探测要打真实搜索请求、占 45 次/分钟配额；探测的 `error` 态在 UI 上无法与 `unauthorized` 区分，会把网络抖动说成「你没有 NSFW 权限」。本次的门是一次本地布尔读值——没有网络请求，没有中间态，没有可误报的信号。ADR-011 反对的是「用嘈杂的服务端信号压成二值门禁」，本次根本不使用服务端信号，两条反对理由都不触及。

### 二、解锁路径存在且唯一，「无处解锁」的风险被消除

ADR-011 判定线稿方案不可接受的直接原因是三条解锁路径里两条无处落地。本次只有一条解锁路径，且它就在同一块 UI 里可达：锁定态 chip 被点击 → 收起筛选 popover → 弹出设置面板 → 停在「内容」页签 → 开关就在眼前。从「点不了」到「能改」是一次点击的距离，不依赖任何尚未存在的界面。这也是为什么锁定态一定要挂 `onOpenContentSettings` 而不是单纯 `disabled`：单纯禁用会让用户卡在原地，挂了出口才构成完整闭环。

### 三、「默认关闭 + 明确文案」同时满足产品定位与知情权

ADR-011 的 Rationale 三节确立的产品定位是「NSFW 可见性由使用者自己决定，不由应用代为判断你配不配看」。本机开关是这个定位的直接实现：判断权仍完全在使用者手里，应用只是把默认态设为关闭、并把后果（可能包含裸露、暴力、色情）写在开关旁边由使用者确认。它不是权限审查，而是默认值选择 + 知情确认，与 ADR-011 的定位一致，且补上了 ADR-011 自己在「负面」一节承认丢失的那层提示——「防止用户在不知情下打开 NSFW」。

### 四、只在关闭方向收敛，避免开关变成「替用户做决定」

开关打开时若顺手勾上 NSFW，等于应用替使用者做了「我要看成人内容」的决定，与第三节的定位相悖，也会让只想解锁选项的用户被强制改掉当前筛选。因此只做关闭方向的收敛（把已勾的收回），打开方向保持中立。

## Consequences

### 正面

- 恢复了对 NSFW 的默认保护与知情提示，且没有引入任何网络请求、配额开销或可误报的失败态。
- 锁定态有唯一且可达的解锁路径（点击直达设置 · 内容），不构成 ADR-011 批评过的「坏掉的功能」。
- 中英双语同步：新增 7 条词条（内容 / 成人内容 / 允许成人内容（NSFW）/ 说明长句 / 已开启 / 已关闭 / 需先在设置 · 内容中启用），`zh-Hans.lproj` 与 `en.lproj` key 集合完全一致。
- 两处读同一个 `UserPreferenceKey` 常量，排除了 key 拼写漂移导致的静默不一致。

### 负面

- NSFW 档在默认态下与另两档视觉不对等（`opacity 0.45`），回归了线稿「三档不对等」的形态。这是有意回归：本次的不对等有出口，线稿的不对等没有。
- 本机开关无法保证服务端一定返回 NSFW 结果（账号侧仍需自行开启）。这是有意的：本 ADR 明确不做账号侧推断（Trap 17），开关只管本机意愿。
- 设置面板从 3 个页签增至 4 个，560×460 的 segmented 控件项宽变窄；英文下 `API Key / Appearance / Content / About` 需确认不裁切。

### 与 ADR-011 的关系

ADR-011 依然有效：它取消的是**权限门禁与探测基础设施**，`probeNSFWPermission()` 与 `NSFWProbeResult` 不会被重建，Trap 15 / 17 两条禁令继续生效。ADR-012 取代的只是 ADR-011 结论中「NSFW 档一律可自由切换」这一条交互形态。二者分处不同层：ADR-011 管「从哪里获取判断依据」（答案：不从服务端获取），ADR-012 管「拿到依据之后的默认态」（答案：默认关，由本机开关开）。

## Alternatives Considered

**保持 ADR-011 的完全自由切换，只加设置开关但不联动。** 开关与筛选面板脱钩，用户开了开关却看不出变化，等于两个独立功能，反而更难理解。否决。

**重做 ADR-011 删除的探测，按账号权限决定是否锁定。** 直接违反 ADR-011 的两条核心论证（配额开销、失败态误报），且重新引入死代码。否决。

**锁定态只 `disabled` 不给出口。** 正是 ADR-011 否决线稿方案的直接原因，会让档位变成「看得见点不了、且不知道去哪解锁」。否决。

**开关打开时自动勾上 NSFW。** 应用替使用者做了内容偏好决定，与「可见性由使用者自己决定」的定位冲突。否决。

**把开关放进「外观」页签而不新增页签。** 内容策略与视觉主题是两类设置，混在一个页签里会让「允许成人内容」看起来像配色选项。否决。
