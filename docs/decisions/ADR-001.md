# ADR-001: 图片加载选用 Nuke 13.2.0

## Status: Accepted (2026-10-08)

## Background

IHaven 主窗口的核心是壁纸浏览瀑布流（F1，PRD RICE Score 900）。图片加载是全项目最高频的性能敏感路径：

- 首屏 24 张缩略图需 2 秒内渲染
- 1000 张规模滚动需稳定 60fps
- 滚动中持续触发加载与取消

同时项目硬约束为 macOS 26+ / Swift 6 严格并发。候选方案：SDWebImageSwiftUI 3.1.4 + SDWebImage 5.21.7（现有 2020 雏形工程用过）、Nuke 13.2.0、自研 URLSession + NSCache + 磁盘缓存 + LRU。

图片管线的并发竞态属于典型「沉默逻辑错误」——不崩溃、不报错，只是偶发错图或偶发崩溃，最难靠测试发现。因此「线程安全是否由编译器保证」是本次选型的决定性维度，而非基准性能。

## Decision

选用 **Nuke 13.2.0**（SPM，产品 `Nuke` + `NukeUI`）。

版本经 `git ls-remote --tags` 与 GitHub API 核验：13.2.0 发布于 2026-08-15，为当前最新。

## Rationale

### 决定性因素：编译期线程安全保证

Nuke 13.0 起引入全局 `ImagePipelineActor`，`ImagePipeline`、`ImageTask`、`ImagePrefetcher` 等子系统全部在该 actor 上同步。这带来两个后果：

1. 线程安全成为编译器可验证的事实，而非代码评审时的口头约定
2. 移除 20 处 `@unchecked Sendable`，数据竞争检查在编译期生效

这与项目「Swift 6 严格并发」的硬要求直接匹配，且把最高频的竞态风险从「靠测试碰运气」转为「编译期拦截」。

### 瀑布流压力点契合

| 瀑布流需求 | Nuke 对应能力 |
| --- | --- |
| 快速滚动时取消在途请求 | 类型化 `throws(ImagePipeline.Error)`，含独立 `.cancelled` case，与 `CancellationError` 区分 |
| 预取不抢占用户可见请求 | priority-aware 并发受限队列 |
| 同图不重复下载 | 请求合并 |
| 后台解码不阻塞滚动 | 后台解压 + 可配解码尺寸上限 |
| 缩略图按需降采样 | `ImageRequest.ThumbnailOptions` 按请求控制 |

### 自研方案的成本被低估

自研看似只需 URLSession + NSCache，实际必须自建：LRU 淘汰、并发上限、请求合并、后台解压队列、磁盘过期策略。其中每一项都是静默错误高发区（LRU 边界 off-by-one、并发上限下任务饥饿、解压时机错误导致的滚动卡顿）。按 MVP 不做过度设计的原则，这是明确的负收益。

### 为何放弃 SDWebImage

不是它不好，而是它无法提供本项目需要的并发保证：

- 核心是 Objective-C + category 体系，在纯 Swift + Swift 6 项目里拿不到编译器级并发验证，只能依赖注解与人工评审
- 5.x 模块化后功能分散到独立仓库，`SDWebImageWebPCoder` 等需单独引入且独立版本控制，对 wallhaven 的 WebP 素材是额外供应链面
- 默认仅注册 GIF 与 APNG 动画 coder，其他格式需自行注册

SDWebImage 在 UIKit 老项目里仍是合理选择；本项目是纯 Swift 新工程，前提不同。

## Consequences

### 正面

- 最高频的并发路径获得编译期保证
- 瀑布流所需的预取、取消、合并能力开箱可用
- Nuke 13.2.0 要求 Swift 6.2 / Xcode 26 / macOS 12，本项目工具链（Swift 6.4 / Xcode 27 / macOS 26 目标）满足
- Nuke 无 package dependencies，供应链面最小
- 13.x 仍在活跃迭代，96% 测试覆盖，测试套件 1.3s（并行化后）

### 负面

- 引入一个第三方依赖（MIT 许可，与 PRD 隐私定位无冲突）
- SwiftUI 组件为 Nuke 自有的 `LazyImage` 而非 Apple 原生，无法用原生控件外观
- Nuke 13 有若干从 Combine 迁移到 Swift Concurrency 的 API 变更，接入时需按 13.x API 写

### 关键约束（必须写入实现规范）

**Nuke 13.0.3 起，自动降采样实现已移除。** `ImagePipeline.Configuration.maximumDecodedImageSize` 与 `ImageDecodingContext.maximumDecodedImageSize` 已废弃，设置无效。缩略图尺寸必须通过 `ImageRequest.ThumbnailOptions` 按请求控制，不得依赖全局配置。按旧文档写会静默失效——这是典型的沉默逻辑错误。

## Alternatives Considered

**SDWebImageSwiftUI 3.1.4 + SDWebImage 5.21.7**：维护活跃（5.21.7 / 2026-02-26），但拿不到 Swift 6 编译期并发保证，且需额外引入 WebP coder 依赖。否决。

**自研 URLSession + NSCache**：预估 800-1200 行，四项核心能力全部需重造，静默错误风险集中。否决。

**降级预案**：若 Nuke 13.2.0 在 Xcode 27.0 出现兼容问题（尚未验证，见 ARCHITECTURE.md 风险 #3），回退至 Nuke 12.9（已开启 Swift 6 支持、去除 Combine 依赖）。**不使用自研作为降级方案**。
