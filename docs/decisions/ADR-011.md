# ADR-011: 移除 NSFW 纯度档位的权限门禁

## Status: Accepted (2026-10-11)

## Background

线稿 `docs/wireframes/filter-panel.svg` 的「纯度」分组把三档画成了不对等的状态：全年龄与轻微暗示可自由切换，NSFW 一档灰置不可点，并预留了一组 hover 文案来解释「为什么点不了」。这套文案规划了三层门禁原因，由轻到重依次为密钥缺失、账号侧 L2 开关未开、本次可见 L3 开关未开，其中密钥缺失那一档还挂了「打开密钥设置」的跳转路由：

| 层级 | 门禁原因 | 线稿中的呈现 | 解锁动作 |
| --- | --- | --- | --- |
| L1 | 需要密钥 · 未配置 | NSFW 档灰置，hover 说明缺 Key | 走「打开密钥设置」路由填入 Key |
| L2 | 需要开启 NSFW（账号侧）· 已关闭 | NSFW 档灰置，hover 说明账号未开 | 用户去 wallhaven 站点开启 |
| L3 | 需要开启本次可见 · 已关闭 | NSFW 档灰置，hover 说明本次会话未开 | 用户在菜单栏面板里开一次 |

为了让 UI 能判断该显示哪一条原因，代码侧准备了对应的探测基础设施：`WallhavenAPIProtocol` 声明了 `func probeNSFWPermission() async -> NSFWProbeResult`，`WallhavenClient` 以「固定 `purity=001`、不带任何用户筛选」的方式打一次搜索请求，用 `meta.total` 是否大于 0 判定账号有无 NSFW 权限，结论封装为 `NSFWProbeResult`（`authorized` / `unauthorized` / `keyInvalid` / `error`）。也就是说，探测方法与结果类型的**唯一用途**就是喂给这套门禁；它们是门禁的手段，而不是独立能力。

产品决定推翻了这个前提：**NSFW 不需要加限制了**。三档（全年龄 / 轻微暗示 / NSFW）一律可自由切换，不再存在「不允许打开 NSFW」的状态。

## Decision

一、**移除 NSFW 档位的门禁**。NSFW 档与另两档在交互上完全等价：不再灰置，不再显示门禁原因，不再依赖任何前置探测结果。筛选面板的默认档仍为 `PurityFilter.browseDefault`（`Core/Models/Query.swift`）——全年龄 ON / 轻微暗示 ON / NSFW OFF——但「NSFW OFF」从此只是用户可随手改掉的默认值，而不是被强制的状态。用户想看 NSFW，勾上即可，不需要先证明自己有权限。

二、**同步删除已成死代码的探测基础设施**，不留残骸：`Core/Protocols/WallhavenAPI.swift` 中删除 `probeNSFWPermission()` 声明与其文档注释、删除整个 `public enum NSFWProbeResult`；`Infrastructure/Network/WallhavenClient.swift` 中删除对应实现及其上方两行关于「固定宽 purity=001、不带用户筛选」的注释。删除后 `WallhavenAPIProtocol` 只剩 `search(_:)` 与 `keyStatus`，协议文件里不再出现任何 NSFW 字样。

三、**以下既有约束不受本次决定影响，全部保留**：认证仍走 `X-API-Key` 请求头（不回退到 query）；仍禁止用 `/settings` 端点验证 Key；仍禁止用响应里的 `data.purity` 判断 NSFW 权限（Trap 15 / Trap 17）。

## Rationale

### 一、门禁的承载界面在 MVP 阶段根本不存在，「灰置但永远点不开」比不做门禁更糟

三层原因看似完整，但逐层追问「用户去哪里把开关打开」就会发现它们各自依赖一个尚不存在的界面：L2 是 wallhaven 账号侧的站点设置，若要在应用内引导，需要一个设置页来承载解释与跳转；L3 是「本次可见」这类临时开关，按线稿的规划要挂在菜单栏面板里。而 MVP 阶段这两个界面都不在范围内——设置页没有、菜单栏面板也没有。

于是现状是：三条解锁路径里有两条无处落地，唯一能真正执行的是 L1（填 Key），而 L1 又只解决「有 Key」这一件事，解决不了账号侧到底开没开 NSFW。结果就是这个档位会被永久灰置。

永久灰置的体验比不做门禁更差。一个不做门禁的开关，用户看到的是「这个功能我能用」；一个灰置且附带 hover 解释、但点开解释后却发现无处可去的开关，用户看到的是「这个功能坏了」。前者是范围外功能（还没做），后者是损坏的功能（做了但不work）——后者对可信度的伤害远大于前者。与其交付一个解释得很详细却永远无法解除的门禁，不如先不设门禁，把三档做成平等的。

### 二、探测本身要消耗配额，且失败态在 UI 上无法与「没权限」区分

探测不是免费的：它是一次真实的搜索请求，占用 45 次/分钟的 API 配额，且在筛选面板打开、Key 变更等场景下会重复发起。为一个注定要被移除的门禁反复付出配额，本身就是净亏损。

更麻烦的是结论的语义。`probeNSFWPermission()` 只有四种返回值，其中 `unauthorized`（`total == 0`）与 `error(Error)` 在 UI 上是两种完全不同的含义：前者是「你有 Key 但账号没开 NSFW」，后者可能是网络错误、配额耗尽、限流、服务端异常。可 UI 能呈现的只有「这个档位点不了」加一句原因文案——把网络抖动说成「你没有 NSFW 权限」，是一句明确的误导性提示，而且用户没法通过重试来反驳它，因为 UI 已经替他下了结论。401 虽然能单独识别为 Key 失效（Trap 16），但那本来就是 Key 状态该管的事，不需要借道 NSFW 探测来表达。

也就是说，这套探测把一个「连续且嘈杂的信号」（网络可用性 + 配额 + 账号权限）强行压成一个二值门禁判断，压缩过程中丢失的信息恰好是 UI 解释文案最需要的部分。门禁一旦取消，这个失真问题也就一并消失了。

### 三、产品已明确要求不加限制

前两条论证说明「当前形态的门禁不该做」，这一条决定「这个阶段根本不需要门禁」：产品方明确提出 NSFW 不需要加限制。这不是对实现难度的妥协，而是对产品定位的判断——IHaven 是用户自己在本机上用的壁纸工具，NSFW 内容的可见性应由使用者自己决定，而不是由应用代为判断「你配不配看」。产品判断优先于线稿里的交互细节，线稿是手段，不是约束来源。

### 为什么三条保留的约束与本次决定不冲突

需要特别说明，移除门禁不等于放宽任何一条 API 纪律。仍在执行的三条约束——走 `X-API-Key` 头、不用 `/settings` 验 Key、不用 `data.purity` 判 NSFW——共同的本质是**不得依赖错误的信号源**：Key 的有效性不能靠一个语义不同的端点来推断，NSFW 权限不能靠响应数据里一个会被服务端过滤行为污染的字段来推断。它们约束的是「从哪里获取判断依据」，与「拿到判断依据之后门不门禁」是两个正交的问题。本次取消的是后者的策略，前者一条不动。

## Consequences

### 正面

- 三档交互对等，筛选面板不再存在「看得见但点不了」的坏掉状态，也不需要为不存在的设置页 / 菜单栏面板编写引导文案。
- 死代码被彻底删除：`WallhavenAPIProtocol` 收缩为两个成员，`WallhavenClient` 少一条网络路径，协议里不再有 NSFW 概念，后续阅读者不会被一个无人调用的方法误导为「还有门禁」。
- 省掉探测请求的配额开销，也消除了把网络错误误报为「无权限」的误导性提示。
- 三条错误信号源约束（Trap 14 / 15 / 17）保持完整，未因本次改动出现任何纪律松动。

### 负面

- 失去了「防止用户在不知情下打开 NSFW」的提示层。此前灰置至少在视觉上暗示了这一档与普通档不同；现在 NSFW 与另两档外观一致，用户可能在浏览时意外开启。此项已由产品决定接受。
- 将来若重新引入门禁，需要重建整套探测基础设施（协议方法、结果类型、客户端实现），而非取消一次开关。本 ADR 的 Rationale 一、二节应作为重建时的前置检查清单，避免重蹈「门禁存在但无处解锁」的覆辙。
- 线稿 `filter-panel.svg` 与代码暂时不一致：线稿仍画着灰置与三层 hover 文案。文档以本 ADR 为准。

### 对既有文档的取代关系

线稿 `docs/wireframes/filter-panel.svg` 中「纯度」分组的灰置样式说明与三层门禁 hover 文案**已被本 ADR 取代**，不再作为实现依据。后续若需重新引入 NSFW 门禁，应以本 ADR 为起点（尤其是「承载界面是否存在」与「失败态能否与无权限区分」两条前置条件），而不是直接照抄线稿的原始设计——那份设计的前提（存在设置页与菜单栏面板）在 MVP 阶段并不成立。

## Alternatives Considered

**保留探测方法但默认放开 NSFW。** 看似稳妥的折中，实际留下一个无人调用的方法与一个无人构造的结果类型，之后每次重构协议、改网络层都要为它付出维护成本，还要解释「为什么有个没人用的探测」。死代码本身即是成本。否决。

**保留灰置，并补一个设置开关来承载 L2/L3。** 这个方案逻辑上完整，但等于在 MVP 阶段新建一个设置页与一个菜单栏面板，超出当前范围；而且产品已明确不需要限制，为一个不需要的门禁去补界面是双重浪费。否决。

**只在 UI 上去掉灰置、保留探测以便将来复用。** 保留了最贵的一部分（网络请求与配额），却不使用它。不运行的代码无法被验证——探测逻辑一旦与真实请求脱节（例如端点、字段、配额语义变化），不会有任何测试失败来提醒，将来复用时反而要重新验证一遍。要复用就等真有门禁需求时按本 ADR 重建。否决。
