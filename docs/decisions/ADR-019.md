# ADR-019: AI 图生视频作为动态壁纸的可选帧来源（Plan B）

## Status: Accepted (2026-10-18)

## Background

ADR-016 把动态壁纸定为「静态图 → 本地渲染 JPEG 帧序列 → 桌面层窗口逐帧播」，刻意**不接云端**：
零成本、离线、CPU 可控、无缝循环。代价是只能对静图做 Ken Burns 式运镜，做不了「真·画面运动」。
`AnimationGeneratorView` 的注释里因此预留了一句「AI 生视频作为后续可选项（设置里填 Key 后启用）」。

用户要补上这个可选项，且明确要「主流」的那种——即 AI **生成会动的画面**（图生视频），
而不是「AI 画张图再运镜」。但这里有个张力：主流动态壁纸靠**视频播放**，而 ADR-016 的引擎只播帧。

## Decision

新增 **AI 图生视频**作为动态壁纸的**可选帧来源**，与「本地渲静图」并列，**不推翻 ADR-016 的播放引擎**。

1. **管线**：选一张本地静态图 + 运动描述 → 调 AI 图生视频 API（用户自备 Key）拿 MP4 →
   **AVFoundation 抽帧**成 `frame-%04d.jpg` → 落 `Animations/<uuid>/` → 现有 `DynamicWallpaperEngine` 照播。
   引擎、帧存储、性能护栏、循环语义全部复用，一行不改。

2. **为什么抽帧而非给引擎加视频播放（即不改 ADR-016）**：给桌面层窗口加 `AVPlayer` 是最主流，
   但会把 ADR-016 否决的一整包问题请回来——codec 兼容、CPU/解码占用、视频资产管理、循环接缝。
   抽帧方案让「帧来源」可插拔（本地渲静图 / AI 视频抽帧），播放侧保持单一、轻、可控。
   AVFoundation 原生解 H.264/HEVC，**不捆 FFmpeg**（Non-goals 守住）。

3. **协议分层**：`AIVideoGenerating` + `VideoFrameExtracting` 两个 Core 协议；实装在
   Infrastructure（`VendorVideoClient` —— 按用户在设置里选的厂商分派各家策略，见下方
   「修正」一节）与 Platform（`AVFoundationFrameExtractor`）。Feature 只见协议；
   具体厂商可换（加一个策略文件 + 厂商目录里加一条，装配点不动）。

4. **成本护栏（硬要求）**：每一次生成花用户 Key 的真金白银。故——每次生成前一次确认弹窗；
   设置页明示「会计费 / 需自备 Key / 需能访问服务商网络 / 内容合规自负」；客户端绝不自动重试连打。

5. **Key 按厂商独立存储**：`~/.ihaven/ai-key-<vendorID>`（ADR-010 同机制、`0600`、不进 git/日志）。
   六家厂商各自一把 Key、各自一个文件，与 wallhaven Key 也分开；**同一 vendorID 必须返回同一个
   `KeyProvider` 实例**（设置面板写 / 客户端读同一实例，避免内存缓存漂移）。旧的
   `~/.ihaven/ai-key`（聚合层 Replicate 的 Key）不迁移、不删除 —— 见「修正」一节。

## Rationale

- **为什么是图生视频而不是文生图**：用户要的是「会动的画面」。文生图 + 运镜仍是静图的错觉，
  达不到「主流 AI 动态壁纸」的预期。图生视频给的是真实运动。
- **为什么不视频播放**：见 Decision 2——用「换帧来源」绕开「换播放内核」，以最小架构改动拿到
  主流观感，同时不牺牲 ADR-016 立下的轻量 / 可控 / 无缝。
- **成本为何要单独成条**：这是本 App 第一个「花用户钱」的功能。默认开启的静默计费是不可接受的，
  所以确认弹窗 + 明示边界是功能的一部分，不是附加说明。

## 补充：多模型走聚合层（2026-10-19，已被 2026-10-20 的决策取代，以下仅作历史留档）

[!] 本节结论已于 2026-10-20 推翻（改为直连各模型厂商），以下仅作历史留档，现行方案见下一节。

用户问「能不能接多种模型（国内 + 国外流行的）」。当时的结论：**先聚合层，不逐家直连**。

- **为什么**：直连 8 家 = 8 套鉴权头、8 套任务模型（同步 / 轮询 / webhook）、8 种图片上传方式
  （data URI vs 先上传换 URL）、8 份 Key 管理。Replicate（以及 fal.ai）这类聚合层**一个 Key
  就能跑 MiniMax / 阿里万相 / 快手可灵 / 字节 Seedance / Google Veo / 生数 Vidu** 等国内外主流模型，
  一次接入即换来「多模型」。直连只留给聚合层没有、或标杆级的两三家（后续按需补）。
- **模型目录在 Core**：`AIVideoModel` + `AIVideoModelCatalog`（`Core/Models/AIVideoModel.swift`）。
  Infrastructure 取入参键名发请求，Features 取名字与说明渲染 UI，**换模型只动这一个文件**。
- **[!] 底图入参键名各模型不同，写错就是 422**（这条是本 ADR 里最贵的一条经验）。已按
  Replicate 各模型页内嵌的 openapi schema 逐条核对（2026-10-19）：

  | 模型 | 底图入参 |
  |------|----------|
  | `minimax/video-01` | `first_frame_image` |
  | `wan-video/wan-2.7-i2v` | `first_frame` |
  | `kwaivgi/kling-v2.5-turbo-pro` | `start_image`（该模型的 `image` 已被官方标 deprecated） |
  | `bytedance/seedance-2.0-fast` | `image` |
  | `google/veo-3.1-fast` | `image` |
  | `vidu/q3-pro` | `start_image` |

- **OpenAI Sora 2 Videos API 已于 2026-09-24 下线**，不接。
- 选择持久化在 `UserPreferenceKey.aiVideoModel`；客户端现读现用，改选后下一次生成即生效。

## 修正：改为直连各模型厂商（2026-10-20）

上一节「先聚合层，不逐家直连」的结论**已被推翻**。上节原文保留作历史留档，以下为现行决策。

- **为什么推翻（用户原话）**：「不想使用统一的服务商（接口商），想使用各自的模型厂商，选完模型
  厂商后再去获取key，然后在设置key 再选模型。不同模型厂商做成不同的策略吧。」
  拆开是两条硬要求，聚合层一条都满足不了：
  1. **不要中间商** —— 计费方与 Key 归属必须落在模型厂商自己身上；聚合层把「到底谁在收钱」
     藏在了它自己的账单里，用户看到的永远是一个总数。
  2. **流程必须是「先选厂商 → 再去该厂商官网拿 Key → 再选该厂商的模型」** —— 聚合层是一把 Key
     对应六家模型，用户根本无法回答「我这把 Key 是为哪家申请的、扣的是哪家的钱」。

  代价很实在：直连 6 家 = 6 套鉴权头、6 套任务模型（同步返回 / 异步轮询）、6 种底图入参形状、
  6 份 Key 管理 —— 上一节正是因为这个代价选了聚合层。**用户明确接受这个代价换「厂商自选 +
  计费透明」**，故推翻原结论。

- **厂商目录在 Core**：`AIVideoVendor`（id / 展示名 / Key 获取页 URL / Key 长什么样 / 计费与网络
  要求 / 该厂商可选的 `AIVideoModel` 列表）+ `AIVideoVendorCatalog`（`selected()` 与
  `selectedModel()` **现读现用**，不缓存成常量 —— 用户会在进程运行期间改选厂商）。
  模型 id 是**厂商自己的**模型名（`veo-3.1-fast-generate-preview`、`MiniMax-H3` …），不是全局
  命名空间，只在所属厂商的 `models` 里有意义。

- **`AIVideoModel` 精简为 `id / nameKey / noteKey`，删掉 `imageInputKey` / `promptInputKey`**：
  直连后各家请求体形状完全不同 —— Google 是 `instances[].image.inlineData`（裸 base64，不带
  `data:` 前缀）；MiniMax / 火山方舟是 `content[]` 包 `image_url` 且要额外给 `role: first_frame`；
  阿里百炼是 `input.media[]`；快手可灵是 `contents[]`；生数 Vidu 是裸数组 `images: []`。
  键名看着相似，层级 / 包装 / 前缀规则全不同，**一个「底图键名」抹不平**；继续挂在模型上只会误导
  （照着 `image` 去填 Google 就是 422）。差异下移到各家策略实现，模型层只留「选哪一家的哪个模型」。

- **策略实现在 Infrastructure**：新增 `Infrastructure/Network/AIVendor/` —— `AIVendorVideoStrategy`
  协议（submit / poll / downloadHeaders 三件事）+ 六家各一个实现 + `VendorHTTP` 共用原语。
  `VendorVideoClient` 是**唯一的 `AIVideoGenerating` 实现**，只做「底图转 JPEG → 按选中厂商取策略
  → 提交 → 轮询 → 下载 MP4」的骨架，自身不含任何厂商细节。加第 7 家 = 加一个策略文件 +
  目录里加一条，`VendorVideoClient` 与 Feature 层一行不改。

- **每厂商一个独立 Key 文件 + 一条硬约束**：Core 新增
  `AIVendorKeyProviding { func keyProvider(for vendorID: String) -> KeyProvider }`，由 App 层
  `AIKeyStore.shared`（`AIVendorKeyVault`）实现，路径 `~/.ihaven/ai-key-<vendorID>`。
  [!] **同一 vendorID 每次必须返回同一个 `KeyProvider` 实例**：`FileKeyProvider` 把 Key 缓存在内存
  `currentKey` 里，若设置面板（写）与生成客户端（读）各持一个实例，就会重演「设置里刚存了 Key、
  客户端还读到空」这个老问题。未知 vendorID（厂商下线 / 手改偏好）返回一份空的内存实现，
  **不落文件** —— 为一个拼错的 id 在 `~/.ihaven/` 下建真实文件是纯副作用，且没人会去清理。

- **切厂商必须把模型 id 归位**：模型 id 不跨厂商通用，残留旧 id 会拿 B 厂的模型名去打 A 厂的
  接口（404 / model not found，而错误信息不会提示是串厂商，极难排查）。故设置页在
  `.onChange(of: vendorID)` 时强制把 `aiVideoModel` 重置为新厂商的第一个模型，`onAppear` 也归位
  一次（老用户偏好里存的还是聚合层时代的 id）。

- **成本护栏沿用且更硬**：每次生成前一次确认弹窗、设置页明示「计费 / 需自备 Key / 需能访问该厂商
  网络 / 内容合规自负」、客户端绝不自动重试连打。直连后每一家的钱都是用户自己的，没有聚合层
  兜底，这条比原来更重要。

### 已知代价 / 首次真 Key 首验清单

- **六套协议全部未真机验证**。需要说清的是：上一节的 Replicate 路径**同样从未真机跑通过**
  （只走到 HTTP 422），所以这不是「从已验证退回未验证」，而是**未验证的面积从 1 套扩大到 6 套**。
  首验按厂商逐个做，每家四件事：
  1. 鉴权头是否与实现所写一致（`Authorization: Bearer` / `X-API-Key` / 各家自定义头）；
  2. 底图入参形状（`data:` 前缀要不要、base64 裸不裸、要不要额外的 `role: first_frame`）；
  3. 任务模型是同步返回还是异步轮询，轮询路径与终态字段是什么；
  4. 输出形态（单个 URI / 数组）与实际计费，是否与目录里那行「约 $x/秒」对得上。
- **目录里的价格与规格文案来自各厂商公开页面（2026-10-19 调研），不是实测账单**，会漂移；
  首验后按实际账单回写 `AIVideoVendor.swift`。
- **旧 `~/.ihaven/ai-key`（聚合层 Replicate 的 Key）不迁移、不删除**：它与新的六家没有任何对应
  关系，自动搬运只会制造误会；用户可自行清理。

## 已知限制 / 待首验

- **[历史] Replicate 端点已真机修正（2026-10-19）** —— 该实现（`ReplicateVideoClient`）已随
  2026-10-20 的决策删除，此条随实现一起失效，仅留档：官方模型必须走
  `POST /v1/models/{owner}/{name}/predictions`，body **只有 `input`**；通用 `/v1/predictions`
  必填 `version`（版本哈希），body 里**没有 `model` 字段** —— 传 `{"model": …}` 会直接 422。
  仍用 `Prefer: wait` 同步等 ≤60s，超时转轮询。
- **默认厂商 / 模型**：目录首位的 Google（Veo）及其第一个模型 `veo-3.1-generate-preview` 为默认
  —— 理由是 AI Studio 一键出 Key，新用户最容易跑通全流程，而不是因为它是唯一验证过的。
  **六家里没有一家真机打通过**，首验清单见上一节。
- **循环接缝**：AI 视频片段通常不为无缝循环设计，循环点可能跳。抽帧后做「正放 + 倒放」的
  ping-pong（`VideoFrameExtracting(pingPong:)`），末帧平滑折返起点，已实现为 AI 生成的默认行为。
- **输入格式**：底图统一转 ≤1024 长边 JPEG 再上传（模型可靠吃 JPEG 且减小请求体）；源库的
  HEIC/WebP 由这一步归一，不依赖模型原生支持。
- 输出分辨率即 AI 视频分辨率（抽帧时长边 ≤1920），非严格等于屏幕比例；铺放由系统按当前填充模式处理。

## 关联

- 依赖/不改：ADR-016（播放引擎）、ADR-015（本地库 / `kind` 分类，AI 产物落 `kind: .animation`）。
- 明确不做：free-form 裁剪比例（ADR-018 已否决）、视频播放内核（本 ADR 决定不改）。
