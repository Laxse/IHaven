# ADR-009: 代码组织与单文件 300 行约束

## Status: Accepted (2026-10-08)

## Background

`code-organization` 规范要求落地为可执行的目录结构与文件组织约束：单文件 ≤300 行、单一职责、入口只装配、按资源分包。

IHaven 是全新工程，无存量代码迁移负担，是建立这套纪律的最佳时机。生成式代码产出最容易在「文件越来越长」上滑向失控——单文件超长会让后续每次修改都需通读全部上下文，信噪比塌陷。

## Decision

### 分层架构（依赖严格单向向下）

```
Presentation (SwiftUI)
    ↓ 仅依赖 Feature 层；不直接触碰 DB / Network / Wallpaper
Feature (Browse / Favorites / Filter / Assign / Editor / Settings)
    ↓ 仅依赖 Domain 协议
Domain (纯值类型 + 协议，无 UIKit / DB 依赖)
    ↓
Infrastructure (Database / Network / Image / Security / Telemetry)
    ↓
Platform (WallpaperEngine / ScreenWatcher / Media)
```

### 目录结构

```
IHaven/
  App/                应用入口，只做装配
  Core/
    Models/                纯值类型
    Protocols/             领域协议定义
    Extensions/
  Features/                按用户能力切分，每个子目录文件 ≤300 行
    Browse/  Favorites/  Filter/  Assign/  Editor/  Settings/
  Infrastructure/
    Database/ Network/ Image/ Security/ Telemetry/
  Platform/
    Wallpaper/ Screen/ Media/
  Resources/
    Assets.xcassets/  Localizable.xcstrings
```

### 六条硬规则

1. **单文件 ≤300 行**。超出即拆，不靠压缩排版过关。
2. **入口文件只做装配**。`IHavenApp.swift` 不含业务逻辑。
3. **按资源分包**，不建 `Views/` `Models/` `Utils/` 这类横向大杂烩目录。
4. **依赖单向向下**。Feature 不得 import Infrastructure 的具体类型，只依赖 Domain 协议。
5. **禁止反向 import**。Core 不得依赖 Features/Infrastructure；Domain 不得依赖 UIKit 或数据库。
6. **单一职责**。一个文件解决一类问题。发现文件名需要 `And` 时就该拆。

## Rationale

### 为何按「用户能力」而非「技术类型」分包

`Views/` `Models/` `Utils/` 这种横向切分在文件数量增长后会失去定位能力——想找「收藏功能的数据库逻辑」需跨三个目录。`Features/Browse/` 这样组织后，一个功能的全部代码在一个子树内。

按技术类型分包在小项目里看起来整洁，在瀑布流 + 收藏 + 筛选 + 多屏分配 + 编辑器五个 Feature 的规模下会迅速失控。

### 为何 Feature 层必须依赖协议而非实现

`Domain` 层定义 `FavoritesRepository`、`KeyProvider`、`ImagePipeline` 等协议，`Infrastructure` 提供 GRDB / Keychain / Nuke 实现。这样测试可用内存实现替换全部外部依赖。

**这不是过度设计**：PRD F7 的离线兜底测试、401 区分测试、限流边界测试全部依赖这个能力。没有协议抽象，这些测试需要真实网络与真实 Keychain，无法自动执行。

### 为何 300 行是硬约束而非建议

文件长度与后续每次修改的上下文成本直接相关。300 行大约是一个「完整读完不需要来回滚动」的阈值。超过后：
- 修改时需通读全文，上下文信噪比下降
- 职责边界模糊，容易在长文件里塞入不相干逻辑
- 代码评审的有效性下降

关键点：**拆分要在写的时候就做，而不是等文件长到 300 行再拆**。后者往往因为拆分成本高而被拖延，最终容忍更长的文件。

## Consequences

### 正面

- 文件职责边界清晰，修改时上下文成本可控
- Domain 协议使测试可完全离线运行
- 按 Feature 分包让功能删除或重排的成本低
- 单文件约束与生成式代码的「沉默逻辑错误」防线一致——短文件更容易被完整测试覆盖

### 负面

- 文件数量较多（预计 MVP 阶段约 60-80 个 Swift 文件）
- 初期需要刻意遵守，后期靠 CI 维持
- 跨 Feature 的共用类型需要判断放入 Core 还是某个 Feature，初期会有少量摇摆

### 关键约束

**CI 门禁（已实现并通过双向测试）**：

三个门禁脚本已落地 `scripts/`，每条规则都用「注入违规 -> 确认拦截 -> 清理 -> 确认通过」的方式双向验证：

| 脚本 | 依据 | 拦截内容 |
| --- | --- | --- |
| `scripts/api-gate.sh` | ADR-007 | Apple API 存在性核验（`swiftc -typecheck` 对真实 SDK） |
| `scripts/security-gate.sh` | ADR-006/008 | 明文 Key、`?apikey=` query 传参、Key 落 UserDefaults/日志、`dlopen` 私有 API |
| `scripts/convention-gate.sh` | ADR-004/009 | 单文件 >300 行、`ObservableObject` 体系、Core 层反向依赖、入口文件超长 |

CI 工作流：`.github/workflows/gates.yml`（先 `xcode-select --switch` 到 Xcode，再依次跑三个门禁，最后 `xcodebuild build`）。

**BSD grep 兼容性注意（本项目实际踩过的坑）**：macOS 自带 BSD grep，`-E` 模式**不支持** `\s`、`\d`，basic 模式也**不支持** `\|` alternation。写门禁脚本必须用 POSIX 字符类 `[[:space:]]` 并显式加 `-E`，否则规则会**静默失效**——门禁显示 PASS 但实际抓不到违规。

这是本次的实际经历：首版门禁的 4 条规则里有 3 条因`\s` 与 `\|` 不被支持而完全失效，且脚本返回 PASS。这是比「门禁报错」危险得多的失败模式（假阴性）。任何新增门禁规则都必须先做负向测试，确认真能拦截。

## Alternatives Considered

**横向分包（`Views/` `Models/` `Utils/`）**：小项目整洁，规模上来后失去定位能力。否决。

**单文件不设上限**：早期省事，后期上下文成本失控。否决。

**按 target 强隔离（多个 framework 模块）**：编译期隔离更彻底，但 MVP 阶段构建复杂度与调试成本上升。按「不做过度设计」原则，单 target + 目录分层 + CI 静态检查是恰当强度。若后期某 Feature 需要独立生命周期（如动态壁纸 helper），再拆 target（ADR-003 已预留）。
