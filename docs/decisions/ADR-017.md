# ADR-017: 图片缓存改用 DataCache，并放宽内存缓存单条上限

## Status: Accepted (2026-10-16)

## Background

用户反馈「感觉每次都是重新加载的高清图片和缩略图片」。查下来不是错觉——**高清图确实每次都重新下载**，
而项目此前一直以为「用了 Nuke 就有缓存」。

`NukeImagePipeline` 只写了一行 `static let pipeline = ImagePipeline.shared`，即使用 Nuke 的默认配置
`.withURLCache`。实测（2026-10-16，样本 `5ypv78`，3805×5700，原图 4.66MB）发现这套默认配置**在两头都留不住高清图**：

### 实测一：内存缓存根本不收高清图

`ImageCache.shared` 默认 `costLimit` = 物理内存 15%（封顶 768MB），而 `entryCostLimit` 默认 **0.1** ——
Nuke 的语义是「单条成本超过缓存上限 10% 就**直接不存**」（`Cache.Configuration.recomputeEntryMaxCost`）。

一张 3805×5700 的高清图解码后约 **87MB** > 768MB × 0.1 = **76.8MB**，于是**永远进不了内存缓存**。
同一个进程里连续加载同一张高清图：

| | 默认配置 |
| --- | --- |
| 第 1 次 | 3819 ms |
| 第 2 次 | **2925 ms**（几乎等于重下一次） |

### 实测二：磁盘缓存里也抓不到高清图

`.withURLCache` 的磁盘层只有 `URLCache`（**内存容量 0**、磁盘 150MB）。本机
`~/Library/Caches/com.ihaven.app/Cache.db` 共 402 条记录，**全部是 `th.wallhaven.cc` 缩略图**，
`w.wallhaven.cc/full/`（高清图）**0 条**。

（注：单独的 `URLCache` 实验里 4.6MB 的响应是能存进去的，所以这里不能简单归因为「CFURLCache 不存大文件」；
但结论不变——线上跑出来的结果是高清图一条都没留下。）

## Decision

一、**装配显式配置的管线并写回 `ImagePipeline.shared`**，在 `IHavenApp.init()` 里、早于任何视图构建地调用
`NukeImagePipeline.install()`。

二、**磁盘层换用 Nuke 的激进缓存 `DataCache`**：`withDataCache(name: "com.ihaven.Images", sizeLimit: 512MB)`，
`dataCachePolicy = .storeOriginalData`。注意 `withDataCache` 会顺手把 `urlCache` 置 nil（HTTP 缓存关掉）——
两套磁盘缓存并存只会让命中行为不可预测，留一套可控的。

三、**内存缓存显式配**：`ImageCache(costLimit: 256MB, countLimit: 200)`，`entryCostLimit = 0.5`
（单条上限 128MB，装得下一张高清图）。

## Rationale

### 为什么必须写回 `shared`，而不是自己留一份

NukeUI 的 `LazyImage` 内部是 `private var pipeline: ImagePipeline = .shared` —— 在**视图初始化那一刻**
就把 `.shared` 抄进实例。项目里所有 `LazyImage` 都没显式 `.pipeline(...)`，所以只有替换 `shared` 本体才生效；
反过来也意味着 `install()` 必须早于任何视图构建（故放在 `App.init()`）。

同理，`NukeImagePipeline.pipeline` 改成**计算属性**而非 `static let`：后者会在首次访问时固化当时的 `shared`，
顺序一颠倒就会拿到旧管线。

### 为什么用 DataCache 而不是继续用 URLCache

`DataCache` 存的是**原始字节**，与 HTTP 响应头无关、也不会再去回源校验（ETag / `max-age` 到期后的 304 往返都没有）；
`URLCache` 的落盘行为受响应头和系统实现双重影响，且内存容量被 Nuke 设成 0，每次命中都是一次磁盘读 + 全量解码。
对「看过的壁纸不该再下一次」这个目标，`DataCache` 更可预测。

### 为什么不直接把 `costLimit` 调大到能装下高清图

`entryCostLimit` 是**比例**而非绝对值：只调 `costLimit` 不调 `entryCostLimit`，单条上限按比例一起涨、
缓存会被两三张高清图填满再无意义地抖动。两个值必须一起定。反过来只调 `entryCostLimit` 到 0.25 而保留默认
768MB 上限，等于允许进程常驻 768MB 位图——对常驻桌面的壁纸应用偏大，故内存上限一并收到 256MB。

### 实测对比（同一张 4.66MB / 3805×5700 高清图）

| 场景 | 默认 `.withURLCache` | 本 ADR 配置 |
| --- | --- | --- |
| 同进程内第 2 次加载 | 2925 ms | **0 ms**（内存命中） |
| 冷启动（新进程，内存空） | 2464 ms（走网络） | 命中 `DataCache` 中的 4.66MB 原始字节，**不走网络** |

真机验证：`dist/IHaven.app` 冷启动 12 秒内 `~/Library/Caches/com.ihaven.Images` 已落 25 条缩略图条目，
证明 `install()` 生效、磁盘层可用。

## Consequences

### 正面

- 看过的缩略图与高清图都留在磁盘（512MB LRU），重开应用不再重复下载
- 详情页来回切换同一张高清图为内存命中，进度条也不再出现（配合 ADR-013 的加载进度提示，此时才是真加载）
- 磁盘缓存位置单一、可预测：`~/Library/Caches/com.ihaven.Images`

### 负面

- 磁盘占用最多 512MB（LRU 自动淘汰，但目前设置里没有「清除缓存」入口）
- 内存缓存常驻上限 256MB（原为 768MB，但对高清图实际长期是 0 命中）
- 关掉 `URLCache` 后，若将来接入依赖 HTTP 缓存语义的接口，需重新评估

### 遗留（已在同一轮补齐）

设置面板新增「存储」页签（`Features/Settings/SettingsStorageTab.swift`）：

- **图片缓存**：显示占用 + 「清除」。内容可再生，不弹确认，清完给「已清理」。
- **动态壁纸帧序列**：显示共占用 + 「未使用 N 项 · X MB」，只清理**孤儿目录**（目录名不在库内的动态壁纸 id 里），
  仍在库的动态壁纸一个字节都不碰；无孤儿时按钮禁用。

占用一律**实测目录**而非 `DataCache.totalSize`：后者读内存索引，进程刚起来、索引未建完时是 0，
设置页会显示「占用 0 字节」而磁盘上其实有几百 MB。

## Alternatives Considered

**只改 `entryCostLimit`，不动磁盘层**：内存侧能命中，但重开应用仍然全部重下——用户抱怨的是「每次」，
其中很大一部分是冷启动。否决。

**继续用 `URLCache`，只把容量调大**：内存容量仍为 0、仍受响应头支配，且实测线上 0 条高清图的事实无法解释清楚。
否决。

**给高清图加下采样请求（`ImageRequest.ThumbnailOptions`）**：详情页要「完整显示 + 可设为壁纸」，必须是原图分辨率，
降采样与 ADR-013「完整显示、绝不裁切」冲突。否决。
