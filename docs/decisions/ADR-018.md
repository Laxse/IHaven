# ADR-018: 设置壁纸前的裁剪选框（竖图黑边）

## Status: Accepted (2026-10-18)

## Background

用户反馈原话：「图片是纵向的时候设置壁纸会出现两边儿有黑边儿的情况，看要不要设置壁纸时候出现个二级选框，来选择那部分设置成壁纸，跟一些网站上设置头像的逻辑一样」。

根因不是渲染，是默认值：`WallpaperTarget.fillMode()` 用 `UserDefaults.integer(forKey:)` 读填充模式，未设置时它返回 `0`，而 `WallpaperFillMode` 的 `rawValue == 0` 恰好是 `.fit`（完整可见、四周留白）。原实现里的 `?? .fill` 因此是**死分支** —— `0` 是合法 rawValue，`WallpaperFillMode(rawValue: 0)` 不会返回 nil，永远轮不到回退。竖图铺到横屏上，`scaleProportionallyUpOrDown` + `allowClipping = false` 的必然结果就是左右两条黑边。默认值已在同一次改动中修正（改为先判「有没有写过」，没写过才回 `.fill`）。

但仅修默认值不够：用户要的是「**自己选哪一部分**」，而 `.fill` 只会盲裁居中区域。要满足这个诉求，必须先搞清楚系统层能做到哪一步。

实测结论（`Platform/Wallpaper/SystemWallpaperEngine.swift`，2026-10-17）：`NSWorkspace.setDesktopImageURL(_:for:options:)` 的 `DesktopImageOptionKey` 里**只有** `imageScaling` / `allowClipping` / `fillColor` 三项。**没有任何「从源图的哪个矩形取像素」的参数** —— 系统永远按等比缩放后居中取，裁切焦点不可指定（与 `ARCHITECTURE.md §6.2.2` 的结论一致）。因此裁剪只能在调用系统 API **之前**完成：把结果渲染成一个新文件，再把那个文件交给 `setDesktopImageURL`。

## Decision

提供「设置壁纸前先裁剪」的二级选框，落点如下。

1. **裁剪结果必须先渲染成本地文件**，再交给 `WallpaperEngine.setWallpaper`。
   `sourceURL` 一律是本地 fileURL：远程 URL 进 `setDesktopImageURL` 实测 **SIGABRT（exit 134）**，且是 Objective-C 异常路径、Swift 的 `throws` 拦不住（`SystemWallpaperEngine` 已在入口兜了一层 `isFileURL` 判空，但不依赖它兜底）。网络壁纸走 `OfflineImageStore` 命中优先、否则下载原图；本地导入项直接就是本机文件。

2. **选框锁定目标屏宽高比**（`WallpaperTarget.cropAspect()`），**不做自由比例**。
   自由比例裁完仍然可能不是屏幕比例，铺上去照样有黑边 —— 那等于没解决用户报的问题。选框的宽高比恒等于目标屏，用户只能平移与等比缩放，这是刻意的限制而非功能缺失。

3. **裁剪产物一律以 `.fill` 写入**，覆盖用户当前的填充模式设置。
   产物宽高比已经等于目标屏，但像素取整会有 ±1px 误差；这 1px 在 `.fit` 下会变成一条极细留白（正是用户报的症状），而 `.fill` 只会把边缘裁掉 1px，肉眼不可见。写 `mode: .fill` 而不是 `WallpaperTarget.fillMode()`。

4. **落盘目录 `AppPaths.sub("Crops")`**，与 `Originals` / `Wallpapers` / `Animations` 同级。
   语义是「由原图派生、可重建」，属于缓存而非资产 —— 不写进 `Originals` 是为保住那里 URL 到文件名的一一映射（离线兜底靠这个映射反查），混入派生产物会让映射出现二义。文件名 `<原名去扩展名>-crop-<宽>x<高>.jpg`。

5. **裁剪必须走全分辨率**，不套 `AnimationRenderer.workMaxPixel = 1920`。
   那个 1920 是给动态壁纸**帧序列**降采样用的（每秒 12 帧 × 多秒，体积与内存都要压）；静态壁纸只有一张，降采样会直接损失清晰度。`WallpaperCropWriter` 用 16384 作为 `kCGImageSourceThumbnailMaxPixelSize`（ImageIO 的 MaxPixelSize 只缩不放，小图不会被放大）。

6. **必须 `kCGImageSourceCreateThumbnailWithTransform: true`**。
   wallhaven 的图与手机拍的照片普遍带 EXIF orientation；不先转正的话「用户在预览里框的那一块」与「按像素坐标裁出来的那一块」会差一个 90° 旋转 —— 属于肉眼可见但极难归因的错裁。

7. **入口是显式二级按钮**，不做「每次设壁纸都弹裁剪」。
   详情页「设为壁纸」之后、「下载原图」之后新增「裁剪…」；本地导入卡片 hover 按钮组新增裁剪图标。横图在横屏上本来就没有黑边，强制每次弹窗是交互倒退；后台定时轮换（PRD F13）更没有 UI 可弹。

## Rationale

### 为什么是「先裁成文件」而不是「告诉系统裁哪里」

系统 API 没有这个 option（见 Background 的实测）。这是唯一可行的路径，不是偏好问题。`ARCHITECTURE.md §6.2.2` 早已判过同一件事并给出同一结论（客户端预裁切），本次是把它落地。

### 为什么锁比例

用户报的症状是「黑边」。黑边的充分必要条件是「源图宽高比 ≠ 屏幕宽高比且填充模式为 fit」。锁死比例后，产物宽高比恒等于屏幕，无论系统按 fit 还是 fill 铺都不留白 —— 这一条同时消掉了「用户把填充模式切回适应」时症状复发的可能。自由比例在数学上无法给出这个保证。

### 为什么产物写 `.fill`

见 Decision 第 3 条。补充一层：用户在设置面板里选的是「对原图怎么铺」，而裁剪产物**已经是**按屏幕比例裁好的图，此时再套用「对原图」的偏好是错配 —— 这里覆盖它是语义正确，不是越权。

### 为什么独立目录

`Originals` 的 URL→文件名一一映射是 F7 离线兜底的基础设施（离线时用远程 URL 反查本地已下载的原图）。把派生产物写进去，同一个 wallhaven id 会对应多个文件，映射退化成一对多，离线命中逻辑要么变复杂、要么静默拿错文件。分目录是零成本的结构性隔离。

### 为什么不做全屏强制弹窗

交互成本与收益不成比例。设壁纸是高频操作，绝大多数场景（横图对横屏）不需要裁剪；每次都弹一个 780×620 的 sheet 会把一步操作变成三步。而且轮换日程是后台触发，根本没有可弹的 UI —— 若把裁剪做成必经步骤，轮换链路会直接断掉。

## Consequences

### 正面

- 竖图设壁纸的左右黑边被根治，且由用户决定保留哪一部分（与网站头像裁剪一致的心智模型）
- 产物比例锁定屏幕，用户事后切换填充模式也不会复发
- 裁剪逻辑集中在 `WallpaperCropRect`（纯数学，无 AppKit 依赖）+ `WallpaperCropWriter`（ImageIO），可独立验证
- 入口是显式按钮，不影响既有的「一键设为壁纸」与后台轮换

### 负面

- 每次裁剪会在 `Application Support/IHaven/Crops/` 留一个文件，当前**没有清理策略**（既不按数量淘汰也不按时间淘汰）—— 反复裁同一张图会累积同内容不同尺寸的文件
- 裁剪产物是 JPEG quality 0.92 的有损重编码，比原图略损（原图为 PNG 时损失更明显）
- 大图（4K 以上）解码是同步的，sheet 打开瞬间有几百毫秒的等待（放在 `.task` 里，不卡首帧，但没有 loading 之外的进度反馈）
- 「已设置」记录按 `id` 覆盖（`Database.addApplied` 是 `INSERT OR REPLACE`）：裁剪一张已经设过的壁纸，会用裁剪产物的 `localPath` 与尺寸**替换**掉原图那条记录。语义上可接受（最近一次设的就是裁剪产物），但「已设置」页不会同时保留「原图那次」，且后续从该记录「重新设置」拿到的是裁剪产物而非原图

### 关键约束

**裁剪必须在调用 `setWallpaper` 之前完成，且产物必须是本地文件。** 这两条不是实现细节而是硬约束：远程 URL 会 SIGABRT，且不存在「让系统裁」的替代方案。任何后续重构（例如把裁剪挪到后台队列、或加缓存复用产物）都不得破坏这两条。

**`CropRequest` 只带 `sourceURL`，不带 `aspect` / `screenLabel`。** 两者在 sheet 呈现时现读 `WallpaperTarget.cropAspect()` / `cropScreenLabel()`。存进请求里的话，用户在别的屏上改过目标屏、或呈现期间插拔了显示器，选框锁的就是过期比例 —— 那是一条看不见的错裁。

**`.sheet(item:)` 必须挂在 `BrowseView` 这一层。** 项目已实测过「子视图挂模态会被父级 `.sheet` 抑制，表现为点了没反应」（`BrowseView.swift` L24-27 与 `ImportView.swift` L12-14 均有记载）。详情页与导入页只上抛回调，不自己挂 sheet。

## Alternatives Considered

**给 `SystemWallpaperEngine` 加 `cropRect` 参数**：看起来最自然，但系统 API 的 options 里只有 `imageScaling` / `allowClipping` / `fillColor`，没有任何指定源图矩形的位置。做不到。否决。

**改成默认 `.fill` 就完事**：默认值 bug 确实修了（本次已修），但用户明确要的是「自己选哪一部分」。`.fill` 只会盲裁居中区域，竖图的上下部分被无差别丢掉 —— 用户报的是「我要能选」，不是「替我裁」。部分采纳（默认值照修），不作为本功能的替代。

**每次设壁纸都弹裁剪 sheet**：一致性强，但多数场景无黑边，强制打断是交互倒退；且后台定时轮换没有 UI 可弹，那条链路会直接断掉。否决。

**用 `NSImage` 绘制 / `CGContext` 重绘**：项目现有管线是 ImageIO + `CGImage.cropping`，`AnimationRenderer` 也是这套。再加一条 NSImage 绘制路径意味着两套重采样算法并存，在半像素与 EXIF 方向这类边界上必然出现「预览与实际不一致」的静默差异。否决。
