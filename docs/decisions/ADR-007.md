# ADR-007: macOS 26 弃用 API 规避清单（编译核验产出）

## Status: Accepted (2026-10-08)

## Background

`generated-code-failure-modes` 知识库将「幻觉依赖 / 接口」列为高危失效模式，纠偏纪律是：**依赖与接口存在性核验，版本锚定，按实际版本 API 写，不凭记忆编签名**。

本项目的部署目标是 macOS 26，工具链是 macOS 27.0 SDK + Swift 6.4。这意味着大量「网上还能搜到的写法」与「当前 SDK 的真实 API」存在偏差。凭直觉书写会产出编译失败或——更糟——静默失效的代码。

本文档记录**实际通过编译核验**发现的陷阱，作为实现规范的硬约束。

核验方法：编写探针文件，用 `swiftc -typecheck` 对真实 SDK 编译，让编译器给出精确诊断。

```bash
swiftc -typecheck -sdk "$(xcrun --show-sdk-path)" \
  -target arm64-apple-macosx26.0 docs/VERIFIED-API.swift
```

核验样本存档于 `docs/VERIFIED-API.swift`（零错误零警告）。

## Decision

以下 API 形态为**唯一正确写法**，任何扩写必须先过编译核验门禁。

## 总则：这些陷阱为什么会进入文档

本ADR 的 17 个陷阱不是 17 个独立的失误，而是**三种系统性缺口**的产物。

### 机制一：缺少能让错误假设破产的对照（Trap 1/2/9/10/11/12/13/16）

> **对照组的价值不是「发现新事实」，而是「推翻既有假设」。**

Phase 1 的四次修正—— 401 双语义、`type:` 参数形式、空 Key 静默判有效、NSFW 权限与筛选过窄不可区分 —— **每一条都是被某个对照推翻的**：

| 错误结论 | 哪个对照推翻了它 |
| --- | --- |
| 401 有NSFW 与 Key 无效两种含义 | 同一 Key 跨 purity 对比 |
| `type:` 参数无效 | 把 `type:` 放进 `q=` 内|
| 200 = Key 有效 | 空 Key 与匿名请求对比 |
| NSFW 空结果 = 权限不足 | `purity=001` 不带筛选的固定宽查询 |

**若当初设计了这些对照，四次错误都不会进入文档。**

设计者的观察很精确：若只测 NSFW 组合，我们会看到 401 和 200 两种结果，**可能得出「401 有两种含义」的错误结论** —— 正是这个错误本身。

### 机制二：被测对象的语义未经确认（Trap 3/4/5/6/7/8/14/15/17）

并非所有实测都能靠对照解决。另一类错误发生在**动手测之前**：

| 陷阱 | 缺的不是对照，而是前提 |
| --- | --- |
| `NSScreen.displayID` | 属性名不存在（编译期才发现） |
| `NSImageScaling` 枚举短名 | ObjC 前缀未被剥离 |
| 视频合成 API | macOS 26 已弃用旧形态 |
| 401 = NSFW 权限不足 | **该语义服务端从未承诺** |
| `/settings` 可验证 Key | 端点存在 ≠ 语义符合用途 |
| `/settings` 的 `data.purity` = NSFW 搜索能力 | 该字段描述的是**偏好设置**，服务端从未承诺它等于搜索权限 |

这一类的共同点是：**把「我没找到」等同于「它不存在」**，或把「它能工作」等同于「它能用于我的场景」。

### 机制三：结论的作用域被放大（新增）

> **对照有效、前提正确，但结论被外推到超出实测范围。**

这一类最隐蔽，因为它**完全符合前两条，却仍然错**。

| 错误结论 | 实测范围 | 外推到的范围 |
| --- | --- | --- |
| `purity=001` 探测 `total=0` = NSFW 权限不足 | 仅 NSFW 空结果场景 | 所有空结果场景 |
| `/settings` 返回 404 可用来判 Key 状态 | 仅该端点 | 「401 与 404 是两种 Key 状态」 |

**特征**：样本能区分假设（前两条都通过），被测对象语义也确认了，但结论的适用范围悄悄变大。

**本 ADR 的作者本人也犯过这一类**：客户端校验表里写「`resolutions` / `ratios` 非法值返回 200，不构成风险」。

实测反证：`ratios=99x99` 返回 HTTP 200 + `total=5005` + 24 条数据 —— 但那 24 条的 `ratio` **全部是 `1`**（1:1 方图），尺寸为 2000×2000、6666×6666 等。**200 不代表安全，只代表服务端没报错。**

这条在同文档的 Trap 13 里已正确记录为「静默匹配」，但校验表里写成了「不构成风险」—— **同一份文档内对同一实测给出了矛盾结论**，且危险的那一版更显眼（它在表格里，实施者会照它写代码）。

### 三层的适用条件与操作化判据

| 机制 | 适用前提 | 防御手段 | 操作化判据 |
| --- | --- | --- | --- |
| 对照机制 | 存在**竞争假设** | 设计能让假设破产的对照组 | 「如果我的假设是错的，样本里有什么会与它矛盾？」答不上来 = 样本不足 |
| 前提机制 | 假设**尚未验证** | 编译核验 + 官方文档溯源 | 这个 API/属性**真的存在吗**？**语义是什么**？ |
| **作用域机制** | 假设**已被验证** | 写出结论时附适用边界 | 「该结论的适用边界是 ____，超出此范围需重新实测。」**填不出边界 = 作用域还没想清楚** |

**三层合起来才完整**：本项目15+ 处修正中，第一类被纪律 4 抓住，第二类被 4b 抓住，**第三类此前无纪律覆盖** —— 所以它会继续发生。

**最危险的一条**：作用域错误**看起来像已经验证过**。前两条错误会暴露「我没测」，而作用域错误的症状是「我测了，测得也对，结论也用了」—— 只有回头检查适用边界才能发现。

**一条自查**：同一实测在文档不同位置出现时，**结论必须一致**。矛盾的两版中，更显眼的那版（表格里的）更容易被实施者照抄，风险更高。

## Traps Found: 17 个凭直觉会写错的签名/约束

### Trap 1: 壁纸选项键名是 `.imageScaling`，不是 `.scaling`

编译器诊断：
```
type 'NSWorkspace.DesktopImageOptionKey' has no member 'scaling'
```

正确：
```swift
var opts: [NSWorkspace.DesktopImageOptionKey: Any] = [:]
opts[.imageScaling] = NSImageScaling.scaleProportionallyUpOrDown
opts[.allowClipping] = true
```

注意：ObjC 侧常量名是 `NSWorkspaceDesktopImageScalingKey`，但 Swift 导入后的成员名是 `.imageScaling`，`.allowClipping` 与 `.fillColor` 则保持单词形态。**三者命名规则不一致**，不能类推。

### Trap 2: 枚举成员是 `NSImageScaling.scaleProportionallyUpOrDown`，不是 `.proportionallyUpOrDown`

编译器诊断：
```
type 'NSImageScaling' has no case 'proportionallyUpOrDown', but it does have
a case named 'ScaleProportionallyUpOrDown'; if 'proportionallyUpOrDown'
worked before, a recent change to the underlying C enum may have affected
how prefixes are stripped from its case names
```

**这是最危险的一类陷阱**：ObjC 侧枚举名为 `NSImageScaleProportionallyUpOrDown`，Swift 导入时保留了 `Scale` 前缀。凭 ObjC 经验写出的 Swift 短名不编译。

完整枚举成员（五个填充模式全部核验）：
- `NSImageScaling.scaleAxesIndependently`
- `NSImageScaling.scaleNone`
- `NSImageScaling.scaleProportionallyDown`
- `NSImageScaling.scaleProportionallyUpOrDown`

**系统限制**：`scaleProportionallyDown`（只缩不放）在 AppKit 中定义但**系统声明不支持**。因此小图放大到大屏必然模糊，无法用参数规避，只能靠下载足够分辨率的原图。

### Trap 3: 视频合成 API 在 macOS 26 已弃用旧形态

编译器警告：
```
'AVMutableVideoComposition' was deprecated in macOS 26.0:
Use AVVideoComposition.Configuration instead
'AVMutableVideoCompositionLayerInstruction' was deprecated in macOS 26.0:
Use AVVideoCompositionLayerInstruction.Configuration instead
'AVMutableVideoCompositionInstruction' was deprecated in macOS 26.0
```

新形态是**不可变** `Configuration` 值类型 + 构造函数：

```swift
let layer = AVVideoCompositionLayerInstruction(
    configuration: .init(assetTrack: ct))
let instr = AVVideoCompositionInstruction(
    configuration: .init(backgroundColor: CGColor(gray: 0, alpha: 1),
                         layerInstructions: [layer],
                         timeRange: range))
let session = AVAssetExportSession(
    asset: comp, presetName: AVAssetExportPresetHEVCHighestQuality)!
session.videoComposition = AVVideoComposition(
    configuration: .init(instructions: [instr], renderSize: size))
```

**三个必须知道的性质**：

1. **属性是 `get` only**。编译器诊断 `cannot assign to property: 'c' is a 'let' constant`。必须**在构造时一次性传入全部参数**，构造后不能改。
2. **参数顺序固定且不可跳过**。编译器诊断 `argument 'backgroundColor' must precede argument 'timeRange'`。错误顺序直接编译失败。
3. **不接受额外参数**。诊断 `extra argument 'extraBogus' in call`（用于确认只有单参数成员初始化器）。

**迁移陷阱**：旧 API 是「先 new 再逐个 set」，新 API 是「构造时全给」。按旧模式迁移必然失败。

### Trap 4: `addMutableTrack` 与 `insertTimeRange` 是同步的，不是 async

编译器警告：
```
warning: no 'async' operations occur within 'await' expression
warning: no calls to throwing functions occur within 'try' expression
```

正确写法（`throws` 与 optional 仍需处理）：
```swift
guard let src = try await source.loadTracks(withMediaType: .video).first,
      let dest = comp.addMutableTrack(withMediaType: .video,
                                     preferredTrackID: kCMPersistentTrackID_Invalid)
else { throw CocoaError(.fileReadCorruptFile) }
try dest.insertTimeRange(range, of: src, at: .zero)
```

注意 `addMutableTrack` 返回 **optional**，必须解包。

### Trap 5: `tracks(withMediaType:)` 已弃用，必须用 `loadTracks`

编译器警告：
```
'tracks(withMediaType:)' was deprecated in macOS 13.0:
Use loadTracks(withMediaType:) instead
```

```swift
let tracks = try await asset.loadTracks(withMediaType: .video)
```

这是 macOS 13 起就存在的迁移项，但网上大量文章仍是旧写法。

### Trap 6: 屏幕变化通知名是 `NSApplication.didChangeScreenParametersNotification`

编译错误：
```
type 'NSWorkspace' has no member 'screensDidChangeNotification'
```

正确通知名清单（全部编译核验）：

| 通知 | 宿主 |
| --- | --- |
| `NSApplication.didChangeScreenParametersNotification` | **NSApplication**（不是 NSWorkspace） |
| `NSWorkspace.activeSpaceDidChangeNotification` | NSWorkspace |
| `NSWorkspace.didWakeNotification` | NSWorkspace |
| `NSWorkspace.screensDidSleepNotification` | NSWorkspace |
| `NSWorkspace.sessionDidResignActiveNotification` | NSWorkspace |

另：`NSScreen.maximumPotentialFramesPerSecond` **不存在**。可用的屏幕属性限于 `frame`、`visibleFrame`、`backingScaleFactor`、`localizedName`。

### Trap 7: `NSScreen.displayID` 不存在，且 `cgDirectDisplayID` 是 Optional

这是多屏分配（PRD F2）最容易踩的坑。编译器诊断：
```
value of type 'NSScreen' has no member 'displayID'
```

`NS_REFINED_FOR_SWIFT` 的属性导入后名字变了，且变成**可选**：

```swift
// 正确：注意是cgDirectDisplayID，且返回 CGDirectDisplayID?（Optional<UInt32>）
guard let displayID = screen.cgDirectDisplayID,
      displayID != kCGNullDirectDisplay
else { return nil }
```

头文件依据（`NSScreen.h:72-73`）：
```objc
/// The CGDirectDisplayID for this screen. This will return kCGNullDirectDisplay if there isn't one.
@property (readonly) CGDirectDisplayID CGDirectDisplayID API_AVAILABLE(macos(26.0)) NS_REFINED_FOR_SWIFT;
```

穷举排除的候选名（均编译失败）：`displayID` / `directDisplayID` / `cgDirectDisplayID`（不带 optional 处理时）。

### Trap 8: `deviceDescription` 的键类型不是 String

编译器诊断：
```
cannot assign value of type '[NSDeviceDescriptionKey : Any]' to type '[String : Any]'
```

`deviceDescription` 的键是 `NSDeviceDescriptionKey` 枚举，不是 `String`。且穷举 `.screenNumber` / `.screenNumberValue` / `.vendorNumber` / `.modelNumber` 均编译失败。

**结论：不要用 `deviceDescription` 取显示器标识。** 改用 `CGDisplay*` 系列（已核验存在）：
```swift
CGDisplayVendorNumber(id)   // UInt32
CGDisplayModelNumber(id)    // UInt32
CGDisplaySerialNumber(id)   // UInt32
CGDisplayUnitNumber(id)     // UInt32
```

### Trap 9（最关键）：`CGDirectDisplayID` 不是持久的存储键

这条不是编译错误，是**设计陷阱**——编译能过、运行也对，但持久化后重启就错位。

**引用来源标注**（team-lead 质疑后已复核）：

Apple 官方文档 [CGDirectDisplayID](https://developer.apple.com/documentation/CoreGraphics/CGDirectDisplayID) 的 Discussion 段原文：

> When a monitor is attached, Quartz assigns a unique display identifier (ID). A display ID can persist across processes and **typically remains constant until the machine is restarted**.
>
> When assigning a display ID, Quartz considers the following parameters: Vendor, Model, Serial number, Position in the I/O Kit registry

**重要区分**：这段文字**只存在于 Apple 在线文档，不在 SDK 头文件中**。`CGDisplayConfiguration.h` / `CGDirectDisplay.h` 均未包含任何关于 ID 持久性的表述——`CGDirectDisplay.h:20` 只有 `typedef uint32_t CGDirectDisplayID;`。这一点必须写明，否则会被误当作头文件依据。

结论仍然成立：Apple 用 *typically* 而非 *always*，未承诺跨重启稳定；社区另有多 GPU 机型切换 GPU 时 displayID 变化的记录。**本项目按「displayID 不保证跨重启稳定」设计**，这是保守但正确的取舍。

**依赖的四个 API 已核验无弃用标记**：

```
CGDisplayConfiguration.h:352  CG_EXTERN uint32_t CGDisplayUnitNumber(CGDirectDisplayID display)   API_AVAILABLE(macos(10.2));
CGDisplayConfiguration.h:357  CG_EXTERN uint32_t CGDisplayVendorNumber(CGDirectDisplayID display) API_AVAILABLE(macos(10.2));
CGDisplayConfiguration.h:362  CG_EXTERN uint32_t CGDisplayModelNumber(CGDirectDisplayID display)  API_AVAILABLE(macos(10.2));
CGDisplayConfiguration.h:367  CG_EXTERN uint32_t CGDisplaySerialNumber(CGDirectDisplayID display) API_AVAILABLE(macos(10.2));
```

注：声明位于 `CoreGraphics.framework/Versions/A/Headers/CGDisplayConfiguration.h`。直接 grep `CoreGraphics.framework/Headers/` 会因框架的 `Versions/A` 目录结构而**搜不到**——这是我在核验中实际踩到的定位坑。

**因此两级标识**（已编译核验，见 `VERIFIED-API.swift` §6）：

| 层级 | 键 | 用途 | 稳定性 |
| --- | --- | --- | --- |
| 会话级 | `CGDirectDisplayID` | 运行期索引、窗口与播放器的绑定 | 单次运行内唯一稳定 |
| 持久级 | `v\(vendor)-m\(model)-s\(serial)` | SQLite `display_assignments` 的存储键 | 硬件不变时跨重启稳定 |

会话内用 `sessionKey`；落库用 `hardwareKey`（serial 为 0 时降级为 nil，此时该屏配置不跨重启保留，这是诚实的行为而非静默错误）。

**绝不能用 `NSScreen.screens` 的数组下标做 key** —— 拔插显示器后数组顺序会变，设计侧已识别此风险，架构侧确认成立。

**同型号双屏会使 hardwareKey 冲突**：两台同型号显示器的 vendor/model/serial 完全相同，裁切焦点会互相串。已加入 `hardware_key_ambiguous` 标记处理，见 ADR-002。

### Trap 10：预览与写入各自实现裁切（架构约束，非 API 陷阱）

这条不是编译错误，是**结构性静默错误**。team-lead 依设计侧洞察裁定为架构硬约束。

**反模式**：

```
预览：Core Image 裁切 → 渲染到 SwiftUI Image
写入：另一套参数 → Core Image 再裁一遍 → 写文件
```

两套逻辑在边界条件下（半像素、缩放插值、EXIF 方向、色彩空间）会产生细微差异。不崩溃、用户只会觉得「预览和实际不一样」，是最难抓的一类静默错误。

**硬约束**：裁切模块的输出必须是**不可变的产物对象**，预览与写入消费**同一个对象**：

| 字段 | 类型 | 用途 |
| --- | --- |
| `image` | 已裁切位图 | 预览直接渲染，不再自行裁切 |
| `pixelSize` | `CGSize` | 尺寸标注、放大倍数计算 |
| `cacheKey` | `String` | 命中缓存则复用 |
| `fileURL` | `URL?` | 仅写入需要 |

**实现约束**：
- 预览视图**禁止**自行调用 Core Image 裁切
- 产物对象**不可变**（`let` 属性 + 值类型），焦点变化时生成新对象而非修改
- 产物对象与写入操作之间**不得有第二次变换**

这条把「预览与实际一致」从「需要测试验证的期望」变成**结构上无法违反的架构性质**——预览没有裁切能力，只能渲染产物；写入也只能写同一个产物。

**配套约束：放大倍数禁止缓存跨屏结果**

放大倍数 = `屏物理像素宽 / 壁纸物理像素宽`，是 **(壁纸, 屏幕) 这一对的关系量**，不是壁纸的固有属性。同一张 3840×2160 在 5120×2880 屏上是 1.33倍，在 2560×1440 屏上不需放大。禁止作为壁纸的持久化字段；缓存键必须含目标屏标识。

**配套实测发现：非法参数返回 500 而非 400，且响应体随 `Accept` 头变化**

`atleast` 接受任意 `WIDTHxHEIGHT` 字符串（非枚举），但传非法值时返回 **HTTP 500 + `{"message":"Server Error"}`**，不是 4xx + `error` 字段。

完整实测矩阵（2026-10-08）：

| 请求 | HTTP | 响应体 |
| --- | --- | --- |
| `atleast=abc` / `atleast=1920xabc` | 500 | `{"message":"Server Error"}` |
| `page=0` / `page=-1` | 500 | `{"message":"Server Error"}` |
| `page=99999` | 400 | `{"error":"Bad Request"}` |
| `resolutions=9999x9999` | 200 | **有数据**：1 张真实 9999×9999 壁纸 |
| `ratios=99x99` | 200 | **有数据**：24 张，ratio 被静默忽略 |
| `atleast=20000x20000` / `50000x50000` | 200 | 空数组（格式合法但无匹配） |
| `q=###` / `q=zzzzqqqqxx` | 200 | 空数组 |

两个陷阱：

**（a）500 不可区分。** 服务端故障与客户端非法参数的响应体**完全相同**，无法靠响应区分。唯一出路是发请求前本地校验。

**（b）响应体类型取决于 `Accept` 头。** 实测（连续 6 次一致，非间歇）：

| 请求 | 响应体 |
| --- | --- |
| 带 `Accept: application/json` | JSON |
| 不带/ `Accept: text/html` | **HTML**（`<title>It broke - wallhaven.cc</title>`） |

**客户端必须始终显式发送 `Accept: application/json`**，否则错误路径下拿到 HTML，`JSONDecoder` 会报出误导性的「数据解析失败」，真实原因其实是参数非法。

**客户端校验规则（不依赖服务端正确响应）**：

| 参数 | 本地校验 | 不通过时 |
| --- | --- | --- |
| `atleast` | `^\d+x\d+$` | **不发该参数** |
| `page` | `>= 1` | 停止翻页，不发请求 |
| `resolutions` / `ratios` / `q` | 宽松校验或放行 | 实测非法值返回 200，不构成风险 |

原则：所有参数发请求前本地校验，**不依赖服务端 4xx 告知错误**。

**注意不要过度校验**：`atleast` 的合法上界远超真实分辨率。实测 `atleast=20000x20000` 与 `50000x50000` 都返回 **200 + 空数组**（`total: 0`），而非错误。客户端**不应**对 `atleast` 做上界校验，只校验格式 `^\d+x\d+$`，由服务端返回空结果表达「无匹配」。

**空态 ≠ 错误态**：这类「格式合法但无匹配」是成功响应。UI 应显示「没有符合此组合的壁纸」。区分信号只有一条 —— **请求是否发出**：未发出（本地拦截）= 错误态；已发出且 200 + `data: []` = 空态。

**响应处理顺序（硬约束）**：先判 `statusCode`，非 2xx 直接走错误分支不碰 data，2xx 才解码。**禁止先解码再判状态码** —— 否则 HTML 喂给解码器会把「筛选条件写错」误报成「网络/服务端异常」，属静默错误。

已写入 ARCHITECTURE.md §6.2.3 与 ADR-006 的 `APIError` 分类。

### Trap 11（附）：`atleast` 不是枚举，不可硬编码

2020 雏形工程声明为 `let atleast: String = ""`（`QueryParameter.swift:32`），恒为空串、永远不下发。

新代码必须按当前显示器物理像素实时构造，因为显示器拓扑会变（拔插外接屏、切换分辨率）：

```swift
func atleast(forPhysicalSize size: CGSize) -> String {
    "\(Int(size.width))x\(Int(size.height))"
}
```

固定值必然在某些拓扑下失效。实测各档位结果见 ARCHITECTURE.md §6.2.3 表格。

### Trap 12：`type:` 前缀必须放在 `q=` 内，否则被静默忽略

这条极易导致**用无效参数做验证，得出错误结论**。

`type:` 是 wallhaven 搜索语法的**前缀**，属于 `q=` 参数的一部分，**不是**独立的 query 参数。

| 请求形式 | `type:video` 的total | 说明 |
| --- | --- | --- |
| `/search?type:video`（独立参数） | 501,656 | **被静默忽略**，等价于无筛选 |
| `/search?q=type%3Avideo`（在 `q=` 内） | **0** | 正确用法，真实过滤生效 |

若把 `type:` 当独立参数发送，无论传 `video` / `image` / `gif` / `png` 都返回同一个 501,656，看起来像「参数无效」，实际是「参数根本没生效」。

**正确用法下的实测（可作为「wallhaven 无视频」的判据）**：

| 筛选 | total |
| --- | --- |
| 无筛选 | 501,656 |
| `q=type:png` | 115,989 |
| `q=type:jpg` | 385,667 |
| `q=type:video` | **0** |
| `q=type:gif` | **0** |
| `q=type:image` | 0（`image` 不是合法 type 值） |

**算术证明**：`115,989 + 385,667 = 501,656`，与无筛选总数**完全相等**。说明全库内容恰好被 png 与 jpg 两类穷尽，`type:` 过滤真实有效，且不存在第三种类型。

**教训**：验证服务端行为时，必须确认参数的**位置与语法**都正确。用错误形式得到的「无效结论」比不测更危险 —— 它会被写进文档并影响下游决策。

（补充：文档列出的 `+tag` `-tag` `@user` `id:` `like:` 同属 `q=` 内前缀，规则相同。）

### Trap 13：`ratios` / `resolutions` 非法值被静默匹配，不报错

这条是**静默错误家族里最隐蔽的一类**：不报错、不为空、返回正常数据，但内容与用户意图完全不符。

实测：

| 请求 | total | 真实行为 |
| --- | --- | --- |
| `ratios=99x99` | 5,005 | **静默匹配「比例≈1」**，返回 24 条全为 1:1 方图，`meta.query` 为 `null` |
| `resolutions=9999x9999` | 1 | 精确匹配成功（wallhaven 确实存在 9999×9999 的壁纸，id `45jm21`） |

**为什么 `ratios=99x99` 最危险**：用户以为自己设了「99:99 比例」筛选，实际拿到的是 1:1 内容，**且没有任何错误信号** —— HTTP 200、有数据、meta 正常。UI 会正常显示这批结果，用户只会认为「这个比例的壁纸本来就少」。

对比 `atleast=abc` 至少返回 500（虽然也不该依赖服务端报错）。`ratios` 连报错都没有。

**与 `atleast` 的关键差异**：

| 参数 | 性质 | 客户端策略 |
| --- | --- | --- |
| `atleast` | **任意**分辨率字符串 | 实时构造，只校验格式 `^\d+x\d+$`，**不做上界校验**（`50000x50000` 正常返回 200 + 空数组） |
| `ratios` / `resolutions` | **封闭枚举**，值域极窄 | 必须是封闭 enum，非法值**构造请求前抛出，不发请求** |

**禁止**：新增未在枚举中的取值、或退回自由字符串拼接。

完整枚举定义见 ARCHITECTURE.md §6.2.4。

### Trap 14：空 API Key 返回 200，不能用它判定 Key 有效

**这是最危险的 Key 相关陷阱**，因为它让「保存成功」与「未配置」在界面上完全无法区分。

实测：

| `X-API-Key` 头 | HTTP | 语义 |
| --- | --- | --- |
| 头缺失 | 200 | 匿名 |
| 值为空串 | **200** | **等同匿名** |
| 值为纯空格 / 制表符 | **200** | **等同匿名** |
| 任意非空非法值（1 / 3 / 5 / 8 / 10 / 32 / 300 字符） | 401 | Key 无效 |
| 字面量 `"%20"` / `"null"` | 401 | Key 无效 |

根因：wallhaven 允许匿名浏览，服务端把空/纯空白 Key 等同于「无 Key」。

**错误写法**：
```swift
let ok = (try? await client.verifyKey(key)) == true   // 200 -> 判定有效
```

**正确写法**：
```swift
guard !key.trimmingCharacters(in: .whitespacesAndNewlines).isEmpty else {
    return .emptyKey          // 本地拦截，不发请求
}
// 200 是「非空前提下的结论」，不是「有效」的充分条件
```

**长度阈值不得替代非空判断**。实测长度与判定完全无关；若用 `length >= 8` 拦截，用户填 `"a"` 时本会得到服务端准确的 401，却被本地含糊提示拦截 —— **掩盖了服务端能提供的信息**。

### Trap 15：验证 Key 必须用 `/search`，用 `/settings` 会误判有效 Key 为无效

| 端点 | 无效 Key | 无 Key |
| --- | --- | --- |
| `/api/v1/search` | **401** `Unauthorized` | 200 |
| `/api/v1/settings` | **404** `Nothing here` | 401 |

`/settings` 是「读取用户设置」端点，仅当用户**已开启 API 访问授权**时返回数据。仅持有有效 API Key 但未授权的用户请求它会得 404 —— 与「Key 无效」语义完全不同。

**后果**：用 `/settings` 验证，一个**完全有效**的 Key 会被判为无效，用户根本配不进去。而404 在正常流程里不可达，容易被误当作「Key 无效」处理。

`/search` 在六类边界场景（无效 Key / 超长 / 特殊字符 / 短 Key / 有效 Key / 无参数）**均不返回 404**，仅认证失败时 401。**设置页不需要 404 分支** —— 为不可达状态写 UI 分流是死代码。

若将来引入 `/settings`，404 会立即变成真实且语义不同的分支，届时**切勿归因为「Key 无效」**。

### Trap 16：401 只表示 Key 无效，不表示 NSFW 权限不足（修正早期推断）

本 ADR 与 ARCHITECTURE.md 早期版本都写「401 需区分 NSFW 无权限与 Key 无效」，**该表述与实测不符**。

实测 `purity=001`（NSFW）：

| 场景 | HTTP | 结果 |
| --- | --- | --- |
| NSFW + 无效 Key | 401 | Key 无效 |
| **NSFW + 无 Key** | **200** | **`total=0`** |
| `purity=100`（仅 SFW）+ 无 Key | 200 | `total=501661` |
| 无 `purity` + 无 Key | 200 | `total=501661` |

**匿名请求 NSFW 返回 200 + 空数组，不是 401。** 因此：

- `401` 只有一个含义：**Key 无效**
- **不需要**「分别探测 SFW 与 NSFW 来分类 401」
- NSFW 权限不足表现为「已配置有效 Key + NSFW 请求返回 200 + `total=0`」，这是**权限**问题，与 Key 有效性无关

**教训**：这个错误来自「文档提到 ≠ 能用」的第三层—— 我从官方文档「401 Unauthorized」的表述推断它承担语义分类功能，但**实测显示它不携带这个信息**。错误不是「没测」，而是「测之前就把它当成了已知结论」。

### Trap 17：`/settings` 的 `data.purity` 不等于搜索能力边界

**实测方法**：curl，`GET /api/v1/settings` 与 `GET /api/v1/search?purity=001&page=1`，均带 `X-API-Key` 头与 `Accept: application/json`。**实测日期：2026-10-08**，与 Trap 14 / 15 / 16 同一批。

响应体关键字段（原文）：

| 请求 | HTTP | 关键字段 |
| --- | --- | --- |
| `/settings`（有效 Key） | 200 | `{"data":{"purity":["sfw","sketchy"],"thumb_size":"small","per_page":"24",...}}` |
| `/search?purity=001`（同一把 Key） | 200 | `meta.total = 339163`，返回 24 条 |
| `/search?purity=110`（同一把 Key） | 200 | `meta.total = 952572` |
| `/search?purity=001`（匿名对照，不带 Key） | 200 | `meta.total = 0` |

**矛盾点**：`/settings` 声明该账号的 purity 只有 `sfw` 与 `sketchy`，**不含 nsfw**；同一把 Key 请求 NSFW 却返回 339,163 条。两个端点对同一能力给出互斥答案，且 `/settings` 那一侧是错的 —— 它描述的是**偏好设置**，不是**搜索权限**。

**为什么会踩**：Trap 15 证明了 `/settings` 不能验证 Key（无效 Key 返回 404），于是容易推出反向结论——「`/settings` 能返回 200 + 数据时，它的内容可信」。**这个推论不成立**：200 只说明「该端点这次可读」，不说明「它回答的是你问的问题」。这是前提机制的失守，不是对照机制的失守。

**后果**：用 `data.purity` 决定 NSFW 档位或是否渲染 NSFW 开关，会把**可用**的能力判成**不可用** —— 用户永远看不到那 339,163 条内容，界面无任何异常。与 Trap 14（空 Key 判为有效）同型：**静默错误，且方向是把功能关掉**。

**唯一判据**（SPEC §9.2 / ARCHITECTURE.md §6.4.0）：带 Key 请求 `purity=001` 的固定宽探测，**不带任何用户筛选**。`total > 0` = 有能力，`total = 0` = 无能力。匿名对照必须同时跑，否则 `total = 0` 无法区分「无权限」与「未配 Key」。

**禁止的「优化」**：不要用 `/settings` 预筛来跳过探测（例如「settings 说没有 nsfw，就别探测了」）。省下一次请求，代价是把一次真实可用的检索判死。

**暴露它的那个对照**：同一把 Key 同时打 `/settings` 与 `/search`。这正是纪律 4 要求的「能让假设破产的对照」—— 假设是「`/settings` 反映账号能力」，而「声明不含 nsfw」与「实际返回 339,163 条」无法同时成立，假设当场破产。
