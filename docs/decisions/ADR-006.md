# ADR-006: API 客户端自建令牌桶 + X-API-Key 头，不引入网络库

## Status: Accepted (2026-10-08)

## Background

IHaven 需对接 wallhaven API（`wallhaven.cc/help/api`）。硬约束：

- 限流 **45 次/分钟**，超限返回 429
- 每页 **24 条**，分页非真正无限（`meta.last_page` 是上界）
- NSFW 需 API key，无效 key 返回 401（且 NSFW 权限不足**同样**返回 401，需区分）
- 认证支持 `?apikey=` 查询参数或 `X-API-Key` 请求头
- 认证优先用请求头，避免 key 出现在日志/浏览器历史/代理缓存

候选方案：Alamofire、官方 `URLSession` + async/await、自研令牌桶。

## Decision

使用官方 **`URLSession` + async/await**，**不引入** Alamofire 或任何网络库。

自建以下组件：

- **令牌桶限流器**（`actor` 实现，45 次/分钟）
- **429 指数退避重试**（带 jitter）
- **401 语义区分**（Key 无效 vs 无 NSFW 权限）
- **`X-API-Key` 头注入**

认证方式锁定 **`X-API-Key` 请求头**，禁止使用 `?apikey=` 查询参数。

## Rationale

### 为何不引入网络库

1. **依赖冲突面**：项目已锁定 Nuke（自带 `DataLoading` 协议，可替换网络层）。再叠一层网络库，两个库各自持有 session/拦截器/重试策略，行为难以预测。
2. **所需能力极窄**：Alamofire 的主要价值是拦截器、响应序列化、HTTP 路由。对本项目真正必需的只有令牌桶与退避重试两项——自建成本低于引入一个框架的长期维护与冲突成本。
3. **官方 API 已是一等公民**：`URLSession` 在 Swift 6 下有完整的 Sendable 语义，`async` API 是官方支持路径，不需要第三方封装来「现代化」。

### 令牌桶实现要点

```swift
actor RateLimiter {
    private let capacity: Double      // 45
    private var tokens: Double        // 起始 45
    private var lastRefill: ContinuousClock.Instant

    func acquire() async throws {
        while true {
            refill()
            if tokens >= 1 {
                tokens -= 1
                return
            }
            try await Task.sleep(for: timeUntilNextToken())
        }
    }
}
```

- **`actor` 隔离**：手动改 `DispatchQueue` 会引入 Swift 6 并发违规
- **突发容量 45**：允许短时间突发后按 `45/60 ≈ 0.75 次/秒` 匀速释放。这符合用户快速滚动翻页的真实行为——瞬时拉满比严格匀速体验更好
- **所有请求类型都必须过桶**，包括元数据与图片请求。豁免任何一类都会击穿限额
- **`ContinuousClock` 单调**：免疫系统时间跳变导致的限流计算错误

### 429 退避必须带 jitter

```
第 n 次重试延迟 = min(baseDelay × 2^(n-1) + jitter, maxDelay)
baseDelay = 1s, maxDelay = 60s, maxRetries = 4
```

不加 jitter 时，并发请求会在同一时刻重试，形成同步重试风暴——这正是限流场景最常见的雪崩成因。优先尊重服务端 `Retry-After` 头。

重试耗尽后抛 `APIError.rateLimited(retryAfter:)`，UI 显示明确的下次可用时间，**不静默失败**。

### 401 必须语义区分（PRD F7 明确要求）

wallhaven 对「API Key 无效」与「Key 无 NSFW 权限」返回相同的状态码。唯一可靠的区分方式：用同一 Key 分别探测 SFW 与 NSFW 请求，据结果分类。

不区分的后果：用户会以为「NSFW 打不开是 bug」。

### 分页非无限

`meta.last_page` 是硬上界。到达时必须停止预取并提示，**不得假设无限滚动**——这是 PRD 明确列出的边界条件。

## Consequences

### 正面

- 依赖面最小，供应链风险最低
- 限流与重试逻辑完全可控，符合硬约束
- Key 只出现在请求头，不进日志/历史/缓存
- 与 Nuke 无冲突

### 负面

- 令牌桶与退避需自行实现与测试（约 150 行 + 对应测试）
- 需自己保证幂等性与并发正确性（Swift 6 下由 `actor` 保证）

### 关键约束（实现规范）

1. **`X-API-Key` 头，禁止 `?apikey=`**——key 会进日志、代理缓存、崩溃报告
2. **必须显式发送 `Accept: application/json`**。实测 wallhaven 的错误响应体类型取决于 `Accept` 头：不带该头时错误响应是 HTML 页面而非 JSON。先解码再判状态码会把「参数非法」误报成「数据解析失败」
3. **响应处理顺序：先判 `statusCode`，非 2xx 直接走错误分支不碰 data，2xx 才解码**
4. **所有查询参数发请求前本地校验，不依赖服务端 4xx**。实测非法参数返回 **500 + `{"message":"Server Error"}`**，且该响应体与真实服务端故障**完全相同、无法区分**：

| 参数 | 本地校验 | 不通过时 |
| --- | --- | --- |
| `atleast` | `^\d+x\d+$` | 不发该参数 |
| `page` | `>= 1` | 停止翻页，不发请求 |
| `resolutions` / `ratios` / `q` | 宽松校验或放行 | 实测非法值返回 200 |

5. **`APIError` 五类不可合并**，错误文案必须能区分：

| 类别 | 触发条件 | 文案方向 |
| --- | --- | --- |
| `.invalidParameter` | 本地校验未通过，请求未发出 | 你的筛选条件有问题 |
| `.serverError(status)` | 5xx 且本地参数合法 | wallhaven 服务异常 |
| `.networkUnavailable` | `URLError` 族 | 网络不可用 |
| `.rateLimited(retryAfter)` | 429 | 请求过于频繁 |
| `.decodingFailed` | 2xx 但解码失败 | 服务返回了无法解析的数据 |

合并 `.decodingFailed` 与 `.serverError` 会退回「一律显示加载失败」这个静默错误。
6. Key 从 Domain 层 `KeyProvider` 协议获取，Infrastructure 提供 Keychain 实现，使测试可注入假 Key
7. **Xcode Preview 中禁止打真实网络请求**（Preview 反复求值会迅速耗尽限流额度），使用 `MockWallhavenClient` + fixture
8. 离线兜底：网络失败降级到本地导入库（PRD F8），UI 标注「离线模式」，**不静默显示空列表**
9. 埋点记录 `rate_limit_hit` 时只记 `request_kind` 与 `retry_count`，**不记搜索词或壁纸标签内容**（隐私约束，PRD 埋点方案已定）

## Alternatives Considered

**Alamofire**：拦截器与响应序列化有价值，但我们只需令牌桶 + 重试，且与 Nuke 存在依赖冲突面。否决。

**Swift OpenAPI Generator**：spec-first 生成客户端。但 wallhaven 无公开 OpenAPI spec，且我们只需 5 个端点，引入生成器成本高于手写。否决。

## Key 配置与验证（实测约束，2026-10-08）

### 空 Key = 匿名请求，禁止用 200 判定有效

wallhaven 允许匿名浏览。实测：

| `X-API-Key` | HTTP | 语义 |
| --- | --- | --- |
| 头缺失 | 200 | 匿名 |
| 值为空 / 纯空格 / 制表符 | **200** | **等同匿名** |
| 任意非空非法值（1~300 字符） | 401 | Key 无效 |

**这是 critical 级静默错误**：若以 `200 = 有效` 为判据，空 Key 会「保存成功」且界面无任何异常，用户以为不需要配 Key。

```
本地预校验 -> trim() 为空或纯空白 -> 拦截，不发请求
发请求    -> 401 = 无效 / 200 = 有效（200 是非空前提下的结论）
```

三条硬约束：

1. 本地预校验在**发请求前**完成，空/纯空白直接拦截
2. 保存按钮可用状态由本地预校验决定，不由服务端响应决定
3. 粘贴去空格后**必须再次判空**（`trim()` 成空串后二次拦截）

**长度阈值不得替代非空判断**。实测长度与判定无关（1 字符与 300 字符均 401）。长度阈值会先拦截并给出更含糊的提示，**掩盖服务端本可提供的准确 401 信息**。

### Key 验证端点必须用 `/search`

| 端点 | 无效 Key | 无 Key |
| --- | --- | --- |
| `/search` | **401** Unauthorized | 200 |
| `/settings` | **404** Nothing here | 401 |

`/settings` 需用户额外开启 API 访问授权，未授权的有效 Key 会得 404 —— 与「Key 无效」语义不同。**用 `/settings` 验证会把有效 Key 误判为无效。**

`/search` 在六类边界场景均不返回 404，故设置页**不需要 404 分支**（不可达状态的 UI 分流是死代码）。

### 修正：401 不表示 NSFW 权限不足

本 ADR 早期版本写「401 需区分 NSFW 无权限与 Key 无效」，**该表述与实测不符**。

实测 `purity=001`（NSFW）：

| 场景 | HTTP | 结果 |
| --- | --- | --- |
| NSFW + 无效 Key | 401 | Key 无效 |
| **NSFW + 无 Key** | **200** | **`total=0`（空结果，不是 401）** |
| `purity=100` + 无 Key | 200 | `total=501661` |

**401 只表示「Key 无效」，与 purity 无关。** 匿名请求 NSFW 返回 200 + 空数组。

实现：
- `401` -> `.invalidAPIKey`
- NSFW 请求在**已配置 Key 的前提下**返回 200 + `total=0` -> 「此 Key 无 NSFW 访问权限」（权限问题）
- 不需要「分别探测 SFW/NSFW 分类 401」—— 401 只有一个含义

## 验证纪律（四条 + 一条元规则）

本ADR 的所有 API 结论均来自实测。为防止「实测本身出错」，本项目确立以下纪律。**与 PRD 附录 A-9 / A-10 及 ARCHITECTURE.md §6.4.0 三处保持一致**（改动需同步）。

| # | 纪律 | 本ADR 中的实例 |
| --- | --- | --- |
| 1 | 以状态码判断成功，必须同时确认响应体内容 | 曾误判 `resolutions=9999x9999` 为空结果，实为 `total=1` 有真实数据 |
| 2 | 服务端不报错的参数，必须全部客户端预校验 | `ratios=99x99` 静默匹配「比例≈1」，HTTP 200 且有数据，无任何错误信号 |
| 3 | 参数形式未确认前，不得下「该参数无效」的结论 | 曾把 `type:`（独立参数）判为无效，实为「前缀语法须置于 `q=` 内」 |
| 4 | 实测之后要问：样本是否覆盖了能区分假设的对照组 | 曾测四种组合但未做「同一 Key 跨 purity 对比」，因而误判 401 有两种含义 |
| **5** | **（元规则）端点存在 ≠ 端点语义符合用途；实测通过≠ 测到了你以为的那件事** | 统摄前四条，见下 |

**第 5 条是元规则，不是并列的第五条。** 它同时修正前四条��适用边界：

- 修正纪律 1：状态码是必要条件，响应体才是充分依据
- 修正纪律 2 / 3：预校验的对象是**语义**（会不会静默匹配），不只是**格式**（能不能解析）
- 是纪律 4 的成因：为何会把观察到的相关性误判为语义设计

`/settings` 与 `/search` 的对比正是元规则的典型案例：两者都能「工作」，但语义不同，用错会把有效 Key 误判为无效。

> 归入 ADR-006 的理由：本 ADR 是 API 层决策记录，实测纪律在此最集中。ADR-007（陷阱清单）记录具体陷阱，不重复承载纪律。
