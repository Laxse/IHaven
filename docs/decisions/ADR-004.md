# ADR-004: 状态管理统一使用 Observation（@Observable）

## Status: Accepted (2026-10-08)

## Background

IHaven 需在主窗口（深度浏览管理）与菜单栏面板（高频快捷）之间共享状态并保持同步（PRD 产品形态核心）。

候选方案：`@Observable`（Observation 框架）与 `ObservableObject` + `@Published`。

PROJECT-CONTEXT 已记录一条已知约束：「`@Observable` 与 `@ObservedObject` 不兼容，选定方案需统一」。因此这不是「两者都用」，而是必须选一个并全项目贯彻。

项目为全新重写，无存量代码迁移负担。

## Decision

全项目统一使用 **`@Observable`**，不使用 `ObservableObject`。

硬规则（需 CI 静态检查拦截，防止回潮）：

1. 禁止 `ObservableObject` / `@Published` / `@ObservedObject` / `@StateObject` / `@EnvironmentObject`
2. 状态对象加 `@Observable` + `@MainActor`（UI 相关）或 `actor`（数据相关）
3. 跨视图共享用 `@Environment(Type.self)` + `@Bindable`
4. 用枚举取代布尔标志（`LoadState` 而非 `isLoading: Bool` + `error: Error?`）

## Rationale

### 决定性因素：瀑布流性能

`@Observable` 做属性级追踪——视图未读取的属性变更不触发重绘。`ObservableObject` 是对象级——任一 `@Published` 变更会通知该对象的所有观察者。

瀑布流滚动时，逐格图片加载状态变化极其频繁（每格经历 loading → loaded / failed）。在 `ObservableObject` 模型下，这种高频变化会触发对象级重绘，是明确的性能隐患。PRD 要求 1000 张规模稳定 60fps，`@Observable` 的精细失效范围是达成的必要条件之一。

### 与工具链一致性

Nuke 13 采用全局 `ImagePipelineActor` 做线程隔离，与 Observation 的 actor 隔离思路一致。`ObservableObject` 在 Swift 6 下需额外 `@MainActor` 标注配合，与项目已锁定的 Swift 6 严格并发路径不一致。

### 枚举状态消除非法组合

`isLoading: Bool` + `error: Error?` 有四种组合，其中两种非法（同时 loading 且有 error）。`LoadState` 枚举让非法状态无法表达——这属于编译期防护，符合「沉默逻辑错误是最致命失效模式」的防线原则。

## Consequences

### 正面

- 瀑布流高频状态变更的失效范围最小化
- 与 Nuke / GRDB / Swift 6 严格并发模型一致
- 消除布尔标志组合的非法状态
- 迁移成本为零（新工程）

### 负面

- 无法使用 `ObservableObject` 生态的既有模式（如某些第三方视图的 `@ObservedObject` 要求）
- `@Bindable` 与 `@Environment` 的组合对新人有学习成本
- 需 CI 静态检查防止误用旧 API（项目初期人员少，风险主要来自习惯）

### 关键约束

**跨窗口状态同步**：主窗口与菜单栏面板是同一进程内的两个 SwiftUI 场景（菜单栏面板用 `MenuBarExtra`）。状态共享通过在 app 层级创建单一 `@Observable` 模型 + `@Environment` 注入实现，**不使用** `NSNotificationCenter` 广播（那是同步逻辑的耦合陷阱）。若后续菜单栏面板被拆为独立进程，再改用 XPC 同步（与 ADR-003 的动态壁纸 helper 同机制）。

## Alternatives Considered

**`ObservableObject` + `@Published`**：生态最广，但对象级重绘在瀑布流场景是明确性能隐患，且需额外 `@MainActor` 配合。否决。

**两者混用**：PROJECT-CONTEXT 已指出不兼容，且混用会让「哪些状态用哪种」成为持续决策负担。否决。
