# ADR-013: 缩略图只认 `thumbs.original`；详情大图渲染原图 `path`

## Status: Accepted (2026-10-15)

## Background

用户反馈「详情页里目前宽幅图片是正常的，但是竖向的图片感觉被拉伸了或者裁减了」，随后又反馈「高大于宽的图像，现在详情页显示到了中心位置，但是尺寸不对，而且像是被裁减了」。

排查路径上先修掉了两个**非根因**：mock 的 `image(path:)` 曾把三个缩略图档位一律按 16:9 生成字节（`6e92104`），以及 `DetailImage` 用了 `.aspectRatio(.fill)`（同 commit）。两处修完竖图仍在详情页表现为「居中一条横带」，说明根因另有其人——在**图源本身**。

对 wallhaven 三档缩略图做了直连实测（`curl` 下载 + `sips -g pixelWidth -g pixelHeight`，8 份样本，覆盖竖图 / 16:9 / 21:9，详见 `VERIFIED-WALLHAVEN-DETAIL.md` §缩略图三档实测像素）：

| 档位 | 实测像素 | 是否等比 |
| --- | --- | --- |
| `thumbs.large`（`/lg/`） | **恒 432×243**（8/8） | 否（固定 16:9 硬裁件） |
| `thumbs.small`（`/small/`） | **恒 300×200**（8/8） | 否（固定 3:2 硬裁件） |
| `thumbs.original`（`/orig/`） | 长边 ≤300，短边按原图比例 | 是（唯一等比） |

也就是说：`large` 与 `small` **不是缩略图意义上的等比降级，而是裁切件**。竖图 3805×5700 的 `large` 是一张 432×243 的横图；21:9 的 3440×1440 的 `large` 同样是 432×243。

而 `DetailImage.displayFrame` 的框是按 `wallpaper.width/height`（**声明的原图尺寸**）算的：竖图得到竖框，塞进去的像素却是一张横图，于是居中一条横带 —— 表现就是「居中、尺寸不对、像被裁」。卡片瀑布流同理：框按声明比例算，`small` 却是 3:2 硬裁件，每一张竖图卡片都被裁。

## Decision

一、**全项目统一用 `thumbs.original` 作为缩略图源**，经 `Wallpaper.aspectThumb` 取用。调用点：瀑布流卡片（`WallpaperCard`）、搜索结果预取（`WallhavenClient.search`）、详情低清占位（`DetailImage.lowResPreview`）、收藏与「已设置」记录落库的 `thumbnailURL`。`thumbs.large` / `thumbs.small` 一律不再取用。

二、**详情大图渲染原图 `wallpaper.path`**，不再用任何缩略图档位当最终显示内容；`thumbs.original` 只作原图到货前的低清占位，到货后原地替换。

三、**mock 的三档尺寸必须照真实 CDN 行为合成**：`/orig/` 长边 300 等比；`/large/` 固定 432×243；`/small/` 固定 300×200；`/wallpaper/`（原图）长边 1920 等比。

## Rationale

### 一、框按声明值算、像素来自另一源，就必然裁切或压扁

`displayFrame` 用 `wallpaper.width/height` 算框是**正确且必要**的：它是唯一能提前知道的比例信息（列表接口就带），没有它就无法在图片加载完成前把布局定下来。代价是最终渲染的那张图必须与声明尺寸同源。原图 `path` 实测与 `dimension_x/y` 严格一致（`5ypv78` = 3805×5700），是唯一满足这个约束的图源。缩略图档位里只有 `original` 比例正确，但它长边仅 300px，在 ~1000pt 宽的大图区里放大到糊，不能当最终显示内容。

### 二、为什么不用 `large` 当占位：会闪一下裁坏的比例

占位图的作用是「原图未到货时先给个像样的画面」，所以它同样必须比例正确。`large` 是 432×243 硬裁件，竖图上会先闪一张横图、再跳成竖图；`small` 同理。只有 `original` 等比，且体积 12–27 KB、长边 ≤300px，秒开。

### 三、为什么详情页可以拉原图：图片 CDN 不吃 API 配额

此前「预览用 `thumbs.large`、原图只在下载时拉」的约束建立在「省流量」的直觉上，但它没有区分两类成本：**API 配额**（`api.wallhaven.cc`，45 次/分钟，`detail` 每调一次记一次）与**图片 CDN**（`w.wallhaven.cc` / `th.wallhaven.cc`，与配额无关）。详情页一次展示拉一张原图（实测 4.7 MB）只增加带宽，不消耗任何配额，且在 Nuke 缓存内只发生一次。而它换来的是「框与像素同源」这个硬约束被满足 —— 这是「完整显示、绝不裁切」的前提，不能被省流量压过去。

### 四、mock 必须复刻真实 CDN 的裁切行为

上一轮之所以漏掉这个根因，正是因为 mock 把三档一律做成等比（`image(path:)` 统一的 `scaled(longEdge:)`），于是「选错档位」在 mock 下完全看不出后果。mock 的价值在于复刻真实缺陷，不在于好看；把它做成等比等于主动抹掉一类可复现的 bug。

## Consequences

### 正面

- 竖图 / 超宽图在详情页与瀑布流都按原图比例显示，不再被裁或压扁；`displayFrame` 的框与像素终于同源。
- 瀑布流卡片、收藏卡、「已设置」卡全部换成等比缩略图，竖图卡片不再被裁成 3:2。
- 图源选择收敛到 `Wallpaper.aspectThumb` 一处，注释里写死了实测数据，后来者不会再挑错档位。
- mock 与真实 CDN 行为一致，同类缺陷在 `IHAVEN_MOCK=1` 下即可复现。

### 负面

- 详情页每次展示会下载一张原图（实测 1–5 MB；`←` / `→` 连续翻阅会累积），依赖 Nuke 缓存兜底。弱网下首屏只有 300px 占位，观感偏糊。
- 收藏与「已设置」表里**历史行**的 `thumbnailURL` 仍指向旧的 `small`（3:2 硬裁件），旧记录缩略图依旧是裁过的；只有新写入的记录是等比的。
- 原图解码内存开销上升（3805×5700 ≈ 87 MB 位图），由 Nuke 的缓存回收负责，未做额外降采样。

## Alternatives Considered

**继续用 `thumbs.large` 作最终显示，只把框改成按 432×243 算。** 等于接受「详情大图恒为 432×243 裁切件」——竖图永远看不到完整画面，与「完整显示、绝不裁切」的硬要求直接冲突。否决。

**只用 `thumbs.original`（300px）当最终显示，不拉原图。** 比例正确但像素不足，在 ~1000pt 宽的大图区里放大 3 倍以上，明显糊。否决。

**由 Nuke 请求时降采样原图（`ImageRequest` 目标尺寸）。** 只省解码内存，不省下载字节；而本 ADR 的瓶颈是解码内存可由缓存回收覆盖，引入请求尺寸配置反而增加一处易漂移的耦合。暂不采用，如弱网 / 内存实测有问题再回头。

**给竖图单独走 `original`、横图走 `large`。** 按原图比例分支选图源是典型的场景硬编码：`large` 在 21:9 上同样是错的，分支会立刻失控。否决。
