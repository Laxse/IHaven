# ADR-010: API Key 从 Keychain 改为 home 隐藏文件存储

## Status: Accepted (2026-10-11)

## Background

运行时现象：用户每次启动 IHaven 都弹出系统钥匙串授权框——

> 「IHavenApp 想要使用你储存在钥匙串的 com.ihaven.apikey。请输入登录钥匙串密码。」

用户明确要求消除该弹窗，并提出替代方案：「这个 key 就不能存到 home 目录的一个隐藏文件么，启动程序时候去读取加载？」

### 根因调查（实测，非推测）

| 检查项 | 结果 |
| --- | --- |
| 产物签名 | `Signature=adhoc`，**无 team identifier**，`Info.plist=not bound` |
| designated requirement | 基于 CDHash，即二进制内容哈希 |
| 后果 | 每次重建 → CDHash 变 → 钥匙串 ACL 里「始终允许」记录的身份对不上 → 每次启动重新询问 |
| `kSecUseDataProtectionKeychain: true` | 对 ad-hoc 二进制返回 **-34018**（缺少必需 entitlement），无法绕过 |

即：**这不是代码 bug，是 ad-hoc 签名的固有属性**。只要还是本地无签名构建，弹窗就无法通过修代码消除——只能换存储位置。

### 与既有硬约束的冲突

`OPEN-DECISIONS.md` 架构约束原文：

> Key 存储用 macOS Keychain，**禁止 UserDefaults / plist / 硬编码**

本次改动与之直接冲突，故本 ADR 同时作为该约束的**豁免登记**。

## Decision

新增 `FileKeyProvider`（`Sources/IHavenApp/Infrastructure/Security/FileKeyStore.swift`），`IHavenApp` 装配切换为它：

```swift
@State private var keyStore = FileKeyProvider()
```

存储位置与权限：

| 项 | 值 |
| --- | --- |
| 路径 | `~/.ihaven/apikey` |
| 目录权限 | `0700` |
| 文件权限 | `0600` |
| 写入方式 | `Data.write(options: .atomic)`，写完再 `chmod 0600` |
| 空串语义 | 视为清除，删文件并回到未配置态 |

`KeychainStore.swift` **保留不删**，待签名稳定（Apple Developer 签名或固定 CDHash 的自签身份）后可切回。

## Rationale

### 为何不修 Keychain 而换存储

弹窗根因在 ad-hoc 签名的 CDHash 变化，不是 `kSecAttrAccessible` 或访问组配置问题。开发者 ID 签名能解决，但 MVP 阶段走完整签名链路（证书、notarization、entitlement）的成本与收益不匹配。换存储是**唯一能立刻消除弹窗**的路径。

### 为何 home 隐藏文件仍然满足 P0 事故的约束原意

P0（2026-10-08，Key 硬编码进公开仓库 `QueryParameter.swift:56`）的**实质危害是「Key 进了 git 与 URL」**，不是「Key 在磁盘上」。文件方案逐条对照：

| P0 约束原意 | 文件方案是否满足 |
| --- | --- |
| 不进 git | 满足。`~/.ihaven/` 在仓库外（仓库 `~/IHaven`，路径不同且带点前缀），物理上不可能被 commit |
| 不进 URL query | 满足。仍走 `X-API-Key` 头，未回退到 query |
| 不硬编码 | 满足。运行时读文件，代码无常量 |
| 不留日志 | 满足。与 Keychain 版一致，无 print |

新增风险只有一条：**明文落盘**。

### 明文落盘为何可接受

- 权限 `0600`，同机其他用户读不到；同用户进程可读，但这台机器上的任何进程本来也能以本用户身份打开钥匙串（弹窗只是多一道交互确认，不是安全边界）
- 危害面（P0 记录）：访问 NSFW、消耗 45 次/分钟配额、读取账号设置——**无资金路径、无敏感 PII**
- 与「每次启动弹窗导致用户直接点取消 / 转而把 Key 贴进代码」这一现实降级路径相比，文件方案是**更安全**的选择

### 为何不采用 UserDefaults / plist

`~/Library/Preferences/` 下的 plist 会被 `defaults` 命令、`mdfind`、备份工具枚举，且开发者第一反应就是往里塞 Key，门禁规则（禁 UserDefaults 存 Key）的语义边界会被模糊。独立隐藏文件不进入任何系统索引路径，且权限可控到 `0600`。

## Consequences

### 正面

- 启动不再弹钥匙串授权框（目标达成）
- 无签名构建下 Key 读写稳定，无 -34018
- 用户可自行 `cat ~/.ihaven/apikey` 验证/迁移，Key 不再锁在只有 Keychain Access 能看的地方
- Key 泄露进 git 的路径被物理切断（仓库外）

### 负面

- Key 明文落盘，同用户任意进程可读——已接受，见上
- 不再享受系统级加密容器与跨设备同步（iCloud 钥匙串）——MVP 无需
- 用户手动删除 `~/.ihaven/apikey` 即清空 Key，无系统级恢复手段——可接受，重新填一次即可
- `FileKeyProvider` 与 `KeychainKeyProvider` 并存，需在文档中明确当前生效者，避免后续误切

### 回切条件（写死，避免无限期旁路）

满足**任一**即回切 `KeychainKeyProvider` 并关闭本豁免：

1. 构建带上稳定的 Developer ID 签名（team identifier 固定），或
2. 本地自签身份固定 CDHash（固定的 ad-hoc 身份也可让 ACL 命中）

届时 `IHavenApp.swift:5` 改回一行即可，其余代码面向 `KeyStore` 协议，无需改动。

## Compliance

`scripts/security-gate.sh` 现有规则（禁硬编码 Key、`?apikey=`、Key 落 UserDefaults/日志）**继续生效且全部通过**——本 ADR 未放宽任何一条门禁，只是把 Keychain 这一条架构约束改为文件。门禁的语义是「禁止 Key 以代码/URL/可索引位置形式暴露」，文件方案不触碰其中任何一条。

## Alternatives Considered

**保留 Keychain + 降低可访问性（如 `kSecAttrAccessibleAfterFirstUnlock`）**：不解决弹窗，根因在签名身份而非可访问性等级。否决。

**开发者 ID 签名**：能根治，但 MVP 阶段引入证书管理/notarization/entitlement 成本，且与迭代速度冲突。列为回切条件而非当前方案。否决（暂缓）。

**环境变量 / 启动参数注入**：进程环境可被同用户 `ps` 读取，且需要用户改启动方式，可用性差。否决。

**UserDefaults**：进系统索引路径，模糊「禁 UserDefaults 存 Key」门禁语义。否决。
